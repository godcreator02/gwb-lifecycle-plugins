# gwb 发版规则

全生态的发版规矩与 `devkit.release` 的调法。改一版看一版的内循环、验机、取证在 skill「gwb-devkit」。

## 一、自己的版本号抬哪一位

全生态在 0.x。**0.0.x 的包先一次性提到 0.1.0**——0.0.x 上 `^` 锁的是补丁号，每个补丁都成了破坏。

| 这次改动                                      | 抬哪一位               |
| ----------------------------------------- | ------------------ |
| **破坏契约**                                  | 次版本号：0.8.3 → 0.9.0 |
| 其余一切：修 bug、加功能、加命令、加可选参数、回执加字段、改说明书、改内部实现 | 补丁号：0.8.3 → 0.8.4  |

**契约面**，下面这些变了就是破坏：

* **名字**：服务名、命令名、事件名、说明书名、窗格 id——改名或删掉
* **形状**：服务方法的参数与返回；命令参数（删参数、改类型、可选改必选）；回执（删字段、改字段的类型或含义）；事件载荷
* **共享包**：导出的裸名与用法；令牌名
* **盘上的东西**：data 文档、设置项的键与值的格式、布局档里存的 id
* **行为**：调用方依赖着的语义（比如 `ok: true` 意味着什么）

**拿不准就按破坏抬。** 判成破坏，代价是下游多追一次；判成补丁而实际是破坏，下游悄悄坏。

词汇表包（`@godcreator/gwb-plugin-api`，内核契约）对插件只增不减的改动算补丁。

同一个号永不重发。号在仓里抬、提交，再发。

## 二、依赖怎么写

| 位置                     | 写法                                     | 意思                                                                                                  |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------- |
| dev 里的 `@godcreator` 包 | `^` 范围（如 `^0.8.3`；精确号也合法）              | 下限＝验过的那一版；范围内落后不追——对上游 semver 的信任就是范围声明的含义                                                          |
| peer                   | `^<dev 下限>`，如 `^0.8.3`                 | 下限＝验过的那一版；上限＝下一个破坏边界                                                                                |
| 同仓的包之间                 | dev 写 `workspace:*`；peer 写 `^<仓里当前版本>` | 同上                                                                                                  |
| 生态外的依赖（cordis、react…）  | 照各自原有写法                                | —                                                                                                   |
| 内核安装包                  | 不带插件                                   | 装机由 agent 照内核仓 `INSTALL.md` 做：写 home 的 `package.json`（插件不写版本，取 latest）与 `cordis.yml`，`pnpm install` |
| home 的 `package.json`  | 不管                                     | 一键更新按准确号装                                                                                           |

**pnpm 走默认**：peer 不匹配只警告、照装，仓与 home 的 `pnpm-workspace.yaml` 都不写 `strictPeerDependencies`。
守 peer 的是上面的 `^` 写法与发版检票（第三节）。

**发版检票强制迁**：peer 还写着 `>=` 的仓，下次发版时 `devkit.release` 的检票就拒，改成 `^` 才发得出去。
不去一次性改全生态，每个仓发版时自己迁。`devkit.release` 发出去的 `workspace:` 依赖写成 `^`：同一趟发的写
`^新号`，没跟着发的写 `^<工作区里那个号>`。

## 三、依赖数字什么时候动

**拉，不推。** 上游发版时下游一个数字都不动。

* **自己发版前**，上车检票：每个 `@godcreator` 的 dev，现查 `pnpm view <包> dist-tags.latest`——
  * 还在范围内（含相等）：放行，一个数字都不动——范围内落后无需动作，锁文件想躺多久躺多久
  * 已出范围（上游出了新线）：这就是「必须追」——适配代码，dev 与 peer 的 `^` 一起抬到新线，跑 check
* **要用上游的新东西时**：随这次改动一起抬，下限抬到带那个东西的版本
* `devkit.audit-deps` 报的 `behind`（范围内落后）是提示，无需动作；`out-of-range`（范围外）才是待办；
  `peer-not-caret` 是还没迁 `^` 的 peer，下次发版会被检票拦下

**检票由 `devkit.release` 机械执行**，在构建之后、发第一个包之前，对每个要发的包逐条检：

| 检什么                                                                             | 没过                          |
| ------------------------------------------------------------------------------- | --------------------------- |
| 自己的号是 0.0.x                                                                     | 拒：先抬到 0.1.0                 |
| `@godcreator` 的 peer 不是 `^x.y.z`（`>=`、精确号、`workspace:`、别的写法）                    | 拒，说改成什么                     |
| `@godcreator` 的 dev 写法认不出下限、下限比源上 latest 还新、或 latest 已出 dev 范围（`workspace:` 跳过） | 拒「出范围：先适配再抬」；范围内落后（含相等）一律放行 |
| peer 下限 ≠ 对应 dev 下限（`workspace:` 的认工作区现号）                                       | 拒                           |
| peer 指向的上游自己还在 0.0.x                                                            | 不拒，回执 `reminders` 里提醒一句     |

没过就一个都不发，回执按包一次列全。

## 四、发破坏版多做两步

1. **发之前**：跑 `devkit.audit-deps`，找出 peer 会被甩出范围的下游，往各自仓站 feedback 区的
   `inbox.mdx` 投一条「要追 X 0.9」。还写 `>=` 的下游（`peer-not-caret`）没有上限、不会报冲突，逐个确认
2. **发之后**：一键更新遇到 `^` 没追上的下游，pnpm 只出 peer 警告、照装，那个下游就配着出了它范围的上游跑。
   升 default 之前先追下游，或 `plugin-manager.update-all {"only":[…]}` 只升别的

## 五、发版流程

1. **隔离 home 里验**：`devkit.dev` 内循环，见 skill「gwb-devkit」。一键更新升的是日常那份，替不了这一步
2. **抬号、提交**，仓根 git 树要干净
3. **发团队源**：

   ```
   devkit.release {"dir":"<仓根>"}
   devkit.release {"dir":"<仓根>","packages":["packages/model","packages/engine","plugins/gwb-bn-core"]}
   ```

   `packages` 是相对仓根的包目录，按依赖序（被依赖的在前）；一仓一包不用给。一条走完：
   树干净守卫 → 仓根 `pnpm build` → 照 `files` 白名单验产物 → 同号已在源上就拒 → 上车检票（见第三节）
   → staging 发 `latest`。它不改仓里任何文件，只碰源、不碰 home，从哪个 home 调都行。
   staging 形态里没有 `scripts`，要跑仓里 `prepublishOnly` 钩子的场景，在包目录手工
   `pnpm publish --no-git-checks`（scope 路由住用户级配置，命令行不写 `--registry`）
4. **升 default，当场升**：人在插件管理格点「全部更新」，或 `plugin-manager.update-all`。
   它查新版本 → 一趟 `pnpm` → 升了的条目逐条重挂（plugin-manager 自己最后）→ 整页重载，
   回执按包报 `from → to`。不重启，也没有回退：升坏了往前修。升级途中不插别的命令。
   新插件第一次装走 `plugin-manager.install {"pkg":"<包名>"}`，下一次 `index` 就有它。
   升到 gwb-mcp 自己时在途调用与连接会断，重连后用 `plugin-manager.list` 核对

   不升的代价：说明书与命令停在旧版，agent 照过期手册干活而且不报错
5. **改内核契约**：先装新内核，再发用到新契约的插件
6. **动了门、命令名或参数形状、术语**，收尾两道筛：
   * 拿旧词表（件、井、格、门、command-http，加这次改掉的每个旧名）筛门的 instructions、
     各仓 AGENTS 里讲门与命令的段落、所有随包说明书的描述
   * 文档里点名的每个说明书名与命令名，拿 `skill.list` 与 `index` 现扫一遍，指到不在的修指向

## 机器上的两处配置

都不在任何仓里，换机器或重装会丢：

* **用户级 `~/.npmrc`**：`@godcreator` 的 scope 行与发布 token。仓里不配 `.npmrc`、不写 `publishConfig`
* **用户级 pnpm 配置**（`pnpm config get globalconfig` 报位置）：`minimumReleaseAgeExclude` 放行
  `'@godcreator/*'`——pnpm 11 起刚发的包要放一天才准装，丢了它的症状是「新机器上装不上刚发的包」

**`pnpm-workspace.yaml` 里别再写 `minimumReleaseAgeExclude`**：这份文件对用户级配置是逐项覆盖——写了哪一项就盖掉
用户级的同名那一项，没写的照读用户级。仓或 home 里自己写一份放行，就把用户级那份盖掉了；不写，用户级那条就生效。
