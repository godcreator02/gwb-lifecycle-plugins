# gwb 版本号规则

全生态一套。发版的操作步骤在说明书 `gwb-devkit` 的「发版」。

## 一、升哪一位

1. 对照契约清单，判断这次改动破坏了没有：
   - **名字**改名或删掉：服务名、命令名、事件名、说明书名、窗格 id
   - **形状**变了：服务方法的参数与返回；命令参数（删参数、改类型、可选改必选）；回执（删字段、改字段的类型或含义）；事件载荷；库与接口定义包导出的名字与用法
   - **磁盘上的数据格式**变了：data 文档、设置项的键与值的格式、布局文件里存的 id
   - 调用方依赖着的**语义**变了（比如 `ok: true` 意味着什么）
2. 定升哪一位：
   - 破坏了契约 → 升 x（0.8.3 → 0.9.0），发版时加做第三节的两步
   - 加功能、加命令、加可选参数、回执加字段、修 bug、改说明书、改内部实现 → 升 y（0.8.3 → 0.8.4）。这些都明确是补丁版本
   - 只有改动属于上面的契约清单、又判断不了算不算破坏时，才按破坏升 x
3. 改 `package.json` 的 `version` 并提交。同一个版本号永不重发

**完成判据**：新版本号已提交；`pnpm view <包>@<新版本号> version` 没有输出（源上还没有这个号）；说得出这次升 x 还是 y 对应契约清单的哪一条。

内核包另有规则：

- **包根导出的接口类型**（`GwbContext`、`GwbKernelApi`、`GwbResult`、`GwbWindowApi`、`ShellBoot`，插件 `import type` 取）：只增不减（加类型、给已有类型加可选字段）升 y；删掉、改名、改形状、改调用方依赖的语义升 x
- **接缝**：改了接缝上已有的东西（包括升级 loader、include 的版本、改 home 的布局）升 x，只加东西升 y。内核升 x 后，插件 peer 里内核包的范围不再包含新内核，所有插件都要在新内核上重新验过、把范围改成 `^<新内核的版本号>`

## 二、改依赖版本号

上游发版时下游一个数字都不动，由下游在自己发版时决定跟不跟。

1. 确定要不要跟：
   - 上游出了破坏性版本（peer 里的插件和源上 latest 不在同一条线）必须跟：`devkit.release` 会拒发，拒绝理由里写着怎么改。dev 依赖不查，`pnpm install` 装得上就行
   - 要用上游的新东西：把下限升到带那个东西的版本
2. 写法照规矩总表的「依赖怎么写」「用到的插件写 peer」（说明书 `gwb-devkit` 的附件 `references/rules.md`）：peer 与 dev 都写 `^<源上已经发了的版本>`，同仓的包写 `workspace:*`
3. 要跟的先适配代码，再 `pnpm install`、`pnpm check`

**完成判据**：`pnpm install` 成功（下限写了源上没有的版本会在这里失败）；`pnpm check` 全绿。

## 三、发破坏性版本多做的两步

1. **发之前**：在容器根下各仓的 `package.json` 里搜这个包名（仓在哪用 `unit-folder.list` 查），找出 dev 或 peer 里写了它的下游：peer 里写了它的，下次发版会被发版前检查拒；dev 里写了它的，要用新版时再跟。给每个下游仓投一条反馈「要跟 X 0.9」：写一个文件 `<下游仓的站>/content/future/inbox/<日期>-<来源>-<标题>.mdx`，在那个仓里只提交这一个文件（写法见说明书 `docfirst-docs` 的「给别的仓投反馈」）；还没迁到这种结构的旧站，写进 `content/feedback/inbox.mdx`
2. **发之后**：升 default 之前先让下游跟上，或用 `plugin-manager.update {"only":[…]}` 只升别的。升上去以后，peer 范围不包含新版本的下游由 `plugin-manager.list` 的 `unmetPeers` 报出，它们照常加载、不被拦下。改了名字（命令名、说明书名、术语）的，再查两遍：
   - 拿旧名字搜 MCP 入口的 instructions、各仓 AGENTS 里讲命令的段落、所有随包说明书的描述
   - 文档里点名的每个说明书名与命令名，拿 `skill.list` 与 `index` 再查一遍，指向不存在的就改

**完成判据**：每个下游仓都收到了这一条；default 升级后 `plugin-manager.list` 里所有条目 `active` 为 true；旧名字在上面几处搜不到。
