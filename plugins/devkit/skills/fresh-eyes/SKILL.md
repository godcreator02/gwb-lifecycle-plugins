# 任务说明（除了 token，一字不改——上下文隔离的关键就是任务说明里没有多余信息）

```
你要在一台 Windows 机器上开发一个 gwb 插件。
有一台工作台开着，MCP 入口在 http://127.0.0.1:2870/mcp（无状态 streamableHTTP，只绑本机），
每个请求都要带请求头 Authorization: Bearer <token>。
你的第一步是：连上这个 MCP server，调 index 工具——回执里有 instructions 告诉你怎么干活。
不要读本地文件来找答案——所有答案都在这个 MCP 入口上。
从那开始自己找到做法：建一个插件、写代码、通过检查、发版、装进隔离 home 验证。
安全线：别碰 default home，一切操作都在隔离 home 里做。
```

`<token>` 由派任务的人填：调 `mcp.info` 取可直接复制的配置片段，token 就在里面的请求头里。别的地方一字不加。

# 功能指定（附在任务说明后面，也是它唯一多收到的信息）

给个具体功能，别让它自己想——想什么不是考题，怎么建才是。功能要小而全：命令、数据、窗格各用到一点。默认题：**gwb-notes，agent 与人共享的便签板**（`notes.add {"text"}` / `notes.list` / `notes.clear`，存进 gwbData，窗格里人看得见）。

# 判据（三级，运行完后由审查会话评）

| 等级 | 判据 |
| --- | --- |
| **过了** | 六步全通：check / build / publish / install / ping / 窗格可见 |
| **勉强过** | 走通了但绕了弯——说明书里有的信息没找到，靠猜或反复试错碰对了 |
| **没过** | 卡住走不下去，或做出来的东西是错的 |

「勉强过」比「没过」更有价值——它说明说明书里有那条信息但藏得太深（问题出在找不找得到），修法不同。

# 发现写到哪

写进目标仓文档站 feedback 区的 `inbox`。**改的是正本（说明书、代码），不是任务说明**——在任务说明里补一句提示等于把缺口盖住，下次换个角度还是会漏。修完从 inbox 删掉。

# 什么时候运行

- 发了破坏性版本之后（devkit、模板、MCP 入口有大改）
- 人觉得「改得够多了该验一遍了」
- 不需要频繁运行——它测的是说明书够不够用，不是代码回归

# 运行方法

用 Agent 工具派 `general-purpose` 子代理。主会话只观察不动手：结果回来后对着判据评，逐步说清每一处卡住的原因（说明书缺信息？藏太深？流程的 bug？），发现写进 inbox。**子代理的工作目录要干净**——如果在总控台里运行，先把 `out/` 清空；或者指定一个空目录。
