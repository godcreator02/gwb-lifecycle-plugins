# 未来

**本页回答**：开发套件往哪儿去、哪些事它明确不做、为什么。这一区常改；现状区一字不写未来，
未来的话全在这儿。路线图与当前阶段在[路线图](/future/roadmap)那一页。

## 愿景

一句话：**让「在一个新文件夹里开发一个新件」这条路上的每一步，都有一个 agent 调得到的口。**

这条路本身是硬的，绕不开：起一个独立仓、发一版进本机源、装进 home 看真效果。没有这些口，
每一步都是一段要人记在脑子里的 PowerShell，而 agent 只能照着一份会过期的手册去拼命令行。
有了口，每一步都有回执，错了当场说得出错在哪。

做成了是什么样：一个人（或一个 agent）从「我要写一个件」到「它装在 home 里、我看见它在干活」，
中间没有一步需要打开别的窗口去查怎么做。

## 明确不做

「不做」跟「做」一样是决定。推翻其中任何一条都要落一张[轨迹卡](/trajectory)。

**不管文档站的一生。** 铺骨架、扫容器根找站、起停、到点关，全归站件。判据是这件事里根本没有
「件」这个词：一个不需要钉码的 fumadocs 站也要起停，它凭什么先装一套写 gwb 件的工具。

**不管站里内容对不对。** 核对、确认、重摆生成物归 docfirst，而且那三件事在**仓里**发生：
它们要读仓里的源码、调仓里的 git、写仓里的账本。本件不转发，不起子进程替人跑。

**不做正式发版。** `pnpm publish` 是那个仓自己的事，版本号该抬多少只有写代码的人知道。
内循环里发的是**开发版**，号带 `-dev.` 后缀、标 dev 不动 latest，那是一次性的东西，
跟「这个包对外发了一版」是两件事。

**不做装机。** 把一个件装进日常那份 home 是 plugins 件的口。内循环里的 `pnpm add` 只往
隔离 home 里装，目标是 `default` 当场拒。这条边界不是洁癖：装进日常 home 意味着那儿的
代码被悄悄换掉，而插件清单上一点异常都看不出来。

**不做自动升级、不做回退。** 升坏了就往前修，再发一版再升。留一条回退路意味着要维护
「上一版是什么」这份状态，而它必然跟盘上的事实漂开。

**不替人跑 `pnpm install`。** 建完仓、铺完站都只写文件。替人装依赖，出错时现场在哪都不好找：
是模板的问题、网络的问题、还是那个仓自己的问题，回执里分不清。

**不进程内 import 任何 CLI。** CLI 形态的东西一律经 `gwbNodeCli` 登记。自己写一遍起进程与
超时，换来的是同一件事的第二种回执形状，而每多一种形状，调用方就多一处要单独处理的失败。

**不代挂别的件的说明书。** 说明书是全局单一命名空间，同名的第二份直接不挂、只留一行警告，
而被撞掉的常常是新那份。症状是 agent 读到旧手册、照着做但做错了，最难查。更根本的判据是
知识跟着它描述的代码走：代挂等于把别人的知识钉在自己的发版节奏上。

**不给内循环开「顺手也换 default」的口子。** 见上面那条装机。

## 边界变了怎么办

上面每一条都是当时权衡过的。环境变了就复审，产物是一张新卡，不是偷偷改这一页。
最近的一次移动就是发版那条：立仓时这儿写的是「不做发版」，内循环进来之后它收窄成了
「不做**正式**发版」。边界这样动过，就该在[轨迹区](/trajectory)找得到那次了断。
