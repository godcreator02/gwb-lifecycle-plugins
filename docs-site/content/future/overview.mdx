# 未来

**本页回答**：开发套件往哪儿去、哪些事它明确不做、为什么。这一区常改；现状区一字不写未来，
未来的话全在这儿。路线图与当前阶段在[路线图](/future/roadmap)那一页。

## 愿景

一句话：**让「在一个新文件夹里开发一个新插件」这条路上的每一步，都有一条 agent 调得到的命令。**

这条路本身绕不开：建一个独立的仓、把改动装进隔离 home 看真实效果、发正式版再升级日常用的 home。没有这些命令，
每一步都是一段要人记在脑子里的 PowerShell，而 agent 只能照着一份会过期的手册去拼命令行。
有了命令，每一步都有回执，错了当场说得出错在哪。

做成了是什么样：一个人（或一个 agent）从「我要写一个插件」到「它装在 home 里、我看见它在工作」，
中间没有一步需要打开别的窗口去查怎么做。

## 明确不做

「不做」跟「做」一样是决定。推翻其中任何一条都要写一张[轨迹卡](/trajectory)。

**不管文档站的一生。** 生成骨架、在容器根下找站、启动与停止，全归站点插件。判据是这件事里根本没有
「插件」这个词：一个不需要引用代码的 fumadocs 站也要启动与停止，它不该为此先装一套写 gwb 插件的工具。

**不管站里内容对不对。** 核对、确认、重新生成生成物归 docfirst，而且这三件事在**仓里**发生：
它们要读仓里的源码、调仓里的 git、写仓里的记录文件。开发套件不转发，也不启动子进程替人运行。

**不替人决定版本号。** `devkit.release` 发的是包清单里写着的那个版本号：该升哪一位只有写代码的人知道，
同一个版本号已在源上就拒。开发版（`-dev.<时间>` 后缀）只打成包文件装进隔离 home，不进任何源。

**不往日常用的 home 里装开发版。** 装进日常 home 的是正式版，由那个 home 的插件管理升级（`plugin-manager.update`）。
`devkit.dev` 只经目标 home 的插件管理往隔离 home 里装，目标是 `default` 当场拒。这条边界不是洁癖：
开发版装进日常 home，意味着那儿的代码被悄悄换掉，而插件清单上一点异常都看不出来。

**不做自动升级、不做回退。** 升坏了就往前修，再发一版再升。留一条回退路意味着要维护
「上一版是什么」这份状态，而它必然跟磁盘上的事实对不上。

**不替人运行 `pnpm install`。** 建完仓、建完站都只写文件。替人装依赖，出错时不好找原因：
是模板的问题、网络的问题、还是那个仓自己的问题，回执里分不清。

**对外的命令行工具经 `gwbNodeCli` 登记，不自己再包一条命令。** CDP 驱动 `bin/cdp.mjs` 就是这样成为 `devkit.cdp` 的。
命令内部要运行的 pnpm、git 与 `cdp.mjs` 由开发套件自己启动子进程：这几步要退出码、输出的最后几行，
超时还要确认整棵进程树都退出了，`gwbNodeCli` 的回执给不了这些。

**不替别的插件登记说明书。** 说明书名全局唯一，同名的第二份直接不登记、只留一行警告，
而被撞掉的常常是新的那份。症状是 agent 读到旧说明书、照着做但做错了，最难查。更根本的判据是
知识跟着它描述的代码走：替别人登记，等于把别人的知识绑在自己的发版节奏上。

## 边界变了怎么办

上面每一条都是当时权衡过的。环境变了就复审，产物是一张新卡，不是悄悄改这一页。
最近一次复审见[devkit 0.22 删兜底](/trajectory/2026-09-25-devkit-no-fallbacks)：「不做正式发版」早在
[发正式版进 devkit](/trajectory/2026-09-14-release-comes-to-devkit)时就推翻了，「一律经 `gwbNodeCli`」收窄成对外的命令行工具。
