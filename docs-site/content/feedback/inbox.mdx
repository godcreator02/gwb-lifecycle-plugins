# 投来的反馈

**本页回答**：别的仓在用 devkit 的过程中投来了什么意见。一条一节，处理完删——周转区不是档案，
定下来的判据写成轨迹卡。本仓自己反复做的操作候选在 [hatch](/feedback/hatch)。

## 2026-09-12 devkit 缺一条「往隔离 home 首次装插件」的路

来源：总控台（试 block-note 测试版 + devkit 调试闭环时遇到的）。

`devkit.dev` 预设条目已在 `cordis.yml` 里（做的是 add 之后停用→启用、重新加载）。给刚 `devkit.home.new` 开出来的
空隔离 home **首次**装插件只有两条路，都不对劲：`plugins.install` 经 MCP 调装的是 default（总线在哪个 home
就装哪个），装不到隔离 home；手动 pnpm add + 手写条目 + 重开全是能错的地方。

**建议**：补一条 `devkit.home.add`（`{ home, pkg, spec?, entryId? }`），或让 `devkit.dev` 对无条目的包自动走
首装。守卫照旧：只认 home 名不认端口、default 当场拒。

**顺带三条（同一轮实测遇到）**：

1. `devkit.home.new` / `home.open` 启动的内核不带 `--disable-backgrounding-occluded-windows`，要看画面帧的操作
   （截图、等帧、`--size` 查询）对这种 home 取证拿到陈旧帧或卡住。统一带上，或给个透传参数。
2. `devkit.dev` 隐含前置：目标 home 必须装着 `gwb-plugins`（开头要经它问条目表），空 home 直接运行会失败退出；
   报错文案说清，或 `home.new` 提供装基础插件的选项。
3. agent 侧绕法值得进说明书：**devkit 命令里凡传 Windows 路径一律用正斜杠**（`D:/unitfolders/...`）——
   ZCode 的 MCP 参数会把 `\\` 去掉一层，进 JSON 就是 `\u` 坏转义，报错只说 Bad Unicode escape 不指根因。

**进展**（09-18）：顺带第 1 条 0.14.1 修了（`home.new` / `open` 带调试端口就带遮挡开关）；第 2 条由
`home.new` 自动装基础插件解决。剩主诉「首装自动化」与第 3 条（见下面 09-14 那条正斜杠）。

## 2026-09-14 「路径一律正斜杠」对 `devkit.scaffold` 不成立

来源：同上。

经 HTTP 入口用 curl 传含 Windows 路径的 JSON：`unit-folder.readFile` 接受正斜杠，
`devkit.scaffold` 的 `dir` **必须真反斜杠**——本仓 09-12 那条反馈「凡传 Windows 路径一律用
正斜杠」的绕法在 scaffold 这里行不通，代理在 `bad json` 上来回试了好几轮（稳法见同日投给
base-plugins 的反馈：body 写进文件再 `--data-binary @file`，那条归 command-http 说明书）。

**投来的建议**：scaffold 与一切收路径参数的 devkit 命令统一接受正斜杠（在入口处统一转换），让
「一律正斜杠」这条绕法全线成立。

## 2026-09-14 三条小的：浏览器侧 import type 那一行给得太晚、测试 harness 的无参类型、首装条目复验

来源：同上。

1. 浏览器侧 tsconfig `"types": []` 不读全局声明，`window.gwb` 要在文件头
   `import type {} from '@godcreator/gwb-plugin-api'` 才认。说明书里有这条信息
   （plugin-api ≥0.1.1 声明 `window.gwb`，实测属实），但埋得深——代理是先遇到编译错误才回头
   找到的。建议把这一行提前到写代码/窗格章节开头明写。
2. 模板测试里无参调 handler 类型不过（参数 `unknown` 不自动可省），代理把 harness 的
   handler 类型改成 `(args?: unknown)` 才过。建议模板直接给这个形状。
3. 本仓 09-12「往隔离 home 首次装插件」那条的复验结论：`devkit.home.new` **自动装基础插件已经可用**
   （七个基础插件，`devkit.dev` 不再因为空 home 失败）；首装仍要按 `devkit.dev` 回执里的指引手写
   `plugin-manager.add-entry`——指引清楚，但离那条要的自动化还差最后一步，建议那条不撤。

**进展**（09-18）：第 1 条写进了附件 `references/ui.md`「浏览器半」开头；剩第 2、3 条。

## 2026-09-18 audit-deps 全生态回执过大，经 MCP 工具调用会被客户端截断

来源：总控台（全生态依赖核对会话：12 个仓、30 余个包发版，逐个仓核对时反复要读这份结果）。

情况：全生态 23 仓 / 45 清单 / 166 findings 时，`run devkit.audit-deps` 的回执 JSON 约 50KB——
经 MCP 入口（`run`）调用超出客户端单次回执预算，**尾部被截断**：本会话第一次调用就丢了后半段
（gwb-reimburse / gwb-pomodoro 两段与 `byKind` 汇总）。绕法是把 `bin/client.mjs` 拿到命令行直接运行、
重定向到文件再读（`run mcp.client` 那份说明书里有这个命令行工具），全量拿得到——但得先知道要绕。

**投来的建议**：给 audit-deps 加一个可选过滤参数（如 `{ repo?: "<单元>/<仓>" }`，或 `{ only: [...] }`），
或让回执分两档（摘要 + 按仓索取）。核对依赖的 agent 一次能读完自己那个仓的结果，不必写到文件再解析。

## 2026-09-19 要追 shell 0.10：peer 会出范围，改个号就行

来源：gwb-ui-plugins（窗格模型第二版第一期；shell 0.10.0 今天发团队源）。

shell 0.10.0 按 gwb-release 升了次版本号：开窗格的行为变了（本桌优先、从不切桌面，新窗格放在来源旁边，预览每组一个），

跟进的做法是把 dev 的版本号与 peer 下限升到 `0.10.0`、运行 check，下次发版时带上。

## 2026-09-22 页面加载后才补装的 peer 不进 importmap——devkit.dev 首装流的重载时机偏早

来源：gwb-block-note（v2 引擎线第 2 单验收，隔离 home bn-v2-2609222003）。

情况：`devkit.dev` 首装（回执 note 指引走 `plugin-manager.install` 建条目）之后，install 发现缺 peer
（`@godcreator/block-note`）顺手补装——但**整页重载在 devkit.dev 那一步早就做完了**，importmap 是页面
加载那一刻按当时的 node_modules 拼的快照，后补的 peer 不在表里。首开窗格，浏览器端产物里
`import "@godcreator/block-note"` 解析不到，窗格里一整行红：「加载失败：TypeError: Failed to resolve
module specifier "@godcreator/block-note"」。整页重载一次即愈（快照重拼）。两个让它更难发现的地方：node 侧
日志**全程无 error**——它只在渲染层现形，devkit.dev 的日志基线测不到；且窗格源码没错、装也没错，纯看
「挂上了 / 条目 ACTIVE」全绿。

**投来的建议**（该修的地方在插件管理，devkit 这边至少要把话写进说明书）：`plugin-manager.install`
补装过 peer 后自己触发一次整页重载（与 plugin-manager.update 相同），或 devkit.dev 的回执 note 在「首装建条目」那句后面
带上「install 若补装了 peer，建完条目再整页重载一次」。顺带给验收纪律补一句：带浏览器端代码的插件，实际安装验证要配
截图或窗格渲染取证——这类问题只有渲染层会报出来。

## 2026-09-25 块笔记已撤掉 `gwb.shared`，定案第四节与第六节在块笔记一侧做完

来源：块笔记仓（gwb-block-note）把引擎替换合回 main 之后按全生态机制定案对齐的会话。

定案第四节「块笔记的解析库撤掉 `gwb.shared`，块笔记系列插件各自打包进构建产物」与第六节「外置名单只从提供方读」，块笔记与论文插件的 main 上
都已改完：界面包 `@godcreator/block-notebook-ui` 不再声明 `gwb.shared`、去掉 `gwb` 关键词，不再装进 home；各插件浏览器端只外置内核包清单
`gwb.shared` 的键。同一轮还照写插件的规矩改了几处：命令表抽成无状态的包 `@godcreator/block-notebook-commands`（插件之间不再 import
核心插件的 `./shared`）；`blockNoteLibraries` / `blockNoteExtensions` 继承 `Service`；核心插件卸载时关库的清理返回 promise（第八节）；
契约版本号对不上拒绝加载（第七节）；核心插件补回 `gwb.provides`。都还没发版。
定案「已决定（2026-09-24）」里等块笔记撤声明的那一条，条件已满足，可以更新；删机制本身在内核仓（已另投一条），要等 default 切换卸掉旧的
`@godcreator/block-note` 之后。

## 2026-09-25 内核 0.6.0 删掉了 `gwb.shared` 字段：外置名单与发版检查改成写死 react 的四个名字

来源：总控台会话，内核仓 9061518（轨迹卡 2026-09-25-static-importmap）。

内核 0.6.0 把页面的 importmap 写死在页面入口 `index.html` 里，只有 `react`、`react/jsx-runtime`、`react-dom`、`react-dom/client` 四个包名，
地址相对 `index.html` 指向内核包 `dist/react/`。内核包清单的 `gwb.shared` 字段和 `./react*` 四个出口都删了。devkit 现在读内核包 `gwb.shared`
的几处，装上内核 0.6.0 后都会失败，要先改完，下游插件才能在 0.6 上构建和发版：

- 发版检查（`artifact-check.ts`）：浏览器侧产物能 import 的包名直接是这四个，写死；删掉「从本包 `node_modules` 现读内核包清单」，删掉「内核包以外的包写了 `gwb.shared` 就拒」，
  也删掉「本包 `gwb.shared` 指到的文件」这一段扫描范围。现在读不到 `gwb.shared` 就拒，内核 0.6 上的每个带界面的插件都会被拦
- 模板 `build.ts.tpl`：`external` 直接写这四个名字，删掉 `sharedNamesOfKernel`；`artifact.test.ts.tpl`、`package.json.tpl` 的注释、`README.md.tpl` 跟着改
- 说明书 `gwb-release`（发版前检查表里「浏览器侧产物」那一行）、`gwb-devkit` 与附件 `references/rules.md`、规矩页「页面代码与 importmap」、「依赖怎么写」等处的 `gwb.shared` 说法
- devkit 与插件管理自己 peer 里的内核包改 `^0.6.0`，在跑 0.6.0 的隔离 home 里验过再发

没有直接改：devkit 仓里 `artifact-check.ts`、模板、`scaffold.test.ts` 等正好有另一个会话未提交的改动。

**顺带一条现象**：`devkit.home.new {"short":"static-importmap"}` 开出来的实例（pid 136532，由 default 里的 devkit 启动），我用 `Stop-Process` 停掉之后
约 2 秒，default 自己走了一遍正常退出（default 的 `gwb.log` 里 `17:07:46.709Z info kernel 清理完成，退出`）。原因没查清，值得看一下 `home.new` 启动的
子进程和 default 的生命周期有没有绑在一起；在弄清之前，停这种实例别用杀进程的办法。
