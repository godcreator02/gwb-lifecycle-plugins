# 写 gwb 插件

这份只写步骤、完成判据和工具不会报出来的注意事项。每条命令的参数、回执、什么情况下拒绝，写在它的 usage 里（`search {"prefix":"devkit."}`）；命令没过时，回执会逐条写明怎么改。

## 新写一个插件

1. 要用的能力先看提供方插件发布的 `.d.ts`：它给 cordis 的 `Context` 补了哪几项（`declare module 'cordis' { interface Context { … } }`），方法签名与文档注释就在那里。已经有了就直接用：peer 里写上提供方，`import type` 它的类型，`ctx.inject` 取用。不按名字调别的插件的命令；提供方只有命令、没有服务方法的，先给它加上服务方法
2. 带界面的插件，先读外壳的说明书 `skill.read {"name":"gwb-shell"}`
3. 建仓用 `devkit.scaffold`，往已有的 workspace 仓再加一个插件用 `devkit.scaffold.plugin`。没有团队源（`@godcreator`）发布权限的，两条都加 `scope` 与 `registry`，同一个仓里的插件用同一套；GWB 发布凭据保存在发起 home 的共享 secret `npm-auth`，配置步骤读 `gwb-plugin-manager`。两条命令写完文件后都要联网运行 shadcn 官方 CLI 加上 `button`，顺带把整个仓装一遍依赖
4. 把模板改成真插件，守「写插件的规矩」：
   - `src/index.ts`：模板的 `<短名>.ping` 与窗格 `main` 换成真正的命令与窗格，命令照模板那条的写法登记。每条命令都写 `effect`，三选一：`read`（什么都不改，联网只读也算）、`write`（改本机的文件、设置、数据或界面）、`external`（影响本机以外或打扰人：推送、发到远端、发消息、弹窗或通知），按参数可能做几种事的取最重的那种。命令总线 0.6 起没写 `effect` 就登记失败，插件加载失败
   - `src/client/`：窗格里可点的控件用 shadcn 官方组件，模板已接好 `components.json`、`@/` 别名与 `Button`；要别的组件照外壳说明书的「接入 shadcn 组件」第 3 步起做
   - `tests/`：不启动进程、不开窗口就能测的逻辑抽成纯函数来测
   - 不要界面的插件：照生成的 README 里那张清单删掉浏览器侧的文件、脚本与依赖
   - `package.json`：`description` 写一句话说这个插件做什么；用到的插件写进 peer；不用外壳就删掉 peer 里那一项；有了 `skills/` 目录就把 `skills` 加进 `files`
   - 提供服务：别的插件在进程内要用的能力做成继承 cordis `Service` 的类的方法，给页面和 agent 的命令校验参数后调同一个方法（写法见 `/docs/rules/services`）；只有页面和 agent 用的能力只做命令。在源码里给 `Context` 补上这一项（`declare module 'cordis' { interface Context { gwbExample: GwbExample } }`），`GwbExample` 定义在本包里、写文档注释说清怎么用。模板不输出 `.d.ts`，要加三处：包里加 `tsconfig.build.json`（`"extends": "./tsconfig.json"`，`compilerOptions` 写 `"noEmit": false, "declaration": true, "emitDeclarationOnly": true, "outDir": "dist", "rootDir": "src"`，`"include": ["src/index.ts"]`）；`build` 脚本在 `node build.ts` 之后加 `tsc -p tsconfig.build.json`；`exports["."]` 改成 `{ "types": "./dist/index.d.ts", "default": "./dist/index.js" }`
   - 仓里有文档站的，在现状区写这个插件的首页，功能、接口、依赖、不做的事四节；插件之间的依赖按提供、注入、按名字调用与约定通道三张表记下来（格式见 `/docs/rules/wiring`，没有工具查），记在哪一页不固定，首页的依赖一节写明记在哪、链过去
5. 仓根 `pnpm build`，再 `pnpm check`

**完成判据**：仓根 `pnpm check` 全绿。接着做「改一版看一版」。

## 改已有插件

1. 仓得是 workspace 布局：仓根是 `private: true` 的 `package.json`，`pnpm-workspace.yaml` 的 `packages` 里有 `plugins/*`，插件包在 `plugins/<短名>/`。不是的先照 `devkit.scaffold` 生成的仓迁过来，`devkit.dev`、`devkit.release`、`devkit.scaffold.plugin` 只认这种仓
2. 改代码，守「写插件的规矩」。加减了服务，同步改给 `Context` 补的那几项；加减了命令、服务、说明书、注入，仓里有文档站的在同一个提交里改那个插件的页与记依赖的那一页（插件首页的依赖一节链着它）
3. 仓根 `pnpm build`、`pnpm check`

**完成判据**：`pnpm check` 全绿。接着做「改一版看一版」。

## 改一版看一版

1. `devkit.home.new {"short":"<插件短名或这次验什么>"}` 开一个隔离 home。**一个隔离 home 同一时间只给一个会话用**，不拿别的会话开的 home 来验。机器重启后用 `devkit.home.open` 回到它，验完用 `devkit.home.rm` 删掉
2. `devkit.dev {"home":"<home 名>","dir":"<仓根>","packages":["plugins/<短名>"]}`：构建、打包、经那个 home 的插件管理装上、刷新、取证，一条命令做完。改了内核也用它：`dir` 给内核仓根、`packages` 给 `["apps/desktop"]`，它会重启那个 home
3. 在那个 home 里调新写的命令看回执：`devkit.cdp {"args":["<home 名>","cmd","<命令名>","<JSON 参数>"]}`；界面上的效果按「在页面里取证」做。`cmd` 的回执与 MCP 入口同一个上限（40000 字符，按 MCP 入口交回的文本算），超了不交回、退出码非零：经 MCP 调也会被同样挡下，给这条命令加分页或筛选参数，别换个办法把回执取出来

**完成判据**：`devkit.dev` 回执 `ok: true`；`devkit.cdp … cmd plugin-manager.list` 里这个包的条目 `active` 为 true、版本是这次的开发版号；新命令的回执与预期一致。

- **home 里的包只通过安装来换**：别覆盖 `node_modules` 里的 `dist/`，那会改到 pnpm 全局存储里的同一份文件，node 侧也换不掉；也别动 home 里的 `dev-packs` 目录，home 清单引用着那里的包文件，删了之后这个 home 里的安装与升级全部失败
- **日志**：`%APPDATA%\gwb-kernel\homes\<home 名>\gwb.log`，内核、插件、页面三方的日志都在这一个文件里

## 在页面里取证

1. 读附件：`skill.read {"name":"gwb-devkit","file":"references/evidence.md"}`
2. 用 `devkit.cdp` 在隔离 home 的页面里点击、读数、截图，读数与截图文件路径都在回执里

**完成判据**：`eval` 的读数与预期一致；截图（回执 `file`）里看得到要验证的界面状态。

## 发版

1. 在隔离 home 里验过这一版（「改一版看一版」）。插件包 peer 里内核包 `@godcreator/gwb-kernel-desktop` 的范围 `^x.y.z` 要包含验证时那个内核，不包含就改成 `^<那个内核的版本号>`：`devkit.release` 不查这一点
2. 照说明书 `gwb-release` 升版本号并提交，仓根 git 工作区干净。要发到 npmjs 的，把这个提交推到 GitHub
3. `devkit.release {"dir":"<仓根>","packages":[…]}`，`packages` 按依赖顺序排，被依赖的在前。回执 `ok: false` 时照回执里说的处理：发版前没过的一个包都没发，照回执逐条改完、`pnpm check`、提交，再调一次；GitHub Actions 那一步没成的，回执写着运行的网址，在网页上看日志、修好后重跑。只经这条命令发，不手工 `pnpm publish`：手工发既不构建，也不做发版前检查
4. 升级日常用的 default：照说明书 `gwb-plugin-manager` 的「升级插件」

**完成判据**：`devkit.release` 回执 `ok: true`，`shipped` 里是这次的包、版本与发布目标；default 的 `plugin-manager.list` 里这个包的版本是刚发的正式版、条目 `active` 为 true；再调一次 `index`，看得到这个包的命令与说明书。

- **包的 `repository`** 写源码所在的仓：`"repository": { "type": "git", "url": "https://github.com/<owner>/<仓名>.git" }`，npmjs 的包页面靠它链到源码。发到 npmjs 的带范围的包，`publishConfig` 里还要有 `"access": "public"`，不然按私有包发、免费账号会被拒。都没有工具查
- **发到 npmjs 的包由 GitHub Actions 发**：`devkit.release` 把组装好的包挂到 GitHub release 上，仓里的 `.github/workflows/publish.yml` 用 trusted publishing 发出去，本机不存 npmjs 的 token。仓里还没有这个工作流的，从 devkit 包的 `template/repo/.github/workflows/publish.yml.tpl` 复制一份（去掉 `.tpl`）、提交、推送。一个包第一次上 npmjs 要先由人在本机发一次（`npm publish <目录> --auth-type=web`，浏览器里批准），再登记 trusted publisher：`npx npm@latest trust github <包名> --repo <owner>/<仓名> --file publish.yml --yes`（也要浏览器批准，批准页勾上 5 分钟内不再验证，一批包能一次登记完）；登记后两天内要有一次成功的发布，不然登记作废
- **机器上的两处配置**，不在任何仓里，换机器或重装会丢：
  - 源路由：沿用 pnpm 的 scope 路由；GWB 安装和发布凭据由发起 home 的 `npm-auth` 保管，接入流程见 `gwb-plugin-manager`。普通终端 pnpm 仍用自己的配置
  - 用户级 pnpm 配置（`pnpm config get globalconfig` 报位置）：`minimumReleaseAgeExclude` 放行 `'@godcreator/*'`，丢了的症状是新机器上装不上刚发的包。仓与 home 的 `pnpm-workspace.yaml` 不写这一项，也不写 `strictPeerDependencies`：写了就逐项覆盖用户级的同名项

## 写插件的规矩

规矩总表在附件 `references/rules.md`（`skill.read {"name":"gwb-devkit","file":"references/rules.md"}`），一条一行，写着每条由哪道检查负责、哪些写法容易出错。表里的链接 `/docs/rules/<页>` 对应 `gwb-lifecycle-plugins` 仓（仓的位置用 `unit-folder.list` 查）的 `docs-site/content/docs/rules/<页>.mdx`，每条的做法与例子在那一页。

总表之外，还有几处没有工具查：

- **内核的接口类型从内核包的包根 `import type`**：`import type { GwbContext } from '@godcreator/gwb-kernel-desktop'`。包根只导出类型，`isRecord`、`requireKernel` 这类无状态小函数由插件自带一份（devkit 的 `src/vocab.ts`）
- **node 侧的测试只 import `.ts`**：node 侧的 tsc 没开 jsx
- **说明书跟它描述的代码同仓同提交**，随那个包发布；每个插件只登记自己的说明书
- **文档站的 README**：第一次在站目录 `pnpm doc:render` 之前，把手写 README 里要留的内容搬进 `outputs` 映射里指向 README 的那份 mdx，render 会整份覆盖 README
