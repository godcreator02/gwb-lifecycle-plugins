# 插件管理

home 里有两层：

- **包**：pnpm 装进 home 的 `node_modules`，只是在磁盘上
- **条目**：`cordis.yml` 里指向一个包的一行。有了条目，插件的代码才加载运行。一个包可以有好几条条目，各是一个实例、各存各的数据

`plugin-manager.list` 同时报两层：每个包下有哪些条目，每条启用没有、`active`（加载成功）没有。内核包与 `cordis` 没有条目，按下面「升内核」换。命令作用在 MCP 入口连着的那个 home；要操作隔离 home，经 `devkit.cdp {"args":["<home 名>","cmd","plugin-manager.<命令>","<JSON 参数>"]}` 调。

每条命令的参数与回执字段写在它的 usage 里（`search {"prefix":"plugin-manager."}`）。回执只有外层一层 `ok`：成功时读 `data`，失败时读 `error`。

## 装一个插件

1. `plugin-manager.search` 确认包名（第三方 scope 先按下一节加市场）
2. `plugin-manager.install {"pkg":"<包名>"}`。包已经装了会直接报错：再加一条条目用 `add-entry`，换版本用 `update {"specs":…}`
3. `plugin-manager.list` 看这个包的条目 `active`
4. 调一次 MCP 入口的 `index`，新插件的命令这时出现

**完成判据**：`list` 里这个包的条目 `active` 为 true；`index` 里有它的命令。

`active` 为 false 时原因在 `gwb.log`；日志说数据目录或设置分区属于别的包，见「增删改条目」第 3 步。

## 加一个市场

`search` 只在**市场名单**里的 scope 上找插件。名单是设置插件公共区的一项：`section` 为 `*`、`key` 为 `plugin-markets`，字符串数组，默认 `["@godcreator"]`。每个市场的源地址 `search` 问 pnpm，只认这个 scope 自己的 `@<scope>:registry`。所以加一个市场要做两件事：

1. 确认目标 home，在该目录查询 `pnpm config get @<scope>:registry`。只修改所需源路由，保留其他配置；格式与生效层级按本机 pnpm 的帮助确认。gitea 包源地址为 `<gitea 地址>/api/packages/<用户或组织>/npm/`，以 `/` 结尾。
2. 私有源凭据由本 home 的 `credentials` 管理：共享槽 `section:"*", key:"npm-auth"` 保存 JSON 对象，键是 `//<主机>/<路径>/:_authToken`，值是服务端签发的 token。先查 `credentials.status`；已有整份可用配置用 `credentials.copy/import`。增改一个源时在本地进程中合并现有对象、写临时导入文件再导入，保留其他源；回执只报目标和验证状态，清理临时文件。已授权迁移的 `~/.npmrc` 可以作为一次性导入来源，在本地取值，不将文件内容或 token 输出到对话。
   安装、检索和 devkit 发布只用发起 home 的这份凭据；未配置时匿名请求，不借机器或其他 home 的凭据。GWB 子进程使用临时 auth-file 与环境变量注入，系统 pnpm 的配置不被改写。工程或所属工作区 `.npmrc` 含认证项时会拒绝运行：在本地将这些认证原值合并导入指定 home，核对入库成功后移除工程中的旧认证项，保留路由及无关设置；这是接入操作，插件不会替你改工程文件。对普通终端的影响要在本次接入结果中说明。
3. 把 scope 加进名单：`settings.get {"section":"*","key":"plugin-markets"}` 读出现在的名单（`null` 表示没改过，就是默认值），加上这个 scope 后整份写回 `settings.set {"section":"*","key":"plugin-markets","value":[…]}`。人也可以在插件管理窗格「可安装」一栏加
4. `plugin-manager.search` 核对

**完成判据**：`search` 回执 `data.markets` 里这个 scope 那一项 `ok` 为 true，`data.packages` 里有它上面的插件。

删一个市场：从名单里去掉这个 scope 写回；源路由与 `npm-auth` 中对应项只在不再需要该源时删除，其他源保留。

**源不支持 npm 的检索接口就当不了市场**：GitHub Packages（`https://npm.pkg.github.com/`）检索回 404，`@<GitHub 账号>` 这类范围不加进名单；只配源路由与 `npm-auth`，知道包名就直接 `install`。

**「可安装」一栏是空的、或某个市场报「pnpm 里没配这个市场的源」**：`pnpm config get @<scope>:registry` 输出 `undefined`，照第 1 步补上路由行。

## 升级插件

1. `plugin-manager.outdated` 看谁有新版本
2. `plugin-manager.update`，参数三选一、恰好给一个：`{"all":true}` 全升；`{"only":["<包名>"]}` 只升几个；`{"specs":{"<包名>":"<版本号、tag 或 file:<绝对路径>>"}}` 按给定写法装已装的包。`specs` 写一个更旧的版本号会失败：不做回退，升坏了就发一个修好的新版
3. 读回执：条目的 `action` 是 `remounted`、`state` 是 `ACTIVE` 才算加载成功。`dependents` 是没点名、但跟着重新加载的包，多半是 peer 里写了被升级包的插件。`action` 是 `deferred` 的是插件管理自己和 peer 里直接或经别的包写了插件管理的包（baseui、devkit 这类），回执发出之后才依次重新加载，要等它们回到 `active` 再往下走。升到 gwb-mcp 自己时进行中的 MCP 请求会断，重连一次再核对
4. 回执带 `restartRequired: true`、`note` 说 peer 成环时：环上的包与依赖它们的包这次没换成新版本，把 `note` 转告人，重启由人决定；环要到那几个包的仓里拆掉
5. 插件管理不整页重新加载：拿到成功回执后自己调一次 `shell.reload`，界面才换成新代码。插件管理窗格在插件管理回来后就整页刷新，这时 baseui 可能还在重新加载，插件管理窗格短暂不见，再刷新一次即可
6. `plugin-manager.list` 核对版本与 `active`，再调一次 `index`

**完成判据**：`outdated` 里不再有这次升的包；`list` 里它们的版本是新版、条目 `active` 为 true，`dependents` 里的包条目 `active` 也为 true；升级后调过 `shell.reload`；有 `restartRequired` 时已告诉人。

上游发了破坏性版本时怎么升，见说明书 `gwb-release` 的「发破坏性版本多做的两步」。

## 升内核

内核包 `@godcreator/gwb-kernel-desktop` 只经 `update` 的 `specs` 换，`outdated` 不报它。新内核先在隔离 home 里升、重启验完，再升 default。

1. `plugin-manager.update {"specs":{"@godcreator/gwb-kernel-desktop":"<版本号或 latest>"}}`，可以连同别的包一起写。`cordis` 不写：插件管理照内核包 peer 里写的版本自己对齐
2. 回执 `restartRequired` 为 true 时，告诉人要重启工作台才生效。**重启由人决定，不要自己重启**
3. 重启后调 `plugin-manager.list`，`unmetPeers` 里有内核包那一项的插件，peer 范围不包含新内核（下一节）
4. `ok: false` 且 `error` 说先别重启：内核包已经装上、`cordis` 没对齐。照 `error` 修好再调一次

**完成判据**：回执 `ok` 为 true，人已知道要重启；重启后 `runtime.json` 报的内核版本是回执里内核包的 `to`，`list` 里 peer 范围不包含新内核的插件已告诉人。

## 查插件 peer 里的内核包与别的插件满没满足

1. `plugin-manager.list`，列出 `unmetPeers` 不空的包。这些只是报告、照常加载；出了问题先怀疑它们
2. 按没满足的那一项处理：
   - 内核包：到那个插件的仓里在隔离 home 验证后改 peer 里内核包的范围，再发版（说明书 `gwb-devkit` 的「发版」）
   - peer 里的插件太旧或没装：`update {"only":["<那个插件的包名>"]}` 或 `install`；装着的版本比范围新（上游出了破坏性版本）的，到写 peer 的那个插件的仓里适配后改 peer 再发版
   - `range` 不是 `^x.y.z`：到那个插件的仓里改写法再发版

**完成判据**：给出 `unmetPeers` 不空的全部包名与每条没满足的 peer。

## 增删改条目

1. `plugin-manager.list` 找到条目的 entryId
2. 调对应的命令：

   | 要做什么 | 命令（前缀 `plugin-manager.`） |
   | --- | --- |
   | 给已装的包再加一条条目 | `add-entry {"pkg":"<包名>"}` |
   | 删一条条目、留着包 | `remove-entry {"entryId":"…"}`，随时可以 `add-entry` 加回来 |
   | 删包连同它的全部条目 | `uninstall {"pkg":"<包名>"}`，设置与数据留在磁盘上；依赖它的插件停在未加载 |
   | 启用、停用 | `enable` / `disable {"entryId":"…"}`，立即生效 |
   | 手动重新加载一条 | 先 `disable` 再 `enable`；命令插件、MCP 入口、插件管理自己除外，见下 |

3. 插件加载失败、日志说「数据目录 … 归 X」或「设置分区 … 归 X」：这个 id 的数据或设置是别的包留下的。同一个插件改了包名的照下一节改归属；不相干的两个包撞了 id，照数据插件与设置插件报错里说的处理
4. `plugin-manager.list` 核对

**完成判据**：`list` 里条目的有无、启停与 `active` 都是你要的状态。

## 包改了名，接着用原来的设置与数据

设置（凭据也在里面）与数据按条目 id 存，各记着归哪个包；包名变了，新包加载时被拒。新包的默认 id 和旧包相同（去掉 scope 与 `gwb-` 前缀），按下面的顺序换：

1. `plugin-manager.list` 记下旧包每条条目的 id
2. `uninstall {"pkg":"<旧包名>"}`
3. 每个 id 调一次 `transfer-owner {"entryId":"<id>","pkg":"<新包名>"}`，回执的 `settingsFrom`、`dataFrom` 是改之前的归属，没有那一样就没有那个字段
4. `install {"pkg":"<新包名>"}`，拿到第一个 id；旧包原来有几条条目，就再 `add-entry` 几次，id 照旧按 `-2`、`-3` 排下去
5. `plugin-manager.list` 核对新包的条目都 `active`

`transfer-owner` 只改记着归属的那几样，设置与数据都没记这个 id 就报错（多半是 id 写错了）；这个 id 的条目正在加载别的包时也报错，先卸掉旧包。已经先装了新包、它正被拒着的，照常调 `transfer-owner`，再把那条条目 `disable`、`enable` 一次。

**完成判据**：新包的条目都 `active`；设置窗格里原来的设置项与凭据都还在，插件读到的是原来的数据。

## 容易出错的地方

- **别用 `disable` 加 `enable` 重新加载调用要经过的插件**：命令插件、MCP 入口、插件管理自己停用以后，`enable` 调不进去，条目停在停用状态。这几个换版本经 `update`，它在一条命令里做完停用与启用
- **同一个 home 同一时刻只做一个改动**：`install`、`uninstall`、`update` 运行时再调会回 `BUSY`。`add-entry`、`remove-entry`、`enable`、`disable`、`transfer-owner` 不受这道检查，`update` 运行时别动它要重新加载的条目。插件管理之外在同一个 home 里运行的 pnpm（`devkit.dev`、手工运行）它管不到，和插件管理的改动同时写 home 会丢改动，而且都退出码 0
- **人在 home 里手工运行 pnpm 要设环境变量 `pnpm_config_auto_install_peers=false`**：命令行参数 `--config.auto-install-peers=false` 会被 pnpm 忽略。插件管理自己启动 pnpm 时已经带着，所以 `install` 不补装缺的 peer，缺的看 `list` 的 `unmetPeers`，要用就另外 `install`
- **是不是插件只看包清单 `keywords` 里有没有 `gwb-plugin`**，名字不参与。`search` 回的是名单里各市场上按这条规则筛出的全部结果，不维护的旧包也在里面
