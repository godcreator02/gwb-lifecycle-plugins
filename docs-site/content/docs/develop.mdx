**本页回答**：开发套件怎么装、装完怎么确认；什么时候才进这个仓；第一次怎么准备；提交前运行哪些检查；改了 devkit 或插件管理怎么在隔离 home 里验证；发版按什么顺序做；文档站怎么检查、怎么生成 AGENTS.md 这些文件。

## 安装与确认

开发套件与别的插件一样用插件管理装：

```
plugin-manager.install {"pkg":"@godcreator/gwb-devkit"}
```

装完下一次调 MCP 入口的 `index` 就有 `devkit.*` 命令，不用重连。devkit 不另定义设置项；访问私有源前，发起 home 须按 `gwb-plugin-manager` 说明书配置共享凭据 `npm-auth`。

**确认它加载了**：`<home>\gwb.log` 里有「开发套件就绪」那一行，说明 `apply` 执行完了。安装命令回的「装完了」不算：包装进 `node_modules` 与插件加载成功是两件事。这个 home 上此刻有哪几条命令，以 `search {"plugin":"@godcreator/gwb-devkit"}` 的结果为准。

插件管理是基础插件：`devkit.home.new` 开的隔离 home 自带它，日常用的 `default` 在装机时装好。

## 什么时候进这个仓

**用 devkit 不进这个仓**，命令在任何装了它的 home 里都能调。**改这两个包本身才进来**：开发套件 `plugins/devkit/`、插件管理 `plugins/plugin-manager/`。改动只在隔离 home 里实际运行验证，不碰日常用的 `default`。两个包为什么在一个仓里见[关键设计](/docs/design#开发套件与插件管理放在同一个仓)。

## 第一次准备

在仓根：

```powershell
pnpm install
```

仓根的 workspace 包含两个插件包与 `docs-site`，一次装齐；devkit 的 peer 里写着插件管理（`workspace:^`），装好后 devkit 从工作区里的插件管理取它导出的函数与类型。文档站目录里另有自己的 `pnpm-workspace.yaml` 与锁文件，这是本仓特有的布局，模板生成的新仓没有。

实验材料放 `probes/<时间戳>_<目的>/`：一次实验一个目录、自包含、进 git、不在 workspace 里。

## 提交前的检查

{/* ref file="../package.json" lines="7-7" hash="dce8c11e4e22" blob="98383c87d541" */}

```powershell
pnpm check          # 各包的 check：开发套件是 typecheck + vitest，插件管理另加 oxlint
pnpm build          # 只构建 plugins/*，两个包都先清空 dist/：开发套件 esbuild 打包成一个 dist/index.js、tsc 只出类型声明，插件管理 tsc 直接输出；文档站不在里面
```

**`pnpm check` 不构建。** 它检查的是源码，全绿只说明源码没问题，跟「装出来能不能运行」是两件事。

**构建先清空 `dist/`**：不清的话，源码里删掉的模块还留在 `dist/` 里，随 `files` 白名单一起发出去。两个包的 `build` 脚本都先删 `dist/`。

**开发套件的构建**：`build.ts` 用 esbuild 从 `src/index.ts` 把 node 侧打成一个 `dist/index.js`，外置 node 内置模块、`electron`、`cordis` 与 peer 里的包，其余（yaml、es-module-lexer）打包进去；类型声明由 tsc 另外输出到 `dist/`。`bin/cdp.mjs` 不打包，产物里对它的 import 原样留成 `../bin/cdp.mjs`：产物与源码都在包根下一层，`import.meta.url` 算出来的包内路径（`bin/`、`skills/`、`template/`）打包前后指向同一处。打包进来的 yaml 是 CommonJS、会 `require` node 内置模块，ESM 产物里本来没有 `require`，所以产物开头用 `createRequire` 造了一个——删了它 vitest 照样全绿（vitest 自己提供 `require`），只有 `tests/built-artifact.test.ts` 另起的那个 node 进程会失败：

开发套件的测试里有两份启动真的子进程：`tests/process-tree.test.ts` 看超时之后孙进程真的没了（假实现证明不了），`tests/built-artifact.test.ts` 另起一个 node 进程 import 构建产物（没有 `dist/` 时整组跳过），还经产物调 `devkit.scaffold.plugin` 真的启动 pnpm：环境变量把 pnpm 的源指到本机一个没人监听的端口、不重试，加组件那一步当场失败，不联网，测的是插件文件已经写出、回执说清卡在组件这一步。都几秒钟就运行完，跟着 `pnpm check` 一起运行。

**开发套件的类型检查与测试用的是插件管理的 `dist/`**：插件管理的清单把主入口指到 `dist/index.js` 与 `dist/index.d.ts`，开发套件从那里 import。刚拉下来的仓、或者改了插件管理导出的函数，先 `pnpm build` 再 `pnpm check`，不然开发套件那一半报找不到模块，或者用的还是旧函数。

## 在隔离 home 里验证

单元测试覆盖不了「装出来能不能加载、命令调不调得通」，这要在隔离 home 里实际运行，步骤照说明书 `gwb-devkit` 的「改一版看一版」。本仓的 `packages` 给 `["plugins/devkit"]`，改的是插件管理就给 `["plugins/plugin-manager"]`。验 devkit 自己的命令也在隔离 home 里调——命令在隔离 home 的进程里运行，跟日常用的 home 里那份 devkit 无关。

`devkit.dev` 只拒绝以 `default` 或 devkit 自己所在的 home 为目标，所以从日常用的 home 往隔离 home 装开发版的 devkit 是可以的；日常用的 home 里的 devkit 只能发正式版后用 `plugin-manager.update {"all":true}` 升级。装的是插件管理自己时，它的条目在回执之后才重新加载（回执 `selfDeferred: true`），`devkit.dev` 会轮询 `plugin-manager.list` 等它回来。

改了模板时，模板生成的新仓能不能顺利运行完 install / build / check，单元测试回答不了：用构建产物实际建一个仓运行一遍，做法见 `probes/2609191042_workspace-scaffold/`；建仓要联网调 shadcn CLI 加组件，CLI 在插件包目录里实际怎么做见 `probes/2609301700_shadcn-cli-in-scaffold/`。

要验 devkit 开、停 home 的行为（`home.new`、`home.rm`，或者结束它开出的实例会怎样），在两个隔离 home 之间做：脚本直接用安装版启动隔离 home A、装上 devkit，经 `bin/cdp.mjs` 让 A 里的 devkit 开隔离 home B，再对 B 操作、看 A 的反应。不拿日常用的 home 当 A——它退出或卡住，正在用它的会话一起断。做法见 `probes/2609251010_parent-exit-on-child-kill/`。

## 发版

升哪一位版本号、依赖怎么写，正本是 devkit 的说明书 `gwb-release`（`skill.read {"name":"gwb-release"}`），**每次升版本号之前都读一遍**；发版的每一步与发完升级 `default`，在说明书 `gwb-devkit` 的「发版」。本仓只多下面几条。

`devkit.release` 的 `packages` 按依赖顺序排：

- 只发开发套件：`devkit.release {"dir":"<本仓根>","packages":["plugins/devkit"]}`
- 发插件管理：`["plugins/plugin-manager"]`；两个一起发时插件管理排在前面：`["plugins/plugin-manager","plugins/devkit"]`，devkit 的 peer 里插件管理那一项写成这次发的 `^<版本号>`

发完升级 `default` 时，升到插件管理自己，它的条目在回执发出之后才重新加载（回执 `selfDeferred: true`），过一会儿再用 `plugin-manager.list` 核对它 `active`。

发版只走 `devkit.release`，它自己先在仓根构建；两个包的 `package.json` 都不写 `prepublishOnly`，不手工 `pnpm publish`。

**开发套件的 `files` 白名单五项，一项都不能少**：

| 少了哪项 | 什么马上坏掉 |
| --- | --- |
| `dist` | 插件加载不了 |
| `template` | `devkit.scaffold` 回「包内 template/ 不在」 |
| `skills` | 说明书装不进 home，agent 读不到 |
| `bin` | `devkit.cdp` 指向一个不存在的文件，`devkit.dev` 的装包、刷新、核对三步一起失败 |
| `src` | 类型跳转与读源码断掉（不影响运行） |

插件管理的 `files` 是 `dist`、`skills`、`src` 三项。

## 文档站

文档站在 `docs-site/`。页面写什么、分区、钉码钉哪种话，照说明书 `docs-writing`；核对、确认黄灯、生成文件的命令照 `docs-site`；轨迹卡怎么写照 `trajectory`。在 `docs-site` 目录里：

```powershell
pnpm doc                                # docfirst check：页面引用的代码改了、生成文件与正本不一致，都会报出来
pnpm doc:confirm                        # 机械写回：草稿换成正式记号、挪了位置的写回行号、重新生成生成文件
pnpm doc:confirm <页的路径…> --accept    # 引用的代码改了、页上的说法仍成立时确认黄灯；只点名自己改的页
pnpm doc:render                         # 按 content/docs/outputs/ 重新生成 AGENTS.md、CLAUDE.md、README.md 与说明书
pnpm build                              # 构建文档站；端口见 package.json 的 start 脚本（4322）
```

**生成文件不手改**：`plugins/devkit/AGENTS.md`、`CLAUDE.md`、`README.md`、两个插件 `skills/` 下的 `SKILL.md` 与 `references/` 附件都由 `content/docs/outputs/` 下的 mdx 生成（附件 `references/rules.md` 由 `rules/index.mdx` 生成），对应关系在 `docfirst.config.mjs` 的 `outputs`；改 mdx、运行 `pnpm doc:render`，mdx 与生成文件放进同一个提交。
