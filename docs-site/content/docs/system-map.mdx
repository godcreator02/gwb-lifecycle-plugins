# 系统地图

**本页回答**：开发套件拆成哪几块、块与块之间谁依赖谁、纯逻辑与真机器切在哪一刀、新来的人按什么顺序读。

这个包是一个普通的 gwb 件：装进 home 才有它的命令，挂不上就什么都没有。它把「在一个新文件夹里
开发一个新件」这条路上的每一步都开成一个口，让 agent 能调到。

## 依赖方向

**硬依赖只有一条：命令总线。**

@@docfirst ref ../src/index.ts:50-51 @@

没有命令总线，这个件登记的一切都出不了这个进程，那时它确实不该挂上。别的服务全走
`ctx.inject([...], fn)` 这种局部注入：设置、外壳、node CLI、说明书四个面各开一条子 fiber，
缺哪个，那条 fiber 停在 PENDING，主件照常挂。少一条硬依赖就少一处挂不上的可能。

**文档站那半不是依赖，是两个字符串。** 建仓要铺 fumadocs 骨架、要装六区，这两件事分别归站件与
docfirst 件。本包不引它们的任何包，只在命令总线上按名字找那两条命令，找不到就跳过那一步。

@@docfirst ref ../src/index.ts:59-71 @@

耦合面因此只有那两个名字。哪个件没装，`hasCommand` 当场就知道，而且它现问不缓存：件是热挂载的，
装一个新件之后这个答案当场就变。

**说明书只挂自己那份。**

@@docfirst ref ../src/index.ts:680-686 @@

说明书是全局单一命名空间，同名的第二份直接不挂、只留一行警告，而被撞掉的那份未必是旧的。代挂别人的
说明书还有个更根本的问题：知识跟着它描述的代码走，代挂等于把别人的知识钉在自己的发版节奏上。

那支页面驱动是 CLI 形态的东西，所以经 `gwbNodeCli` 登记，不做总线命令、不进程内调。

@@docfirst ref ../src/index.ts:449-456 @@

登记进去的命令会自动镜像成同名总线命令，于是自动是 MCP 工具，回执自带 stdout、stderr 与退出码。
自己写一遍 spawn 与超时，换来的只是同一件事的第二种回执形状。

## 纯逻辑与真机器：切在哪一刀

判据只有一句：**这段逻辑能不能不起进程、不开窗、只喂输入看输出。**

能的那半是纯机，住 `scaffold.ts`、`daemon.ts`、`home.ts`、`dev.ts`。时序、守卫、命名、版本号、
「查不出算不算不在」这类判断全在这儿，测试拿假件把整条路跑完。

不能的那半是手，住三个 `node-*-deps.ts`。它们只负责在真机器上拿到答案：开进程、查进程表、查端口
持有者、读写盘、连 CDP。这一层不做任何判断，也不进单测。

隔离面是**显式接口**，不是自觉：`RegistryDeps` / `HomeDeps` / `DevDeps` 三张表由纯机那边定义，
真跑时传 `node-*-deps.ts`，测试时传一套假的。依赖方向因此是单向的：真身认识纯机，纯机不认识真身。

建仓那块是另一种形状。它不需要接口，因为它只做纯计算与同步写盘，所以它的测试直接写临时目录跑。
给一个「往盘上放文件」的函数塞替身，等于没测。

## 代码地图

**在哪**：件那半全在仓根的 `src/` 与 `bin/`，文档站自己一套依赖住 `docs-site/`。

**先读**：`src/index.ts` 的 `apply`，那是全部接线，一眼能看出这个件对外开了哪些口。想知道某件事
的判断怎么做的，再去它对应的纯机模块。

**读序**：`index.ts` 吃四个纯机模块，纯机模块吃自己那张注入面，`node-*-deps.ts` 实现注入面。
反过来的 import 一条都没有。

**可跳过**：`dist/` 是构建产物；`template/` 是发给别的仓的骨架模板，不是本件的逻辑；
`docs-site/.next` 与 `docs-site/.source` 是站的生成物。
