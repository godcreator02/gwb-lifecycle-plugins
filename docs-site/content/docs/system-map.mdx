# 系统地图

**本页回答**：开发套件拆成哪几块、块与块之间谁依赖谁、纯逻辑与真机器操作分在哪里、新来的人按什么顺序读。

这个包是一个普通的 gwb 插件：装进 home 才有它的命令，加载不成功就什么都没有。它把「在一个新文件夹里
开发一个新插件」这条路上的每一步都做成一条命令，让 agent 能调到。

## 依赖方向

**必需的依赖只有一个：命令总线 `gwbCommands`。**（本插件用到五个服务：`gwbCommands` 写在 `export const inject` 里；`gwbShell`、`gwbNodeCli`、`gwbSkills`、`gwbSettings` 都用 `ctx.inject([...], fn)` 局部注入，各在一个子 fiber 里。）

{/* ref file="../plugins/devkit/src/index.ts" lines="44-45" */}

没有命令总线，这个插件登记的一切都出不了这个进程，那时它确实不该加载。别的服务全走
`ctx.inject([...], fn)`：外壳、node CLI、说明书各开一个子 fiber，
缺哪个，那个 fiber 停在 PENDING，主插件照常加载——`gwbShell`（报名字）、`gwbNodeCli`（登记 `devkit.cdp` 这个 CLI）、`gwbSkills`（登记三份说明书）、`gwbSettings`（看 home 的根目录在哪）四个都这样。少一个必需依赖，就少一处加载不成功的可能。服务怎么用的规矩见[写插件的规矩](/docs/rules/services)。

**本插件没有浏览器侧代码。** 它的使用者是 agent，读的是回执，所以外壳那个子 fiber 里只有一句
`describeSelf`——报一个给人看的名字，好让它在插件清单里认得出来。没有窗格，也就没有
`dist/client/`、没有第二份 tsconfig、没有第二次 tsc。

{/* ref file="../plugins/devkit/src/index.ts" lines="418-423" */}

**建站那部分不是依赖，是两个命令名。** 建仓要建 fumadocs 骨架、要装六区，这两件事分别归站点插件与
docfirst 插件。本包不引它们的任何包，只在命令总线上按名字找那两条命令，找不到就跳过那一步。

{/* ref file="../plugins/devkit/src/index.ts" lines="47-59" */}

两边只通过这两个名字联系。哪个插件没装，`hasCommand` 当场就知道，而且它每次现问、不缓存：插件是热加载的，
装一个新插件之后这个答案当场就变。

**说明书只登记自己那份。**

{/* ref file="../plugins/devkit/src/index.ts" lines="883-889" */}

说明书是全局单一命名空间，同名的第二份直接不登记、只留一行警告，而被挤掉的那份未必是旧的。替别人登记
说明书还有个更根本的问题：知识跟着它描述的代码走，替别人登记等于把别人的知识绑在自己的发版节奏上。

插件 UI 接入规则由 shell 发布的 `gwb-shell` 说明书维护。devkit 主说明书指向它，
`skills/gwb-devkit/references/ui.md` 只保留兼容的指路；模板按这套规则写，不带第二份 UI 规范。

页面驱动是 CLI 形态的东西，所以经 `gwbNodeCli` 登记，不做总线命令、不在进程内调用。

{/* ref file="../plugins/devkit/src/index.ts" lines="430-439" */}

登记进去的 CLI 会自动变成同名的总线命令，于是自动是 MCP 工具，回执自带 stdout、stderr 与退出码。
自己写一遍 spawn 与超时，换来的只是同一件事的第二种回执形状。

## 纯逻辑与真机器操作：分在哪里

判据只有一句：**这段逻辑能不能不启动进程、不开窗口、只给输入看输出。**

能的那部分是纯机（纯逻辑），在 `scaffold.ts`、`structure.ts`、`probes.ts`、`home.ts`、`dev.ts`、`release.ts`、`tested-kernel.ts`、`audit.ts`、`capabilities.ts`。时序、
检查、命名、版本号、「查不出算不算不在」、「装上的是不是这次发的号」、「哪个依赖版本落后了」、「测过的内核在不在同一条版本线上」这类判断全在
这里，测试用假的依赖实现把整条路跑完。

不能的那部分在四个 `node-*-deps.ts`。它们只负责在真机器上拿到答案：启动进程、查进程表、查端口
被谁占着、读写磁盘、连 CDP、问源。这一层不做任何判断，也不进单测。

两边靠**显式接口**隔开，不靠自觉：`HomeDeps` / `DevDeps` / `ReleaseDeps` 三张表由纯逻辑那边定义，
真运行时传 `node-*-deps.ts` 的实现，测试时传一套假的。依赖方向因此是单向的：真机器那层认识纯逻辑，纯逻辑不认识它。

建仓那块是另一种形状。它不需要接口，因为它只做纯计算与同步写盘，所以它的测试直接写临时目录。
给一个「往磁盘上写文件」的函数换成假实现，等于没测。

## 代码地图

**在哪**：插件的代码全在 `plugins/devkit/` 的 `src/` 与 `bin/`，仓侧测试守卫工具包在 `packages/repo-kit/`，
文档站自己一套依赖在 `docs-site/`。

**先读**：`src/index.ts` 的 `apply`，那里登记了全部命令，一眼能看出这个插件对外有哪些命令。想知道某件事
怎么判断的，再去它对应的纯逻辑模块。

**读序**：`index.ts` 调用各纯逻辑模块，纯逻辑模块只依赖自己定义的那张依赖接口，`node-*-deps.ts` 实现这些接口。
反方向的 import 一条都没有。

**可跳过**：`dist/` 是构建产物；`template/` 是给别的仓用的骨架模板，不是本插件的逻辑；
`docs-site/.next` 与 `docs-site/.source` 是站的生成物。
