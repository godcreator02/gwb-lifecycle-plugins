**本页回答**：这个仓里反复出现的词各指什么，一个词一行，并指向定义它的那一页或那处代码；已经不用的词与命令现在该怎么说、怎么做。

收三类：这个生态自己起的名字、通用词在这里有特定含义的、读者第一次见会问「这是什么」的。通用编程词不收。

| 术语 | 意思 | 定义在哪 |
| --- | --- | --- |
| 插件 | 工作台里可以安装、卸载的功能单位，`package.json` 的 `keywords` 含 `gwb-plugin`。装进 home 并加了条目才会运行 | 内核仓文档站 |
| home | 磁盘上的一个目录，放一套独立的插件、数据、设置、日志与运行时记录。同一台机器上可以有很多个，互不影响 | 内核仓文档站 |
| 条目 | `cordis.yml` 里的一项，表示这个 home 要加载某个包。装了包不等于有条目，有条目不等于加载成功 | [插件管理](/docs/plugin-manager/home) |
| entryId | 一条条目的 id。停用、启用、重新加载、改显示名都按它指定 | [插件管理](/docs/plugin-manager/ids) |
| 日常 home | 人每天在用的 `default`。只装正式版，开发版不进它 | [关键设计](/docs/design#开发版只进隔离-home) |
| 隔离 home | 为一次验证新开、验完就删的 home。一次验证开一个新的，不复用上一次留下的 | [测试 home](/docs/devkit/home) |
| 控制台 home | 运行 `devkit.dev` 的那个 home（通常是 `default`）。它操作别的 home，不操作自己 | [改一版看一版](/docs/devkit/dev) |
| 基础插件 | `devkit.home.new` 在新 home 启动前装好的七个插件：命令、外壳、数据、设置、说明书、插件管理、基础界面 | [测试 home](/docs/devkit/home) |
| 内核包 | `@godcreator/gwb-kernel-desktop`：内核作为 npm 包装在每个 home 的根上，和 `cordis` 并列（安装包只带启动器，启动器从 home 里加载内核）。插件在 peer 里写它的范围 `^x.y.z`，声明兼容哪些内核；它的包根导出内核给插件的接口类型（`GwbContext` 等），插件只 `import type` | [兼容哪个内核](/docs/rules/kernel-compat) |
| importmap | 页面上「包名 → 文件地址」的表，浏览器侧代码里的包名 import 靠它解析。里面只有内核包在清单 `gwb.shared` 里声明的 react 四个包名，别的包写 `gwb.shared` 内核不收 | [页面代码与 importmap](/docs/rules/importmap) |
| 团队源 | gitea 个人源 `https://git.tianshen02.online:28377/api/packages/godcreator/npm/`，常驻，是 gwb 生态发版与安装唯一的 npm 源；scope 路由与发布 token 写在用户级 `~/.npmrc` | 说明书「gwb-release」 |
| 包源 | npmrc 里的一条 scope 路由加上它的凭据行：某个 scope 的包从哪个 npm 源装。第三方的包源写在机器级 `~/.npmrc`，由插件管理的 `source.*` 增删；`@godcreator` 那条是团队源，不经它改 | [找插件与配包源](/docs/plugin-manager/sources) |
| 开发版 | 版本号形如 `<patch+1>-dev.<时间戳>`、tag 为 `dev` 的一次性版本，只为把此刻的改动装进一个隔离 home，不影响 `latest` | [改一版看一版](/docs/devkit/dev) |
| 重新加载（remount） | 把一条条目停用再启用，让它重新 import。换了版本号才真的换得了代码；由 `plugin-manager.remount` 一条命令做完 | [改一版看一版](/docs/devkit/dev) |
| 取证 | 换完之后确认「它真的在运行」：装上的是这次的版本号、条目是 `ACTIVE`、日志新增部分里没有 error。加载了不算 | [改一版看一版](/docs/devkit/dev) |
| 调试端口 | 内核启动时用 `--remote-debugging-port` 打开的 Chromium 调试入口。从外面操作一个正在运行的页面全靠它，但**它不用来指定 home**：指定 home 用名字，端口是查出来的 | [CDP 驱动](/docs/devkit/cdp) |
| 运行时记录 | 每个 home 里的 `runtime.json`：pid、启动时间、应用目录、调试端口、MCP 入口地址。内核与 MCP 入口插件写，别的只读 | [测试 home](/docs/devkit/home) |
| 按名字定位 | 给 home 名，工具自己去运行时记录里查端口。**找到一个 home 只有这一种方式**，几条命令都不收端口 | [测试 home](/docs/devkit/home) |
| 验活 | 读运行时记录之后，确认记录里的进程还在、那个端口还是它在监听。记录只说「曾经」，验活才说「此刻」 | [测试 home](/docs/devkit/home) |
| 交叉核对 | 连上页面之后，拿页面自己报的 home 名跟要找的那个对一次。记录回答「要的是哪个」，页面回答「连上的实际是哪个」 | [CDP 驱动](/docs/devkit/cdp) |
| 命令总线 | 命令插件提供的服务 `gwbCommands`：插件在上面登记命令，界面、命令行、agent 调的是同一批命令 | 基础插件仓文档站 |
| 说明书 | 随包发布、由说明书插件登记给 agent 的 `SKILL.md`，经 `skill.read` 读。内容跟着它描述的代码一起发版 | [开发套件](/docs/devkit#说明书) |
| 建仓 | `devkit.scaffold` 把新插件的骨架写进一个新目录，插件文件与文档站分两部分完成 | [建仓与加插件](/docs/devkit/scaffold) |
| workspace 仓 | 仓根是不发布的 private 包，插件在 `plugins/<短名>/`、别的包在 `packages/`。模板只生成这一种布局；代码注释里叫「薄壳」 | [建仓与加插件](/docs/devkit/scaffold) |
| 旧布局仓 | 仓根本身就是插件包的仓，结构体检里叫 `bare-root-single`。改到哪个就迁哪个 | [结构体检](/docs/devkit/structure) |
| 发版前检查 | `devkit.release` 构建之后、发第一个包之前查的那几条：版本不在 0.0.x、dev 范围、peer 只写 `cordis` 与内核包、构建产物里的包名 import 与空 import、关掉 `skipLibCheck` 的类型检查、peer 里内核包的范围、`gwb.requires` 的写法。代码里的函数名与旧文档里叫「上车检票」 | [开发套件](/docs/devkit#发正式版的检查) |
| 最低版本要求 | 插件在 `package.json` 的 `gwb.requires` 里写的「home 里这个包不低于 x.y.z」。`plugin-manager.list` 报没满足的（`unmetRequires`），只报告不拦 | [要求别的插件的最低版本](/docs/rules/requires) |
| 纯逻辑 | 不读写磁盘、不启动进程、只看输入输出的那部分代码，测试用假实现跑完。对面是只执行、不判断的 `node-*-deps.ts`。代码注释里叫「纯机」 | [关键设计](/docs/design#纯逻辑与真机器操作分开) |
| 六区 | docfirst 文档站的六个目录：现状、轨迹、交接、未来、生成文件正本、反馈候选 | [开发](/docs/develop#文档站) |

一个词进表的门槛：在两页以上出现，或者读者第一次见会问「这是什么」。名字定了就别改，改名是历史，去轨迹区写一张卡。

## 退役的词

现状页与生成文件的正本不再用这些词（2026-09-13 的改名见[轨迹卡](/trajectory/2026-09-13-terminology-rename)）。旧卡、代码注释与更早的会话记录里还见得到，意思如下：

| 词 | 指的是 |
| --- | --- |
| **件 / 枚件** | 插件。件仓＝插件仓，站件＝站点插件，写件＝写插件 |
| **口** | 多数是端口（调试口、CDP 口、MCP 口、随机口、挑口），少数是入口（装机口、能被 agent 调到的口） |
| **门** | 入口（「cdp 是门」＝「cdp 是入口」；「开门」＝打开调试端口；「门插件」＝MCP 入口插件） |
| **格** | 窗格（如旧卡里的「状态格」）；「记录里那格」指记录的一个字段 |
| **重挂** | 重新加载一条条目（remount） |
| **薄壳** | workspace 仓的仓根：不发布、没有代码的 private 包 |
| **纯机** | 纯逻辑 |
| **上车检票 / 检票** | 发版前检查 |
| **底座** | 基础插件 |
| **钉 / 钉版** | 依赖写准确版本号；在文档站里指代码引用 |
| **词汇表包** | 内核接口的纯类型包 `@godcreator/gwb-plugin-api`，内核 0.5.0 起不再发。这些类型从内核包的包根 `import type`，见[轨迹卡](/trajectory/2026-09-24-importmap-kernel-only-check) |

## 退役的命令与参数

别的文档里还写着这些名字，说明那份文档过期了。为什么删见[砍掉没人用的那一半](/trajectory/2026-09-11-cut-the-half-nobody-uses)。

| 名字 | 从哪一版起没有 | 现在怎么办 |
| --- | --- | --- |
| `registry.log` | 0.6.0 | 源是常驻的 gitea 个人源，不需要启动停止 |
| `devkit.dev-check` | 0.6.0 | `devkit.cdp {"args":["<名>","cmd","plugin-manager.list"]}`，那是看，不是验证 |
| `devkit.home.stop` | 0.6.0 | 并进 `devkit.home.rm`：带 `force` 先停再删 |
| cdp 的 `targets` / `raise` / `probe` / `probes` | 0.6.0 | 连不上时报错里带着候选页面；`shot` 自己把窗口提到前面；读一组值用 `eval` |
| `home.new` 的 `cdp` / `skipBuild`、`home.open` 的 `cdp`、`dev` 的 `build` / `registry`、cdp 的 `--repo` / `--homes` | 0.6.0 | 都不收：每一个都是跳过一道检查的机会 |
| 「插件源」窗格 | 0.6.0 | 本插件没有界面了 |
| `D:\unitfolders\26090520zzv\registry.ps1` | 0.6.0 | 随本机 npm 源一起退役 |
| `kernel-dir` 设置与启动 home 时构建内核 | 0.12.0 | 启动 home 用宿主安装版；改内核源码的验证走内核仓自己的流程；`audit-deps` 的容器根问 `unit-folder.list` |
| `devkit.cdp-eval` | 0.4.0 | `eval` 是 `devkit.cdp` 的一个动作 |
| `devkit.livedoc` | 0.3.0 | 核对、确认、生成都在仓里运行：`cd <仓>\docs-site` 之后 `pnpm doc` / `pnpm doc:confirm` / `pnpm doc:render` |
| `plugin-sources.search` / `add` / `list` / `remove`、说明书 `gwb-plugin-sources` | `gwb-plugin-sources` 0.1.0 之后不再发 | 并回插件管理：`plugin-manager.search`、`plugin-manager.source.add` / `list` / `remove`，参数与回执不变；说明书读 `gwb-plugin-manager`。见[轨迹卡](/trajectory/2026-09-24-plugin-sources-back-to-plugin-manager) |
