**本页回答**：这个仓里反复出现的词各指什么，一个词一行，并指向定义它的那一页或那处代码；已经不用的词与命令现在该怎么说、怎么做。

收三类：这个生态自己起的名字、通用词在这里有特定含义的、读者第一次见会问「这是什么」的。通用编程词不收。

| 术语 | 意思 | 定义在哪 |
| --- | --- | --- |
| 插件 | 工作台里可以安装、卸载的功能单位，`package.json` 的 `keywords` 含 `gwb-plugin`。装进 home 并加了条目才会运行 | 内核仓文档站 |
| home | 磁盘上的一个目录，放一套独立的插件、数据、设置、日志与运行时记录。同一台机器上可以有很多个，互不影响 | 内核仓文档站 |
| 条目 | `cordis.yml` 里的一项，表示这个 home 要加载某个包。装了包不等于有条目，有条目不等于加载成功 | [插件管理](/docs/plugin-manager/home) |
| entryId | 一条条目的 id。停用、启用、重新加载都按它指定 | [插件管理](/docs/plugin-manager/ids) |
| 日常 home | 人每天在用的 `default`。只装正式版，开发版不进它 | [关键设计](/docs/design#开发版只进隔离-home) |
| 隔离 home | 为验证新开、验完就删的 home，由 `devkit.home.new` 开。一个隔离 home 同一时间只给一个会话用 | [测试 home](/docs/devkit/home) |
| 控制台 home | 运行 `devkit.dev` 的那个 home（通常是 `default`）。它操作别的 home，不操作自己 | [改一版看一版](/docs/devkit/dev) |
| 基础插件 | `devkit.home.new` 在新 home 启动前装好的插件：命令、外壳、数据、设置、说明书、插件管理、基础界面，加上提供 `timer` 服务的第三方 cordis 插件 `@cordisjs/plugin-timer` | [测试 home](/docs/devkit/home) |
| 内核包 | `@godcreator/gwb-kernel-desktop`：内核作为 npm 包装在每个 home 的根上，和 `cordis` 并列（安装包只带启动器，启动器从 home 里加载内核）。插件在 peer 里写它的范围 `^x.y.z`，声明兼容哪些内核；它的包根导出内核给插件的接口类型（`GwbContext` 等），插件只 `import type` | [兼容哪个内核](/docs/rules/kernel-compat) |
| importmap | 页面上「包名 → 文件地址」的表，浏览器侧代码里的包名 import 靠它解析。由 kernel 根据插件登记准备；React 由 shell 提供，其他插件也可登记 | [页面代码与 importmap](/docs/rules/importmap) |
| 团队源 | gitea 个人源 `https://git.tianshen02.online:28377/api/packages/godcreator/npm/`。`@godcreator` 的包正从这里迁到 npmjs：迁完之前本机的 `@godcreator` 仍从这里装（scope 路由写在用户级 `~/.npmrc`），发版经 `alsoPublishTo` 同时发到这里，发布 token 来自发起 home 的 `npm-auth` 凭据 | [pnpm 与包源](/docs/seams/pnpm-registry) |
| 包名范围 | 包名 `@<范围>/<名>` 里的 `@<范围>`。团队的是 `@godcreator`；`devkit.scaffold` 的 `scope` 参数定生成的插件在哪个范围下 | [建仓与加插件](/docs/devkit/scaffold) |
| 发布目标 | 一个包的正式版发到哪个源：它 `package.json` 的 `publishConfig.registry`，没写 `devkit.release` 就拒发。`devkit.scaffold` 的 `registry` 参数写这个字段 | [pnpm 与包源](/docs/seams/pnpm-registry) |
| 包源 | 某个 scope 的包从哪个 npm 源装，由 pnpm 的 scope 路由决定；认证由当前 home 的 `npm-auth` 提供。路由配置和凭据原值迁移由 agent 照说明书 `gwb-plugin-manager` 编排，产品不改持久化 npmrc；`@godcreator` 那条是团队源 | [找插件](/docs/plugin-manager/sources) |
| 市场 | `plugin-manager.search` 去找插件的一个 scope。市场名单是设置插件公共区的 `plugin-markets`，默认只有 `@godcreator`；名单外的包源不查。一个市场的源地址就是它在 pnpm 配置里的包源 | [找插件](/docs/plugin-manager/sources) |
| 开发版 | 版本号形如 `<patch+1>-dev.<yyyyMMddHHmmss>` 的一次性版本，只为把此刻的改动装进一个隔离 home；打成包文件、经那个 home 的插件管理装，不发到团队源 | [改一版看一版](/docs/devkit/dev) |
| 包文件 | `pnpm pack` 打出的 `.tgz`。开发版的包文件放在目标 home 的 `dev-packs` 目录，home 清单用 `file:./dev-packs/<包文件>` 引用它；每版一个新路径，旧的不删 | [改一版看一版](/docs/devkit/dev) |
| 重新加载（remount） | 把一条条目停用再启用，让它重新 import。换了版本号才真的换得了代码；由插件管理在目标进程里做：`plugin-manager.update` 装完在同一条命令里做，手动重新加载一条是先 `disable` 再 `enable` | [改一版看一版](/docs/devkit/dev) |
| 取证 | 换完之后确认「它真的在运行」：装上的是这次的版本号、条目是 `ACTIVE`、日志新增部分里没有 error。加载了不算 | [改一版看一版](/docs/devkit/dev) |
| 调试端口 | 内核启动时用 `--remote-debugging-port` 打开的 Chromium 调试入口。从外面操作一个正在运行的页面全靠它，但**它不用来指定 home**：指定 home 用名字，端口是查出来的 | [CDP 驱动](/docs/devkit/cdp) |
| 运行时记录 | 每个 home 里的 `runtime.json`：pid、启动时间、内核版本、调试端口、MCP 入口地址。内核与 MCP 入口插件写，别的只读 | [测试 home](/docs/devkit/home) |
| 按名字定位 | 给 home 名，工具自己去运行时记录里查端口。**找到一个 home 只有这一种方式**，几条命令都不收端口 | [测试 home](/docs/devkit/home) |
| 验活 | 读运行时记录之后，确认记录里的进程还在、那个端口还是它在监听。记录只说「曾经」，验活才说「此刻」 | [测试 home](/docs/devkit/home) |
| 交叉核对 | 连上页面之后，拿页面自己报的 home 名跟要找的那个对一次。记录回答「要的是哪个」，页面回答「连上的实际是哪个」 | [CDP 驱动](/docs/devkit/cdp) |
| 命令总线 | 命令插件提供的服务 `gwbCommands`：插件在上面登记命令，界面、命令行、agent 调的是同一批命令 | 基础插件仓文档站 |
| 说明书 | 随包发布、由说明书插件登记给 agent 的 `SKILL.md`，经 `skill.read` 读。内容跟着它描述的代码一起发版 | [开发套件](/docs/devkit#说明书) |
| 建仓 | `devkit.scaffold` 把新插件的初始文件写进一个新目录，只写插件的文件，不建文档站 | [建仓与加插件](/docs/devkit/scaffold) |
| workspace 仓 | 仓根是不发布的 private 包，插件在 `plugins/<短名>/`、别的包在 `packages/`。模板只生成这一种布局 | [建仓与加插件](/docs/devkit/scaffold) |
| 发版前检查 | `devkit.release` 构建之后、发第一个包之前查的那几条：peer 只写 `cordis`、内核包与插件、peer 里的插件和源上 latest 在同一条线、构建产物里的包名 import、peer 里内核包的写法、带界面插件的样式、插件注入的服务提供方写在 peer 里；dev 依赖不查。代码里的函数与类型名用 ticket（`Ticket`、`ticketRefusal`） | [发正式版](/docs/devkit/release) |
| wiring 页 | 有文档站的插件仓记插件之间依赖的地方：按插件写提供、注入、按名字调用与约定通道三张表，钉码钉字面量所在的那一行。记在哪一页不固定（本仓是 `docs/wiring.mdx`「插件之间怎么连」），插件首页写明记在哪。是约定，没有工具查 | [插件之间的依赖记在哪](/docs/rules/wiring) |
| peer | 插件 `package.json` 的 `peerDependencies`：运行时从 home 里得到的包——按值 import 的 `cordis`、内核包、用到的别的插件。node 侧构建产物只能按包名 import 这里写了的包。只在 `ctx.inject([...], fn)` 里用的插件在 `peerDependenciesMeta` 标 `optional`，意思是 home 里可以没有它、有的话版本要在范围里。`plugin-manager.list` 报没满足的（`unmetPeers`），只报告不拦 | [用到的插件写 peer](/docs/rules/plugin-peers) |
| 同一条线 | 两个版本号之间没有破坏性版本：主版本号为 0 时次版本号相同，≥1 时主版本号相同。`devkit.release` 拿它比 peer 里的插件和源上的 latest | [用到的插件写 peer](/docs/rules/plugin-peers) |
| 纯逻辑 | 不读写磁盘、不启动进程、只看输入输出的那部分代码，测试用假实现运行完。对面是只执行、不判断的 `node-*-deps.ts` | [关键设计](/docs/design#纯逻辑与真机器操作分开) |

一个词进表的门槛：在两页以上出现，或者读者第一次见会问「这是什么」。名字定了就别改，改名是历史，去轨迹区写一张卡。

## 退役的词

现状页与生成文件的正本不再用这些词（2026-09-13 的改名见[轨迹卡](/trajectory/2026-09-13-terminology-rename)）。旧卡、代码注释与更早的会话记录里还见得到，意思如下：

| 词 | 指的是 |
| --- | --- |
| **件 / 枚件** | 插件。件仓＝插件仓，站件＝站点插件，写件＝写插件 |
| **口** | 多数是端口（调试口、CDP 口、MCP 口、随机口、挑口），少数是入口（装机口、能被 agent 调到的口） |
| **门** | 入口（「cdp 是门」＝「cdp 是入口」；「开门」＝打开调试端口；「门插件」＝MCP 入口插件） |
| **格** | 窗格（如旧卡里的「状态格」）；「记录里那格」指记录的一个字段 |
| **重挂** | 重新加载一条条目（remount） |
| **薄壳** | workspace 仓的仓根：不发布、没有代码的 private 包 |
| **纯机** | 纯逻辑 |
| **上车检票 / 检票** | 发版前检查 |
| **底座** | 基础插件 |
| **钉 / 钉版** | 依赖写准确版本号；在文档站里指代码引用 |
| **devkit 仓、仓名 gwb-devkit、根包名 gwb-devkit-workspace** | 本仓 `gwb-lifecycle-plugins`，2026-09-25 改名（[轨迹卡](/trajectory/2026-09-25-repo-renamed-lifecycle-plugins)）。包名 `@godcreator/gwb-devkit` 与说明书 `gwb-devkit` 没改；gitea 上的远端仓仍叫 `godcreator/gwb-devkit` |
| **词汇表包** | 内核接口的纯类型包 `@godcreator/gwb-plugin-api`，内核 0.5.0 起不再发。这些类型从内核包的包根 `import type`，见[轨迹卡](/trajectory/2026-09-24-importmap-kernel-only-check) |
