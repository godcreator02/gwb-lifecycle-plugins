**本页回答**：`gwb-lifecycle-plugins` 仓里哪些决定错了难改、为什么这么定；每条推出了什么、代价是什么；哪些事刻意不做。只写错了难改的：命令怎么用、每一步的细节在各包的页与说明书里。每个包的功能与接口见[开发套件](/docs/devkit)、[插件管理](/docs/plugin-manager)。

## 开发套件是一个普通插件

devkit 没有任何特权：装进 home 才有它的命令，和别的插件一样由插件管理安装、升级、卸载（[gwb-devkit 这个插件](/trajectory/2026-09-08-gwb-devkit)）。它提供的每条命令都是「在一个新文件夹里开发一个新插件」这条路上的一步，让 agent 能调用。

推出了：

- **使用者是 agent，所以没有界面**：结果全在回执里；参数形状写进每条命令的 `usage`，参数错了回执带完整用法——命令总线不带参数形状，agent 能看到的只有这些
- **说明书与模板随包发布**：装上哪一版就读到哪一版，不另外维护一份（[说明书与模板回到包里](/trajectory/2026-09-09-skills-and-templates-ride-package)）；只登记自己的说明书，说明书名全局唯一
- **只有一个必需服务**：命令总线写在 `export const inject`，外壳、node 命令行、说明书都局部注入，缺了只少一部分功能

代价：devkit 的改动也要走发版、安装才能用上；改 devkit 自己不能用 `devkit.dev` 装进它自己所在的 home（见下面「开发版只进隔离 home」）。

## 写插件只有一条路：打包、安装、验证

每个插件都在自己的仓里开发，按 `files` 白名单打成包再装进 home：开发版打成包文件、经目标 home 的插件管理装进隔离 home，正式版发到包的发布目标、再装进日常用的 home。**安装这一步本身就在验证**：`exports` 漏了一个子路径、`files` 少带了一个目录，只有装出来才会暴露。

推出了：

- **改一版看一版也换版本号**：`devkit.dev` 每次打一个开发版号的包文件放进目标 home 的 `dev-packs`。包文件的路径变了，pnpm 虚拟存储里的目录才变，重新加载时 Node 才会重新执行新代码；覆盖 home 里 `node_modules` 下的文件会改坏 pnpm 全局存储里的原件（[开发版打成包文件、经插件管理装](/trajectory/2026-09-25-dev-via-pack-and-plugin-manager)）
- **包文件每版一个新路径、只增不删**：覆盖写同一个路径，pnpm 退出码 0 却装着旧代码；home 清单还引用着的包文件一删，这个 home 里之后的 `pnpm add` 全部失败（[pnpm 在 home 里对包文件的表现](/trajectory/2026-09-25-dev-install-via-file-tgz)）
- **正式版只从提交过的状态发**：版本号在仓里改、随提交走；`devkit.release` 在 git 工作区不干净、同号已在发布目标上、发版前检查没过时一概不发，也不改仓里任何文件（[发正式版进 devkit](/trajectory/2026-09-14-release-comes-to-devkit)）
- **最后一步是取证**：`devkit.dev` 回成功之前，确认装上的是这次的版本号、条目在运行、日志新增部分里没有 error

代价：比直接覆盖文件慢；隔离 home 的 `dev-packs` 与 pnpm 存储里会积累开发版，前者随隔离 home 一起删，存储要定期清理。

## 包名与发到哪用 npm 的标准字段

包的身份就是 `package.json` 的 `name`，发到哪就是 `publishConfig.registry`，不另造配置（[包名范围与发布目标交给开发者](/trajectory/2026-09-25-scope-and-publish-target)）。`devkit.scaffold` 的 `scope`、`registry` 两个参数写的就是这两个字段；`devkit.release` 照每个包自己的 `publishConfig.registry` 发；开发版不经过任何源。没有团队源发布权限的开发者给自己的范围与源，就能走完建仓、改一版看一版、发正式版。

推出了：

- **没写 `publishConfig.registry` 就拒发**：发到哪由包自己写明，不给缺省值，也不交给机器上 `~/.npmrc` 的范围行（[删掉给旧仓留的两个缺省值](/trajectory/2026-09-25-drop-legacy-defaults)）
- **是不是插件看 `keywords`，不看包名范围**：发版前检查对任何范围下的插件都一样查；dev 依赖不查
- **问别的包的 latest 交给 `~/.npmrc`**：不指定源，按用户级 `~/.npmrc` 的范围行找；只有「这个版本号在发布目标上有没有」指定发布目标

代价：每个要发的包都得写 `publishConfig.registry`；装别的范围下的插件，那个范围的源得先配进 `~/.npmrc`。

## 开发版只进隔离 home

开发和验证都在单独新建的隔离 home 里做，日常用的 `default` 只装正式版。

- **`devkit.dev` 拒绝 `default`**：开发版进了 `default`，版本号看起来跟正式版没两样，界面上一点异常都看不出来
- **`devkit.dev` 运行在另一个 home 里，操作目标 home**：换插件要把条目停用再启用，工具自己运行在被换的 home 里，换到命令总线、MCP 入口或它自己时，调用方会跟着停掉。所以构建、打包在本进程做，安装、刷新、核对经 CDP 发到目标页面；目标就是 devkit 自己所在的 home 也拒
- **安装与重新加载交给目标 home 的插件管理**：一条 `plugin-manager.update` 在目标进程里装包、重新加载，插件管理自己的条目推迟到回执之后——被换的是插件管理自己或命令总线时，这边再发的第二条命令没人接收（[重新加载是一条命令](/trajectory/2026-09-17-remount-is-one-command)）
- **升级 `default` 是发正式版之后的事**：`devkit.release` 只发到源、不碰任何 home

代价：改 devkit 自己只能发正式版再升级；想在隔离 home 里验证 devkit 自己，要从另一个 home 驱动。

## 只按名字定位一个 home

说出 home 名，工具去这个 home 的 `runtime.json` 里查调试端口，并确认 pid 还活着、那个 pid 确实在监听这个端口；连上页面之后，再拿页面自己报的 home 名核对一次。`devkit.dev`、`devkit.cdp` 与启动 home 的两条命令都不收端口（[端口不是地址](/trajectory/2026-09-11-port-is-not-an-address)、[按名字定位](/trajectory/2026-09-11-address-a-home-by-name)）。

理由：端口是一个没有含义的数字，敲错一位就连到另一个 home，而那个 home 会照样收下这次的安装与重新加载。名字有拼写、有记录、能交叉核对，这三样端口都没有。

推出了：调试端口由 `devkit.home.new` / `open` 自动选，先沿用这个 home 上次那个；`runtime.json` 由内核写，devkit 只读。

代价：记录坏了的 home 连不上，要停掉重开一次；CDP 驱动只能操作 gwb 的窗口。

## 查不出就报错，认不出就拒

**认不出的就拒、查不出的就报错，只在系统边界上校验，一个判断只写一份**（[devkit 0.22 删兜底](/trajectory/2026-09-25-devkit-no-fallbacks)）：

- 进程表、端口占用、`pnpm view` 查不出，直接报错，不当成「没在运行」「没人监听」「没发过」
- 每条命令拒认不出的参数键，报出是哪个
- 流程只写在说明书里，回执只带这次特有的东西，不复述流程
- 页面属于哪个 home，只在 `cdp.mjs` 连上时核对一处

## 纯逻辑与真机器操作分开

判据一句话：**这段逻辑能不能不启动进程、不开窗口、只给输入看输出。**

能的部分是纯逻辑：时序、检查、命名、版本号、「记录里的 pid 还是不是那个 home」「装上的是不是这次打包的版本」「peer 里的插件和源上 latest 在不在同一条线」这些判断都在这里，测试用假的依赖把整条流程运行完。不能的部分在 `node-*-deps.ts` 与 `node-process-tree.ts` 里，只负责在真机器上拿到答案：启动进程、超时终止整棵进程树、查进程表与端口、读写磁盘、连 CDP、问 npm 源。这一层不做判断，也不进单元测试；唯一的例外是超时终止整棵进程树，用真的子进程测（孙进程真的没了，假实现证明不了）。

两边靠显式接口隔开：`HomeDeps`、`DevDeps`、`ReleaseDeps` 由纯逻辑定义，运行时传 `node-*-deps.ts` 的实现，测试时传假实现。依赖方向单向：真机器那一层认识纯逻辑，纯逻辑不认识它。

## 开发套件与插件管理放在同一个仓

插件管理仍是 home 里的普通插件：由 `cordis.yml` 里的一条条目加载、单独发版、用 `plugin-manager.update` 升级。它和 devkit 放在一起，是因为两者互相依赖的地方多（[插件管理迁入 devkit 仓](/trajectory/2026-09-24-plugin-manager-joins-devkit)）：

- `devkit.dev` 在目标页面里调 `plugin-manager.install` 与 `plugin-manager.update {"specs":{…}}` 装包并重新加载，再用 `plugin-manager.list` 取证
- `devkit.home.new` 把插件管理作为基础插件装进新 home，之后往这个 home 加插件、升内核都经它
- 插件 peer 里内核包的范围两边都用：插件管理在 `list` 里拿它和运行中的内核比对，`devkit.release` 发版前拒绝没写或写法不对的插件包。规则只有一份，在插件管理；devkit 的 peer 里写着插件管理，从它的主入口 import 判断写法的 `isCaretRange`，连同找 pnpm 的 `locatePnpm`

放在一个仓里，这些地方一个提交就能改两边。

仓名 `gwb-lifecycle-plugins` 说的是两个插件合起来管的范围：devkit 管建仓、验证、发版，插件管理管装、升级、卸载。改的只是仓名，发出去的包名 `@godcreator/gwb-devkit`、`@godcreator/gwb-plugin-manager` 与说明书名不变，改包名是破坏性变更（[仓改名 gwb-lifecycle-plugins](/trajectory/2026-09-25-repo-renamed-lifecycle-plugins)）。

代价：发版要用 `packages` 指明发哪个包，两个一起发时插件管理排在前面；devkit 离了插件管理加载不了。改插件管理的命令名、参数、回执形状或主入口导出的函数是破坏性变更——插件管理窗格、`devkit.dev`、agent 的说明书都按它们写死了调用。

## 模板是唯一正本，仓只有一种布局

仓的布局只有一种：workspace 仓，插件在 `plugins/<短名>/`。只有一个插件的仓也是这个布局，加第二个插件是一条命令（[只有一种仓的布局](/trajectory/2026-09-19-one-shape-workspace-always)）。

- **建仓与加插件用同一份插件包模板** `template/pkg/`，两种命令生成的插件包格式一致靠这个，不靠纪律
- **模板带的产物测试与发版前检查用同一套名单**：生成的插件包在被生成的仓里 `pnpm check` 就能查出发版时会被拒的包名 import（[4 模板与发版前检查](/docs/seams/template-release)）
- **`devkit.dev` 与 `devkit.release` 的 `packages` 必给**：要装、要发的包目录由调用方列出；`devkit.scaffold.plugin` 只往 `pnpm-workspace.yaml` 里有 `plugins/*` 的仓里加插件

代价：不是 workspace 布局的仓用不了这几条命令，要先照模板迁。

## 刻意不做

- **不收端口**：见「只按名字定位一个 home」
- **不写 `runtime.json`**：已有内核与 MCP 入口插件两个写入者，第三个只会让记录说不清
- **不构建内核**：启动 home 用宿主自己那个安装版应用；改内核源码的验证走内核仓自己的流程
- **不做设置项**：一项都不需要；将来要加用 `gwbSettings.define`，不读 `cordis.yml` 条目上的 `config`——写在 yml 里的那份界面看不见、agent 也不知道
- **不自动清理**：现有的 home 由 `devkit.home.list` 列出，删哪个由调用方决定
- **不建文档站**：建仓与加插件只写插件的文件，文档站由站点插件与 docfirst 插件自己的命令建
- **不巡检别的仓**：依赖写法、peer 与产物在各仓发版时由 `devkit.release` 查
- **不留没人用的命令与参数**：退役的名字与现在怎么做，列在[术语表](/docs/glossary#退役的命令与参数)
