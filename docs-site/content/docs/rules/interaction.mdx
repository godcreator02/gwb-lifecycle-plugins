# 插件之间怎么交互

**本页回答**：一个插件要用另一个插件的能力、数据或类型时，允许走哪几条路；共享代码和共享数据格式怎么做；接口的类型放在哪一边。

## 规则

**插件之间只通过 cordis 服务和命令交互，不 import 别的插件。** 要共享代码，提供方另外发布一个无状态的接口定义包；要共享磁盘上的数据格式或一组命令的结构，按区间比对契约版本。**谁提供接口，谁定义它的类型。**

## 怎么判

- **「import 别的插件」**指 import 带 `apply` 或有模块状态的插件包入口和子路径。import 一个库或接口定义包不算：接口定义包只有类型、常量和纯函数，没有模块状态，使用方写 dev、打包进自己的构建产物
- **跨插件边界只传**纯数据、函数和 `{ ok, data, error }` 形状的命令返回值；不对别的插件所带库里的类做 `instanceof`，各插件带的是不同的拷贝。`Error`、`URL` 这类平台全局对象不受限
- **依赖在不在、要不要跟着提供方重新加载**，交给 cordis 的 inject：提供方重新加载时，依赖它的插件会被卸载、再重新加载（见[cordis 服务怎么提供和使用](/docs/rules/services)）
- **按名字调命令，不 import 提供方的常量**：import 进来就把提供方变成了运行时依赖
- **数据目录归它的主人**：插件的数据目录只由它自己读写；别的插件要那份数据，调它的命令。几个插件共同约定的文件（比如单元的 `unit.json`）归定义它的那个插件，读的一方按它发布的契约读

## 契约版本按区间比对

几个插件读写同一份磁盘上的数据格式、或者依赖同一组命令的参数与返回值结构时：

- 提供方在存在标记服务上给出 `contract`（现在的版本）与 `minCompatible`（还兼容的最低版本）两个数。改命令的参数或返回值结构就把 `contract` 加一，破坏了旧结构还要升 `minCompatible`
- 使用方把自己期望的版本**写死在自己代码里**，落在区间外就在 `apply` 里抛错、拒绝加载，不只是警告

```ts
// 本插件照着第 8 版命令写的，写死在自己代码里，不从接口定义包里取
export const EXPECTED_CONTRACT = 8

export function apply(ctx: GwbContext): void {
  const mark = ctx.blockNote!
  if (EXPECTED_CONTRACT < mark.minCompatible || EXPECTED_CONTRACT > mark.contract) {
    // 在 apply 里抛错，这个插件就进入 FAILED 状态，等于拒绝加载
    throw new Error(`提供方支持第 ${mark.minCompatible}–${mark.contract} 版命令，本插件按第 ${EXPECTED_CONTRACT} 版写的`)
  }
  // …
}
```

两种写法不对：要求版本完全相等（提供方加一个可选字段就判为不兼容）；使用方从共享的接口定义包里取期望版本（比对的两边永远相等，等于没比）。

## 类型放在提供方那边

- **内核的接口**（`gwbKernel`、页面上 `window.gwb` 的 `command` / `on`、外壳的默认导出）：类型在词汇表包 `@godcreator/gwb-plugin-api` 里，纯类型，只增不减
- **插件的接口**：服务接口、命令的参数和返回值类型都由提供方导出，放在它自己的包或它发布的接口定义包里。不把插件之间的契约塞进词汇表包
- **调用方**取类型只用 `import type` 引提供方的包。有意不引提供方类型的调用方（对方是可选的插件），对返回值做防御式的类型收窄，不算违反
- **不用 `as` 把东西强转成提供方的类型**：要收窄接口，就通过赋值让类型检查来验证

## 为什么

各插件带的库是各自的一份拷贝，模块单例和 `instanceof` 在插件之间不成立；命令总线只传 `{ ok, data, error }` 形状的返回值，所以各插件各自带一份库不会出错，真正的风险是各方版本不一致、磁盘上的数据格式对不上，这由契约版本区间来拦。类型放在提供方那边，提供方改了实现，类型检查会在调用方那里报出来；放在调用方那边，提供方改了什么都没人拦得住。
