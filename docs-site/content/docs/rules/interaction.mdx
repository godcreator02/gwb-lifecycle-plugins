# 插件之间怎么交互

**本页回答**：一个插件要用另一个插件的能力、数据或类型时走哪几条路；两边的版本对不上时靠什么发现；接口的类型放在哪一边。这一页都是写法建议，没有工具检查，违反了也不会被拦。

## 走服务和命令

- **能力走服务和命令**：扩展点用服务，读写和动作用命令（见[cordis 服务怎么提供和使用](/docs/rules/services)）。依赖在不在、要不要跟着提供方重新加载，交给 cordis 的 inject
- **跨插件边界只传**纯数据、函数和 `{ ok, data, error }` 形状的命令返回值；不对别的插件所带库里的类做 `instanceof`，各插件带的是不同的拷贝。`Error`、`URL` 这类平台全局对象不受限
- **按名字调命令**，不 import 提供方的常量：import 进来就把提供方变成了运行时依赖
- **数据目录归它的主人**：插件的数据目录只由它自己读写；别的插件要那份数据，调它的命令。几个插件共同约定的文件（比如单元的 `unit.json`）归定义它的那个插件
- **要共享代码**，提供方另外发布一个无状态的接口定义包（只有类型、常量和纯函数），使用方写 dev、打包进自己的构建产物

**按值 import 别的插件的主入口也可以**，前提是把它写进 peer：devkit 从插件管理的主入口 import 找 pnpm、在 home 里启动 pnpm 的环境、peer 里内核包写法的判定这几个纯函数，规则只存一份。代价是 import 会加载对方整个主入口模块，离了对方加载不了；对方升级后真实目录变了，插件管理会把这边一起重新加载（见[用到的插件写 peer](/docs/rules/plugin-peers)）：

## 版本对不上靠 peer 发现

使用方在 peer 里写提供方的 `^x.y.z`；提供方改了命令的参数或回执、磁盘上的数据格式这类契约，按说明书 `gwb-release` 升 x。home 里装着的提供方出了范围，`plugin-manager.list` 在使用方的 `unmetPeers` 里报出来；使用方发版时，`devkit.release` 拒和源上 latest 不在同一条线的 peer。不另在服务上放契约版本号、在 `apply` 里比对。

## 类型放在提供方那边

- **内核的接口**（`gwbKernel`、页面上 `window.gwb` 的 `command` / `on`、外壳的默认导出）：类型由内核包 `@godcreator/gwb-kernel-desktop` 的包根导出，纯类型，只增不减；插件 peer 里写着内核包，直接 `import type`
- **服务的类型**由提供方导出，放在它自己的包或它发布的接口定义包里：inject 它的一方要用。不把插件之间的契约塞进内核包
- **命令回执的类型**有调用方要 import 时才由提供方导出，没有就不导出；回执形状以那条命令的 `usage` 为准
- **调用方**取类型只用 `import type` 引提供方的包；不用 `as` 把东西强转成提供方的类型，要收窄就通过赋值让类型检查来验证

## 为什么

各插件带的库是各自的一份拷贝，模块单例和 `instanceof` 在插件之间不成立；命令总线只传 `{ ok, data, error }` 形状的返回值，所以各插件各自带一份库不会出错，真正的风险是两边版本对不上，这由 peer 范围和升 x 来发现，不另设一套契约版本号。类型放在提供方那边，提供方改了实现，类型检查会在调用方那里报出来；放在调用方那边，提供方改了什么都没人拦得住。
