# 写插件的规矩

**本页回答**：写一个 gwb 插件要守哪些规矩；每条由哪道检查负责；哪些规矩现在只能靠人；这个仓自己哪些还没照做。

规矩对新写的插件和这次改到的插件都生效。每条的做法、理由和例子在分页里，本页只列总表。

两件事不在这一组页里：

- **版本号升哪一位**：照说明书 `gwb-release`（`skill.read {"name":"gwb-release"}`），全生态一套
- **一件事该进内核还是做成插件**：判据在内核仓文档站的「关键设计」页——只有第一个插件运行之前必须完成的事才进内核，其余一律做成插件

写一个新插件，先读[依赖怎么写](/docs/rules/deps)和[cordis 服务怎么提供和使用](/docs/rules/services)，再读[卸载清理](/docs/rules/dispose)；要和别的插件打交道时读[插件之间怎么交互](/docs/rules/interaction)；带界面的读[页面代码与 importmap](/docs/rules/importmap)；发版之前读[兼容哪个内核](/docs/rules/kernel-compat)。

## 有哪些检查

| 检查 | 什么时候跑 | 没过会怎样 |
| --- | --- | --- |
| `devkit.release` 的发版前检查 | 构建之后、发第一个包之前 | 一个包都不发，回执按包列全 |
| `devkit.audit-deps` | 手动调，扫一个容器根下的各仓 | 只报告，不拦 |
| `devkit.audit-structure` | 手动调，查一个仓或全生态 | 只报告，不拦 |
| 模板带的产物测试 | 构建之后跑 `pnpm check`（没有 `dist/` 时整组跳过） | 测试红 |

模板带的产物测试是 `devkit.scaffold` 生成进每个插件的 `tests/artifact.test.ts`。

## 总表

| 规矩 | 做法见 | 由谁检查 | 现状 |
| --- | --- | --- | --- |
| peer 只写 home 根上的两个包——构建产物里按值 import 的 `cordis` 与内核包 `@godcreator/gwb-kernel-desktop`，其余写 dev | [依赖](/docs/rules/deps) | `devkit.release` 拒 peer 里 `cordis` 与内核包以外的包、拒 node 侧产物按值 import 了 `cordis` 却没写 peer，写了 peer `cordis` 而产物没 import 只提醒；`devkit.audit-deps` 报 `peer-not-cordis` | — |
| `cordis` 不写进 `dependencies` | [依赖](/docs/rules/deps) | `devkit.audit-structure`（`cordis-in-dependencies`，error） | — |
| `@godcreator` 包的 dev 写 `^` 范围或精确号，范围包含源上最新的正式版 | [依赖](/docs/rules/deps) | `devkit.release` 拒写法认不出、下限比源上 latest 新、latest 已出范围；`devkit.audit-deps` 报 `dead-pin`、`behind`、`out-of-range`、`loose-dev-pin` | — |
| 构建产物里的包名 import 只能是 node 内置模块、`electron`、`cordis` 与页面 importmap 里的名字 | [依赖](/docs/rules/deps) | `devkit.release` 两侧都查，浏览器侧只放行内核包清单 `gwb.shared` 的键（从包目录 `node_modules` 里装好的内核包读，读不到也拒）；模板带的产物测试同样查两侧 | — |
| 类型引用到的包由使用方在 dev 里列全，`skipLibCheck: false` 下类型检查通过 | [依赖](/docs/rules/deps) | `devkit.release` 发版前关掉 `skipLibCheck` 做一次类型检查 | — |
| 只引类型写 `import type`，不写 `import { type X }` | [依赖](/docs/rules/deps) | `devkit.release` 拒构建产物里的空 import（`import { type X }` 编译后留下的 `import {} from`） | — |
| 源码里不指回别的仓：tsconfig `paths` 只有指向包内的 `@/*` 一项，没有 `link:` / `file:` 依赖 | [依赖](/docs/rules/deps) | `devkit.audit-structure`（`tsconfig-paths`、`local-protocol-dep`，error） | 跨仓的 `workspace:` 不查；只查包根的 tsconfig，`src/client/tsconfig.json` 不查 |
| node 侧用 tsc 直接输出时，相对 import 带 `.js` | [依赖](/docs/rules/deps) | 模板带的产物测试 | — |
| 带界面的插件，`style.css` 的颜色类只用主题令牌（外壳 `theme.reference.css` 与本插件 `@theme` 声明的 `--color-<名>`），不用 Tailwind 出厂调色板 | [importmap](/docs/rules/importmap) | 模板带的产物测试 | 只查 `text-` / `bg-` / `border-` / `from-` / `via-` / `to-` / `divide-` 开头的类，`ring-`、`fill-` 等别的前缀不查 |
| 留着 `prepublishOnly: pnpm build`，`files` 白名单列全 | [依赖](/docs/rules/deps) | `devkit.audit-structure`（`prepublish-only`、`files-whitelist`，error）；`devkit.release` 照 `files` 验构建产物在不在 | — |
| 页面 importmap 只有内核包声明的 react 四个包名；内核包以外的包不写 `gwb.shared` | [importmap](/docs/rules/importmap) | 内核只读内核包自己的 `gwb.shared`；`devkit.release` 拒内核包以外写了 `gwb.shared` 的包，插件与库都拒 | — |
| 外置名单只从内核包清单的 `gwb.shared` 读，不手抄 | [importmap](/docs/rules/importmap) | 没有工具检查；抄了 importmap 里没有的名字，`devkit.release` 的浏览器侧检查会拒 | — |
| 扩展点服务继承 cordis 的 `Service`，注册随调用方卸载自动撤销 | [服务](/docs/rules/services) | 没有工具检查 | 外壳 `gwbShell` 与命令总线 `gwbCommands` 0.4.6 起继承 `Service` |
| 扩展点用服务，数据读写和动作用命令，同一能力只提供一种调用方式 | [服务](/docs/rules/services) | 没有工具检查 | — |
| 命令的 `name`、`description`、`usage` 都是非空字符串：`description` 一句话说做什么，参数形状写进 `usage`，无参数写「无参数」；`plugin` 可以不写，写了必须等于自己的完整包名 | [服务](/docs/rules/services) | 命令总线 `gwbCommands` 0.5.0 起登记时检查，缺字段、只有空白、`plugin` 与调用方的包名不同都直接抛错，插件加载失败；`plugin` 不写由命令总线从调用方取；`usage` 写没写对参数形状没有工具检查 | — |
| 窗格的 `client` / `style` 从插件自己的模块地址算（`new URL('./client.js', import.meta.url).href`），是路径以 `.js` / `.css` 结尾的 `file://` 地址 | 说明书 `gwb-shell` | 外壳 `gwbShell` 0.13.6 起 `registerPane` 登记时检查，不合格直接抛错 | — |
| `gwb.provides` 里源码提供的每个服务都有一条；每个键是源码提供的服务名，或本包 `exports` 里的 import 说明符（主入口写包名，子路径写 `包名/子路径`）；`summary`、`usage` 不空 | [服务](/docs/rules/services) | `keywords` 含 `gwb` 或 `gwb-plugin` 的包：`devkit.release` 拒；`devkit.audit-structure` 报 `provides-declaration`（error） | — |
| `gwbKernel` 用 `requireKernel` 取、不写进 `inject`；不写 `instanceof Service`；类的私有字段用 TS `private` | [服务](/docs/rules/services) | 没有工具检查 | — |
| 插件之间只通过服务和命令交互，不 import 别的插件 | [交互](/docs/rules/interaction) | `devkit.release` 拒构建产物按值 import 别的插件（上面「包名 import」那一条）；只 import 类型不受影响 | — |
| 共享磁盘数据格式或命令结构时，按区间比对契约版本，区间外拒绝加载 | [交互](/docs/rules/interaction) | 没有工具检查 | — |
| 谁提供接口谁定义类型；调用方不手写、不用 `as` 强转成提供方的类型 | [交互](/docs/rules/interaction) | 没有工具检查 | — |
| 插件的数据目录只由它自己读写 | [交互](/docs/rules/interaction) | 没有工具检查 | — |
| 自己启动或创建的一切，卸载时清理掉，并返回 promise | [卸载清理](/docs/rules/dispose) | 没有工具检查 | — |
| 插件包在 peer 里写内核包 `@godcreator/gwb-kernel-desktop`，范围 `^x.y.z` 包含运行中的内核 | [兼容哪个内核](/docs/rules/kernel-compat) | `devkit.release` 拒没写、写法不是 `^x.y.z`、范围不包含运行中的内核；`plugin-manager.list` 按包报范围不包含 home 里内核的插件 | — |
| 用到别的插件某个版本才有的东西时写 `gwb.requires`（包名 → 最低版本号 x.y.z），每个包也写在 dev 里、要求不高于 dev 下限 | [要求的插件版本](/docs/rules/requires) | `devkit.release` 拒不是对象、值不是 x.y.z、包不在 dev 里、要求高于 dev 下限；`plugin-manager.list` 按包报 `unmetRequires` | — |
| 0.x 里只在破坏契约时升 x，其余升 y；0.0.x 先升到 0.1.0；同一个号不重发 | 说明书 `gwb-release` | `devkit.release` 拒 0.0.x 与源上已有的号；升哪一位没有工具检查 | — |

## 这个仓自己还没照做的

插件管理（`plugins/plugin-manager/`）与 devkit 插件的清单都按上面的规矩写：peer 里只有内核包；插件管理的服务只表示「插件管理装了」，上面没有方法。还差三处：

- **devkit 与插件管理等内核包 0.5.0 发版**：两个包的接口类型改从内核包的包根 `import type`，peer 写 `^0.5.0`。0.5.0 发到源上、仓根 `pnpm install` 装上之前，包根还不导出这些类型，类型检查与发版前检查都过不了
- **模板注册命令还包着 `ctx.effect`**：命令总线 0.4.6 起随调用方卸载自动注销命令，模板对命令总线的 dev 下限已是 0.5.0，这层包装可以删，还没删
- **模板的窗格入口还手写外壳的类型**：外壳在工作区里已经导出窗格入口用到的类型，还没发正式版。外壳发版后，模板的 `src/client/index.tsx` 改成从外壳 `import type`、把外壳的下限升上去
