# 卸载清理

**本页回答**：插件卸载时要清理哪些东西、promise 返回到哪里、状态该放在哪；哪几种情况允许不清理，例外要怎么写明。

## 规则

**插件自己启动的进程、定时器、监听，以及还没完成的写盘和网络请求，卸载时都要清理掉，并返回 promise。**

## 怎么判

- **返回到哪里**：从 `ctx.effect` 的清理函数里返回 promise；继承了 `Service` 的，由它的清理方法返回。注册类接口返回的注销函数也包进 `ctx.effect`（服务继承了 `Service` 的除外，见[cordis 服务怎么提供和使用](/docs/rules/services)）。用 `.catch(() => {})` 把 promise 吞掉、或者 `void` 掉不返回，都算没有返回
- **清理什么**：子进程要结束整棵进程树、等它真正退出；定时器清掉；还没完成的写盘要写完再 resolve，不是丢掉待写的数据；进行中的网络请求要能中止；`server.close()` 要等它真正关闭
- **状态放哪**：每次重新加载都该清掉的状态放在 `apply` 里；模块顶层的状态在同一版本重新加载时不会重置，只放真正需要跨越重新加载保留的东西。数据写盘通过数据插件，配置通过设置插件，home 下的路径只从 `gwbKernel.dataDir` 取

一个会启动子进程的插件，卸载清理大致是这样：

```ts
export function apply(ctx: GwbContext): void {
  const running = new Set<ChildProcess>()          // 运行中的子进程，退出时从表里删掉
  // …启动子进程时 running.add(child)，child.on('exit', () => running.delete(child))

  ctx.effect(() => () =>
    // 返回 promise：对每个子进程结束整棵进程树，全部真正退出才 resolve
    Promise.all([...running].map((child) => killTreeAndWait(child))),
  )
}
```

有写盘队列的插件，清理函数返回「待写的数据写完」的 promise，而不是清掉等待写盘的定时器——清掉定时器等于丢掉这次写盘。

只需要断开引用、没有异步工作的清理，返回一个普通函数就够了。插件管理登记说明书时，清理函数就是登记返回的注销函数：

## 例外

例外都要在代码里写明理由：

- **有意比宿主（内核）活得更久的进程**（测试 home、外部编辑器）：以 detached 启动并 `unref`，插件下次加载时（包括工作台重启之后）能找到它、重新接管
- **插件对自己发起的重新加载**：这个任务天然在自己卸载之后继续运行，只允许持有 loader 的条目树与事先拿到的 logger
- **位置由外部固定的文件**（`runtime.json` 里 MCP 入口那一项、`~/.npmrc`）和用户指定的数据根目录（论文库这类）：不经过数据插件
- **中途结束会让共享的磁盘状态只改了一半的子进程**：卸载时让它运行完，不结束。插件管理的 pnpm 就是这一类：

## 谁来查

没有工具检查，只靠写插件的人自己守：清理漏了、promise 没返回，加载与发版都照样成功，现象是卸载或退出之后进程、定时器还在，或者写了一半的数据丢了。

## 为什么

内核退出时只等插件返回的 promise，超过 5 秒就强制退出；没返回 promise 的清理，内核不会等它，写了一半的数据就丢在那里。数据写盘做成插件、不进内核，所以每个插件自己负责把自己的写盘在卸载前写完。
