# 依赖怎么写

**本页回答**：插件 `package.json` 里每个依赖该写进 peer、dev、`dependencies` 还是不写；构建产物里允许留下哪些包名 import；谁来查。

## 规则

**peer 只写运行时从 home 里得到的三类包：插件在构建产物里按值 import 的 `cordis`、声明兼容哪些内核的内核包 `@godcreator/gwb-kernel-desktop`、用到的别的插件；其余一律写 dev。** 按值 import 指 import 的是运行时的值，不只是类型。内核包每个插件包都写（见[兼容哪个内核](/docs/rules/kernel-compat)），`cordis` 只在按值 import 时写，别的插件在经 `ctx.inject` 用它的服务、或 import 它的类型时写（见[用到的插件写 peer](/docs/rules/plugin-peers)）。peer 里的包，pnpm 会装进插件的 `node_modules`，类型从那里取，不另写 dev：内核给插件的接口类型（`GwbContext`、`GwbKernelApi`、`GwbResult` 等）从内核包的包根 `import type`，别的插件的类型从那个插件 `import type`。

构建产物里剩下的包名 import（直接写包名、不带相对路径的 import，比如 `from 'cordis'`）只能是：

- node 侧代码：node 内置模块、`electron` 与 peer 里写了的包（也就是 `cordis`、内核包、用到的插件，都是 home 里装着、按包名解析得到的）
- 浏览器侧代码：页面 importmap 里的名字，也就是内核包页面入口 `dist/index.html` 里写死的 react 四个包名（见[页面代码与 importmap](/docs/rules/importmap)）

判据只看构建产物，构建产物里多出一个别的包名 import 就是违反。模板的 `build.ts` 用 esbuild 把两侧各打成一个文件，外置名单就是上面两份，其余依赖全部打包进去，照模板构建就不会违反。

## 按运行时由谁提供来决定

| 运行时由谁提供 | 写法 |
| --- | --- |
| 宿主提供、插件按值 import（`extends Service` 这类） | peer `cordis`，dev 里也写一份给本地构建和类型检查 |
| 内核（运行时不 import；声明兼容哪些内核，接口类型只 `import type`） | peer `@godcreator/gwb-kernel-desktop`，范围 `^<验证时的内核版本号>` |
| 运行环境自带（node 内置模块、`electron`） | 不声明 |
| 页面通过 importmap 提供（react 的四个包名，由内核包提供） | dev；浏览器侧代码构建时外置 |
| 另一个插件（经 `ctx.inject` 用它的服务、import 它的类型） | peer，范围 `^x.y.z`；只在 `ctx.inject([...], fn)` 里用的在 `peerDependenciesMeta` 标 `optional: true`（见[用到的插件写 peer](/docs/rules/plugin-peers)）。只按命令名调它的命令的不写 |
| 本插件运行时自己用的库、接口定义包 | dev；打包进构建产物，产物里不留它的包名 import |
| 构建时才用到的输入（样式映射文件、tailwind 之类） | dev |
| 打包不进构建产物的自用库（原生可执行文件、运行时按路径读自己文件的包） | `dependencies`，原因写进文档站 |
| 外部程序、python 环境 | 不声明；用的时候检测它在不在 |

「按值 import」和「只 import 类型」的区别，看编译后留不留下东西：

```ts
// 按值 import：Service 是一个类，运行时要用到它，构建产物里原样留下这一句——写 peer cordis
import { Service } from 'cordis'
export default class MyPlugin extends Service { /* … */ }

// 只 import 类型：编译后整句消失，构建产物里没有 cordis——不写 peer，cordis 写 dev
import type { Context } from 'cordis'
export function apply(ctx: Context) {
  ctx.gwbCommands!.register(/* … */)   // ctx 是 cordis 交给插件的，不用 import
}
```

**peer `cordis` 的意思是「运行时要从 home 里解析到这个包」**，所以只看构建产物里有没有这个包名 import。d.ts 里有 `declare module 'cordis'` 也不写 peer：那只是类型，用这些类型的一方自己在 dev 里列 `cordis`。插件照样依赖 cordis 的协议，但这份兼容性不靠 peer `cordis` 表达：宿主换 cordis 大版本是内核的破坏性版本，内核升 x，所有插件都要在新内核上重新验过、改写 peer 里内核包的范围（见[兼容哪个内核](/docs/rules/kernel-compat)）。

cordis 靠协议键在多份拷贝之间工作，插件自带一份也照样 provide、inject、跟着依赖重新加载；只有跨拷贝的 `instanceof` 为 false，所以代码里不写 `instanceof Service`。

**`files` 白名单列全**：少一项，装包那一刻就少东西。`devkit.dev` 与 `devkit.release` 都照 `files` 查产物在不在。

类型检查平时开着 `skipLibCheck`。上游 d.ts 里又引用到、本插件没列的包，类型会不报错地变成 any；改了依赖之后想核对，在包目录运行一次 `tsc --noEmit -p tsconfig.json --skipLibCheck false`，缺哪个包它会写出包名，写进 dev（peer 里有的不用再写）。

## 谁来查

- **`devkit.release` 的发版前检查**（插件包）：peer 里 `cordis`、内核包与插件以外的包拒；node 侧产物的包名 import 不在「node 内置模块、`electron`、peer」里拒；浏览器侧产物的包名 import 不在页面 importmap 里拒；相对 import 指向的文件不在拒；`files` 白名单里的产物不在拒。dev 依赖不查，写了源上没有的版本，仓根 `pnpm install` 当场失败。细节见[发正式版](/docs/devkit/release)
- **只靠人守**：用到的插件写没写进 peer（插件只用了类型、产物里没留下它的包名时，发版前检查看不出来）

## 为什么

- cordis 靠 `Symbol.for` 协议键在多份拷贝之间工作，插件自带一份也好、home 里另有一份也好，只有跨拷贝的 `instanceof` 为 false。实测记录在内核仓 `probes/2609231600_cordis-multi-copy/`
- 只写 dev 时，类型引用到的包靠 pnpm 默认的提升来解析，少列一个就悄悄变成 any，关掉 `skipLibCheck` 才报出来。实测记录在内核仓 `probes/2609231600_types-without-peer/`
- 删掉的几条（源码不指回别的仓、留着 `prepublishOnly`、清单不写 `//` 键、相对 import 带 `.js`、只写 `import type`、`cordis` 不写进 `dependencies`）的理由见轨迹卡[写插件的规矩只留有工具查的](/trajectory/2026-09-25-rules-only-checked-ones)
- peer 的意思是「运行时从 home 里得到这个包」，所以只给 home 里装着的 `cordis`、内核包与插件用；库、接口定义包不在 home 里按包名解析，写 dev 或 `dependencies`。pnpm 对不满足的 peer 只警告，插件管理的 `list` 把它报出来，取舍见轨迹卡[插件之间的运行时要求写 peer](/trajectory/2026-09-24-plugins-peer-each-other)
