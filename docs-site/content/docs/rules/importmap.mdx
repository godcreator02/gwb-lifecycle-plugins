页面里的裸名 import 由 importmap 解析。kernel 提供机制，shell 提供 React，其他插件可以提供自己的运行时。
使用方必须明确依赖提供方，不能把一个名字外置之后期待页面碰巧装了它。

## 使用现有提供方

React 的四个名字由 shell 提供：`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`。
使用方把 shell 写进 peer，从其代码出口取外置名单：

```ts
import { browserImports } from '@godcreator/gwb-shell/browser-imports'

// esbuild 的浏览器侧配置
external: Object.keys(browserImports())
```

模板采用这份代码。React 仍是插件本地开发依赖，供类型检查和构建工具使用；浏览器产物不再打入另一份 React。
没有提供方承诺的依赖打包进自己的产物。使用另一个提供方时，peer 也写上它，从它的出口取名单。

## 提供模块

包的 `exports["./browser-imports"]` 指向一个纯 ESM 模块，导出同步、无副作用的 `browserImports()`：

```ts
export function browserImports() {
  return { 'example/runtime': new URL('./runtime.js', import.meta.url).href }
}
```

这是普通代码出口，不是插件主入口。它只计算映射，不能初始化服务、读取当前 home 或要求 Electron 环境。
出口和运行时文件都必须进入 `files` 发布白名单。插件主进程复用它：

```ts
ctx.effect(() => ctx.gwbKernel.registerImports(browserImports()))
```

只接受精确裸名和本地 `.js` / `.mjs` 文件 URL。同名同地址可以复用，不同地址冲突会拒绝整个登记。
没有 `gwb.shared` 字段、额外 JSON 或 home 扫描。

## 加载顺序与生命周期

提供方先登记，调用方再执行 `await window.gwb.prepareImports(required?)`，之后才动态 import。
kernel 加载 shell、shell 加载窗格已经执行这一步。调用方通过 cordis 注入保证依赖先就绪；
`required` 中有名字未登记会直接报错，准备函数不等待未来插件。

新名字可以在下一次准备时追加。主进程撤销登记不会卸载页面模块；已注入的地址变更或撤销时需要整页重载。
提供方发新版本后刷新页面，kernel 更新后重启 home。

## 发版检查

devkit 只求值被发布包自身与直接 peer 的 `./browser-imports` 出口，不加载插件主入口。
它核对导出函数、同步映射、本地 URL、目标位于提供方包内、文件存在且被 `files` 包含，并拒绝同名不同地址。
浏览器产物与自身提供的运行时模块沿相对 import 检查；裸名必须在合并后的名单里。

没有任何提供方代码出口的旧项目继续使用旧 kernel HTML 的静态 importmap 检查。这是 devkit 的兼容路径；
新 kernel 不提供静态表，迁移到新 kernel 的插件必须改用代码出口。历史 `gwb.shared` 机制不恢复。
