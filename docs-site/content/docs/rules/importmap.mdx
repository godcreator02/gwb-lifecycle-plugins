# 页面代码与 importmap

**本页回答**：插件的浏览器侧代码里哪些包由页面的 importmap 提供、哪些要自己打包；importmap 里的名字由谁声明；外置名单从哪来。

## 规则

**页面 importmap 里只有内核包 `@godcreator/gwb-kernel-desktop` 在自己清单的 `gwb.shared` 里声明的名字**，现在就是 react 的四个包名（`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`）。别的包——插件也好、库也好——都不写 `gwb.shared`：内核只读内核包自己的清单，别的包写了它不收；`devkit.release` 的发版前检查见到内核包以外的包写了 `gwb.shared` 就拒。

## 怎么判

同一个模块在页面上出现两份就会出错（全局单例、hooks、跨组件树的 context 这类），才该由页面统一提供。只是体积大、或者好几个插件都用，不算，各自打包进构建产物——页面从本机 `file://` 加载，重复几百 KB 可以接受。现在满足这条的只有 react，它由内核包打包并声明。

浏览器侧代码照这几条写：

- **react 的四个包名外置**：构建时不打包，运行时由页面 importmap 解析
- **其余依赖一律打包进构建产物**，包括别的插件发布的接口定义包、块笔记的解析库这类体积大的库。外置成包名而 importmap 里没有这个名字，运行时就是「Failed to resolve module specifier」
- **外置名单只从内核包的清单读**：外置名单是构建时不打包、留给 importmap 提供的包名清单。插件 peer 里写了内核包，pnpm 把它装进插件的 `node_modules`，构建脚本从那里读出 `gwb.shared` 的键，不手抄
- **react 升大版本就是内核包升 x**
- **插件之间共享 React context**，只能靠 react 自己（全页一份）或者通过 props 传；各插件自带的库里的 context 在插件之间不通

用到 react 的插件，把那几个包写进 dev（见[依赖怎么写](/docs/rules/deps)）：构建时外置，运行时由页面解析。

## 发版前怎么查

`devkit.release` 对浏览器侧产物（`dist/client.js` 顺着相对 import 走到的文件）里的每个包名 import，拿内核包清单 `gwb.shared` 的键比对，清单从包目录的 `node_modules` 现读，读不到就拒并提示 peer 写上内核包、再 `pnpm install`；内核包以外的包，不论是插件还是库，清单里写了 `gwb.shared` 就拒（细节见[发正式版的检查](/docs/devkit#发正式版的检查)）：

## 为什么

importmap 是页面级的运行时服务，由内核在页面加载时写入。react 是全生态每个带界面的插件都用的运行时，和 cordis 一样由宿主给：升 react 就是升内核，不用再约定「谁来提供 react」。只收内核包一家，内核就不用扫描 home 里各包的清单、处理同名冲突，也不要求库装成 home 的直接依赖；别的共享代码各自打包，页面上多几份只多占体积、不影响正确性。拦截放在发版前检查上，写错的人发版那一刻就知道。决定的经过见轨迹卡[importmap 只收内核包的名字](/trajectory/2026-09-24-importmap-kernel-only-check)。
