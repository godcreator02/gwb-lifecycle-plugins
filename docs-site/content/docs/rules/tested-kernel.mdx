# 在哪个内核上测过

**本页回答**：插件怎么声明自己在哪个内核版本上测过；「同一条版本线」怎么算；谁在什么时候查这个字段；内核升级之后插件要做什么。

## 规则

**插件包在 `package.json` 的 `gwb` 字段里写 `testedKernel`：它在哪个内核版本上验过。** 这个版本要和运行中的内核在同一条版本线上，插件才发得出去。只查插件包（`keywords` 里有 `gwb-plugin`），库和工具包不写。

## 同一条版本线

主版本号为 0 时比前两位，主版本号 ≥1 时只比主版本号。`0.2.7` 和 `0.2.9` 在同一条线上，和 `0.3.0` 不在；`1.4.0` 和 `1.9.2` 在同一条线上。

{/* ref file="../plugins/devkit/src/tested-kernel.ts" lines="7-21" */}

这和内核的版本号规矩对得上：内核改了接缝上已有的东西——包括升级 loader、include 的版本、改 home 的布局——就升 x，版本线跟着变，所有插件都要在新内核上重新验过。只加东西的内核版本升 y，版本线不变，插件的声明照样有效。

## 谁在查

**`devkit.release` 发版前检查**：对每个要发的插件包，没写、写的不是合法版本号、和运行中的内核不在同一条版本线上，三种都拒，一个包都不发。「运行中的内核」是调 `devkit.release` 的那个 home 里的内核：

{/* ref file="../plugins/devkit/src/release.ts" lines="180-194" */}

**`plugin-manager.list` 按包报**：`testedKernel` 是包清单里声明的版本（没写时没有这个字段），`kernelUntested` 在声明的版本和运行中的内核不在同一条版本线上、没声明或声明的不是合法版本号时为 true。它只报告，不阻止加载（为什么只报告、回执怎么读，见插件管理那组页面里的[同名一页](/docs/plugin-manager/kernel-compat)）：

比对规则在 devkit 与插件管理两边各存一份，不跨包 import（见[插件之间怎么交互](/docs/rules/interaction)）；改规则时两份一起改。

## 内核升级之后

1. `plugin-manager.list` 里 `kernelUntested: true` 的就是还没在新内核上验过的插件
2. 在隔离 home 里用 `devkit.dev` 验一遍（隔离 home 用的是装好的那个内核）
3. 验过了，把 `gwb.testedKernel` 改成新内核的版本号，按补丁升自己的版本号，再 `devkit.release`

没验就改这个字段，等于撒谎：它是「在这个内核上验过」的声明，不是「兼容这个内核」的愿望。

## 新插件的初始值

`devkit.scaffold` 与 `devkit.scaffold.plugin` 生成的 `package.json` 把 `gwb.testedKernel` 写成运行这条命令的那个 home 的内核版本号（模板占位符 `{{testedKernel}}`）：新插件在同一台机器的隔离 home 里验证，用的就是这个内核。换到别的内核上验过之后再改这个值：

## 为什么

插件管理这类插件依赖 loader 条目树之类内核没写进文档的结构，内核一改就可能把它弄坏；与其让内核维护一份下游名单、改动时逐个通知，不如每个插件自己声明测过的内核版本，由插件管理报告、由发版前检查拦下没在当前内核上验过的发版。
