# 用到的插件写 peer

**本页回答**：插件用到别的插件时依赖怎么写；什么算「用到」、什么时候标可选；发版时、在 home 里各由谁查；为什么 pnpm 要关掉自动补装 peer。

## 规则

**插件用到别的插件——经 `ctx.inject` 用它的服务，或 import 它的类型——就把它写进 `peerDependencies`，范围写 `^x.y.z`，下限是开发、验证时用的那一版。** 只是可选使用的（`ctx.inject([...], fn)` 局部注入、缺了只少一部分功能），在 `peerDependenciesMeta` 里标 `optional: true`。写进 peer 的插件不再另写 dev：插件仓里 pnpm 把 peer 装进 `node_modules`，类型从那里取。

peer 的意思是「运行时从 home 里得到这个包」。插件的 peer 因此只有三类：按值 import 的 `cordis`、内核包 `@godcreator/gwb-kernel-desktop`（见[兼容哪个内核](/docs/rules/kernel-compat)）、用到的别的插件。库、接口定义包、构建工具不是 home 里的插件，照[依赖怎么写](/docs/rules/deps)写 dev 或 `dependencies`。

## 怎么判

- **该写，必需**：`export const inject` 里写了它的服务（缺了插件就不加载），或者经命令总线登记命令、用外壳注册窗格与样式令牌这类少了就没法工作的；按值 import 它主入口导出的函数也是（发版前检查只放行 node 侧对 peer 里写了的包的 import，这种用法本身是例外，见[插件之间怎么交互](/docs/rules/interaction)）
- **该写，可选**：用 `ctx.inject([...], fn)` 局部注入它的服务，缺了只少那一部分功能——标 `optional: true`，没装不算没满足
- **不用写**：只按命令名调它的命令（经命令总线查找，命令不在就回执说明），不用它的服务也不 import 它的类型
- **下限写开发、验证时用的那一版**：用到了那个插件某个版本新加的东西（比如外壳新加的主题令牌），下限就写到那一版
- **范围只写 `^x.y.z`**：精确号、`>=`、`~` 都不认，发版前检查拒，`plugin-manager.list` 算没满足

## 谁在查

**`devkit.release` 发版前检查**（只查插件包，`keywords` 含 `gwb-plugin`）：peer 里 `cordis` 与内核包以外的每个包，读包目录 `node_modules` 里它的清单，`keywords` 含 `gwb-plugin` 或同时含 `cordis` 与 `plugin`（cordis 官方插件）才算插件，不是插件、清单读不到都拒；peer 里的每个 gwb 插件（清单 `keywords` 含 `gwb-plugin`，不分包名范围；内核包、`workspace:` 与 cordis 官方插件除外）范围要是 `^x.y.z`，并且和源上 `dist-tags.latest` 在同一条线（问哪个源由用户级 `~/.npmrc` 的范围行决定）——主版本号为 0 时只比次版本号，≥1 时只比主版本号。不在同一条线说明上游出了破坏性版本，拒绝理由里写着适配、验过之后改成的 `^<latest>`：

**`plugin-manager.list` 按包报 `unmetPeers`**：只看插件 peer 里内核包与 `cordis` 以外的包，每条没满足的是 `{ pkg, range, installed? }`——没装（没有 `installed`；optional 的没装不算）、装着的版本不在范围里、或范围不是 `^x.y.z`。只报告，不拦加载、不拦安装（回执怎么读见插件管理那组页面里的[peer 满没满足](/docs/plugin-manager/peers)）。

**`plugin-manager.update` 一起重新加载**：升级了某个包，home 里 peer 写了它的插件被 pnpm 装进新目录，插件管理比装之前与装之后的真实目录发现它，在同一条命令里重新加载，回执 `dependents` 列出来（见[热升级](/docs/plugin-manager/upgrade#真实目录变了的包一起重新加载)）。

## pnpm 不自动补装缺的 peer

pnpm 默认把 home 里没装的 peer 自动装进 `node_modules/.pnpm`：它不写进 home 的 `package.json`、没有条目，插件管理也不认它，只是写 peer 的插件能 import 到它。devkit 与插件管理在 home 里启动 pnpm 时一律带环境变量 `pnpm_config_auto_install_peers=false`；插件仓里不关，仓里开发正是靠自动补装把 peer 里的内核包与插件装进 `node_modules`、拿到类型的；命令行参数 `--config.auto-install-peers=false` 会被 pnpm 忽略，只有环境变量或 home 的 `pnpm-workspace.yaml` 里的 `autoInstallPeers: false` 关得掉。缺了的 peer 由人装，`list` 的 `unmetPeers` 把它报出来。

装进一个外壳还是 0.12.4 的 home，`plugin-manager.list` 里 devkit 这个包带着：

```json
{
  "unmetPeers": [{ "pkg": "@godcreator/gwb-shell", "range": "^0.13.7", "installed": "0.12.4" }]
}
```

处理办法是升级那个插件：`plugin-manager.update {"only":["@godcreator/gwb-shell"]}`。

## 为什么

peer 是 npm 标准的「运行时由宿主提供」的写法，插件的 peer 里写内核包就是这个意思，别的插件和插件之间是同一种关系。pnpm 在 home 里装 peer 有两处要处理：被 peer 的包一升级，写 peer 的插件被装进新目录，所以热升级要把它一起重新加载；缺的 peer 默认被自动补装，所以要关掉。取舍与实验记录见轨迹卡[插件之间的运行时要求写 peer](/trajectory/2026-09-24-plugins-peer-each-other)。
