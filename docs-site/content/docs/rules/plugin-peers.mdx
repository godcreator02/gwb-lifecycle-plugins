# 用到的插件写 peer

**本页回答**：插件用到别的插件时依赖怎么写；什么算「用到」、什么时候标可选；发版时、在 home 里各由谁查；为什么 pnpm 要关掉自动补装 peer。

## 规则

**插件用到别的插件——经 `ctx.inject` 用它的服务，或 import 它的类型——就把它写进 `peerDependencies`，范围写 `^x.y.z`，下限是开发、验证时用的那一版。** 标不标可选照代码写：写在 `export const inject` 里的是普通 peer，只在 `ctx.inject([...], fn)` 里用的在 `peerDependenciesMeta` 里标 `optional: true`（例外见下面「怎么判」的第一条）。写进 peer 的插件不另写 dev：插件仓里 pnpm 把 peer 装进 `node_modules`，类型从那里取。

可选 peer 的意思是「home 里可以没有它；有的话版本要在范围里」。它和不写 peer 不一样：不写的话，装着的版本出了范围没人报，发版时也不和源上 latest 比，开发时还得另写 dev 才拿得到类型。

peer 的意思是「运行时从 home 里得到这个包」。插件的 peer 因此只有三类：按值 import 的 `cordis`、内核包 `@godcreator/gwb-kernel-desktop`（见[兼容哪个内核](/docs/rules/kernel-compat)）、用到的别的插件。别的插件包括第三方 cordis 插件（如提供 `timer` 服务的 `@cordisjs/plugin-timer`）：它和 gwb 插件一样装进 home、在 `cordis.yml` 里有条目。库、接口定义包、构建工具不是 home 里的插件，照[依赖怎么写](/docs/rules/deps)写 dev 或 `dependencies`。

## 怎么判

- **该写，必需**：`export const inject` 里写了它的服务（缺了插件就不加载）；只在 `ctx.inject([...], fn)` 里用、但缺了它本插件一样功能都没有的也算（插件管理的命令都登记在命令总线上，它经 `ctx.inject` 取命令总线，只为缺了命令总线时插件管理照样加载）；按值 import 它主入口导出的函数也是（发版前检查只放行 node 侧对 peer 里写了的包的 import，这种用法本身是例外，见[插件之间怎么交互](/docs/rules/interaction)）
- **该写，可选**：只在 `ctx.inject([...], fn)` 里用它的服务，缺了只少那一部分功能——标 `optional: true`，没装不算没满足
- **别标反**：`export const inject` 里的服务标成可选，home 里缺它时插件不加载，`unmetPeers` 也不报；`devkit.release` 发版前拒这种写法（见下面「谁在查」）
- **写 peer 会成环的不写**：局部注入、提供方是同一个工作区里的插件、它自己 peer 或 dev 写了本包时，本包再写它就成了包依赖环，pnpm 12 的 `pnpm -r` 遇环直接退出。命令总线对说明书插件就是这样
- **peer 不成环**：顺着 peer 里的 gwb 插件一路走回本包，`devkit.release` 拒；插件管理升级时按 peer 排重新加载的先后，环上的包排不出先后，只能重启工作台才换上新版本。两个插件互相要用时，一个方向写 peer，反方向按上一条改用局部注入、不写 peer；不在同一个工作区的，局部注入也要写可选 peer、照样成环，反方向改成由被写 peer 的一方提供扩展点、另一方往里注册：A 的 peer 写了 B、B 又要用 A 的能力，就让 B 提供扩展点，A 把这项能力注册进去
- **插件之间不按命令名互相调用**（见[cordis 服务怎么提供和使用](/docs/rules/services#服务还是命令)），所以没有「只调它的命令、不写 peer」这种用法；源码里按命令名调别的插件命令的，改成注入它的服务时补上 peer
- **下限写开发、验证时用的那一版**：用到了那个插件某个版本新加的东西（比如外壳新加的主题令牌），下限就写到那一版
- **范围只写 `^x.y.z`**：精确号、`>=`、`~` 都不认，发版前检查拒，`plugin-manager.list` 算没满足

## 谁在查

**`devkit.release` 发版前检查**（只查插件包，`keywords` 含 `gwb-plugin`）：peer 里 `cordis` 与内核包以外的每个包，读包目录 `node_modules` 里它的清单，`keywords` 含 `gwb-plugin`（gwb 插件）或同时含 `cordis` 与 `plugin`（第三方 cordis 插件，cordis 官方插件都这么写）才算插件，不是插件、清单读不到都拒；peer 里的每个插件（不分包名范围；内核包、`workspace:` 除外）范围要是 `^x.y.z`，并且和源上 `dist-tags.latest` 在同一条线（问哪个源由用户级 `~/.npmrc` 的范围行决定）——主版本号为 0 时只比次版本号，≥1 时只比主版本号。不在同一条线说明上游出了破坏性版本，拒绝理由里写着适配、验过之后改成的 `^<latest>`：

同一道检查还扫插件包源码里注入的服务，找出提供方：必需注入的提供方要写在 peer 里、不标 `optional`，局部注入的提供方要写在 peer 里（标不标 `optional` 都放行）。怎么扫、提供方怎么判、哪些放行，见下面「源码注入由谁查」。

**`plugin-manager.list` 按包报 `unmetPeers`**：只看插件 peer 里内核包与 `cordis` 以外的包，每条没满足的是 `{ pkg, range, installed? }`——没装（没有 `installed`；optional 的没装不算）、装着的版本不在范围里、或范围不是 `^x.y.z`。只报告，不拦加载、不拦安装（回执怎么读见插件管理那组页面里的[peer 满没满足](/docs/plugin-manager/peers)）。

**`plugin-manager.update` 一起重新加载**：升级了某个包，home 里 peer 写了它的插件被 pnpm 装进新目录，插件管理比装之前与装之后的真实目录发现它，在同一条命令里重新加载，回执 `dependents` 列出来（见[热升级](/docs/plugin-manager/upgrade#真实目录变了的包一起重新加载)）。

## 源码注入由谁查

`devkit.release` 的发版前检查，只查插件包（`keywords` 含 `gwb-plugin`），和别的插件包检查一起列在回执里。它扫包的 `src/` 下的源码（`.d.ts` 除外），每个注入的服务找出提供方，看 peer 写得对不对：

- **必需注入**（`export const inject = [...]`、`static inject = [...]`）的提供方写在 peer 里，不标 `optional`
- **局部注入**（`<上下文>.inject([...], fn)`）的提供方写在 peer 里。标 `optional` 是常规写法；缺了它本插件一样功能都没有时写必需（插件管理对命令总线就是这样），两种都放行
- **提供方怎么判**：peer 与 dev 里的插件（gwb 插件或第三方 cordis 插件，判法同上），读包目录 `node_modules` 里它的类型入口（`exports["."]` 的 `types`），看 `declare module 'cordis' { interface Context { … } }` 补了哪些名字。只读这一个文件，不顺着 `export type … from` 往下找，所以提供方要把这段声明写在包入口的源文件里。几个插件都补了同一个名字（外壳为了 pnpm 的目录布局把 `gwbCommands`、`gwbData` 按真类型再声明一遍），只认运行时代码里 `super(<上下文>, '<名>')` 或 `.provide('<名>')` 提供它的那个；还是判不出就拒
- **不查的**：`gwbKernel`（内核接口，用 `requireKernel` 取）；本包自己提供的服务。给 `Context` 补了名字、但不是插件的包（只有类型的包）不算提供方
- **不写 peer 也放行的只有一种**：局部注入、提供方是同一个工作区里的插件、它自己 peer 或 dev 写了本包——本包再写它就成了包依赖环，pnpm 12 的 `pnpm -r` 遇环直接退出。命令总线对说明书插件就是这样。这条按规则判出来，包清单里不另写例外

扫描先去掉注释、字符串与模板字面量的内容、正则字面量，再找 `inject` 这个标识符：

| 写法 | 算什么 |
| --- | --- |
| `export const inject = ['<名>', …]`（可带类型标注、`as const`） | 必需注入 |
| `static inject = ['<名>', …]` | 必需注入 |
| `<上下文>.inject(['<名>', …], fn)`，可带类型参数 `inject<…>(…)` | 局部注入 |
| 上面三种、但参数不是只由字符串字面量组成的数组（变量、对象形式 `{ required: […] }`、展开 `...more`）；叫 `inject` 的变量；对象字面量里值是数组的 `inject:` 键（`ctx.plugin({ inject: [...] })`）；不经 `.` 直接调用 `inject([...])` | **认不出，拒**，报出文件、行号与那一行，改写成上面三种 |
| 属性读取（`plugin.inject ?? []`）、类型里的 `inject` 成员与方法声明 | 不是注入，不管 |

提供只认服务名是字符串字面量的 `super(<上下文>, '<名>')` 与 `.provide('<名>')`：名字不是字面量的不算、也不报，因为 `super` 与 `provide` 都是常见的名字（继承 `Error` 的 `super(message)`、别的库的 `provide` 方法）。

扫不准的就拒、让人改写成扫得准的写法，不做模糊匹配。命令名不在这里查：源码里命令名有字面量、常量、模板串、条件登记四种形态，扫出来的数和运行时对不上（见轨迹卡[能力地图挪到运行时](/trajectory/2026-09-18-capability-map-moves-to-runtime)）。

## pnpm 不自动补装缺的 peer

pnpm 默认把 home 里没装的 peer 自动装进 `node_modules/.pnpm`：它不写进 home 的 `package.json`、没有条目，插件管理也不认它，只是写 peer 的插件能 import 到它。devkit 与插件管理在 home 里启动 pnpm 时一律带环境变量 `pnpm_config_auto_install_peers=false`；插件仓里不关，仓里开发正是靠自动补装把 peer 里的内核包与插件装进 `node_modules`、拿到类型的；命令行参数 `--config.auto-install-peers=false` 会被 pnpm 忽略，只有环境变量或 home 的 `pnpm-workspace.yaml` 里的 `autoInstallPeers: false` 关得掉。缺了的 peer 由人装，`list` 的 `unmetPeers` 把它报出来。

```json
{
  "unmetPeers": [{ "pkg": "@godcreator/gwb-shell", "range": "^0.15.0", "installed": "0.14.3" }]

```

处理办法是升级那个插件：`plugin-manager.update {"only":["@godcreator/gwb-shell"]}`。

## 为什么

peer 是 npm 标准的「运行时由宿主提供」的写法，插件的 peer 里写内核包就是这个意思，别的插件和插件之间是同一种关系。pnpm 在 home 里装 peer 有两处要处理：被 peer 的包一升级，写 peer 的插件被装进新目录，所以热升级要把它一起重新加载；缺的 peer 默认被自动补装，所以要关掉。取舍与实验记录见轨迹卡[插件之间的运行时要求写 peer](/trajectory/2026-09-24-plugins-peer-each-other)。
