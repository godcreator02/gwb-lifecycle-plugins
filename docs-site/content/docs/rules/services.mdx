# cordis 服务怎么提供和使用

**本页回答**：一项能力该做成服务还是命令；提供服务怎么写、命令怎么包住服务方法；使用服务时 `inject` 的三种写法各在什么时候用；命令怎么登记；取内核接口、写类时容易出错的地方。除了「容易出错的几处」，这一页都是写法建议，没有工具检查。

## 服务还是命令

**插件之间的能力走服务；命令只给进程外的调用方，是服务方法的薄封装。**

- **服务**：别的插件在进程内要用的能力，读写数据、执行动作、扩展点（让别的插件往这里注册窗格、命令、工具）、回调，都做成继承 cordis `Service` 的服务。方法带类型，类型由提供方导出（见[插件之间怎么交互](/docs/rules/interaction#类型放在提供方那边)）；依赖方 inject 它，必需的写进 `inject`，可有可无的用 `ctx.inject([...], …)`
- **命令**：给进程外的调用方用，也就是页面（包括本插件自己的窗格）和经 MCP 来的 agent。处理函数校验参数，然后调同一个服务方法，不另写实现
- **插件之间不按名字调命令**：要用别的插件的能力，就 inject 它的服务。只想跟着提供方一起加载、卸载（比如装了它才注册某个窗格）的，inject 的也是它真正的服务，不另提供一个空对象当标记
- **只有进程外调用方的能力只做命令**：没有别的插件在进程内调用，就不加服务方法；出现第一个进程内调用方时再加
- **调用方要区分的失败写进方法的返回类型**：比如「被别的会话占用」这种调用方要另做处理的情况，返回类型里有它，调用方不靠匹配错误文本认出来
- 一条命令只做一件事，多步流程写进说明书。唯一的例外是判定依赖同一份「这次执行之前」状态的事务

同一能力有服务方法与命令两种调用方式，靠「命令只调服务方法」保持一致：命令里只有参数校验和回执的包装，没有第二份逻辑。方法的用法写在类型的文档注释里，命令的用法写在 `usage` 里。一条命令带一个 `action` 参数做四件事，调用方就看不出它到底能做什么。

## 提供服务

**服务一律继承 cordis 的 `Service` 类。** 服务方法里的 `this.ctx` 是**调用方**插件的上下文，所以服务可以把注销函数登记到调用方的上下文里：调用方卸载时，它注册进来的东西自动撤销，调用方不用自己包 `ctx.effect`；服务也能从调用方身上认出是哪个插件在调用，按调用方的包名放行或记录。

```ts
import { Service } from 'cordis'
import type { Context } from 'cordis'

export default class GwbExample extends Service {
  constructor(ctx: Context) {
    super(ctx, 'gwbExample')          // 注册成名为 gwbExample 的服务
  }
  /** 读写与动作：带类型的方法，命令和别的插件调的都是它 */
  async rename(id: string, title: string): Promise<RenameResult> {
    // …
  }
  /** 扩展点：别的插件往这里注册 */
  register(item: Item): () => void {
    table.add(item)
    const unregister = () => table.delete(item)
    // this.ctx 是调用方的上下文：调用方卸载时，unregister 自动执行
    this.ctx.effect(() => unregister)
    // 返回给调用方，想提前注销时调它
    return unregister
  }
}
```

同一个插件给页面和 agent 登记的命令只校验参数，再调这个方法：

```ts
ctx.gwbCommands.register(
  { name: 'example.rename', description: '…', usage: '{ id: string, title: string }；回执 RenameResult', effect: 'write' },
  async (args) => {
    const { id, title } = renameArgsFrom(args)   // 参数不对就抛错，命令总线转成失败回执
    return { ok: true, data: await ctx.gwbExample.rename(id, title) }
  },
)
```

代价是构建产物里有 `import { Service } from 'cordis'`，要写 peer `cordis`（见[依赖怎么写](/docs/rules/deps)）。不用 `ctx.provide` 提供普通对象：它拿不到调用方的上下文，只能把注销函数还给调用方，调用方忘了包 `ctx.effect`，卸载之后注册的东西还留在表里；也认不出是谁在调用。

服务名用 `gwb` 开头的小驼峰，跟插件名对应。**要让别的插件知道这个服务，就在自己的类型声明里给 cordis 的 `Context` 补上这一项**，服务的类型也定义在自己的声明里，在类型上写文档注释说清怎么用。插件管理就是这样写的：

## 使用服务：三种 inject

使用服务不继承任何类，也不用 import `cordis`，读 `ctx.<服务名>` 就行。没在 inject 里声明就读，cordis 直接抛错。

| 写法 | 什么时候用 |
| --- | --- |
| `export const inject = [...]` | 函数式插件的必需依赖：服务都在了 cordis 才调 `apply`，任何一个重新加载，本插件跟着重新加载 |
| `static inject = [...]` | `Service` 类的必需依赖，含义同上 |
| `ctx.inject([...], (ctx) => { … })` | 可有可无的依赖：那个服务出现时回调运行，消失时回调里注册的东西自动撤销，主插件照常加载 |

用哪一种也决定提供方插件在 peer 里标不标可选：前两种写普通 peer，第三种标 `optional: true`（见[用到的插件写 peer](/docs/rules/plugin-peers)）。

## 登记命令

命令的字段由命令总线在登记时查：`name`、`description`、`usage` 缺一或只有空白就抛错，插件加载失败。`description` 一句话说命令做什么（MCP 入口的 `index` 列它），参数形状写进 `usage`（`search` 列它，命令总线不带参数 schema，agent 知道参数怎么给只能看它），无参数写「无参数」；`plugin` 不写，命令总线从调用方取包名。

**`effect` 必写**，说明调这条命令会动到什么，agent 按它决定能不能直接调：

| 取值 | 什么时候用 |
| --- | --- |
| `read` | 什么都不改，联网只读也算 |
| `write` | 改本机的文件、设置、数据或界面（开窗格、开窗口也算） |
| `external` | 影响本机以外或打扰人：推送、发到远端、发消息、调会把数据发给外部服务的接口、弹窗或系统通知 |

一条命令按参数可能做几种事的，取最重的那种（`external` 重于 `write`，`write` 重于 `read`）。写了这三个以外的值，登记时抛错；命令总线 0.6 起没写也抛错，插件加载失败。经 `gwbNodeCli` 登记的命令行工具同样写 `effect`。模板那条 `<短名>.ping` 只回插件名与时间，写的是 `read`。

## 容易出错的几处

- **`gwbKernel` 用 `requireKernel(ctx)` 取，不写进 `inject`**：内核接口在根上下文上、永不撤销。`requireKernel` 与 `isRecord` 两个无状态小函数由各插件自带一份，内核包的包根只导出类型（插件管理那一份见本节末尾）
- **不写 `instanceof Service`**：插件和宿主用的 cordis 可能是两份拷贝，跨拷贝判断为 false
- **类的私有字段用 TS 的 `private`，不用 `#`**：cordis 派生上下文用 `Object.create(this)`，`#` 私有字段在派生出来的对象上一读就抛错
- **每次重新加载都该清掉的状态放在 `apply` 里**：重新加载只重新运行 `apply`，模块顶层的状态在同一版本重新加载时不会重置
- **配置一律 `gwbSettings.define`**，条目上只写 `id`：写在 `cordis.yml` 条目上的配置界面看不见，agent 也不知道有它

## 谁来查

- **命令总线登记时**：命令的字段，见上一节
- 其余都没有工具检查：「容易出错的几处」写错了，现象写在每一条里；别的是写法建议

## 为什么

插件之间按名字调命令，参数与回执都没有类型：调用方要自己校验回执的形状、靠错误文本认出是哪种失败，提供方没装要到调用时才报错。做成服务，类型检查在调用方那里报出提供方的改动，inject 在加载时就说明提供方在不在。命令照旧留给页面和 agent，它们在进程外、拿不到服务。代价是同一能力有方法与命令两种写法要一起说明，依赖方跟着提供方重新加载。服务统一继承 `Service`，是因为只有这种写法能让服务拿到调用方的上下文：注册的清理跟着调用方走，不靠每个调用方记得包 `ctx.effect`；服务也能按调用方认出是谁在调用。取舍见轨迹卡[服务是本体，命令是薄封装](/trajectory/2026-10-07-services-first)。
