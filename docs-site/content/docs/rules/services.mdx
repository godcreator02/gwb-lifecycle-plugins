# cordis 服务怎么提供和使用

**本页回答**：一项能力该做成服务还是命令；提供服务用哪种写法；使用服务时 `inject` 的三种写法各在什么时候用；命令怎么登记；取内核接口、写类时要避开的坑。

## 服务还是命令

**扩展点用服务，数据读写和动作用命令；同一能力只提供一种调用方式。**

- **服务**用于命令表达不了的东西：注册（让别的插件往这里注册窗格、命令、工具）、回调、需要跟着提供方一起重新加载的生命周期。服务上不放读写数据和执行动作的方法
- **命令**是可序列化的读写和动作。页面、agent、插件都用同一套命令，这是插件对外提供能力的唯一方式；插件内部想要类型安全，就通过提供方发布的类型化客户端来调（放在接口定义包里，见[插件之间怎么交互](/docs/rules/interaction)）
- **存在标记服务**：依赖方需要跟着提供方一起重新加载、但又只用命令时，inject 提供方的一个存在标记服务。它是一个普通对象，只带契约版本号，上面没有方法
- 一条命令只做一件事，多步流程写进说明书。唯一的例外是判定依赖同一份「这次执行之前」状态的事务

同一能力既有服务方法又有命令，两种调用方式会悄悄变得不一致；一条命令带一个 `action` 参数做四件事，调用方就看不出它到底能做什么。

## 提供服务：两种写法

**扩展点服务一律继承 cordis 的 `Service` 类。** 服务方法里的 `this.ctx` 是**调用方**插件的上下文，所以服务可以把注销函数登记到调用方的上下文里：调用方卸载时，它注册进来的东西自动撤销，调用方不用自己包 `ctx.effect`；服务也能从调用方身上认出是哪个插件在注册。

```ts
import { Service } from 'cordis'
import type { Context } from 'cordis'

export default class GwbExample extends Service {
  constructor(ctx: Context) {
    super(ctx, 'gwbExample')          // 注册成名为 gwbExample 的服务
  }
  register(item: Item): () => void {
    table.add(item)
    const unregister = () => table.delete(item)
    // this.ctx 是调用方的上下文：调用方卸载时，unregister 自动执行
    this.ctx.effect(() => unregister)
    // 返回给调用方，想提前注销时调它
    return unregister
  }
}
```

代价是构建产物里有 `import { Service } from 'cordis'`，要写 peer `cordis`（见[依赖怎么写](/docs/rules/deps)）。用 `ctx.provide` 提供普通对象的扩展点服务拿不到调用方的上下文，只能把注销函数还给调用方；调用方忘了包 `ctx.effect`，卸载之后注册的东西还留在表里。

**不需要认出调用方的服务（存在标记服务）用 `ctx.provide`。** 它只是一个普通对象，不用 import `cordis`，也就不写 peer。插件管理就是这样：对外只有命令，服务 `gwbPluginManager` 只表示「插件管理装了」：

## 使用服务：三种 inject

使用服务不继承任何类，也不用 import `cordis`，读 `ctx.<服务名>` 就行。没在 inject 里声明就读，cordis 直接抛错。

| 写法 | 什么时候用 |
| --- | --- |
| `export const inject = [...]` | 函数式插件的必需依赖：服务都在了 cordis 才调 `apply`，任何一个重新加载，本插件跟着重新加载 |
| `static inject = [...]` | `Service` 类的必需依赖，含义同上 |
| `ctx.inject([...], (ctx) => { … })` | 可有可无的依赖：那个服务出现时回调运行，消失时回调里注册的东西自动撤销，主插件照常加载 |

## 登记命令

- `plugin` 字段写包名
- `description` 一句话说命令做什么，MCP 入口的 `index` 列出它
- 参数形状写进 `usage`（`{ entryId, enabled? }`），无参数就写「无参数」。`search` 命中的那一行带 `usage`；命令总线不带参数 schema，agent 知道参数怎么给只能看它
- repo-kit 的插件守卫查 `apply` 登记的每条命令：`plugin` 是包名，`name`、`description`、`usage` 非空。不查命令名的前缀，也不查有几条命令

## 几个坑

- **`gwbKernel` 用 `requireKernel(ctx)` 取，不写进 `inject`**：内核接口在根上下文上、永不撤销。`requireKernel` 与 `isRecord` 两个无状态小函数由各插件自带一份，词汇表包只提供类型（插件管理那一份见本节末尾）
- **不写 `instanceof Service`**：插件和宿主用的 cordis 可能是两份拷贝，跨拷贝判断为 false
- **类的私有字段用 TS 的 `private`，不用 `#`**：cordis 派生上下文用 `Object.create(this)`，`#` 私有字段在派生出来的对象上一读就抛错
- **每次重新加载都该清掉的状态放在 `apply` 里**：重新加载只重跑 `apply`，模块顶层的状态在同一版本重新加载时不会重置
- **配置一律 `gwbSettings.define`**，条目上只写 `id`：写在 `cordis.yml` 条目上的配置界面看不见，agent 也不知道有它

## 为什么

命令表是页面、agent、插件共用的同一份事实来源；再提供一套服务方法，就有了两份并行的来源。服务留给命令表达不了的扩展点和生命周期。扩展点统一继承 `Service`，是因为只有这种写法能让服务拿到调用方的上下文：注册的清理跟着调用方走，不靠每个调用方记得包 `ctx.effect`——没包的插件卸载后，命令名还留在命令表里，2026-09-09 出过这种事。
