**本页回答**：两个插件用的是哪一个 pnpm、怎么找到它、各拿它做什么；在 home 里运行 pnpm 时为什么关掉自动补装 peer；正式版发到哪个源、哪几处指定源、哪几处靠用户的 `~/.npmrc`；开发版与正式版怎么分开；插件管理找插件时读哪两份 npmrc、怎么决定去哪条源检索；第三方包源谁来配。

## 连接的模块

- 插件管理：`plugins/plugin-manager/src/pnpm-location.ts`（找 pnpm）、`src/pnpm.ts`（启动 pnpm）；找插件在 `src/package-sources.ts`、`src/sources.ts`、`src/search.ts`、`src/registry.ts`、`src/home.ts`
- devkit：`plugins/devkit/src/dev.ts`、`src/release.ts`、`src/home.ts`、`src/node-dev-deps.ts`；找 pnpm 用插件管理主入口导出的 `locatePnpm`
- 用户装的 pnpm 12 可执行文件；团队源（gitea 上 `godcreator` 组织的 npm 源）与第三方包源；npmjs、Verdaccio、gitea 都实现的 npm registry 检索接口
- 两份 npmrc：机器级 `~/.npmrc`（agent 照说明书 `gwb-plugin-manager` 往里写第三方包源）与 home 级 `<home>/.npmrc`；插件管理两份都只读，pnpm 安装时读的是同一批配置行

## 接口

**devkit 与插件管理用同一个 pnpm**：每条要运行 pnpm 的命令开头按顺序检查两个位置——`%LOCALAPPDATA%\pnpm\bin\pnpm.exe`（pnpm 12 官方安装脚本的默认位置）、`%APPDATA%\npm\node_modules\pnpm\pnpm.exe`（npm 全局装的 pnpm 包里的原生可执行文件）——用第一个存在的，运行 `--version` 核对是 12.x 并且不低于 12.4.2；不存在、版本不对都报错，不去试另一个位置，不看 PATH。找到的文件直接启动，不经 shell。规则只有一份，写在插件管理的 `src/pnpm-location.ts`，devkit 从插件管理的主入口 import `locatePnpm`（插件管理怎么找、怎么启动见 [pnpm](/docs/plugin-manager/pnpm)）：

**插件管理拿它做什么**：只在 home 里运行 `add`（对齐 `cordis` 那一次带 `--save-exact`）、`remove`、`outdated --json`，不传 `--registry`，源由 npmrc 决定。

**devkit 拿它做什么**：`devkit.home.new`、`devkit.dev`、`devkit.release` 三条命令开头各找一次，找不到就回 `ok: false`、什么都不做。用在六处：

| 命令 | 在哪运行 | 谁调 | 去哪个源 |
| --- | --- | --- | --- |
| `pnpm build` | 被测仓的仓根 | `devkit.dev`、`devkit.release` | 不适用 |
| `pnpm pack --pack-destination <目标 home>\dev-packs` | 临时目录里组装好的发布内容 | `devkit.dev` | 不适用 |
| `pnpm publish --no-git-checks --tag latest` | 临时目录里组装好的发布内容 | `devkit.release` | 发布目标，写在发布内容清单的 `publishConfig.registry`，命令行不带 `--registry` |
| `pnpm view <包@版本> version` | 系统临时目录 | `devkit.release` | 发布目标：带范围的包名带 `--config.<范围>:registry=<发布目标>`，不带范围的带 `--registry` |
| `pnpm view <包> dist-tags.latest` | 系统临时目录 | `devkit.release` | 不指定，按 `~/.npmrc` 的 scope 路由 |
| `pnpm add <内核包、cordis（带 --save-exact）、七个基础插件>` | 新 home | `devkit.home.new` | 不指定 |

`devkit.dev` 不在目标 home 里启动 pnpm：装包是目标 home 的插件管理在它自己的进程里运行的 `pnpm add`（见 [devkit 调插件管理](/docs/seams/plugin-manager-calls)）。

**在 home 里运行的 pnpm 都关掉自动补装 peer**：启动 pnpm 时环境变量原样传下去，加一项 `pnpm_config_auto_install_peers=false`（插件管理另去掉 `ELECTRON_RUN_AS_NODE`）。插件管理的 pnpm 都在 home 里运行；devkit 只在 `home.new` 的三次 `pnpm add` 带它，在插件仓里的 build 与临时目录里的 pack、publish、view 不带——插件仓里开发要靠自动补装把 peer 里的内核包与插件装进 `node_modules`，带上它 pnpm 会按新配置重装、把这些 peer 拿掉，构建时找不到类型。插件的 peer 写了别的插件、home 里没装那个插件时，pnpm 默认把它装进 `node_modules/.pnpm` 且不提示，不写进 home 的 `package.json`、没有条目，插件管理也不认它。命令行参数 `--config.auto-install-peers=false` 会被 pnpm 忽略，只有环境变量或 home 的 `pnpm-workspace.yaml` 关得掉（实验见本仓 `probes/2609242300_peer-between-plugins/`）：

## 约定

devkit 与插件管理都保证：在 home 里启动 pnpm 时带 `pnpm_config_auto_install_peers=false`，在 home 里 `pnpm add` 照 pnpm 默认在清单里写 `^` 范围，只有装 `cordis` 带 `--save-exact`；devkit 在插件仓里启动 pnpm 时不带前者。人在 home 里手工运行 pnpm 时要自己设这个环境变量。

插件管理保证：

- 会写 home 的 pnpm 只在经过 BUSY 检查的命令里运行，同一时刻最多一个；只读的 `pnpm outdated` 不经过 BUSY
- 两份 npmrc 只读不写
- 回执与日志里不带 token
- `search` 不带参数，查全部配好的 scope（`@godcreator` 在前、其余按名字排），各条源并发查，一条失败不影响别的，全都失败才 `ok: false`

devkit 保证：

- 正式版发到包的发布目标（`publishConfig.registry`，没写就拒），打 `latest`；开发版不发到任何源
- 同一个版本号在发布目标上已有就不发
- 发布内容与开发版的包文件都在临时目录里组装，不改仓里的 `package.json`

团队源需要保证的：`dist-tags.latest` 是正式最新版。源地址与 `~/.npmrc` 里 `@godcreator` 那一行一致**靠约定**：`vocab.ts` 的注释写着两者同一个地址，没有代码核对。发版前检查问 peer 里各个插件的 latest 靠 npmrc 按包名范围路由，`@godcreator` 的插件靠那一行，机器上没有它就问不出、发版前检查拒。

插件包需要保证的：`package.json` 的 `keywords` 里写 `gwb-plugin`；库不写。

**改 home 的是同一个 pnpm，但互斥只在插件管理里**：插件管理与 `devkit.home.new` 找到的是同一个文件；插件管理的改动经过它自己的 BUSY 检查，`devkit.dev` 装包也经目标 home 的插件管理，所以同样经过这道检查；`devkit.home.new` 不经过插件管理（那时插件管理还没装、home 还没启动），同时有别的 pnpm 写同一个 home 会丢改动（见[同一时刻只允许一个改动](/docs/plugin-manager/busy)）。

`devkit.release` 不在命令行写 `--registry`，照包清单的 `publishConfig.registry`。

## 不负责的事

- devkit 与插件管理都不安装、不升级 pnpm 本身；要求的 pnpm 版本写在插件管理里，换版本就是发一版插件管理
- devkit 与插件管理都不写 `~/.npmrc` 与 token；第三方包源由 agent 照说明书 `gwb-plugin-manager` 手写
- 插件管理不看环境变量或 pnpm 全局配置里指定的源，只看两份 npmrc
- `devkit.release` 不运行包里的 `scripts`：发布内容来自临时目录，那里没有 `scripts`
