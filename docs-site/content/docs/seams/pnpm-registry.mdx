**本页回答**：两个插件用的是哪一个 pnpm、怎么找到它、各拿它做什么；团队源的地址写在哪、哪几处显式传、哪几处靠用户的 `~/.npmrc`；开发版与正式版怎么分开；依赖对账怎么查源；插件管理找插件、配包源时读写哪两份 npmrc、怎么决定去哪条源检索、读 gitea 插件的哪两项设置。

## 连接的模块

- 插件管理：`plugins/plugin-manager/src/pnpm.ts`、`src/pnpm-path.ts`、`src/pnpm-location.ts`；找插件与配包源在 `src/package-sources.ts`、`src/sources.ts`、`src/search.ts`、`src/registry.ts`、`src/home.ts`
- devkit：`src/pnpm-location.ts`、`src/dev.ts`、`src/release.ts`、`src/home.ts`、`src/node-dev-deps.ts`、`src/node-audit-deps.ts`
- 用户装的 pnpm 12 可执行文件；团队包源（gitea 上 `godcreator` 组织的 npm 源）与第三方包源；npmjs、Verdaccio、gitea 都实现的 npm registry 检索接口
- 两份 npmrc：机器级 `~/.npmrc`（插件管理的 `source.add` / `source.remove` 改它）与 home 级 `<home>/.npmrc`（只读）；pnpm 安装时读的是同一批配置行
- gitea 插件（gitea 插件仓 gwb-gitea）的设置：`gitea` 分区的 `base-url` 与 `token`，经设置插件的命令 `settings.get` 读

## 接口

**两个插件用同一个 pnpm**：每条要运行 pnpm 的命令开头按顺序检查两个位置——`%LOCALAPPDATA%\pnpm\bin\pnpm.exe`（pnpm 12 官方安装脚本的默认位置）、`%APPDATA%\npm\node_modules\pnpm\pnpm.exe`（npm 全局装的 pnpm 包里的原生可执行文件）——第一个存在的作数，运行 `--version` 核对是 12.x 并且不低于 12.4.2；不存在、版本不对都报错，不去试另一个位置，不看 PATH。找到的文件直接启动，不经 shell。规则写在 `src/pnpm-location.ts`，两个插件各存一份、逐字相同，由 devkit 的对照测试保证：

**插件管理拿它做什么**：只在 home 里运行 `add`、`remove`、`outdated --json`，不传 `--registry`，源由用户级 `~/.npmrc` 决定。细节见[插件管理的 pnpm](/docs/plugin-manager/pnpm)。

**devkit 拿它做什么**：`devkit.home.new`、`devkit.dev`、`devkit.release` 三条命令开头各找一次，找不到就回 `ok: false`、什么都不做。用在五处：

| 命令 | 在哪运行 | 谁调 | 带 `--registry` |
| --- | --- | --- | --- |
| `pnpm build` | 被测仓的仓根 | `devkit.dev`、`devkit.release` | 不适用 |
| `pnpm publish --no-git-checks --tag <dev 或 latest>` | 临时目录里组装好的发布内容 | `devkit.dev`、`devkit.release` | 带 |
| `pnpm view <包@版本> version`、`pnpm view <包> dist-tags.latest` | 系统临时目录 | `devkit.dev`、`devkit.release` | 带 |
| `pnpm install` | 目标 home | `devkit.dev` | 不带 |
| `pnpm add <七个基础插件>` | 新 home | `devkit.home.new` | 不带 |

## 约定

插件管理保证：
- 改 home 的 pnpm 都排进同一个串行队列
- `source.add` / `source.remove` 只改机器级 `~/.npmrc`，home 级只读；`@godcreator` 的路由与凭据不改不删
- `source.add` 同一个 scope 已有就原地替换；换源、删源时，旧源的凭据行只在没有别的 scope 还指向它时才删；写完重读一遍，读不到写进去的行就回 `ok: false`
- 回执与日志里不带 token：写进去的行里 token 换成 `***`，`source.list` 只报有没有 token
- home 级有同名 scope 指向别的地址时，`source.add` 的回执 `note` 里提醒 pnpm 用的是 home 级那条
- `search` 不带参数时查全部配好的 scope（`@godcreator` 在前、其余按名字排），各条源并发查，一条失败不影响别的，全都失败才 `ok: false`

devkit 保证：
- 发版只发到 `DEFAULT_REGISTRY`，开发版不动 `latest`
- 同一个版本号在源上已有就不发
- 发布内容在临时目录里组装好，不改仓里的 `package.json`

团队源需要保证的：`@godcreator` 的包能按 packument 格式匿名读取，`dist-tags.latest` 是正式最新版。源地址与 `~/.npmrc` 里 `@godcreator` 那一行一致**靠约定**：`dev.ts` 的注释写着两者同一个地址，没有代码核对。

插件包需要保证的：`package.json` 的 `keywords` 里写 `gwb-plugin`；库、共享包不写。

gitea 插件需要保证的（gitea 插件仓的约定）：条目 id 是 `gitea`，设置名是 `base-url` 与 `token`。

**改 home 的是同一个 pnpm，但不在同一个队列里**：插件管理、`devkit.home.new`、`devkit.dev` 找到的是同一个文件；插件管理的改动排进它自己的串行队列，devkit 的两条命令不经过这个队列。

本仓 AGENTS 写「手工发版别手写 `--registry`，scope 对应的源写在 `~/.npmrc`」；`devkit.dev` 与 `devkit.release` 的 `publish` 与 `view` 显式带 `--registry`。

## 不负责的事

- 两个插件都不安装、不升级 pnpm 本身；插件管理换 pnpm 版本就是发一版插件管理
- devkit 不配置 `~/.npmrc` 与 token；包源的配置归插件管理的 `source.*`
- 插件管理不看环境变量或 pnpm 全局配置里指定的源，只看两份 npmrc；不写 home 级 `.npmrc`，那里的行要手工改
- gitea 插件不知道插件管理在读它的设置
- `devkit.release` 不运行包里的 `prepublishOnly`：发布内容来自临时目录，那里没有 `scripts`
