**本页回答**：两个插件用的是哪一个 pnpm、怎么找到它、各拿它做什么；在 home 里运行 pnpm 时为什么关掉自动补装 peer；正式版发到哪个源、哪几处指定源、哪几处靠用户的 `~/.npmrc`；开发版与正式版怎么分开；插件管理找插件时怎么决定去哪个源检索；第三方包源谁来配。

## 连接的模块

- 插件管理：`plugins/plugin-manager/src/pnpm-location.ts`（找 pnpm）、`src/pnpm.ts`（启动 pnpm）、`src/registry-auth.ts`（每 home 的 registry 鉴权）；找插件在 `src/package-sources.ts`、`src/sources.ts`、`src/search.ts`、`src/pnpm-config.ts`、`src/registry.ts`
- devkit：`plugins/devkit/src/dev.ts`、`src/release.ts`、`src/home.ts`、`src/node-dev-deps.ts`；找 pnpm 用插件管理主入口导出的 `locatePnpm`
- 用户装的 pnpm 12 可执行文件；团队源（gitea 上 `godcreator` 组织的 npm 源）与第三方包源；npmjs、Verdaccio、gitea 都实现的 npm registry 检索接口
- pnpm 的配置：机器级 `~/.npmrc`（agent 照说明书 `gwb-plugin-manager` 往里写第三方包源）、home 级 `<home>/.npmrc`、pnpm 自己的全局配置与环境变量，pnpm 把它们合成一份；插件管理找插件时向 pnpm 要这份合并结果，不自己读 npmrc

## 接口

**devkit 与插件管理用同一个 pnpm**：每条要运行 pnpm 的命令开头按顺序检查两个位置——`%LOCALAPPDATA%\pnpm\bin\pnpm.exe`（pnpm 12 官方安装脚本的默认位置）、`%APPDATA%\npm\node_modules\pnpm\pnpm.exe`（npm 全局装的 pnpm 包里的原生可执行文件）——用第一个存在的，运行 `--version` 核对是 12.x 并且不低于 12.4.2；不存在、版本不对都报错，不去试另一个位置，不看 PATH。找到的文件直接启动，不经 shell。规则只有一份，写在插件管理的 `src/pnpm-location.ts`，devkit 从插件管理的主入口 import `locatePnpm`（插件管理怎么找、怎么启动见 [pnpm](/docs/plugin-manager/pnpm)）：

**插件管理拿它做什么**：只在 home 里运行 `add`（对齐 `cordis` 那一次带 `--save-exact`）、`remove`、`outdated --json`，不传 `--registry`，源由 pnpm 的配置决定；找插件时另运行只读的 `config list --json` 取路由，凭据只取当前 home 的 `npm-auth`。

**devkit 拿它做什么**：`devkit.home.new`、`devkit.dev`、`devkit.release` 三条命令开头各找一次，找不到就回 `ok: false`、什么都不做。用在这几处：

| 命令 | 在哪运行 | 谁调 | 去哪个源 |
| --- | --- | --- | --- |
| `pnpm build` | 被测仓的仓根 | `devkit.dev`、`devkit.release` | 不适用 |
| `pnpm pack --pack-destination <目标 home>\dev-packs` | 临时目录里组装好的发布内容 | `devkit.dev` | 不适用 |
| `pnpm publish --no-git-checks --tag latest` | 临时目录里组装好的发布内容 | `devkit.release` | 发布目标，写在发布内容清单的 `publishConfig.registry`，命令行不带 `--registry`；npmjs 不走这一条 |
| `pnpm pack --pack-destination <系统临时目录>` | 临时目录里组装好的发布内容 | `devkit.release`，发布目标是 npmjs 的包 | 不适用：包文件传到 GitHub release 上，由 Actions 发（见[发正式版](/docs/devkit/release#发到-npmjs交给-github-actions)） |
| `pnpm view <包@版本> version` | 系统临时目录 | `devkit.release` | 发布目标：带范围的包名带 `--config.<范围>:registry=<发布目标>`，不带范围的带 `--registry` |
| `pnpm view <包> dist-tags.latest` | 系统临时目录 | `devkit.release` | 不指定，按 `~/.npmrc` 的 scope 路由 |
| `pnpm add <内核包、cordis（带 --save-exact）、基础插件>` | 新 home | `devkit.home.new` | 不指定：`@godcreator` 的包按 `~/.npmrc` 的 scope 路由，`cordis` 与 `@cordisjs/plugin-timer` 走默认源 |

`devkit.dev` 不在目标 home 里启动 pnpm：装包是目标 home 的插件管理在它自己的进程里运行的 `pnpm add`（见 [devkit 调插件管理](/docs/seams/plugin-manager-calls)）。

**在 home 里运行的 pnpm 都关掉自动补装 peer**：启动 pnpm 时非认证环境变量沿用，加一项 `pnpm_config_auto_install_peers=false`（插件管理另去掉 `ELECTRON_RUN_AS_NODE`）。插件管理的 pnpm 都在 home 里运行；devkit 只在 `home.new` 的三次 `pnpm add` 带它，在插件仓里的 build 与临时目录里的 pack、publish、view 不带——插件仓里开发要靠自动补装把 peer 里的内核包与插件装进 `node_modules`，带上它 pnpm 会按新配置重装、把这些 peer 拿掉，构建时找不到类型。插件的 peer 写了别的插件、home 里没装那个插件时，pnpm 默认把它装进 `node_modules/.pnpm` 且不提示，不写进 home 的 `package.json`、没有条目，插件管理也不认它。命令行参数 `--config.auto-install-peers=false` 会被 pnpm 忽略，只有环境变量或 home 的 `pnpm-workspace.yaml` 关得掉（实验见本仓 `probes/2609242300_peer-between-plugins/`）：

**第三方包源接入由 skill 编排**：说明书 `gwb-plugin-manager` 的「加一个市场」分开处理 pnpm scope 路由和本 home 的 `npm-auth`。已授权的旧凭据在本地直接导入，不回显；写完调 `plugin-manager.search` 核对。

`withHomeRegistryAuth` 是插件管理主入口给 devkit 的公开导出：绑定发起 home 的凭据，为指定操作注入认证并清理临时文件、脱敏结果。实际工程或工作区 `.npmrc` 存在认证项时先拒绝，由 skill 完成迁移并保留非敏感路由，产品不自动修改工程配置。`devkit.home.new` 的安装使用发起 home 身份，新 home 后续操作需自己配置。

## 约定

devkit 与插件管理都保证：在 home 里启动 pnpm 时带 `pnpm_config_auto_install_peers=false`，在 home 里 `pnpm add` 照 pnpm 默认在清单里写 `^` 范围，只有装 `cordis` 带 `--save-exact`；devkit 在插件仓里启动 pnpm 时不带前者。人在 home 里手工运行 pnpm 时要自己设这个环境变量。

插件管理保证：

- 会写 home 的 pnpm 只在经过 BUSY 检查的命令里运行，同一时刻最多一个；只读的 `pnpm outdated` 不经过 BUSY
- 不改持久化 npmrc；找插件时的 `pnpm config` 只读，认证临时文件在操作结束后清理
- 回执与日志里不带 token
- `search` 不带参数，只查市场名单里的 scope（顺序照名单），各市场并发查，一个失败不影响别的，全都失败才 `ok: false`

devkit 保证：

- 正式版发到包的发布目标（`publishConfig.registry`，没写就拒），本机装这个包的源与它不同、又不是 npmjs 时也发一份，打 `latest`；开发版不发到任何源
- 同一个版本号在发布目标上已有就不发；只在本机装包的源上有的，跳过那里、只补发布目标
- 发布内容与开发版的包文件都在临时目录里组装，不改仓里的 `package.json`

团队源需要保证的：`dist-tags.latest` 是正式最新版。devkit 只经 `~/.npmrc` 里 `@godcreator` 那一行知道团队源：发版时往哪多发一份、发版前检查问 peer 里各个插件的 latest，都按范围路由走；机器上没有这一行，公开包只发 npmjs，`@godcreator` 的插件的 latest 就去 npmjs 问。

插件包需要保证的：`package.json` 的 `keywords` 里写 `gwb-plugin`；库不写。

**改 home 的是同一个 pnpm，但互斥只在插件管理里**：插件管理与 `devkit.home.new` 找到的是同一个文件；插件管理的改动经过它自己的 BUSY 检查，`devkit.dev` 装包也经目标 home 的插件管理，所以同样经过这道检查；`devkit.home.new` 不经过插件管理（那时插件管理还没装、home 还没启动），同时有别的 pnpm 写同一个 home 会丢改动（见[同一时刻只允许一个改动](/docs/plugin-manager/busy)）。

`devkit.release` 不在命令行写 `--registry`，照包清单的 `publishConfig.registry`。

## 不负责的事

- devkit 与插件管理都不安装、不升级 pnpm 本身；要求的 pnpm 版本写在插件管理里，换版本就是发一版插件管理
- devkit 与插件管理不修改 `~/.npmrc` 或工程认证文件；第三方包源路由与原值迁移由 agent 照说明书 `gwb-plugin-manager` 完成
- 插件管理不去市场名单以外的源找插件：npmrc 里 pnpm 自带的 `@jsr`、公司私有源这类路由不查
- `devkit.release` 不运行包里的 `scripts`：发布内容来自临时目录，那里没有 `scripts`
