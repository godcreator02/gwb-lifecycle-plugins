**本页回答**：devkit 与插件管理用了工作台的哪几个服务、各调了哪个方法；哪个是必需的，缺了会怎样；服务的形状由谁定。

## 连接的模块

- devkit（`plugins/devkit`，包 `@godcreator/gwb-devkit`）
- 插件管理（`plugins/plugin-manager`，包 `@godcreator/gwb-plugin-manager`）
- 工作台服务，都在别的仓，由各自的插件提供：命令总线 `gwbCommands`（`@godcreator/gwb-commands`）、node 命令行工具登记 `gwbNodeCli`（`@godcreator/gwb-node-cli`）、说明书 `gwbSkills`（`@godcreator/gwb-skills`）、外壳 `gwbShell`（`@godcreator/gwb-shell`）

## 接口

**devkit 只把 `gwbCommands` 写进 `export const inject`**，其余三个都用 `ctx.inject([...], fn)` 局部注入：

{/* has file="../plugins/devkit/src/index.ts" text="export const inject = ['gwbCommands']" */}

devkit 对命令总线用了两个方法：`register(定义, 处理函数)` 登记命令，定义带 `name`、`plugin`（包名）、`description`、`usage`，撤销由命令总线登记在调用方的 effect 上，devkit 卸载时自动撤销；`list()` 只在就绪日志里用，列出此刻总线上本包的命令（见下面「约定」末尾）。devkit 不调别的插件的命令。

{/* has file="../plugins/devkit/src/index.ts" text="plugin: '@godcreator/gwb-devkit'," */}

`gwbNodeCli` 只用来登记一条命令行工具 `devkit.cdp`，`entry` 是包里 `bin/cdp.mjs` 的绝对路径；这条登记同样由 `gwbNodeCli` 自己放进调用方的 effect：

{/* has file="../plugins/devkit/src/index.ts" text="scoped.gwbNodeCli.register({" */}

{/* has file="../plugins/devkit/src/index.ts" text="entry: CDP_ENTRY," */}

`gwbSkills` 登记包内 `skills/` 目录，`gwbShell` 只调一次 `describeSelf` 报一个显示名，devkit 没有窗格：

{/* has file="../plugins/devkit/src/index.ts" text="scoped.effect(() => scoped.gwbSkills.register(new URL('../skills/', import.meta.url)))" */}

{/* has file="../plugins/devkit/src/index.ts" text="scoped.gwbShell.describeSelf({ title: '开发套件', icon: 'wrench' })" */}

devkit 源码里没有注入 `gwbSettings`，它没有设置项。

**插件管理的两个依赖都局部注入**：`gwbCommands`、`gwbSkills`。它自己提供服务 `gwbPluginManager`，值是空对象 `{}`：

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="76-82" hash="d3e1c817c32a" blob="8fed14154427" */}

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="89-94" hash="e4cfa73e8502" blob="8fed14154427" */}

这些服务的类型来自各服务包自带的 `declare module 'cordis'`：两个插件对这些服务包都只做 `import type`（devkit 另从插件管理的主入口按值 import 几个函数，见[插件之间怎么交互](/docs/rules/interaction)），服务包写在 peer 里（必需的命令总线直接写，局部注入可选使用的标 `optional`，见[用到的插件写 peer](/docs/rules/plugin-peers)），运行时不 import：

{/* has file="../plugins/devkit/src/index.ts" text="import type {} from '@godcreator/gwb-commands'" */}

每个服务的 peer 写法、缺了会怎样，逐个列在[插件之间怎么连](/docs/wiring)。

## 约定

devkit 保证：
- 必需的服务只有 `gwbCommands`；`gwbNodeCli`、`gwbSkills`、`gwbShell` 缺了，只少对应的那条命令行工具、那两份说明书、那个显示名，devkit 照常加载
- 每条命令的 `plugin` 写包名 `@godcreator/gwb-devkit`，`description` 一句话说做什么，参数形状写在 `usage` 里
- 只登记自己包里的说明书，不替别的插件登记

插件管理保证：
- 两个依赖都可以缺；`gwbCommands` 缺了，它就没有任何对外接口
- 命令的 `plugin` 写包名 `@godcreator/gwb-plugin-manager`
- 命令的参数或回执有破坏性变化时升 x（`gwbPluginManager` 的值上不放版本数字）

工作台服务保证：`gwbCommands.register` 与 `gwbNodeCli.register` 自己把登记放进调用方的 effect、`list()` 的每一项带 `name` 与 `plugin`、`run` 回 `{ ok, data?, error? }`——这几条写在各服务包的类型声明与说明书里，两个插件只经类型检查对上，**运行时靠约定**。

devkit 的就绪日志从 `list()` 里筛出 `plugin` 等于包名 `@godcreator/gwb-devkit` 的命令，与登记命令时写的 `plugin` 相同：

{/* has file="../plugins/devkit/src/index.ts" text=".filter((entry) => entry.plugin === '@godcreator/gwb-devkit')" */}

## 不负责的事

- 服务的方法签名、命令总线的回执信封由各服务所在的插件决定，devkit 与插件管理只按类型使用
- 两个插件在运行时不检查这些服务的版本：peer 里写的范围由 `devkit.release` 发版前对照源上的 latest、由 `plugin-manager.list` 在 home 里比对并报 `unmetPeers`；类型对不上只在各自的类型检查里暴露
- 插件管理不注入 `gwbShell`，也不调 `shell.reload`：升级完的整页重新加载由调用方做，见[热升级](/docs/plugin-manager/upgrade#一次热升级依次发生什么)
