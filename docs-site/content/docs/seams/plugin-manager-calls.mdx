**本页回答**：devkit 在哪几处用到插件管理，每一处靠什么对上；插件管理改了命令名、参数、回执或导出的函数，devkit 哪里先出问题；devkit 在哪一处不经插件管理直接改 home。

## 连接的模块

- devkit 的 `devkit.dev`（`plugins/devkit/src/dev.ts`）、`devkit.home.new`（`src/home.ts`），以及 import 插件管理导出的几个模块（`src/index.ts`、`src/dev.ts`、`src/home.ts`、`src/release.ts`、`src/artifact-check.ts`、`src/node-dev-deps.ts`、`src/node-home-deps.ts`）
- 插件管理的 `plugin-manager.install`、`plugin-manager.update`、`plugin-manager.list`（`plugins/plugin-manager/src/index.ts`、`src/update.ts`），主入口导出的函数与命令名
- 被操作的那个 home 里的 `cordis.yml`、`package.json` 与 `dev-packs/` 目录

## 约定

插件管理保证：

- `plugin-manager.list` 的 `data` 是按包列出的数组，每条条目有完整 `entryId` 与 `active`
- `plugin-manager.install` 收 `{ pkg, spec }`，`spec` 可以是 `file:` 写法；包已装就报错；成功回 `data: { pkg, entryId }`
- `plugin-manager.update` 收 `{ specs }`：一次 `pnpm add`；装之前与装之后真实目录变了的包逐条重新加载；插件管理自己的条目推迟到回执之后（回执 `selfDeferred: true`，那条条目的 `action` 是 `deferred`）；不整页重新加载；有内核包时照装上的内核包 peer 对齐 `cordis`、不重新加载任何条目，回执带 `restartRequired`
- 改这三条命令的名字、参数或回执形状，删改主入口导出的名字或签名，都是破坏性变更：升 x、先通知下游（见[什么算破坏性变更](/docs/plugin-manager#什么算破坏性变更)）

devkit 保证：

- 目标 home 是 `default` 或 devkit 自己所在的 home，都不动手
- 只读目标 home 的 `package.json`，在目标 home 里只写 `dev-packs/` 下的新包文件：每版一个新路径，已存在就拒，旧的不删
- 已装的包只发一条 `update`，不另发 `disable`、`enable`
- 装上的版本号不是这次打包的就回 `ok: false`

**第一处靠约定**：devkit 不 import 插件管理的回执类型（插件管理把它们放在子路径 `./receipts`，给界面插件的浏览器侧用），也拿不到插件管理的服务（它经 CDP 调用），回执里用到的几个字段在 `dev.ts` 里手写解析。第三处有类型检查：插件管理改了导出函数或命令名常量，devkit 的 `pnpm check` 当场报错。

内核仓文档站的「home 布局与条目树」一页写的是：插件管理是唯一写 home 的插件，`cordis.yml` 只经条目树改，`package.json` 与 `node_modules/` 只经插件管理运行的 pnpm 改。`devkit.dev` 守这一条；`devkit.home.new` 是例外，那时插件管理还没装、home 还没启动，它用的 pnpm 和插件管理是同一个。

## 不负责的事

- devkit 不写目标 home 的 `package.json` 与 `cordis.yml`，不删 `dev-packs/` 下的包文件
- 插件管理不知道 devkit：三条命令对谁调用都一样；它不知道 `dev-packs/` 目录，只照 `file:` 写法装
- devkit 不保证目标 home 里此时没有别的改动在进行；插件管理的改动命令经 BUSY 检查，同时来的第二条回 `BUSY`
