**本页回答**：devkit 在哪几处用到插件管理，每一处靠什么对上；插件管理改了命令名或回执，devkit 哪里先出问题；devkit 在哪几处绕过插件管理直接改 home。

## 连接的模块

- devkit 的 `devkit.dev`（`src/dev.ts`）与 `devkit.home.new`（`src/home.ts`）
- 插件管理的 `plugin-manager.list` 与 `plugin-manager.remount`（`plugins/plugin-manager/src/index.ts`、`src/remount.ts`）
- 被操作的那个 home 里的 `cordis.yml` 与 `package.json`

## 约定

插件管理保证：
- `plugin-manager.list` 按包列出，每条条目有完整 `entryId` 与 `active`
- `plugin-manager.remount` 收 `{ entryId }`（完整 id 或不带前缀的 id），回 `{ id, action, state }`；目标是插件管理自己时回 `deferred`，回执发出之后才重新加载
- 改这两条命令的名字、参数或回执形状算破坏性变更：升版本号的 x、`gwbPluginManager` 的 `contract` 加一、先通知下游（写在本仓 AGENTS 的「本仓还有插件管理」）

devkit 保证：
- 一条条目只发一条 `remount`，不拆成 `disable` 加 `enable`
- 目标 home 是 `default` 或 devkit 自己所在的 home，都不动手
- 装上的版本号对不上就停，不重新加载
- 目标 home 里没有这个包的条目时不建条目，回执里给出 `plugin-manager.install {"pkg": …, "spec": "<这次的版本号>"}`

**这几处都靠约定**：devkit 不 import 插件管理的类型，也不读 `gwbPluginManager` 的 `contract`（它经 CDP 调用，拿不到那个服务），回执形状在 `dev.ts` 里手写。约定写在三处：插件管理 `remount` 与 `list` 两条命令的 `usage`、`dev.ts` 的 `entriesOf` 与 `remount`、本仓 AGENTS。目标 home 的插件管理早于 0.4.0 时没有 `remount`，devkit 的报错里写着这个版本要求。

内核仓文档站的「home 布局与条目树」一页写的是：插件管理是唯一写 home 的插件，`cordis.yml` 只经条目树改，`package.json` 与 `node_modules/` 只经插件管理运行的 pnpm 改。`devkit.home.new` 在内核启动前直接写 `cordis.yml`、运行三次 `pnpm add`；`devkit.dev` 直接写目标 home 的 `package.json`、运行 `pnpm install`。两处用的 pnpm 和插件管理是同一个，只是不经插件管理的串行队列。本站[插件管理的 home 页](/docs/plugin-manager/home)把 `devkit.dev` 列为例外，没有提 `devkit.home.new`。

## 不负责的事

- devkit 不建条目、不调 `install` / `update` / `uninstall`；第一次建条目由人调 `plugin-manager.install`
- 插件管理不知道 devkit：`remount` 与 `list` 对谁调用都一样
- devkit 不保证目标 home 里此时没有别的改动在进行；插件管理的 BUSY 互斥只挡插件管理自己的命令，挡不住 devkit 直接运行的 pnpm
