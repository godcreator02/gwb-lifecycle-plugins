**本页回答**：`gwb.testedKernel` 写在哪、谁读、拿什么比；比对规则为什么有两份、两份靠什么保持一样。

## 连接的模块

- 插件包的 `package.json`：`gwb.testedKernel` 写这个插件验过的内核版本号
- devkit 的 `devkit.release`（`src/release.ts` + `src/tested-kernel.ts`）：发版前检查
- 插件管理的 `plugin-manager.list`（`src/index.ts` + `src/tested-kernel.ts`）：按包报 `testedKernel` 与 `kernelUntested`
- 内核：内核服务 `gwbKernel` 的 `version`，由内核仓提供

## 约定

devkit 保证：插件包的 `gwb.testedKernel` 没写、不合法、不在当前内核版本线上，一个包都不发，回执里写改成什么；不是插件的包不查。

插件管理保证：`kernelUntested` 只报告，不拦加载、不拦安装。

**两份规则保持一样靠同一个提交一起改，加一组对照测试把关**：「改规则时两份一起改」写在两份 `tested-kernel.ts` 的文件头、本仓 AGENTS 的「本仓还有插件管理」与本站[在哪个内核上测过](/docs/plugin-manager/kernel-compat)；devkit 的 `tests/tested-kernel-parity.test.ts` 把两份都 import 进来，拿同一组版本号与包清单跑三个函数，返回值或抛出的错误不同就失败。

插件管理的 `loader.test.ts` 还把 loader、include、cordis 三个 `devDependencies` 的版本与 `gwb.testedKernel` 那个内核对齐，见[条目树 loader](/docs/seams/entry-tree)。

建仓模板的 `template/pkg/package.json.tpl` 写 `gwb.testedKernel`，值是占位符 `{{testedKernel}}`：`devkit.scaffold` 与 `devkit.scaffold.plugin` 填入运行命令的那个 home 的 `gwbKernel.version`，所以新仓在同一个内核上 `devkit.release` 时过得了这一项检查；结构体检不查这个字段。

## 不负责的事

- 内核不读 `gwb.testedKernel`，版本对不上的插件照常加载
- devkit 只在发版时查，装进 home 时不查；插件管理只报，不拒
- 两处比的都是调用方所在 home 的内核：`devkit.release` 比 devkit 所在的 home，`list` 比插件管理所在的 home，二者可以是不同的内核
