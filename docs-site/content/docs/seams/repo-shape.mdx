**本页回答**：devkit 的几条命令对传给它的仓做了哪些假设；每条假设在哪几处代码里用到；不满足时各自怎样。

## 连接的模块

- devkit 的 `devkit.dev`（`src/dev.ts`）、`devkit.release`（`src/release.ts`、`src/artifact-check.ts`）、发布内容的组装（`src/node-dev-deps.ts`）、`devkit.audit-structure`（`src/structure.ts`）、`devkit.audit-deps`（`src/audit.ts`、`src/node-audit-deps.ts`）
- 被处理的插件仓：别人的仓，也包括本仓

<Diagram name="seam-repo-shape" title="被处理的仓要满足的约定，按目录树排；右边是依赖这条约定的命令">
- `<单元>/unit.json`：`devkit.audit-deps` 与全生态的结构体检先读它决定跳不跳过这个单元
- `<仓根>/.git`：`devkit.release` 要求工作区干净，不是 git 仓也拒
- `<仓根>/package.json`：`devkit.dev` 与 `devkit.release` 在仓根运行 `pnpm build`
- `<仓根>/pnpm-workspace.yaml`：组装发布内容时从包目录往上找到的第一个有它的目录是仓根
- `plugins/*`、`packages/*`：结构体检只扫这两处，`devkit.audit-deps` 另读 `apps/*` 与 `docs-site`
- `<包>/package.json`：`files` 是产物清单，`keywords` 含 `gwb-plugin` 表示插件，node 侧入口是 `exports["."]`
- `<包>/dist/client.js` 是浏览器侧产物入口，`<包>/node_modules/` 里内核包的清单给出页面 importmap 的名字，`<包>/tsconfig.build.json`（没有就用 `tsconfig.json`）是类型检查的依据，这三条只有 `devkit.release` 用
</Diagram>

## 接口

**仓根能 `pnpm build`**：`devkit.dev` 与 `devkit.release` 都在调用方给的 `dir` 上运行 `pnpm build`，不在包目录里构建；失败就停：

**`files` 白名单就是产物清单**：构建之后，白名单里不带 `!`、不带通配的每一项都得在包目录里；组装发布内容时只复制这些，带通配的直接拒：

**产物分两侧，按模板的构建约定认**：`devkit.release` 的构建产物检查把 `exports["."]` 的运行时入口（没有 `exports` 时是 `main`）当作 node 侧入口，把包目录下的 `dist/client.js` 当作浏览器侧入口（内核包再加上它 `gwb.shared` 经 `exports` 指到的文件），各自顺着相对 import 走；入口找不到、相对 import 指向的文件不在，都拒。内核包以外的包在清单里写了 `gwb.shared` 也拒。产物不在这几个位置的仓，那部分文件不被查到：

{/* ref file="../plugins/devkit/src/artifact-check.ts" lines="214-222" */}

**依赖装在包目录的 `node_modules` 里、包目录下有 `tsconfig.build.json` 或 `tsconfig.json`**：浏览器侧产物有包名 import 时，页面 importmap 里的名字从 `<包目录>/node_modules/@godcreator/gwb-kernel-desktop/package.json` 的 `gwb.shared` 现读（插件 peer 里写了内核包，pnpm 把它链接在那里），读不到就拒并提示 peer 写上内核包、再 `pnpm install`。类型检查在包目录里运行 `pnpm exec tsc --noEmit -p <tsconfig> --skipLibCheck false`，只查构建产物的类型，测试与构建脚本不查：node 侧有 `tsconfig.build.json`（模板里它只包含 `src/index.ts`）就按它查，没有才按 `tsconfig.json` 查，两份都没有就拒；包目录下有 `src/client/tsconfig.json`（模板的浏览器侧类型配置）就再查一次。没有 `tsconfig.build.json`、而 `tsconfig.json` 又包含测试的仓，测试引用到的上游包类型有错也会被拦下：

## 约定

devkit 保证：
- 除了 `pnpm build` 生成的构建产物，这些命令不改仓里的文件；发布内容在系统临时目录里组装
- 假设不满足时报错并说明缺了什么，不替调用方补（不补构建、不猜包目录、不改 `files`）

被处理的仓需要满足上面这几条，**全部靠约定**：没有一份检查把它们合在一起查。散在这几处：建仓模板生成的仓天然满足；结构体检查其中一部分（仓根 `build` 含 `pnpm -r`、`files` 白名单、`prepublishOnly`、`plugins/` 布局）；其余只写在各命令的 `usage` 与说明书「gwb-devkit」「gwb-release」里。

## 不负责的事

- devkit 不决定一个仓该有几个包、怎么分组，只按上面的目录名去找
- `devkit.dev` 不看 git 状态，未提交的改动照样发成开发版
- 结构体检不看依赖版本、peer 里内核包的范围与 git 状态
