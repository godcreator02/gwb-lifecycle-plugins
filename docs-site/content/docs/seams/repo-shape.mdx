**本页回答**：devkit 的几条命令对传给它的仓做了哪些假设；每条假设在哪几处代码里用到；不满足时各自怎样；devkit 与被处理的仓各保证什么。

## 连接的模块

- devkit 的 `devkit.dev`（`src/dev.ts`）、`devkit.release`（`src/release.ts`、`src/artifact-check.ts`）、发布内容的组装（`src/node-dev-deps.ts`）、`devkit.scaffold.plugin`（`src/scaffold.ts`）
- 被处理的插件仓：别人的仓，也包括本仓

<Diagram name="seam-repo-shape" title="被处理的仓要满足的约定，按目录树排；右边是依赖这条约定的命令">
- `<仓根>/.git`：`devkit.release` 要求工作区干净，不是 git 仓也拒
- `<仓根>/package.json`：`devkit.dev` 与 `devkit.release` 在仓根运行 `pnpm build`
- `<仓根>/pnpm-workspace.yaml`：组装发布内容时从包目录往上找到的第一个有它的目录是仓根，`catalog:` 依赖的范围从它的 catalog 里取；`devkit.scaffold.plugin` 要求它的 `packages` 里有 `plugins/*`
- `plugins/<短名>/`：`devkit.scaffold.plugin` 把插件包写到这里，目录必须还不存在
- `<包>/package.json`：`files` 是产物清单，`keywords` 含 `gwb-plugin` 表示插件，node 侧入口是 `exports["."]`，`publishConfig.registry` 是 `devkit.release` 的发布目标
- `<包>/dist/client.js` 是浏览器侧产物入口，`<包>/node_modules/` 里装着 peer 里的包、提供方的 ./browser-imports 代码出口给出页面模块名字，这两条只有 `devkit.release` 用
</Diagram>

## 接口

**仓根能 `pnpm build`**：`devkit.dev` 与 `devkit.release` 都在调用方给的 `dir` 上运行 `pnpm build`，不在包目录里构建；失败就停：

{/* ref file="../plugins/devkit/src/dev.ts" lines="662-664" hash="839dce56a7bd" blob="9c7dc37e4061" */}

**包目录由调用方列出**：`devkit.dev` 与 `devkit.release` 的 `packages` 必给，是非空的字符串数组，每项是相对仓根的包目录；不给或写错直接拒，不猜哪些是包：

{/* ref file="../plugins/devkit/tests/commands.test.ts" lines="201-212" hash="c8910824a57a" blob="435270e704c7" */}

**要发的包写了 `publishConfig.registry`**：`devkit.release` 发到这个地址，没写、或写的不是 http(s) 地址就拒（见[pnpm 与包源](/docs/seams/pnpm-registry)）。

**`files` 白名单就是产物清单**：构建之后，白名单里不带 `!`、不带通配的每一项都得在包目录里；组装发布内容与开发版的包文件时只复制这些，带否定式（`!` 开头）或通配的直接拒：

{/* ref file="../plugins/devkit/src/dev.ts" lines="97-100" hash="c53a8f4c178d" blob="48d80099fae0" */}

{/* ref file="../plugins/devkit/src/node-dev-deps.ts" lines="303-309" hash="8c0a0fbe45af" blob="a5afaa67bbb8" */}

**`keywords` 含 `gwb-plugin` 表示插件**：`devkit.release` 只对它查 peer（含 peer 里内核包的范围）与构建产物里包名 import 的两份名单；`devkit.dev` 只收插件与内核包，别的包（库）直接拒：

{/* ref file="../plugins/devkit/src/release.ts" lines="158-158" hash="317b9b806e49" blob="8ecbe5a4c556" */}

{/* ref file="../plugins/devkit/src/dev.ts" lines="467-470" hash="15dd703f95a5" blob="9c7dc37e4061" */}

**产物分 node 侧与浏览器侧，按模板的构建约定认**：`devkit.release` 的构建产物检查把 `exports["."]` 的运行时入口（没有 `exports` 时是 `main`）当作 node 侧入口，把包目录下的 `dist/client.js` 当作浏览器侧入口，各自顺着相对 import 走；入口找不到、相对 import 指向的文件不在，都拒。产物不在这几个位置的仓，那部分文件不被查到：

{/* ref file="../plugins/devkit/src/artifact-check.ts" lines="243-277" hash="2fe54abfbd7b" blob="a4accc3f8598" */}

**peer 里的包装在包目录的 `node_modules` 里**：发版前检查读 `<包目录>/node_modules/<包>/package.json` 判断 peer 里的包是不是插件，读不到就拒并提示先 `pnpm install`；浏览器侧名单读取自身与直接 peer 的 browser-imports 出口，未声明出口的旧项目兼容旧 kernel HTML：

{/* ref file="../plugins/devkit/src/artifact-check.ts" lines="279-296" hash="7e7b5d0544aa" blob="a4accc3f8598" */}

**成员放在哪**：组装发布内容时找 `workspace:` 依赖的版本，从仓根往下扫两层，不认目录名；找不到那个包、或扫到读不懂的 `package.json`，直接报错：

{/* ref file="../plugins/devkit/src/node-dev-deps.ts" lines="79-105" hash="1b46466d6d27" blob="a5afaa67bbb8" */}

这里的「仓根」是从包目录往上找到的第一个有 `pnpm-workspace.yaml` 的目录；一路找到盘根都没有就报错，这个包不发：

{/* ref file="../plugins/devkit/src/node-dev-deps.ts" lines="123-132" hash="53ef6c8aefb8" blob="a5afaa67bbb8" */}

**`catalog:` 的范围写在仓根的 `pnpm-workspace.yaml` 里**：组装发布内容时照 pnpm 的写法读顶层 `catalog` 与 `catalogs.<名>`，`catalog:` 依赖换成那里写的范围（怎么查见[发正式版](/docs/devkit/release#依赖的接口)）；YAML 读不懂、这两个键不是「名字: 范围」的表、顶层 `catalog` 与 `catalogs.default` 都写了，直接报错并写明文件：

{/* ref file="../plugins/devkit/src/node-dev-deps.ts" lines="143-166" hash="63d832fdc45b" blob="a5afaa67bbb8" */}

**`pnpm-workspace.yaml` 的 `packages` 里有 `plugins/*`**：`devkit.scaffold.plugin` 只往这样的仓里加插件，别的一概拒。`packages` 按 YAML 读，带不带引号、块列表还是流式列表都认；读不懂的写法报出是第几行，不当成「没有这一条」：

{/* ref file="../plugins/devkit/src/scaffold.ts" lines="236-241" hash="dbd834dc555d" blob="99db9041bdf1" */}

**git 工作区干净**：`devkit.release` 在构建之前运行 `git status --porcelain=v1`，有一条改动就一个都不发；不是 git 仓也拒。`devkit.dev` 不查：

{/* ref file="../plugins/devkit/src/release.ts" lines="450-459" hash="e996260268bf" blob="8ecbe5a4c556" */}

## 约定

devkit 保证：
- 除了 `pnpm build` 生成的构建产物与 `devkit.scaffold.plugin` 新写的插件包，这些命令不改仓里的文件；发布内容与开发版的包文件在系统临时目录里组装
- 假设不满足时报错并说明缺了什么，不替调用方补（不补构建、不猜包目录、不改 `files`、不给发布目标缺省值）

被处理的仓需要满足上面这几条，**全部靠约定**：没有一份检查把它们合在一起查。建仓模板生成的仓天然满足；其余只写在各命令的 `usage` 与说明书「gwb-devkit」「gwb-release」里。

## 不负责的事

- devkit 不决定一个仓该有几个包、怎么分组，只按上面的约定去找
- `devkit.dev` 不看 git 状态，未提交的改动照样打包进开发版
- 不查一个仓离 workspace 布局有多远、不替它迁：不是 workspace 布局的仓要先照模板迁
