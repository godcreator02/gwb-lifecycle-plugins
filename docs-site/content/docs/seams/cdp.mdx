**本页回答**：`bin/cdp.mjs` 收什么参数、输出什么、退出码什么意思；devkit 从它的输出里读哪几个字段；它对工作台页面假设了什么。

## 连接的模块

- devkit 的两处调用：经 `gwbNodeCli` 登记成命令 `devkit.cdp`（`src/index.ts`）；`devkit.dev` 每一步启动一个子进程运行它（`src/node-dev-deps.ts`、`src/dev.ts`）
- `bin/cdp.mjs`：零依赖单文件 JS，不进类型检查，工作台没启动时也能直接 `node` 运行
- 工作台页面：内核与外壳生成的那个页面，经 Chromium 调试端口连上

## 约定

`cdp.mjs` 保证：
- 第一个位置只收 home 名，连上之后核对页面自报的 home，对不上就不动手
- 页面自报 `default` 时只做只读动作（`shot`、`home`），写动作与 `--size` 不动手就拒；不在分类表里的动作在哪个 home 上都拒
- 写磁盘的位置只收完整的绝对路径，不看工作目录，不写进 devkit 包目录与任何 `node_modules`
- 页面上的命令失败时退出码非零，回执原样放在 `回执` 里

devkit 保证：`devkit.dev` 每一步都按 home 名调它，不传端口；把退出码与 JSON 一起交给 `dev.ts` 判断。

工作台页面需要保证的：外壳在页面上提供 `window.gwb.command`、页面上的脚本与样式表地址是带 home 绝对路径的 `file:///` 地址、home 目录在一个叫 `homes` 的目录下。

**这些全部靠约定**：devkit 插件只从 `cdp.mjs` import 算 home 根目录的 `homesRootOf`（类型写在手写的 `bin/cdp.d.mts` 里，见[内核与 home](/docs/seams/kernel-home)），命令行与输出这一面两边没有共享的类型；参数形状写在 `cdp.mjs` 文件头、`devkit.cdp` 的 `usage` 与 `dev.ts` 的各次调用三处，JSON 的键写在 `cdp.mjs` 的 `run` 与 `dev.ts` 的 `receiptOf` / `reloadPage` 两处；页面这一侧的前提只写在 `cdp.mjs` 的注释里，外壳与内核仓都没有写成对外的承诺。

## 不负责的事

- `cdp.mjs` 不知道页面里有什么、点完该发生什么
- `cdp.mjs` 读 `runtime.json` 只取 `cdp`，不核对 `pid` 是否还活着；它靠连上后核对页面自报的 home 名来发现记录已陈旧
- devkit 不解析 `eval`、`shot` 等动作的输出，那是调用方的事
