**本页回答**：模板生成的插件包要满足发版前检查的哪几条；模板的构建脚本和发版前检查用的是不是同一套名单；两边一致靠什么。

## 连接的模块

- 建仓模板（`plugins/devkit/template/`）：`repo/` 生成仓根，`pkg/` 生成 `plugins/<短名>/`；由 `src/scaffold.ts` 渲染，`devkit.scaffold` 与 `devkit.scaffold.plugin` 共用 `pkg/`
- 发版前检查（`src/release.ts`、`src/artifact-check.ts`、`src/style-check.ts`）：`devkit.release` 构建之后、发第一个包之前运行；样式检查 `devkit.dev` 构建之后也运行

## 接口

模板与发版前检查之间没有函数调用，接口是**模板生成的插件包清单与它的构建产物**。

**peer**：生成的清单 peer 里只有内核包与模板用到的两个插件（命令总线、外壳），内核包的范围是 `^<运行建仓命令的内核的 x.y.z>`，命令总线与外壳的范围是 `^<那个 home 里装着的 x.y.z>`，所以在同一个 home 上建仓、发版，过得了「peer 里的插件和源上 latest 在同一条线」。发版前检查要求 peer 只有 `cordis`、内核包与插件，内核包写成 `^x.y.z`：

## 约定

模板保证：生成的插件包 peer 那几项过得了发版前检查；照模板构建，产物里的包名 import 落在发版前检查的两份名单里。

模板不带任何检查：产物与样式的检查只在 devkit 里一份，改检查不用同步模板。两份外置名单与发版前检查的名单保持一样**靠约定**加 `tests/scaffold.test.ts` 查生成的构建脚本文本；改发版前检查的名单时，同一个提交里改模板的 `build.ts`。

## 不负责的事

- 模板不保证生成的仓能直接 `devkit.release`：peer 里的两个插件要和发版那时源上的 latest 在同一条线
- 模板的起始版本号是 0.1.0；升哪一位照说明书 `gwb-release`
