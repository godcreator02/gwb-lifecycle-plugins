**本页回答**：模板生成的插件包要满足发版前检查的哪几条；模板带的产物测试和发版前检查查的是不是同一套名单；两边一致靠什么。

## 连接的模块

- 建仓模板（`plugins/devkit/template/`）：`repo/` 生成仓根，`pkg/` 生成 `plugins/<短名>/`，`site/plugin.mdx.tpl` 生成文档站现状区的插件页；由 `src/scaffold.ts` 渲染，`devkit.scaffold` 与 `devkit.scaffold.plugin` 共用 `pkg/` 与插件页
- 发版前检查（`src/release.ts`、`src/artifact-check.ts`）：`devkit.release` 构建之后、发第一个包之前运行
- 生成出来的插件包自带的产物测试 `tests/artifact.test.ts`（模板里是 `template/pkg/tests/artifact.test.ts.tpl`）：在被生成的仓里随 `pnpm check` 运行

## 接口

两边之间没有函数调用，接口是**模板生成的插件包清单与它的构建产物**。

**peer**：生成的清单 peer 里只有内核包与模板用到的两个插件（命令总线、外壳），内核包的范围是 `^<运行建仓命令的内核的 x.y.z>`。发版前检查要求 peer 只有 `cordis`、内核包与插件，内核包写 `^x.y.z` 且包含运行中的内核：

## 约定

模板保证：生成的插件包在运行建仓命令的那个内核上，peer 那几项过得了发版前检查；产物测试的两份名单与发版前检查的相同，产物测试在被生成的仓里先把违反的地方报出来，不用等到发版。

两份名单保持一样**靠约定**加 `tests/scaffold.test.ts` 查生成的文本：它断言生成的产物测试里有按自己清单的 peer 放行的那一句、有经 `@godcreator/gwb-kernel-desktop/package.json` 找到装好的内核包的那一句，生成的构建脚本从内核包的 `dist/index.html` 读 importmap、不写 react 包名的字面量；不拿同一组产物分别过两份。改发版前检查的名单时，同一个提交里改模板的产物测试。

## 不负责的事

- 模板不保证生成的仓能直接 `devkit.release`：dev 依赖的范围过不过得了检查，要看发版那时源上的 latest；peer 里的两个插件要和那时源上的 latest 在同一条线
- 产物测试不查 dev 范围、peer 写法与内核范围，这几项只在发版前检查里查
- 两边找 import 的写法不同：发版前检查用 es-module-lexer 按 JS 语法找，产物测试只认顶格的静态 import（模板的 `build.ts` 不压行，外置的包名 import 由 esbuild 放在文件开头）。产物压成一行、或有动态 import 的仓，产物测试查不全，要等发版前检查
- 模板的起始版本号是 0.1.0；升哪一位照说明书 `gwb-release`
