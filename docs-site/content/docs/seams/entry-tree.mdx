**本页回答**：插件管理用了 loader 的哪几样东西、从哪里取到；条目的状态值从哪来；内核换了 loader 的版本，插件管理哪里先发现。内核对 home 布局与 loader 版本的承诺见内核仓文档站的「home 布局与条目树」接缝页。

## 连接的模块

- 插件管理（`plugins/plugin-manager/src/tree.ts`、`src/remount.ts`、`src/inventory.ts`、`src/update-all.ts`）
- `@cordisjs/plugin-loader` 与 `@cordisjs/plugin-include`：版本由内核定，插件管理只在 `devDependencies` 里写同样的版本用于类型与测试；`cordis` 本身同样

## 约定

插件管理保证：
- 改 `cordis.yml` 只经条目树，不直接写文件
- 只经自己那条条目的上一层取树，不写死内核那条 include 条目的 id
- 调用条目树之后不读回 `cordis.yml` 核对，以内存里的条目树为准

loader 与 include 需要保证的：`entry.parent.tree` 这条取法、四个方法的行为、`store` 里每一项的字段名、`FiberState` 的成员顺序。这些是 loader、include、cordis 的内部结构，不是公开接口，**靠约定**加测试：内核仓承诺这几个包的版本一变就升内核版本号的 x；插件管理在 `devDependencies` 里写与内核相同的精确版本，并在 peer 里用内核包的范围记下对应的内核版本（见[peer 里的内核包与插件](/docs/seams/kernel-peer)）。

## 不负责的事

- 插件管理不决定 home 的布局、条目树的结构、包名怎么解析，这些归内核
- 条目树不知道插件管理的 BUSY 互斥与串行队列；互斥只挡插件管理自己的命令
- devkit 不碰条目树；它改条目的唯一方式是经 CDP 调 `plugin-manager.remount`（见 [devkit 调插件管理](/docs/seams/plugin-manager-calls)）
