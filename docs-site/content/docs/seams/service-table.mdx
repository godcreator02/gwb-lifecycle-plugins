**本页回答**：`devkit.services` 与 `devkit.capabilities` 的数据从哪来；它们读 cordis 的哪几个内部字段、读各包 `package.json` 的哪几个字段；读不到时回什么；`gwb.provides` 写得对不对由谁检查、按什么规则。

## 连接的模块

- devkit 的 `devkit.services`（`src/services.ts`）与 `devkit.capabilities`（`src/capabilities.ts`），登记在 `src/index.ts`
- cordis 4.0.0-rc.9 的运行时结构：由内核带进来，devkit 只在 `devDependencies` 里写同一版本
- devkit 所在 home 里各包的 `package.json`：`<home>/package.json` 与 `<home>/node_modules/<包>/package.json`
- 写 `gwb.provides` 的那一侧：`src/provides-declaration.ts` 的检查，`devkit.release` 的发版前检查与 `devkit.audit-structure` 都调它，对着仓里各包的 `package.json` 与 `src/` 下的源码

- `gwb.provides` 的键在两条命令里不一样：贴到服务上时键是服务名，`devkit.capabilities` 的 `import` 段按模块说明符（包名或 `包名/子路径`）作键
- cordis 的结构认不出时回空表并带 `note` 与 `saw`，不抛错；`gwb.provides` 与源码对不对得上，由 `devkit.release` 的发版前检查与 `devkit.audit-structure` 在写的那一侧查

## 接口

**cordis 这边**：从自己的 `ctx.fiber` 沿 `parent.fiber` 往上走（最多 32 层），再遍历 `ctx.registry.entries()` 里每个插件的 `runtime.fibers`；每个 fiber 读 `store` 里的每一项，只收 `impl.fiber` 就是这个 fiber 的；提供者取 `fiber.entry.id` 与 `entry.options.name`，没有条目时退回 `runtime.name`：

**package.json 这边**：

| 字段 | 谁读 | 怎么用 |
| --- | --- | --- |
| `gwb.provides` | `devkit.services` | 键是**服务名**，值 `{ summary, usage }` 贴到那条服务上 |
| `gwb.provides` | `devkit.capabilities` | 键是**模块说明符**（包名，或 `包名/子路径`），值贴到那个入口上 |
| `gwb.shared`（只读内核包的） | `devkit.capabilities` | 与内核相同，按「外置名 → 本包 exports 子路径」的对象读；子路径是非空字符串的那些外置名报成内核包那一项的 `shared`。别的包写了不报 |
| `exports`（没有就退回 `main` / `types`） | `devkit.capabilities` | 列出入口与 d.ts 路径，跳过 `./package.json` |
| `keywords` | `devkit.capabilities` | 含 `gwb-plugin` 是插件，只含 `gwb` 是库，都没有是第三方 |
| `dependencies`（home 的） | `devkit.capabilities` | 决定列哪些包 |

## 约定

devkit 保证：这两条命令只读不写；读不到、形状不对的字段当没写，不让整条命令失败；cordis 结构认不出时回空表加说明，不抛错。入口、d.ts 路径、外置名、身份这些事实每次都从各包的 `package.json` 现读，不抄进任何一份声明：抄一份就多了第二个来源，迟早和 `package.json` 对不上。

各包需要保证的：`gwb.provides` 里的 `summary` 与 `usage` 是非空字符串，写的就是真的。`keywords` 含 `gwb` 或 `gwb-plugin` 的包，这一条由 `src/provides-declaration.ts` 检查，三条规则：源码提供的每个服务在 `gwb.provides` 里都有一条；每个键要么是源码提供的服务名，要么是本包 `exports` 里的 import 说明符（主入口写包名，子路径写 `包名/子路径`，与 `devkit.capabilities` 列出的入口是同一套）；每条的 `summary` 与 `usage` 是非空字符串。`devkit.release` 的发版前检查没过就拒，`devkit.audit-structure` 记一条 error 级的 `provides-declaration`：

源码提供了哪些服务按文本扫 `src/` 下的 `.ts` / `.tsx`，认三种写法，服务名只认标识符，注释里的示意写法不算：

{/* ref file="../plugins/devkit/src/provides-declaration.ts" lines="8-28" */}

cordis 需要保证的：`fiber.store`、`fiber.entry`、`fiber.parent`、`registry.entries()`、`runtime.fibers`、`runtime.name` 这几个字段。它们不是 cordis 的文档化接口，**靠约定**：写在 `services.ts` 的文件头注释（按 4.0.0-rc.9 的字段写），没有测试拿真实的 cordis 核对，结构变了的表现是回执变成空表加 `note`。

`gwb.shared` 只有内核包的算数：内核只读内核包自己清单里的这一项写页面 importmap，别的包写了内核不收，`devkit.capabilities` 也只给内核包报外置名。读法与内核一致：内核把它当作「外置名 → 子路径」的对象读（见内核仓文档站的「页面上的包名 gwb.shared」接缝页），子路径不是非空字符串的那一项不进 importmap；`devkit.capabilities` 按同一条规则取外置名，写成数组或字符串的声明两边都不认：

{/* ref file="../plugins/devkit/src/capabilities.ts" lines="36-46" */}

同一个 `gwb.provides` 里两种键并存：`devkit.services` 只读服务名键，`devkit.capabilities` 只读说明符键；检查两种都认，一个键两种都不是才拒。

## 不负责的事

- 这两条命令只报这个 home 此刻加载了什么、装了什么，不判断对错
- 不聚合入口里导出了哪些符号，只给 d.ts 路径，让 agent 去读原文：摘录会被截断，也会过时
- 不列命令：命令按插件查用 MCP 入口的 `search`
