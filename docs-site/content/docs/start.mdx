# 怎么用

**本页回答**：这个插件怎么装、装完要配什么、它的各组命令各在什么时候用、改完代码跑哪几条检查。

## 安装

```
plugin-manager.install {"pkg":"@godcreator/gwb-devkit"}
```

装完之后，下一次调 MCP 入口的 `index` 就有它的命令：`index` 每次现查，不用重连。

加载成功的证据是 `<home>\gwb.log` 里那句「开发套件就绪」。看那一行，不要看安装命令回的「装完了」：包装进 `node_modules` 与插件真的加载成功是两件事。这个 home 上此刻到底有哪几条命令，以 `index` 的回执为准。

## 没有设置项

装完什么都不用配。启动 home 用的是宿主自己那个应用，不认内核仓；`devkit.audit-deps` 不给 `root` 时现问命令总线上的 `unit-folder.list`。

## 各组命令

参数形状以命令自己的 usage 为准。命令总线不带参数 schema，description 那一句与 usage 就是调用方能看见的全部，所以它们写得出形状；这一页只说什么时候用哪一组。

**建仓**。`devkit.scaffold` 把一个新插件的骨架放进一个新文件夹，默认连文档站一起建。目标目录必须还不存在。建站分两步，经命令总线转给站点插件与 docfirst 插件，哪个插件没装就跳过那一步，插件的骨架照样写到磁盘。参数给错会把整份说明回给你，不必背。

**源**。常驻的 gitea 个人源（`https://git.tianshen02.online:28377/api/packages/godcreator/npm/`），不经本机、不用启动停止。`@godcreator` 是 gwb 线的命名空间，scope 路由写在用户级 `~/.npmrc` 里，命令行上不写 `--registry`。

**测试 home**。`devkit.home.new` 开一个新的，名字是 `<短名>-<时间戳>`，用装好的宿主应用启动窗口、不构建内核；`devkit.home.list` 列全部与哪些在运行，连带调试端口与 MCP 入口；`devkit.home.open` 重开一个已有的；`devkit.home.rm` 删。一次验证开一个新 home，清理放在开新 home 的时候，回执里本来就带着现有清单。

机器重启之后回到原来那个 home 只有 `open` 这一条路：`new` 永远建新目录，插件得全部重装一遍。

**调试端口不收，启动时自己挑**。先沿用这个 home 上次那个端口，被别人占了才另挑，换了会在回执的 `cdpNote` 里说一句。端口稳定下来有好处：人记得住、日志里对得上、开着的检查器不用换地址；而收一个手给的端口，唯一多出来的用法就是「敲错一位落在别人的端口上」。

`rm` **没在运行的直接删；还在运行的要 `force`**，那时先停再删，按 pid 等进程真的退出才删，停的是哪个 pid 写在回执里。**回「已删」只在目录真不在了之后**，删不掉回 `ok: false` 并列出还剩什么。停进程认的是内核启动时写下的 `runtime.json`，所以手工启动的 home 同样停得了。`default` 是日常用的那个：不 `force` 不删，而且**它在运行时 `force` 也不删**——先自己关掉那个窗口。

**改一版看一版**。`devkit.dev` 一条命令从构建做到取证。下一节单独说。

**发正式版**。`devkit.release` 从仓根把包按依赖序发到源（tag latest）：git 树不干净就拒、同号在源上就拒、构建之后发版前检查没过就拒、不改仓里任何文件、不碰任何 home。发版前检查对每个要发的包查：自己不在 0.0.x；`@godcreator` 的 dev 范围包含源上 `dist-tags.latest`（写法认不出、下限比 latest 新、latest 出范围才拒，范围内落后放行）；写成 peer 的 `@godcreator` 包写 `^<dev 下限>`；插件包（`keywords` 含 `gwb-plugin`）的 `gwb.testedKernel` 和运行中的内核在同一条版本线上（没写、不是合法版本号、不在同一条线都拒）。没过一个都不发，回执按包一次列全；peer 指向的上游还在 0.0.x 只在 `reminders` 里提醒。发出去的 `workspace:` 依赖写 `^`：同一次发的写 `^新号`，其余写 `^<工作区里那个号>`。

这几条里哪些依赖该写 peer，规矩在[写插件的规矩](/docs/rules/deps)；发版前检查对 `@godcreator` peer 的要求还是旧规矩，总表里[写明了](/docs/rules)。

**依赖对账**。`devkit.audit-deps` 扫容器根下各仓的 `@godcreator` 声明，对照源上现在的版本，只读。dev：`dead-pin`（写的版本源上没有）、`behind`（落后 latest 但还在范围内——提示，不用处理）、`out-of-range`（latest 出了范围，必须跟）、`loose-dev-pin`（写法既不是精确号也不是 `^`）；peer：`peer-not-caret`（还写 `>=` 或别的写法）、`floor-unverifiable`（下限在源上没有）、`floor-mismatch`（下限 ≠ dev 下限）、`floor-no-mirror`（dev 里没写同一个包）。「最新」认 `dist-tags.latest`，退役单元不扫，`private` 清单只查 dev。

**在页面里操作**。`devkit.cdp` 是经 `gwbNodeCli` 登记的外部 CLI，连上一个工作台页面发真实的鼠标与按键、截图，也能在那张页上跑工作台命令、刷新、问它是哪个 home、把一个文件送进页面里执行（`eval <文件> [JSON 参数]`，文件里写 `(args) => 一张表`）。路径一概不看工作目录：截图缺省写到被截那个 home 自己的 `out\cdp\`，给输出与 `eval` 的文件都只收绝对路径。

{/* ref file="../plugins/devkit/src/index.ts" lines="430-439" */}

十二个动作与五个开关的表在 `bin/cdp.mjs` 的文件头，那份随包发，以它为准。**第一个位置只收 home 名**，给数字当场拒；端口从那个 home 的记录里查，连上之后还要拿页面自报的名字核对一次。**只对隔离 home 用，绝不用在 `default` 上**：这里发的是真实操作，会真的往库里写。内核启动时要带 `--remote-debugging-port=<端口>` 与 `--disable-backgrounding-occluded-windows`，后一个不带，窗口被别的窗口挡住时 Chromium 停止渲染新帧，截图拿到的是旧画面。

**说明书**。写插件的整条路、十条红线、在隔离 home 里怎么验证，在随包发的说明书 `gwb-devkit` 里，经 `skill.read` 取；每条红线的做法与由谁把关在[写插件的规矩](/docs/rules)。

## 改一版看一版

{/* ref file="../plugins/devkit/src/index.ts" lines="470-478" */}

`devkit.dev` 是一条链：仓根构建，给每个包发一个开发版到源（号是 `<patch+1>-dev.<时间戳>`，标 `dev` 不动 `latest`），在目标 home 的清单里写那个准确的号再 `pnpm install`、读回装上的号核对（对不上当场 `ok: false`），每条对应的条目调一次 `plugin-manager.remount` 重新加载（停用再启用在目标进程里一条命令做完，重新加载插件管理自己或命令总线也一次完成；目标 home 的插件管理要 0.4.0 起），整页重载，最后取证。取不到证据就回 `ok: false`。

**构建与源都不能指定。** 跳过构建就是发上一版，而回执一切正常；源在这台机器上只有一个。少一个参数，就少一个跳过检查的机会。

**目标只有一种写法：说出 home 名。** 这条命令不收端口，给了 `cdp` 当场拒，回一句告诉你新写法的话：

{/* ref file="../plugins/devkit/src/index.ts" lines="450-462" */}

端口是查出来的，查的时候顺带确认进程还在：记录读得出、pid 还活着、那个 pid 真的占着那个端口，三项都对才动手。

**为什么端口不是地址。** 它是一个没有语义的数，敲错一位就落在另一个 home 上，而那个 home 会照单收下这次的发版、装包与重新加载，事后也看不出哪儿不对。名字有拼写、有记录、有交叉核对，这三样端口都没有。代价写在这里：**记录坏了、或者启动它的内核太旧的 home 就连不上**，那时停掉重开一次就有了；这个驱动也从此连不了不是 gwb 的 Chromium 窗口。

**名字还带来一道核对。** 名字接着传进链里，每一步连上页面都跟页面自报的名字对一次：记录回答「你要的是哪个」，页面回答「你连上的实际是哪个」。端口会被下一个进程占走，记录会过时，只信记录就会不声不响地把改动推给另一个 home。链里那七步都是按名字调驱动的，为的就是每一步都多一道核对，而不是七次没人看着的重新定位。

**它运行在控制台那个 home 里，操作另一个 home**。换插件那一步要把条目停用再启用，工具自己要是运行在被换的那个 home 里，换到命令总线、外壳、MCP 入口或它自己时，调用方跟着下线。所以磁盘上的那部分（构建、发版、安装）在本进程做，页面上的那部分（重新加载、刷新、取证）经 CDP 送到目标页去。

两道检查会当场拒：目标是 `default`，或者目标就是本插件自己所在的那个 home。前者是开发版进了日常用的 home，版本号看着跟正式版没两样，界面上一点异常都看不出来；后者是这条命令把自己停掉。换 devkit 自己走另一条路：发正式版，再 `plugin-manager.update-all`。

取证这一步不能省。重新加载了、刷新了都不等于验过了：pnpm 退出码 0，装上的可能还是上一次的号；插件 `apply` 里一条 async 不报错地 reject，现象正好是「加载了但什么都没发生」。所以最后回头看三样：装上的是不是这次发的号、条目是不是真的 ACTIVE、这次新增的日志里有没有 error。

**取证只发生在链里那一次**，因为判断要有基线：哪些 error 是这次自己引起的，只有拿装包之前那个日志长度才分得出来。要看一眼某个 home 的条目表，`devkit.cdp {"args":["<名>","cmd","plugin-manager.list"]}` 就行，那是看，不是验证。

## 提交前的检查

{/* ref file="../plugins/devkit/package.json" lines="27-33" */}

```
pnpm check          # typecheck + vitest
pnpm build          # 在仓根跑：只构建 plugins/* 与 packages/*，tsc 直接输出 dist/，没有打包器
```

**`pnpm check` 不构建。** 它只检查源码，全绿只说明源码没问题，跟「装出来能不能运行」是两件事。手工 `pnpm publish` 时发版前那次构建靠 `prepublishOnly` 这条脚本保证，删了它，publish 会把上一版的 `dist/` 原样发出去而且不报错，现象是插件加载了但新写的东西全没生效。

文档站的检查不在 `pnpm check` 里，它要启动文档站的解析，太慢。单独在 `docs-site` 里跑：`pnpm doc` 核对，`pnpm doc:confirm` 确认新的代码引用（先 commit，git 比较器只认已提交的内容），`pnpm doc:render` 重新生成生成物。

## 发一版

先升 `package.json` 的版本号并提交，同一个号永不重发。然后 `devkit.release {"dir":"<本仓根>","packages":["plugins/devkit"]}`（repo-kit 也改了就把 `packages/repo-kit` 排在前面）。

发完就去升 default，别攒着：人在插件窗格点「全部更新」，或者调 `plugin-manager.update-all`。说明书与命令都随包走，不升等于 agent 读到的还是上一版，而它照着一份过期说明书干活不报错。

升哪一位、依赖怎么写、发版流程在说明书 `gwb-release` 里；改一版看一版与验证的纪律在说明书 `gwb-devkit` 里。这一页不复述。
