# 怎么用

**本页回答**：这个件怎么装、装完要配什么、此刻它开出来的口各在什么时候用、改完代码跑哪几条。

## 装

```
plugins.install {"pkg":"@godcreator02/gwb-devkit"}
```

装完要 `/mcp` 重连一次。顶层工具清单与 resources 列表都是连接时的快照，不重连就看不见新长出来的东西。

挂上了的证据在 `<home>\gwb.log`，那句「开发套件就绪」把这一版真登记上的命令逐条列了出来。读那一行，不要读「装完了」这四个字：包装进 `node_modules` 与件真的挂上是两件事。

## 两个设置项

@@docfirst ref ../src/index.ts:190-204 @@

`registry-dir` 是本机 Verdaccio 那个目录，含 `config.yaml`、`storage` 与 `node_modules/verdaccio`。不填，`registry.*` 四条全部回一句「未配置 registry-dir」。

`kernel-dir` 是内核仓的根，即含 `apps/desktop` 的那一级。不填，`devkit.home.new` 与 `devkit.home.open` 不工作；列、停、删不受影响。

两项都不给默认值。目录是这台机器的事实，编一个出来只会得到「配置了但不在」的假象，而那种假象要等到第一次真跑才炸。

## 六组入口

参数形状以命令自己的 description 为准。命令总线不带参数 schema，description 那一句就是调用方能看见的全部，所以它写得出形状；这一页只说什么时候用哪一组。

**建仓**。`devkit.scaffold` 把一个新件的骨架落进一个新文件夹，默认连文档站一起建。目标目录必须还不存在。站那半是两步，经命令总线转给站件与 docfirst 件，哪个件没装就跳过那一步，件那半照样落盘。参数给错会把整份说明回给你，不必背。

**本机源**。`registry.status` 查、`registry.up` 拉起（已经在跑就直接接管）、`registry.down` 停、`registry.log` 看日志尾巴。这台机器上别的仓也在用这个源，停之前想清楚。

**测试 home**。`devkit.home.new` 开一个新的，名字长成 `<短名>-<时间戳>`，默认先 build 内核；`devkit.home.list` 列全部与谁在跑；`devkit.home.open` 重开一个已有的且不 build；`devkit.home.stop` 停；`devkit.home.rm` 删。一次验证开一个新 home，清理放在开新的那一刻，回执里本来就带着现有清单。

**改一版看一版**。`devkit.dev` 一条走完从构建到取证；`devkit.dev-check` 只摆现状不判定。下一节单独说。

**在页面里动手**。`devkit.cdp` 是经 `gwbNodeCli` 登记的外部 CLI，连上一个工作台页面发真鼠标、真按键、截图，也能在那张页上跑工作台命令、刷新、问它是哪个 home。

@@docfirst ref ../src/index.ts:449-456 @@

动作表在 `bin/cdp.mjs` 的文件头，那份随包发，是唯一的真相。**只对隔离 home 用，绝不打 `default`**：这儿发的是真操作，会真往库里写。内核起的时候要带 `--remote-debugging-port=<口>` 与 `--disable-backgrounding-occluded-windows`，后一个不带，窗口被别的窗口盖住时 Chromium 停止产帧，截图拿到的是陈旧帧。

**手册**。写件的整条路、七条红线、验机怎么走，在随包发的说明书 `gwb-devkit` 里，经 `skill_read` 取。

## 改一版看一版

@@docfirst ref ../src/index.ts:460-467 @@

`devkit.dev` 走的是一条链：仓根构建，给每个包发一个开发版到本机源（号打成 `<patch+1>-dev.<戳>`，标 `dev` 不动 `latest`），在目标 home 里装那个准确的号，把对应条目停用再启用，整页重载，最后取证。取不到证就回 `ok: false`。

**它住控制台那个 home，操作另一个 home**。换件那一步要把条目停用再启用，工具自己要是跑在被换的那个 home 里，换到总线、外壳、mcp 或它自己头上时，调用方跟着下线。所以盘那半（构建、发版、装）在本进程做，页那半（重挂、刷新、取证）经 CDP 送到目标页去。

两道守卫会当场拒：目标是 `default`，或者目标就是本件自己所在的那个 home。前者是开发版进了日常那份 home，号看着跟正式版没两样而界面上一点异常都看不出来；后者是这条命令把自己停掉。换 devkit 自己走另一条路：发正式版，再 `plugins.update-all`。

取证这一步不能省。重挂了、刷新了都不等于验过了：件的 `apply` 里一条 async 静默 reject，现象正好是「挂上了但什么都没发生」。所以最后回头看两样，条目是不是真的 ACTIVE，以及这一趟的日志增量里有没有 error。

`devkit.dev-check` 只把现状摆出来，**不下判定**。它单独跑时没有「这一趟之前」的基线，看见的 error 可能是几天前的。拿它的绿色当验收，正好是它防的那件事。

## 门禁

@@docfirst ref ../package.json:24-30 @@

```
pnpm check          # typecheck（两份 tsconfig）+ vitest
pnpm build          # tsc 直出 dist/ 与 dist/client/，没有打包器
```

**`pnpm check` 不构建。** 它吃的是源码，全绿只说明源码站得住，跟「装出来能不能跑」是两件事。发版前那次构建靠 `prepublishOnly` 这条脚本兜着，删了它，publish 会把上一版的 `dist/` 原样发出去而且一声不吭，现象是件挂上了但新写的东西全没生效。

文档站的检查不在 `pnpm check` 里，它要起文档站的解析链，太慢。单独在 `docs-site` 里跑：`pnpm doc` 核对，`pnpm doc:confirm` 重钉（先 commit，git 比较器只认已提交的内容），`pnpm doc:render` 重摆生成物。

## 发一版

先抬 `package.json` 的版本号，同一个号永不重发，发之前先问一句它在不在源上。然后 `pnpm publish --registry http://127.0.0.1:4873/ --no-git-checks`。

发完就去升 default，别攒着：人在插件窗格点「全部更新」，或者调 `plugins.update-all`。手册与命令都随包走，不升等于 agent 读到的还是上一版，而它照着一份过期手册干活不报错。

整条路的细节、发版前先在隔离 home 验那一步、以及验机的几条纪律，在说明书 `gwb-devkit` 里，这一页不复述。
