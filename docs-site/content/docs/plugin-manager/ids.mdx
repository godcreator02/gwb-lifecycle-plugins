# 条目 id

**本页回答**：条目 id 是什么、为什么不能改；新条目的 id 怎么选；不同 scope 的同名插件怎么共存；卸载后另一个同名包拿到同一个 id 时会怎样；同一个插件改了包名，怎么接着用原来的设置与数据。

## id 是身份，一经确定不改

每条条目有一个 id，写在 `cordis.yml` 里；数据插件、设置插件都按 id 给这条条目分目录、分区。改了 id，原来的设置与数据就留在旧分区里，再也读不到，所以插件管理没有改 id 的命令，也不收调用方指定的 id。界面上给人看的名字是插件自报的名字，插件管理不存显示名。

- 字符集是 kebab-case：小写字母、数字、单个连字符分段。数据插件与设置插件用同一套字符集校验，三处必须一起改——生成的 id 通不过它们的校验，这条条目就存不下任何设置和数据
- 默认 id 是包名去掉 scope 与最外层 `gwb-` 前缀：`@godcreator/gwb-py-cli` → `py-cli`；一个字符都剩不下时用 `plugin`
- 重名时加数字后缀：`py-cli-2`、`py-cli-3`，中间空着的号先补上

## 选 id：默认 id，条目树上重名加后缀

`install` 与 `add-entry`（只收 `{ pkg }`）给新条目选 id 时只看条目树：默认 id 没被占就用它，被占了就从 `-2` 起找第一个空着的号。默认 id 去掉了 scope，`@a/gwb-foo` 和 `@b/foo` 都叫 `foo`，同时装着时后装的那个拿到 `foo-2`，两个插件各用各的数据与设置；同一个包再加一条条目也一样加后缀。

## 选 id 不读归属记录

数据插件、设置插件各记着每个 id 属于哪个包，删了条目也还在。插件管理选 id 时不读这两份记录：卸载一个包之后，另一个默认 id 相同的包可能拿到同一个 id，加载时读到前一个包留下的数据目录或设置分区，这时由数据插件与设置插件自己的归属检查报错，条目加载失败，`list` 里 `active` 为 false、原因在 `gwb.log`。是不相干的两个包撞了 id 时，照那两个插件的报错处理。

## 包改名：改归属

同一个插件改了包名（比如私有包从 `@godcreator/…` 改成 `@godcreator02/…`），新包的默认 id 和旧包相同，设置、凭据与数据都还在那个 id 下面，只是归属记着旧包名，新包一加载就被拒。`transfer-owner {"entryId","pkg"}` 把这个 id 的归属改给新包名，之后新包接着用原来那一份：

1. `uninstall` 旧包：它的条目全删掉，设置与数据留在磁盘上
2. 对旧包的每个条目 id 调一次 `transfer-owner`，`pkg` 写新包名
3. `install` 新包，拿到同一个默认 id；旧包原来有几条条目的，再 `add-entry`，id 照旧按 `-2`、`-3` 排下去

只改记着归属的那几样：这个 id 没有数据目录，就不替它建一个；设置与数据都没记这个 id，多半是 id 写错了，直接报错。条目树上这个 id 的条目正在加载另一个包时也直接报错——先改了归属，正在运行的旧包就读写不了。条目加载的已经是新包名（先装了新包、它正被拒着）时照常改，改完把那条条目 `disable` 再 `enable` 重新加载一次。

归属记录归数据插件、设置插件管：插件管理只调它们的 `owners()` 与 `transferOwner()`，不自己拼路径去碰 `settings.json` 与数据目录，所以这两个插件有一个没装，`transfer-owner` 就不登记。
