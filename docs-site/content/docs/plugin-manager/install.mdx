# 安装与卸载

**本页回答**：装一个包经过哪几步、每一步失败时回执是什么样；为什么已装的包不许再 `install`；为什么建条目不等加载；为什么不替插件装它 peer 里的插件、也不判断是不是库；卸载为什么先删条目、失败不回滚。条目 id 怎么选见[条目 id](/docs/plugin-manager/ids)。

## 装包与加条目在一条命令里

`install` 一条命令做完三步：校验参数 → 一次 `pnpm add`（home 的 `package.json` 里照 pnpm 默认写 `^` 范围，为什么见 [home 与条目](/docs/plugin-manager/home)）→ 选 id、加一条启用的条目，回执 `data` 是 `{ pkg, entryId }`。拆成「先装包、再加条目」两条命令，中间可能插进别的改动，调用方也得自己处理「包装上了、条目没加上」的中间状态。

<Diagram name="pm-install" title="安装一个包：三步依次做，每一步失败时回执是什么样，回执里逐步多出哪几行">
1. **校验参数**：包名与版本写法不合规就抛错——拦的是 `-r` 这类会被 pnpm 当成命令行选项的参数，参数全程以数组传给 pnpm、不经过 shell。包已在 home 的 dependencies 里也抛错。只有调用方写错才抛，下面每一种失败都转成 `ok: false` 的回执
2. **一次 `pnpm add`**：先在两个固定位置找到 pnpm 并核对版本（见 [pnpm](/docs/plugin-manager/pnpm)），再经 `applyToHome` 运行。失败时 `error` 末尾带 pnpm 输出的最后几行，不加条目
3. **选 id，加一条条目**：经条目树 `create` 写进 `cordis.yml`，回执带 `entryId`。写不进 `cordis.yml` 时回 `ok: false`，包留在 home 里、不回滚——删包比留着危险，删除时也未必只删掉这一个
</Diagram>

## 已装的包直接报错

包已在 home 的 dependencies 里，`install` 直接报错、一次 pnpm 都不运行，报错指向两条路：再加一条条目用 `add-entry`，换版本用 `update {"specs":{…}}`（见[热升级](/docs/plugin-manager/upgrade)）。已装的包再 `pnpm add` 一次，只会悄悄换掉版本号、再多一条条目，两件事都不是调用方要的。

## 建条目只等写入、不等加载

第 3 步只等条目写进 `cordis.yml` 就返回回执，不等插件加载完；加载成功没有看 `list` 里的 `active`，失败原因在日志里。条目树的 `create` 返回的 promise 里包含加载过程，而 inject 满足不了的插件，fiber 会一直等待——等它的话，装一个依赖还没装齐的插件，这条命令就永远没有回执。

写回 `cordis.yml` 在 `create` 的第一个 `await` 之前就同步安排好了，所以不 `await` 也不影响写入；加载失败只记一条 warn。id 一定显式传给 loader：不给的话 loader 每次启动生成一个新的随机 id。

这一条没有单元测试：要验证，就在隔离 home 里装一个依赖还没装齐的插件，看命令是否照常返回回执、`list` 里是否显示未加载。

## home 里只有插件、内核包与 cordis

安装只装点名的那个包，不替它装它 peer 里写的插件或任何别的包，也不按 `keywords` 猜它是不是库。pnpm 默认会把缺的 peer 自动补装进来，插件管理启动 pnpm 时把这一项关掉了（见 [pnpm](/docs/plugin-manager/pnpm#参数环境与读回什么)）。插件运行时用到的东西各有提供方，不需要另外装进 home：

<Diagram name="pm-home-contents" title="home 的 node_modules 里只有插件、内核包与 cordis；插件运行时用到的东西各由谁提供">
- 内核包 `@godcreator/gwb-kernel-desktop` 与 `cordis` 装在 home 根上，由创建 home 的一方装，内核包经 `update` 的 `specs` 换、`cordis` 由插件管理照内核包对齐；`cordis` 的版本等于内核包 peer 里写的那个，内核与插件 import 的是同一份
- 插件用到的别的插件写在它的 peer 里，是 home 里另一个有条目的插件，装不装由人决定；没装或版本不在范围里，`list` 的 `unmetPeers` 报出来
- 页面上必须只有一份的运行时代码经页面的 importmap 提供：kernel 负责登记与准备，提供方通过代码交出模块地址；React 由 shell 提供，更新提供方后整页重载
- 插件自己用的库、接口定义包打包进它自己的构建产物
- 只取类型的 import（内核包导出的接口类型、别的插件的类型）编译后就消失了
</Diagram>

所以 home 里除了内核包与 `cordis` 只该有插件：插件 peer 里的插件是另一个要由人装、要加条目的插件，被 pnpm 自动补装进来的那份没有条目，也不在 home 的 `package.json` 里。插件管理自己也没有 `dependencies`：运行时 import 的 `cordis` 是 home 根上那一份（写在 peer 里），pnpm 是用户装在机器上的，不在 home 里。

没按这个规矩写的插件——peer 写了插件以外的包、构建产物里留着没打包的库——装上以后运行时找不到依赖，加载失败，在 `list` 里显示为未加载。装了一个没有 `apply` 的包（比如一个库），条目照样加上、加载失败（日志 `invalid plugin, expect function or object with apply`），不要它就 `uninstall`。

## 卸载：先删条目、后卸包

`uninstall` 先删这个包在 `cordis.yml` 里的全部条目，再 `pnpm remove`，回执 `data` 是 `{ pkg }`。设置与数据留在磁盘上，重新装回来时默认 id 在条目树上空着，拿到的就还是它，接着用那一份（见[条目 id](/docs/plugin-manager/ids)）。内核包与 `cordis` 不许卸，直接报错：卸掉 home 就启动不了。没装的包也直接报错；只删一条条目、保留包，用 `remove-entry`。

反过来先卸包，条目会指向一个不在 home 里的包。先删条目，fiber 当场卸载，依赖它的插件也被 cordis 一起卸载，状态是干净的。pnpm 失败不回滚：`error` 说明条目已删几条、包还在，包会出现在「已装、没有条目」那一组里，要用再加条目。

<Diagram name="pm-uninstall" title="卸载：先删全部条目，再 pnpm remove；pnpm 失败不回滚">
- 第 1 步：逐条 `tree.remove`，写回 `cordis.yml` 并当场卸载；依赖它的插件被 cordis 一起卸载，停在未加载
- 第 2 步：经 `applyToHome` 运行 `pnpm remove`
- 成功：设置与数据留在磁盘上；失败：不回滚，包留在「已装、没有条目」那一组
- 反过来先卸包：条目会指向一个不在 home 里的包
</Diagram>
