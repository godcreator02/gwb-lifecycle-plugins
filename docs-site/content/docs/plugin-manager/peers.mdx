# peer 满没满足

**本页回答**：`list` 回执里的 `unmetPeers` 怎么算；「装着的版本」从哪读；为什么只报告、不拦加载；缺的 peer 为什么不会被自动装上。什么时候该写 peer、怎么写是写插件的规矩，见[用到的插件写 peer](/docs/rules/plugin-peers)。

## list 回执里的 unmetPeers

插件包在 `peerDependencies` 里写它用到的别的插件，范围 `^x.y.z`，意思是运行时 home 里那个插件装的版本在这个范围里；只是可选使用的在 `peerDependenciesMeta` 标 `optional: true`。`list` 回执里每个包都带 `unmetPeers`，每条是 `{ pkg, range, installed? }`：

- 只看插件（`keywords` 含 `gwb-plugin`）peer 里 `cordis` 以外的包；`cordis` 由插件管理在升内核时对齐（见[升内核](/docs/plugin-manager/kernel-upgrade)）
- 内核包 `@godcreator/gwb-kernel-desktop`：对照正在运行的内核，范围不包含就列进来，`installed` 是运行中的内核版本（见[内核兼容性](/docs/plugin-manager/kernel-compat)）；peer 里没写内核包就不列这一项
- 别的包没装：列进来，没有 `installed` 字段；optional 的没装不算
- 装着但版本不在范围里：列进来，带 `installed`；optional 的也一样
- 范围不是 `^x.y.z`：`range` 原样照抄，算没满足
- 不是插件的包、清单读不到的包、全都满足时是空数组

内核包与别的包用同一个比法 `caretRangeCovers`（内核包经 `kernelRangeCovers`，运行中的内核版本号不合法就报错）：主版本号为 0 时次版本号相同，≥1 时主版本号相同，并且不低于 x.y.z；只比 x.y.z 三段，装的是同一条线上的开发版也算在范围里。

**装着的版本从哪读**：home 的 `node_modules/<包名>/package.json` 在就算装了，版本取它的 `version`。`list` 本来就读 home 的 dependencies 与条目里每个包的清单；插件 peer 里点名了别的包时再补读一次，内核包不读。不合包名规则的键（比如 `../escape`）不拿去拼路径，按没装报。

## 只报告，不拦加载

`unmetPeers` 不空的插件照常加载、照常能装能升，插件管理不拦它，也不替它装或升级它 peer 里的插件。版本不够新多半只是某处样式或某个新功能不对，整个插件拦下来反而没法用；必需的服务真没装，cordis 本来就让插件停在等待状态。pnpm 自己对不满足的 peer 也只是警告，照样把写 peer 的插件链到 home 里装着的那一版。看到报告，升级或安装那个插件就解决了；要保证发出去的 peer 写得对，在发版时由 `devkit.release` 检查（见接缝页 [peer 里的内核包与插件](/docs/seams/kernel-peer)）。

## 缺的 peer 不会被自动装上

插件管理启动 pnpm 时带环境变量 `pnpm_config_auto_install_peers=false`，`install` 与 `update` 都不会把插件 peer 里 home 没装的插件顺带装进来（见 [pnpm](/docs/plugin-manager/pnpm#参数环境与读回什么)）。pnpm 默认会把缺的 peer 装进 `node_modules/.pnpm`，但不写进 home 的 `package.json`、不加条目，插件管理也不认它，成了一个谁也管不到的包。装哪个插件由人决定，缺的由 `unmetPeers` 报出来。

在隔离 home 里实测过：node 命令行插件从 0.4.6 升到 0.4.7，peer 写了它的 devkit 列在 `update` 回执的 `dependents` 里、换到新的真实目录重新加载；0.4.6 的 peer 写着 home 里没装的 `@godcreator/gwb-plugin-api`，pnpm 没有自动补装，`list` 的 `unmetPeers` 报出了它（轨迹卡[自动补装 peer 只在 home 里关](/trajectory/2026-09-25-auto-install-peers-home-only)）。
