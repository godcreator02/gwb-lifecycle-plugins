# 重新加载一条条目

**本页回答**：重新加载一条条目按什么顺序做、为什么要等旧的卸载完；为什么要用 `remount` 一条命令，而不是 `disable` 加 `enable`；目标是插件管理自己时怎么办。热升级重新加载每条条目用的也是这一套。

## 停用 → 等旧的卸载完 → 启用

**是什么**：重新加载一条条目 = 停用 → 等旧实例卸载完 → 启用 → 等新实例加载完，返回新实例的状态。启用时 loader 重新 import 包名，内核按真实路径解析——包换了版本，路径就换了，拿到的就是新版本；条目在 `cordis.yml` 里的位置与 id 都不变。原本停用的条目，重新加载后是启用的。

**为什么要等**：loader 停用条目时调 `fiber.dispose()` 但不等它结束，而插件提供的服务是在卸载过程中才撤销的。停用后马上启用，新实例启动时旧实例的服务可能还在，cordis 报「service has been registered」：

<Diagram name="pm-remount" title="停用后马上启用会遇到还没撤销的旧服务；等旧的卸载完再启用就正常">
- 上：停用后马上启用。旧实例还在卸载、服务还没撤销，新实例启动时提供同名服务，cordis 报 service has been registered
- 下：等旧实例卸载完再启用。新实例启动时同名服务已经撤销，正常加载到 `ACTIVE`
</Diagram>

**怎么做**：每一步用 cordis 的 `fiber.await()` 等它把手头的事做完，最多等 5 秒，超时就继续，读到什么状态报什么（`ACTIVE` 才算加载成功）。修改条目树时抛错，回执的 `action` 是 `failed`，`state` 里是那句错误。

## 用 remount 一条命令，不用 disable 加 enable 两条

**是什么**：要让一条条目重新 import（比如装了新版本之后），调 `remount`，停用与启用在这一条命令里做完。`devkit.dev` 装完开发版就是这样重新加载目标 home 里的条目的（见[改一版看一版](/docs/devkit/dev)）。

**为什么**：停用和启用之间不能隔着第二条命令。被停用的插件可能正是调用方发命令要经过的那一个：目标是命令插件时，`disable` 一返回命令表就没了，`enable` 调不进去；目标是 MCP 入口（`gwb-mcp`）时，连接就断了。`remount` 在插件管理自己的 `await` 链里做完两步，这条链只持有条目树与 logger，不经任何 ctx；被重新加载的条目卸载时连带卸掉谁，都不影响它把启用做完。

<Note>
**别用 disable 加 enable 两条命令代替重新加载**：目标是调用方发命令要经过的插件时，条目会停在停用状态，调用方没法再发命令把它启用回来，只能换一条调用途径（比如插件管理窗格）或手工改 `cordis.yml` 再重启。
</Note>

## 目标是插件管理自己：先回执、后重新加载

**是什么**：`remount` 的目标是插件管理自己那条条目时，回执的 `action` 是 `deferred`，`state` 是动手前的状态；回执发出后，下一个宏任务才重新加载。不会有第二份回执，调用方之后用 `plugin-manager.list` 核对 `active`。

**为什么**：在命令处理函数里停用自己，这条 `await` 链随插件管理的实例一起卸载，回执永远到不了调用方。所以先回执，再动手。

**怎么做**：排到下一个宏任务的那段代码只持有条目树、id 与事先拿到的 logger——那时插件管理原来的实例已经卸载，ctx 上的东西都不能用。`devkit.dev` 重新加载插件管理时收到 `deferred`，就轮询 `plugin-manager.list` 等它回来，带超时。
