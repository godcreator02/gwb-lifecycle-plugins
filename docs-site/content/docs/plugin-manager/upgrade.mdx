# 热升级

**本页回答**：怎么查出哪些包有新版本；`update` 的三种参数各做什么；为什么升级与重新加载必须在同一条命令里；升级计划按什么排；为什么真实目录变了的别的包（多半是 peer 写了被升级包的插件）也要一起重新加载、怎么找出它们；一次热升级从头到尾依次发生什么、整页重新加载由谁做；内核包为什么不热升级、`specs` 里有内核包时做了什么。重新加载一条条目的时序在[重新加载一条条目](/docs/plugin-manager/remount)。

热升级管 home 里除内核包与 `cordis` 之外的全部包，插件管理自己和命令插件也在其中：它们各是 `cordis.yml` 里的一条条目，和别的插件一样升级。

## 查新版本

**是什么**：`outdated` 运行一次 `pnpm outdated --json`，回执 `data.updates` 是「包名 → `{ current, latest }`」，空对象表示全都最新。内核包与 `cordis` 从结果里拿掉：热升级换不掉它们（见[升内核](#升内核)），列出来只会让界面上「全部更新」的数字里多出两个永远升不掉的包。

**怎么做**：退出码 1 表示「有过期包」，是结果不是失败；找不到 pnpm、输出解析不了都转成 `ok: false` 的回执，界面上只显示一句提示。它不写文件，不经过 BUSY 检查，和正在运行的安装、升级同时运行也不影响它们（见[包：只经 applyToHome](/docs/plugin-manager/home#包只经-applytohome)）。

## 三种参数

**是什么**：`update` 的参数三选一、恰好给一个。不给参数、给了空对象、三种里给了两种、有认不出的键，都直接报错，报错里带着三种写法；要升全部就给 `{"all":true}`。

| 参数 | 装什么 | 查不查 `outdated` |
| --- | --- | --- |
| `{ "all": true }` | `outdated` 查到的全部过期包，各升到它查到的精确版本 | 查 |
| `{ "only": ["<包名>", …] }` | 只升点名的几个过期包；名字不在 home 的 dependencies 里、是内核包或 `cordis` 直接报错，已是最新的写进 `note` | 查 |
| `{ "specs": { "<包名>": "<写法>" } }` | 给已装的包按给定写法装：版本号、tag 或 `file:<绝对路径>`，每项 `<包名>@<写法>` 原样交给同一次 `pnpm add`；包不在 home 的 dependencies 里直接报错（首次安装用 `install`）；内核包也写在这里，`cordis` 不许写（见[升内核](#升内核)） | 不查 |

**为什么全部升级要显式给**：一条改 home 的命令，不给参数时不能执行影响最大的那个动作：漏写参数就整个 home 一起升级、当场生效（见[轨迹卡](/trajectory/2026-09-25-update-takes-all-param)）。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="781-810" */}

**一律写精确版本号、`specs` 装完核对**：三种参数的 `pnpm add` 都带 `--save-exact`，home 的 `package.json` 里写精确版本号，下次重装不会解析到范围里的别的版本（为什么一律写精确版本号见[轨迹卡](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)）。pnpm 退出码 0 不等于装上了要的版本：清单里原来写成 `^` 时，pnpm 12 沿用 `^`，锁文件里范围内的别的预发布版照样算满足（devkit 仓 `probes/2609241510_pnpm-add-exact-prefix/`）。所以 `specs` 装完读 `node_modules/<包名>/package.json`：写法是准确版本号（`x.y.z`，可带预发布段）的，装上的 `version` 必须就是它，对不上回 `ok: false`，`error` 逐项写要的与装上的版本号，一条条目都不重新加载；tag 与 `file:` 写法看不出该是哪一版，不核对。读不到某个包的版本号也回 `ok: false`。

**`specs` 的回执**：`updated` 每项的 `from` 是装之前 `node_modules/<包名>/package.json` 里的 `version`（读不到就没有这个字段），`to` 是装完读到的 `version`，不是写法原文。

## 升级与重新加载在同一条命令里

**是什么**：`update` 一条命令做完：一次 `pnpm add` 把包装到计划的版本 → 逐条重新加载（装之前与装之后真实目录变了的别的包也在其中）。三种参数装完都走这同一套，`specs` 里有内核包时除外；没有「只升包、不重新加载」的命令。

**为什么**：升完不重新加载，运行着的还是旧版本的代码，等于没升。旧版本目录也不会一直留着：home 里没有 `pnpm-workspace.yaml`（default 就没有）时用 pnpm 的默认值，旧目录保留约 7 天（pnpm 文档写 `modulesCacheMaxAge` 默认 10080 分钟）后清掉。升级与重新加载分成两条命令，中间运行的一直是旧版，隔得久了目录被清掉，旧版再读自己的文件就读不到：

<Diagram name="pm-upgrade-gap" title="分两条命令时，升完到重新加载之间运行的仍是旧版">
- 分两条命令：`pnpm add` 装上 A@1.1，到另一条命令停用再启用之前，运行的仍是旧版 A；A@1.0 的目录约 7 天后被清掉，那之后旧版 A 读自己的文件就读不到
- 同一条命令：`pnpm add` 一结束马上停用再启用，运行的就是新版，也不再依赖旧目录
</Diagram>

**例外**：命令本该保持原子、一条只做一件事，多步流程写进说明书由调用方一步步调。`update` 是允许的例外：升完不重新加载就等于没升，拆开只多出上图那段运行旧版的空档。`pnpm add` 失败时一条条目都不动。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="524-558" */}

这一条只能实机验证：在隔离 home 里先装某个包的旧版本，再调 `plugin-manager.update {"all":true}`，看条目回到 `ACTIVE`、`list` 里是新版本。

## 升级计划

**是什么**：装哪些包、它们的哪些条目要重新加载、按什么顺序，由纯函数在 `pnpm add` 之前算出，单独测：`all` 与 `only` 按 `outdated` 的结果算，`specs` 按给定的写法算。跟着重新加载的别的包要装完才知道，不在计划里，见下一节。

{/* ref file="../plugins/plugin-manager/src/update.ts" lines="38-54" */}

- **精确版本**：`all` 与 `only` 用 `outdated` 查到的版本号，不用 `@latest` 标签——两次查询之间又发了一版，也不会装成回执上没写的那个；`specs` 的写法原样交给 pnpm
- **每条条目各自重新加载**：被别的插件 inject 的插件重新加载时，cordis 会把依赖它的插件停用再启动，但那是重新运行内存里的旧代码，磁盘上的新版本没有加载，所以不能指望这种连带
- 包按包名排，包内的条目按条目树里的先后；本来就停用的条目保持停用，记为 `skipped`
- **跟着重新加载的包排在升级的包之后**：装之前与装之后真实目录变了的别的包，按包名排，理由与找法见下一节
- **插件管理自己那条标 `self`**：它照包名、照树里的先后排，不挪位置；执行到它时只记 `deferred`、跳过，回执发出之后才重新加载（见下面「插件管理自己在回执之后」），排在哪都一样
- 给了 `only` 就只升点名的几个；名字不在 home 的 `package.json` 的 dependencies 里（多半拼错）直接报错、说出是哪个，一次 pnpm 都不运行；在 home 里但已是最新的，回执的 `note` 里列出来
- **`all` 与 `only` 不升内核包与 `cordis`**：`outdated` 本来就不含它们；`only` 点了它们的名直接报错，指向 `specs` 写法，一次 pnpm 都不运行。理由见下面[升内核](#升内核)
- **`specs` 的包必须已装**：键不在 home 的 dependencies 里直接报错，一次 pnpm 都不运行；写了 `cordis` 也直接报错

## 真实目录变了的包一起重新加载

**是什么**：`pnpm add` 之前与之后各读一次 home 的 `package.json` 的 dependencies 里每个包的真实目录（`node_modules/<包名>` 这个目录链接指向的、pnpm 虚拟存储里的目录），目录变了、本身又没升级的包，它的条目在同一条命令里跟着重新加载。一次读得到、一次读不到，也算变了。回执的 `dependents` 按包名列出这些包，每个带各条条目的结果；原本停用的条目照样 `skipped`，插件管理自己在里面时照旧记 `deferred`、回执之后才重新加载，回执 `selfDeferred` 是 `true`。

**为什么**：pnpm 的虚拟存储目录名带着 peer 的版本，A 的 peer 写了 B，B 一升级，A 就被装进新目录（`A@1.0.0_B@1.0.0` 变成 `A@1.0.0_B@1.1.0`），而 pnpm 的输出里只写 B 变了。只重新加载 B 的话，正在运行的 A 还是从旧目录加载的、拿到的还是旧的 B；旧目录被清掉之后 A 再加载自己的文件就会失败（实验见 devkit 仓 `probes/2609242300_peer-between-plugins/`）。哪些包换了目录，直接比装之前与装之后的真实目录，不按 peer 关系去推 pnpm 的目录命名规则：peer 写了 A 的 C 会不会跟着换目录、不是插件的包换没换，都照实看得到（为什么这样找见[跟着重新加载的包改成直接比真实目录](/trajectory/2026-09-25-dependents-by-realpath)）。

**怎么做**：读真实目录是读盘，在入口文件里做；比两次读到的目录、挑出要重新加载的包是纯函数，单独测。不合包名规则的键不拿去拼路径。

## 一次热升级依次发生什么

<Diagram name="pm-upgrade" title="一次热升级的时间线：每一行是一个参与方，竖虚线是回执发出的时刻">
- 调用方调用 `update`；插件管理查过期包（给 `specs` 时不查），定计划，记下装之前每个包的真实目录
- 插件管理一次 `pnpm add` 精确版本；磁盘上 A@1.1 装上，peer 写了 A 的 B 也换进新目录；再读一次真实目录，B 变了，跟着重新加载
- 条目 A 停用再启用，重新解析拿到 A@1.1，回到 `ACTIVE`；接着条目 B 同样停用再启用
- 回执发出，调用方收到 `selfDeferred: true`
- 下一个宏任务里重新加载插件管理自己，拿到新版本
- 调用方拿到回执后自己调外壳的 `shell.reload` 整页重新加载，窗格拿到新版本的页面代码
</Diagram>

**插件管理自己在回执之后**：升级的包或跟着重新加载的包里有插件管理自己时，它那条条目在回执发出之后才重新加载，回执里 `selfDeferred` 是 `true`，它的条目 `action` 是 `deferred`。理由与[重新加载插件管理自己](/docs/plugin-manager/remount#目标是插件管理自己先回执后重新加载)相同。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="555-557" */}

{/* has file="../plugins/plugin-manager/tests/commands.test.ts" text="升级清单里有插件管理自己：自己那条先回 deferred，回执之后才重新加载，之后不整页重新加载" */}

**整页重新加载由调用方做**：插件管理不调外壳的 `shell.reload`，回执里也没有和它有关的字段。`shell.reload` 在主进程里同步重载页面，经页面调用这条命令的调用方（插件管理窗格、经 CDP 在目标页面里调命令的 devkit）回执还没送回页面，页面就开始重载了，会收不到回执；插件管理替调用方决定什么时候刷新，还会和调用方自己的刷新抢先后。所以升级完要换界面代码的，由调用方拿到成功回执后自己调 `shell.reload`：插件管理窗格点「全部更新」后自己调；`devkit.dev` 本来就自己刷新目标页面；agent 经 MCP 升级完调一次（为什么交给调用方见[轨迹卡](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)）。

{/* has file="../plugins/plugin-manager/tests/commands.test.ts" text="升一个包：一次 pnpm add --save-exact 精确版本，它的条目在这条命令里重新加载，停用的跳过；不整页重新加载" */}

**升到 MCP 入口自己**：`gwb-mcp` 重新加载时，进行中的 MCP 请求会中断，agent 要重连一次，再用 `plugin-manager.list` 核对版本与 `active`。

## 升内核

**是什么**：内核包 `@godcreator/gwb-kernel-desktop` 也经 `update` 的 `specs` 换，升到最新写 `{"specs":{"@godcreator/gwb-kernel-desktop":"latest"}}`，也可以给版本号或 `file:<绝对路径>`，还可以连同别的包一起写。`specs` 里有内核包时插件管理运行两次 pnpm：先一次 `pnpm add` 装上 `specs` 里的全部包（照上面[三种参数](#三种参数)核对准确版本号），再读 home 里内核包的 `package.json`，取它 `peerDependencies.cordis` 写的精确版本号，`pnpm add cordis@<那个版本>`，装完读回核对 `cordis` 装上的就是它。不重新加载任何条目，`updated` 每项的 `entries` 是空数组，末尾多一项插件管理自己对齐的 `cordis`。回执另带两个字段：`restartRequired`，装上的内核版本和正在运行的不同时是 `true`，`note` 说重启工作台后才生效、重启由人决定；`pluginsOutsideRange`，见下面。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="472-512" */}

**为什么合成一条**：devkit 开发内核时要把内核开发版与插件开发版一次装完再重启那个 home；升内核另有一条命令的话，两条命令先后怎么排都不对，所以只留 `specs` 这一条路（见[轨迹卡](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)）。

**为什么不热升级**：内核在主进程里运行，停用再启用条目换不掉它；home 根上的 `cordis` 是内核与所有插件共用的那一份，内核与插件都已经 import 了它，换了也要重启才生效。所以 `outdated` 与 `list` 都不列这两个包，`update` 的 `only` 点了它们直接报错，`uninstall` 也不许卸它们（卸掉 home 就启动不了），什么时候重启由人决定。

**为什么 `cordis` 由插件管理对齐**：内核包把 `cordis` 写成 peer，pnpm 把它解析到 home 根上的那一份；home 根上的版本和内核包要的不同，内核就运行在它没验过的 `cordis` 上。该装哪个版本只有装上的内核包自己知道（`latest` 与 `file:` 写法事先看不出），所以 `specs` 里不许写 `cordis`，写了直接报错；内核包 peer 里的 `cordis` 必须是精确版本号，写成范围就说不清 home 根上该装哪一个，这时不装 `cordis`、回 `ok: false`。

**失败时**：第一次 `pnpm add` 失败，什么都没改；装上的内核包不是 `specs` 里写的准确版本号，`cordis` 不动。内核包装上了、而 peer 里的 `cordis` 不是精确版本号、装 `cordis` 失败、或装上的 `cordis` 不是要的版本，回执 `ok: false`，`data.kernel` 是已经装上的内核版本（`{ from?, to }`），`error` 说明 `cordis` 没对齐、先别重启——这时重启，新内核会运行在没对齐的 `cordis` 上。

**范围不包含新内核的插件**：回执的 `pluginsOutsideRange` 列出 home 里 `keywords` 含 `gwb-plugin`、peer 里内核包的范围不包含新内核（或没写范围）的插件，按包名排。直接用 `list` 算 `kernelUntested` 的那个函数判断（见[内核兼容性](/docs/plugin-manager/kernel-compat)），同样只报告：重启后它们照常加载，要不要先升它们由人决定。
