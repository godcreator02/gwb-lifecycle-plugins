# 热升级

**本页回答**：怎么查出哪些包有新版本；`update` 的三种参数各做什么、`specs` 装完怎么核对；为什么升级与重新加载必须在同一条命令里；装之前定什么、装之后怎么定下要重新加载的包（真实目录变了的都重新加载，没点名的包为什么也会变）；这些包按什么先后重新加载、peer 成环时怎么办；一次热升级从头到尾依次发生什么、整页重新加载由谁做。`specs` 里有内核包时走另一套，见[升内核](/docs/plugin-manager/kernel-upgrade)；重新加载一条条目的时序见[重新加载条目](/docs/plugin-manager/remount)。

热升级管 home 里除内核包与 `cordis` 之外的全部包，插件管理自己和命令插件也在其中：它们各是一条条目，和别的插件一样升级。

## 查新版本

`outdated` 运行一次 `pnpm outdated --json`，回执 `data.updates` 是「包名 → `{ current, latest }`」，空对象表示全都最新。内核包与 `cordis` 从结果里拿掉：热升级换不掉它们，列出来只会让界面上「全部更新」的数字里多出两个永远升不掉的包。

退出码 1 表示「有过期包」，是结果不是失败；找不到 pnpm、别的退出码、输出解析不了，都回 `ok: false`。它不写文件，不经过 BUSY 检查（见[同一时刻只允许一个改动](/docs/plugin-manager/busy)）。

## 三种参数

`update` 的参数三选一、恰好给一个。不给参数、给了空对象、三种里给了两种、有认不出的键、值的类型不对，都直接报错，报错里带着三种写法。

| 参数 | 装什么 | 查不查 `outdated` |
| --- | --- | --- |
| `{ "all": true }` | `outdated` 查到的全部过期包，各升到它查到的精确版本 | 查 |
| `{ "only": ["<包名>", …] }` | 只升点名的几个过期包；名字不在 home 的 dependencies 里、是内核包或 `cordis` 直接报错，已是最新的写进 `note` | 查 |
| `{ "specs": { "<包名>": "<写法>" } }` | 给已装的包按给定写法装：版本号、tag 或 `file:<绝对路径>`，原样交给 pnpm；包不在 home 的 dependencies 里直接报错（首次安装用 `install`）；内核包也写在这里，`cordis` 不许写 | 不查 |

全部升级要显式给 `{"all":true}`：一条改 home 的命令，不给参数时不能执行影响最大的那个动作，漏写参数就整个 home 一起升级、当场生效（见轨迹卡 [update 显式 all 加 specs](/trajectory/2026-09-25-update-takes-all-param)）。

## specs 装完核对版本号

三种参数的 `pnpm add` 都照 pnpm 默认在清单里写 `^` 范围（为什么见 [home 与条目](/docs/plugin-manager/home)）。pnpm 退出码 0 不等于装上了要的版本：清单里那一项写成 `^` 时，pnpm 12 沿用 `^`，按点名的更旧版本装会留着范围里更新的那个，范围里的预发布版也照样算满足（本仓 `probes/2609241510_pnpm-add-exact-prefix/`）。所以 `specs` 在 `pnpm add` 前后各读一次 `node_modules/<包名>/package.json` 的 `version`：

- 写法是准确版本号（`x.y.z`，可带预发布段）的，装上的必须就是它；对不上回 `ok: false`，`error` 逐项写要的与装上的，并指出把清单那一项改成精确版本号，一条条目都不重新加载
- tag 与 `file:` 写法看不出该是哪一版，不核对
- 装完读不到某个包的版本号，也回 `ok: false`
- 回执 `updated` 每项的 `from` 是装之前读到的版本（读不到就没有这个字段），`to` 是装完读到的版本，不是写法原文

`all` 与 `only` 装的是 `outdated` 查到的最新版，范围里没有比它更新的，不再核对。往回退版本不支持：`specs` 点名更旧的版本会在核对时回 `ok: false`，升坏了就发一个修好的新版。

## 升级与重新加载在同一条命令里

`update` 一条命令做完：一次 `pnpm add` 把包装到定好的版本 → 真实目录变了的包按 peer 排的先后逐条重新加载。三种参数装完都走这同一套（`specs` 里有内核包时除外）；没有「只升包、不重新加载」的命令。`pnpm add` 失败时一条条目都不动。

升完不重新加载，运行着的还是旧版本的代码，等于没升。旧版本目录也不会一直留着：home 里没有 `pnpm-workspace.yaml`（default 就没有）时用 pnpm 的默认值，旧目录保留约 7 天（pnpm 文档写 `modulesCacheMaxAge` 默认 10080 分钟）后清掉。升级与重新加载分成两条命令，中间运行的一直是旧版，隔得久了目录被清掉，旧版再读自己的文件就读不到：

## 装之前：装什么

`pnpm add` 之前只定装哪些包、装成什么写法，回执里每个包的 `from` / `to` 也在这时定下（`specs` 的要装完读清单）。由纯函数算出，单独测：`all` 与 `only` 按 `outdated` 的结果算，`specs` 按给定的写法算。哪些条目要重新加载要装完才知道，见下一节。

{/* ref file="../plugins/plugin-manager/src/update.ts" lines="36-52" hash="a3936156f741" blob="0faf236053dc" */}

- **精确版本**：`all` 与 `only` 用 `outdated` 查到的版本号，不用 `@latest` 标签——两次查询之间又发了一版，也不会装成回执上没写的那个；`specs` 的写法原样交给 pnpm，只拦空白与以 `-` 开头的写法
- **`only`**：名字不在 home 的 dependencies 里（多半拼错）直接报错、说出是哪个；在 home 里但已是最新的写进 `note`
- **内核包与 `cordis`**：`outdated` 本来就不含它们；`only` 点了它们直接报错，指向 `specs` 写法；`specs` 的键不在 home 的 dependencies 里、或写了 `cordis`，直接报错。报错都在一次 pnpm 都没运行之前

## 装之后：真实目录变了的包都重新加载

`pnpm add` 之前与之后各读一次 home 的 dependencies 里每个包的真实目录（`node_modules/<包名>` 这个目录链接指向的、pnpm 虚拟存储里的目录）。**目录变了的包都在同一条命令里重新加载，没变的不动**；一次读得到、一次读不到也算变了。点了名的包（升级的、`specs` 装的）也只按这一条判断：虚拟存储的目录名带着版本号，升级一定换目录；装的就是原来那一版时目录不变，它的条目也就不动。

回执里点了名的包归 `updated`（目录没变的也列出，`entries` 为空），没点名、目录变了的归 `dependents`，每个带各条条目的结果。两组合在一起排重新加载的先后（下一节），组内也照这个先后列。

- **每条条目各自重新加载**：被别的插件 inject 的插件重新加载时，cordis 会把依赖它的插件停用再启动，但那是重新运行内存里的旧代码，磁盘上的新版本没有加载，所以不能指望这种连带
- **包内的条目**按条目树里的先后；本来就停用的条目保持停用，记为 `skipped`
- **插件管理自己那条标 `self`**：它所在的包排进回执之后那一段，见下一节

没点名的包为什么也会换目录：pnpm 的虚拟存储目录名还带着 peer 的版本：A 的 peer 写了 B，B 一升级，A 就被装进新目录（`A@1.0.0_B@1.0.0` 变成 `A@1.0.0_B@1.1.0`），而 pnpm 的输出里只写 B 变了。只重新加载 B 的话，正在运行的 A 还是从旧目录加载的、拿到的还是旧的 B；旧目录被清掉之后 A 再加载自己的文件就会失败（实验见本仓 `probes/2609242300_peer-between-plugins/`）。哪些包换了目录，直接比装之前与装之后的真实目录，不按 peer 关系去推 pnpm 的目录命名规则（见轨迹卡[跟着重新加载的包改成直接比真实目录](/trajectory/2026-09-25-dependents-by-realpath)）。

读真实目录要读磁盘，在 `index.ts` 里做；比两次读到的目录、定下要重新加载的包是纯函数。不合包名规则的键不拿去拼路径。

## 重新加载的先后：被依赖的先

一个插件重新加载时，它 inject 的服务如果还是旧提供方给的，注入照样算满足，`apply` 照常执行；要用提供方新版才有的方法，就当场抛错、停在 `FAILED`。cordis 不会替失败的插件重来：提供方随后换了服务，这条失败的条目也不动，只有停用再启用才会重来。所以提供方必须先重新加载。

先后按 `pnpm add` 之后读到的每个包清单里的 `peerDependencies` 排，**只看这批要重新加载的包之间的 peer**：`updated` 与 `dependents` 合成一批，被依赖的先；前面的都排完之后同时可以重新加载的算一层，同一层按包名，结果只由包名与 peer 决定。依赖关系只认 peer：发版前检查要求「注入了谁就在 peer 写谁」；反方向用局部注入的不写 peer，也不需要排在提供方之后。

块笔记一次升级的那一批是个例子：点了名的 `bn-core`、`bn-comment`、`bn-query`、`bn-journal`，跟着换了目录的 `bn-props`、`bn-single`、`bn-papers`；评论、查询、日记、属性、单文件库的 peer 写了核心，论文库写了核心与属性。排出来是三层：核心；评论、日记、属性、查询、单文件库；论文库。按包名排的话评论排在核心前面，评论重新加载时拿到旧核心，调新方法抛错。

<Diagram name="pm-upgrade" title="一次热升级的时间线：每一行是一个参与方，竖虚线是回执发出的时刻">
- 调用方调用 `update`；插件管理查过期包（给 `specs` 时不查），定计划，记下装之前每个包的真实目录
- 插件管理一次 `pnpm add` 精确版本；磁盘上 A@1.1 装上，peer 写了 A 的 B 也换进新目录；再读一次真实目录，B 变了，跟着重新加载
- 按 peer 排先后：B 的 peer 写了 A，A 先；条目 A 停用再启用，重新解析拿到 A@1.1，回到 `ACTIVE`；接着条目 B 同样停用再启用
- 回执发出，调用方收到 `selfDeferred: true`；插件管理自己与 peer 了它的包的条目记 `deferred`
- 下一个宏任务里先重新加载插件管理自己，再依次重新加载 peer 了它的包
- 调用方拿到回执后自己调外壳的 `shell.reload` 整页重新加载，窗格拿到新版本的页面代码
</Diagram>

**插件管理自己在回执之后**：升级的包或跟着重新加载的包里有插件管理自己时，它那条条目与 peer 了它的包的条目在回执发出之后才重新加载，回执 `selfDeferred` 是 `true`，这些条目的 `action` 是 `deferred`。在命令里停用自己，回执就发不出去了，理由与做法见[重新加载条目](/docs/plugin-manager/remount#插件管理自己先回执后重新加载)；为什么这样排见轨迹卡[按 peer 排重新加载的先后](/trajectory/2026-09-30-remount-in-peer-order)。

**整页重新加载由调用方做**：插件管理不调外壳的 `shell.reload`。`shell.reload` 在主进程里同步重载页面，经页面调用这条命令的调用方（插件管理窗格、经 CDP 在目标页面里调命令的 devkit）回执还没送回页面，页面就开始重载了，会收不到回执；插件管理替调用方决定什么时候刷新，还会和调用方自己的刷新抢先后。所以要换界面代码的，由调用方拿到成功回执后自己调 `shell.reload`：插件管理窗格点「全部更新」后自己调，`devkit.dev` 本来就自己刷新目标页面，agent 经 MCP 升级完调一次（见轨迹卡[升内核并进 specs](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)）。

**升到 MCP 入口自己**：`gwb-mcp` 重新加载时，进行中的 MCP 请求会中断，agent 要重连一次，再用 `plugin-manager.list` 核对版本与 `active`。

这一整条只能实机验证：在隔离 home 里先装某个包的旧版本，再调 `plugin-manager.update {"all":true}`，看条目回到 `ACTIVE`、`list` 里是新版本。
