# 插件管理

**本页回答**：插件管理有哪些功能、别的模块怎么用它、它依赖什么、哪些事不归它管。包名 `@godcreator/gwb-plugin-manager`，源码目录 `plugins/plugin-manager/`，入口文件 `src/index.ts`。

插件管理是 home 里的一个普通插件：由 `cordis.yml` 里的一条条目加载，单独发版，和别的插件一样用 `plugin-manager.update-all` 升级。它和 devkit 放在同一个仓里开发，原因见轨迹卡[插件管理迁入 devkit 仓](/trajectory/2026-09-24-plugin-manager-joins-devkit)。

## 功能

它管 home 里的两层东西：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**。只装包、不加条目，插件不会运行。装之前先要知道配好的源上有什么可装、第三方 scope 从哪条源装，这也归它管。

- **列出 home 里的包与条目**：每个包下面是它的条目，带启停、是否在运行，见[home 的两层与唯一写入者](/docs/plugin-manager/home)
- **报告每个包兼容哪些内核**：`list` 的每个包带 `kernelRange`（包的 `peerDependencies` 里内核包 `@godcreator/gwb-kernel-desktop` 的范围）与 `kernelUntested`，只报告、不拦加载，见[内核兼容性](/docs/plugin-manager/kernel-compat)
- **报告每个包 peer 里的别的插件满没满足**：`list` 的每个包带 `unmetPeers`（没装、版本不在范围里的 peer），只报告、不拦加载，见[peer 满没满足](/docs/plugin-manager/peers)
- **装一个包并加一条条目**：一条命令做完，只等条目写入、不等它加载完，见[安装与卸载](/docs/plugin-manager/install)
- **卸载一个包**：先删它的全部条目、再卸包，数据与设置留在磁盘上，见[安装与卸载](/docs/plugin-manager/install#卸载先删条目后卸包)
- **加删条目、启用或停用一条条目**：条目只经 loader 的条目树改，见[home 的两层与唯一写入者](/docs/plugin-manager/home#条目只经-loader-的条目树)
- **重新加载一条条目**：停用 → 等旧的卸载完 → 启用，一条命令做完，见[重新加载一条条目](/docs/plugin-manager/remount)
- **查新版本、一键热升级**：升级与重新加载在同一条命令里，不重启；装之前与装之后真实目录变了的别的包（多半是 peer 写了被升级包的插件）一起重新加载；内核包与 `cordis` 不在其中，见[热升级](/docs/plugin-manager/upgrade)
- **升内核**：先装新的内核包，再把 home 根上的 `cordis` 对齐到内核包 peer 里写的版本；不重新加载任何条目，重启工作台后生效，见[升内核](/docs/plugin-manager/upgrade#升内核)
- **选条目 id**：沿用本包留在磁盘上的旧 id，避开别的包的数据与设置，见[id 与归属](/docs/plugin-manager/ids)
- **转归属**：插件改了包名时把一个 id 的数据与设置转给新包，见[id 与归属](/docs/plugin-manager/ids#转归属transfer-owner)
- **同一时刻只允许一个改动**：安装、卸载、热升级、升内核、重新加载重入时回 BUSY，所以同一个 home 里同一时刻最多一个写 home 的 pnpm，见[home 的两层与唯一写入者](/docs/plugin-manager/home#同一时刻只允许一个改动busy)
- **只用两个固定位置的 pnpm 12**：官方安装脚本的默认位置、npm 全局装的 pnpm 包，第一个存在的作数，核对版本；直接启动、不设超时，见 [pnpm](/docs/plugin-manager/pnpm)
- **找可装的插件**：在配好的每条 npm 源上检索，地址按 scope 从两份 npmrc 里找、和 pnpm 安装读同一批配置行；是不是插件只看包清单 `keywords` 里的 `gwb-plugin`，见[找插件与配包源](/docs/plugin-manager/sources)
- **配第三方包源**：往机器级 `~/.npmrc` 增删 scope 路由与凭据，`@godcreator` 不改不删，token 不进回执；这几条不改 home、不经 BUSY，见[找插件与配包源](/docs/plugin-manager/sources#包源只写机器级-npmrc)

## 接口

别的模块经下面这几样使用插件管理。

**16 条命令**：都登记在命令插件上，`plugin` 写包名。这是插件管理唯一的调用方式，页面、agent、别的插件调的是同一条命令。参数与回执见[对外只有命令](/docs/plugin-manager/commands)。

- `plugin-manager.list`：列出 home 里装了哪些包、各有哪些条目；每个包带 `kernelRange`（包的 `package.json` 里 `peerDependencies` 给内核包写的范围，没写时没有这个字段）与 `kernelUntested`（只标插件：范围不包含运行中的内核就是 `true`，没写、写的不是 `^x.y.z` 也算；库、第三方 cordis 插件、内核包与 `cordis` 一律 `false`），`unmetPeers`（插件 peer 里内核包与 `cordis` 以外、home 里没装或版本不在范围里的包，每条 `{ pkg, range, installed? }`，optional 的没装不算）
- `plugin-manager.install`：装一个包并加一条条目（经 BUSY 检查）
- `plugin-manager.uninstall`：先删一个包的全部条目，再卸包（经 BUSY 检查）
- `plugin-manager.add-entry`：给已装的包再加一条条目
- `plugin-manager.remove-entry`：删一条条目，不删包
- `plugin-manager.enable`：启用一条条目
- `plugin-manager.disable`：停用一条条目
- `plugin-manager.remount`：重新加载一条条目（经 BUSY 检查）
- `plugin-manager.outdated`：查已装的包哪些有新版本
- `plugin-manager.update-all`：一键热升级过期的包，不重启；装之前与装之后真实目录变了的别的包一起重新加载；内核包与 `cordis` 不升（经 BUSY 检查）
- `plugin-manager.update-kernel`：升内核包，再把 home 根上的 `cordis` 对齐到内核要的版本，重启工作台后生效，参数 `{ version? }`（经 BUSY 检查）
- `plugin-manager.transfer-owner`：把一个 id 的数据与设置的归属转给另一个包
- `plugin-manager.search`：在配好的 npm 源上检索插件，参数 `{ scope? }`，不给就查全部源
- `plugin-manager.source.add`：往机器级 `~/.npmrc` 写一条包源，参数 `{ scope, registry?, owner?, token? }`
- `plugin-manager.source.list`：列出机器级与 home 级两份 npmrc 里的包源
- `plugin-manager.source.remove`：从机器级 `~/.npmrc` 删一条包源

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 内核服务 `gwbKernel` 的 `dataDir` 与 `version` | home 目录（pnpm 的工作目录、`package.json` 所在的目录）；运行中的内核版本号，和各包 peer 里内核包的范围比对 | 构造时报错「ctx.gwbKernel 不在」，插件管理不加载；内核版本号不合法时 `list` 报错 |
| loader 的条目树：`store`、`create`、`update`、`remove`、`resolve` | 读条目、加删条目、启用停用、重新加载 | 构造时报错：取不到条目树（插件管理不是经 `cordis.yml` 的条目加载的），或条目树少了某个方法（loader 的接口变了），都说清是哪一种 |
| 用户装的 pnpm 12（`%LOCALAPPDATA%\pnpm\bin\pnpm.exe` 或 `%APPDATA%\npm\node_modules\pnpm\pnpm.exe`，版本不低于 12.4.2） | `add`、`remove`、`outdated --json` | 要运行 pnpm 的命令回 `ok: false`，原因里写明检查了哪两个位置、找到的版本不对时该装哪个版本；`list`、启停条目不受影响 |
| home 的 `package.json` | 装了哪些包、各自的版本范围 | 读不到或解析不了就当空表：`list` 里只有条目那一层 |
| home 的 `node_modules/<包名>` 这个目录链接指向的真实目录 | `update-all` 在 `pnpm add` 之前与之后各读一次，找出跟着换了目录的包 | 读不到当没装；在但读不了，`update-all` 报错并带上路径 |
| 装在 home 里的每个包自己的 `package.json` | 读 `peerDependencies` 与 `peerDependenciesMeta`：内核包的范围、peer 里别的插件的范围，以及那些插件装着的 `version`；`update-kernel` 另读新装的内核包的 `version` 与 `peerDependencies.cordis`、各插件的 `keywords` | 文件不在就当不是插件，`kernelUntested` 是 `false`；peer 里的包文件不在就算没装；文件在但读不了、或不是合法 JSON，`list` 与 `update-kernel` 报错并带上文件路径；内核包 peer 里的 `cordis` 不是精确版本号时 `update-kernel` 不装 `cordis`、回 `ok: false` |
| 命令插件 `gwbCommands`（`@godcreator/gwb-commands`，局部注入） | 登记 16 条命令；热升级后按名字查找并执行 `shell.reload`；`source.add` 的 `owner` 写法按名字调 `settings.get` | 命令登记不上，插件管理没有调用方式；服务照常提供 |
| 外壳插件的 `shell.reload` 命令（按命令名查找） | 热升级后整页重新加载 | `update-all` 的回执 `reload` 是 `unavailable`，界面要手动刷新 |
| 数据插件 `gwbData`（`@godcreator/gwb-data`，局部注入） | 读和转数据目录的归属记录 | 选 id 时看不到数据目录的归属；`transfer-owner` 回执里 `data` 是 `false` |
| 设置插件 `gwbSettings`（`@godcreator/gwb-settings`，局部注入） | 读和转设置分区的归属记录 | 选 id 时看不到设置的归属；`transfer-owner` 回执里 `settings` 是 `false` |
| 说明书插件 `gwbSkills`（`@godcreator/gwb-skills`，局部注入） | 登记自带的说明书 | 没有说明书，插件管理照常加载 |
| 各条 npm 源的检索接口 `GET <registry>/-/v1/search`（网络） | `search` 检索可装的插件 | 这条源在回执 `note` 里点名，别的源照常；全部没查成时 `search` 回 `ok: false` |
| 机器级 `~/.npmrc` 与 home 级 `<home>/.npmrc` | 按 scope 找源地址与 token；`source.add` / `source.remove` 改机器级那份 | 文件不在当空文本；在但读不了，命令报错并带上路径 |
| gitea 插件的设置：`gitea` 分区的 `base-url` 与 `token`，经设置插件的命令 `settings.get` 按名字读 | `source.add` 的 `owner` 写法拼源地址、取 token | 地址按代码里写的默认 gitea 实例拼；没显式给 token 时 `source.add` 回 `ok: false` |
| cordis：`provide`、`effect`、`inject`、`logger` 与条目的加载状态 | 提供服务、局部注入、卸载时撤销、写日志、判断条目加载到哪一步 | 由内核提供，不会缺；cordis 的状态名变了，`list` 的「是否在运行」与重新加载的等待会判断错，由状态名对照测试拦住 |
| 内核包 `@godcreator/gwb-kernel-desktop` 包根导出的类型（peer 里写的就是它） | `GwbContext`、`GwbResult`、`GwbKernelApi` 的类型 | 只有类型，形状改坏了类型检查失败 |

插件管理不写 `export const inject`：命令、数据、设置、说明书四个插件都用 `ctx.inject` 局部注入，缺了只少一部分功能，插件管理照常加载。这四个插件写在 peer 里，命令插件必需，另外三个标 `optional`（见[依赖怎么写](/docs/rules/deps#例子插件管理的清单)）；cordis、loader、include 写在 `devDependencies`；内核与这四个插件的类型都从 peer 里的包 `import type`，构建产物里没有它们的 import。

内核对插件管理的承诺——home 的文件布局、loader 与 include 的版本、按真实路径解析包名——写在内核仓文档站的接缝页「home 布局与条目树」。

## 不做的事

- **不写 home 级 `.npmrc`，不改不删 `@godcreator` 的路由**：home 级那份只放手工加的行；`@godcreator` 是本机所有安装与发版用的源
- **不看环境变量或 pnpm 全局配置里指定的源**：找源地址只读两份 npmrc
- **不画界面**：插件管理窗格在界面平台仓的 `gwb-baseui`，它经命令调用插件管理
- **不管插件之间的依赖齐不齐**：缺了的插件由 cordis 停在「等待缺少的服务」，`list` 里看得到它没在运行，它 peer 里没满足的插件列在 `unmetPeers`
- **不替插件装 peer、库**：插件自己把库打包进去；peer 只该是内核包、`cordis` 与别的插件，缺了的插件由人装，pnpm 的自动补装也关掉了，理由见[安装与卸载](/docs/plugin-manager/install#home-里只有插件内核包与-cordis)
- **不管条目加载成没成功**：条目由 loader 加载，成没成功看 `list` 的「是否在运行」，原因在 `gwb.log` 里
- **不删数据与设置**：卸载包、删条目都不动它们，内容归数据插件与设置插件管；插件管理只读、只转它们的归属记录
- **不拦范围不包含当前内核的插件**：`kernelUntested` 只报告；发版前拒绝 peer 里没写对内核包范围的插件是 `devkit.release` 的事
- **不重启工作台**：`update-kernel` 装完只在回执里说要重启，重启由人决定；主进程里的内核热替换不了
- **一键热升级不动内核包与 `cordis`**：它们的版本由内核决定，经 `update-kernel` 一起升
- **不拦 peer 没满足的插件，也不替它装或升级 peer 里的插件**：`unmetPeers` 只报告，装不装、升不升由人或 agent 决定；发版前拒绝 peer 没写对的包是 `devkit.release` 的事
- **不替人装 pnpm，也不找 PATH 上的 pnpm**：两个固定位置都没有、或版本不对，就报错说明该怎么装
- **不猜承载 `cordis.yml` 的条目叫什么**：条目树从自己那条条目的上一层取
