# 插件管理

**本页回答**：插件管理管什么、刻意不知道什么、对外提供哪些接口、依赖哪些接口、怎么单独测、代码从哪读起。每个机制的细节在同目录的子页，本页只指过去。

## 管什么

包名 `@godcreator/gwb-plugin-manager`，源码在 `plugins/plugin-manager/`。它是 home 里一条普通条目加载的插件，单独发版，和别的插件一样用 `plugin-manager.update` 升级；和 devkit 同仓开发的原因见轨迹卡[插件管理迁入 devkit 仓](/trajectory/2026-09-24-plugin-manager-joins-devkit)。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="46-49" */}

它是**唯一写 home 的插件**。home 里有两层：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**；插件管理让两层对得上，并如实报告对不上的地方。具体管这几件事：

- **列出包与条目**，并报告每个插件 peer 里内核包的范围包不包含运行中的内核、peer 里的别的插件满没满足：[home 的包与条目](/docs/plugin-manager/home)、[内核兼容性](/docs/plugin-manager/kernel-compat)、[peer 满没满足](/docs/plugin-manager/peers)
- **装包加条目、卸包删条目**：[安装与卸载](/docs/plugin-manager/install)
- **加删、启停、重新加载条目**：[home 的包与条目](/docs/plugin-manager/home)、[重新加载一条条目](/docs/plugin-manager/remount)
- **给条目选 id、转数据与设置的归属**：[id 与归属](/docs/plugin-manager/ids)
- **查新版本、热升级插件**：[热升级](/docs/plugin-manager/upgrade)
- **换内核包、把 `cordis` 对齐到内核包要的版本**：[升内核](/docs/plugin-manager/kernel-upgrade)
- **同一时刻只让一个改动写 home**：[同一时刻只允许一个改动](/docs/plugin-manager/busy)
- **找到并启动 pnpm**：[pnpm](/docs/plugin-manager/pnpm)
- **在配好的 npm 源上找插件、增删机器级 `~/.npmrc` 的包源**：[找插件与配包源](/docs/plugin-manager/sources)

## 不知道什么

**不知道谁在调它。** 插件管理窗格、经 MCP 入口的 agent、经 CDP 调命令的 `devkit.dev`，调的是同一条命令，插件管理对它们一视同仁；它也不知道 devkit 的 `dev-packs/` 目录，只照 `file:` 写法交给 pnpm。

**不知道条目为什么没加载成功。** 条目由 loader 加载，插件管理只读条目的 fiber 状态报 `active`，原因在 `gwb.log`。插件之间依赖齐不齐也不管：缺服务的插件由 cordis 停在等待，`list` 里看得到它没在运行。

**不替人决定装什么。** 插件 peer 里没装的插件、范围不包含运行中内核的插件，`list` 只报告（`unmetPeers`、`kernelUntested`），不拦加载、不替它装或升级；拒绝 peer 没写对的包是 `devkit.release` 在发版时的事。

**不知道数据与设置的内容。** 卸包、删条目都不动它们；插件管理只读、只转数据插件与设置插件记下的归属。

**不知道承载 `cordis.yml` 的条目叫什么。** 条目树从自己那条条目的上一层取。

**不知道机器上别的 pnpm。** 只认两个固定位置的 pnpm 12，不看 PATH、不读设置；插件管理进程外运行的 pnpm（`devkit.home.new`、人手工运行的）它管不到，也拦不住。

**不知道环境变量与 pnpm 全局配置里指定的源。** 找源地址只读两份 npmrc；它不写 home 级 `.npmrc`，也不改不删 `@godcreator` 那条路由。

**不画界面、不重启、不整页重新加载。** 插件管理窗格在界面平台仓的 `gwb-baseui`，经命令调用插件管理；换了内核包只在回执里说要重启，重启由人决定；界面要换成新代码，由调用方拿到回执后自己调 `shell.reload`。

## 提供的接口

### 15 条命令

插件管理对外**只有命令**，都登记在命令总线上，`plugin` 写包名。页面、agent、别的插件调的是同一批命令。每条命令的参数与回执写在它登记时的 `usage` 里，agent 经 MCP 入口的 `search` 读到的就是它；怎么组合着用见说明书 [gwb-plugin-manager](/outputs/skills/gwb-plugin-manager)。本页不复述参数，只列每条做什么、机制在哪页：

| 命令（前缀 `plugin-manager.`） | 做什么 | 机制 |
| --- | --- | --- |
| `list` | 列出包与条目，带内核兼容与 peer 报告 | [home 的包与条目](/docs/plugin-manager/home) |
| `install` / `uninstall` | 装一个还没装的包并加一条条目 / 删全部条目再卸包 | [安装与卸载](/docs/plugin-manager/install) |
| `add-entry` / `remove-entry` | 给已装的包加一条条目 / 删一条条目、留着包 | [home 的包与条目](/docs/plugin-manager/home)、[id 与归属](/docs/plugin-manager/ids) |
| `enable` / `disable` | 启用 / 停用一条条目 | [home 的包与条目](/docs/plugin-manager/home) |
| `remount` | 重新加载一条条目 | [重新加载一条条目](/docs/plugin-manager/remount) |
| `transfer-owner` | 把一个 id 的数据与设置转给另一个包 | [id 与归属](/docs/plugin-manager/ids) |
| `outdated` / `update` | 查新版本 / 升级已装的包（内核包也经 `update` 的 `specs`） | [热升级](/docs/plugin-manager/upgrade)、[升内核](/docs/plugin-manager/kernel-upgrade) |
| `search` | 在配好的全部源上找插件 | [找插件与配包源](/docs/plugin-manager/sources) |
| `source.add` / `source.list` / `source.remove` | 增、列、删包源 | [找插件与配包源](/docs/plugin-manager/sources) |

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="54-68" */}

**回执只有一层 `ok`。** 成功时 `data` 是结果本身，里面没有第二层 `ok`；执行中的失败（找不到 pnpm、pnpm 失败、条目写不进去）回 `{ ok: false, error }`，pnpm 输出的最后几行拼在 `error` 末尾。失败时还要带结构化字段的只有两处：`remount` 失败带 `data: { id, action: "failed", state }`，`update` 装上了内核包而 `cordis` 没对齐时带 `data: { kernel }`（见[升内核](/docs/plugin-manager/kernel-upgrade)）。为什么只留一层见轨迹卡[升内核并进 specs](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)。

### 服务 `gwbPluginManager`

值是空对象，只表示「插件管理装着」：别的插件 inject 它，只为跟着插件管理一起加载、卸载（插件管理窗格就这样用它）。有没有破坏性变化看插件管理的版本号，服务上不放版本数字。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="74-80" */}

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="128-135" */}

同一件事如果既能调命令、又能调服务方法，两种调用方式会慢慢变得不一致，而 BUSY 检查只加在命令上，服务方法会绕过去。所以要加能力就加一条命令，不往服务上加方法。只表示存在的服务用 `ctx.provide` 提供普通对象，不继承 cordis 的 `Service` 类，插件管理因此在运行时不 import `cordis`。

### 主入口给 devkit 的导出

包主入口除了插件本身（`name`、`apply`），只导出 devkit 复用的几样：找 pnpm 的 `locatePnpm`、内核包名 `KERNEL_PACKAGE`、peer 范围的判定 `isCaretRange` 与 `kernelRangeCovers`、取输出最后几行的 `tailLines`，以及 `devkit.dev` 调的三条命令名。devkit 在 peer 里写了插件管理，直接 import 这几样，规则只有这一份；回执类型不导出，调用方照命令的 `usage` 读回执。

### 什么算破坏性变更

命令名、参数、回执形状，服务的值，主入口导出的名字、签名或 devkit 依赖的行为，这几样改了、删了都是破坏性变更，升 0.x 的 x、发之前通知下游；加命令、加可选参数、回执加字段、修 bug 升 y。怎么升、怎么通知照说明书 [gwb-release](/outputs/skills/gwb-release)，发版用 `devkit.release`，`packages` 给 `plugins/plugin-manager`。

## 依赖的接口

插件管理不写 `export const inject`：命令、数据、设置、说明书四个插件都用 `ctx.inject` 局部注入，缺了只少一部分功能，插件管理照常加载。依赖字段怎么写见[依赖怎么写](/docs/rules/deps#例子插件管理的清单)：

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| 内核服务 `gwbKernel` 的 `dataDir` 与 `version` | home 目录（pnpm 的工作目录）；运行中的内核版本号，和 peer 里内核包的范围比 | 内核 | 假 ctx 给临时目录与一个版本号 |
| loader 的条目树：`store`、`create`、`update`、`remove` | 读条目、加删条目、启停、重新加载 | `@cordisjs/plugin-loader`，从 `ctx.fiber.entry.parent.tree` 取 | 假条目树；`tests/loader.test.ts` 用真 loader |
| cordis 条目的 fiber：`state` 与 `await()` | 判断 `active`，重新加载时等卸载、加载做完 | cordis | 假 fiber；`tests/fiber-state.test.ts` 核对状态名 |
| 命令总线 `gwbCommands`：`register`、`run` | 登记 15 条命令；`source.add` 的 `owner` 写法按名字调 `settings.get` | `@godcreator/gwb-commands` | 假命令总线，按名字调登记下来的处理函数 |
| 数据插件 `gwbData`、设置插件 `gwbSettings`：`owners`、`transferOwner` | 选 id 时避开别的包的数据与设置；转归属 | `@godcreator/gwb-data`、`@godcreator/gwb-settings` | 假归属记录 |
| 说明书插件 `gwbSkills`：`register` | 登记自带的说明书 | `@godcreator/gwb-skills` | 不测 |
| pnpm 12 可执行文件 | `add`、`remove`、`outdated --json` | 用户装在两个固定位置之一的 pnpm | `vi.mock` 换成记录参数的假实现；`tests/pnpm-run.test.ts` 用 node 代替 |
| home 的 `package.json`、`node_modules/<包>` 的清单与真实目录 | 装了哪些包；peer、版本号、`keywords`；升级前后哪些包换了目录 | 磁盘 | 临时目录里写文件、建目录链接 |
| 机器级 `~/.npmrc` 与 home 级 `<home>/.npmrc` | 按 scope 找源地址与 token；增删包源 | 磁盘 | 临时目录里的两份文件 |
| npm 源的检索接口 `GET <源>/-/v1/search` | `search` | 各条源 | 换掉全局 `fetch` |
| 设置 `gitea.base-url`、`gitea.token` | `source.add` 的 `owner` 写法拼地址、取 token | gitea 插件声明、设置插件存 | 假 `settings.get` |

## 怎么单独测

判据一条：**能不能不启动进程、不开 home，只传入输入看输出**。能就写成 vitest 用例，不能的用实机验证，两者不互相替代。

{/* tree dir="../plugins/plugin-manager/tests" depth="1" */}

- **纯逻辑直接测**：`ids`、`inventory`、`update`、`peers`、`kernel-compat`、`kernel-upgrade`、`outdated`、`sources`、`search`、`busy` 这些文件不读写磁盘，用例直接给输入看输出
- **读写磁盘的在临时目录里测**：`home.test.ts` 读清单、读真实目录、读写 npmrc；`package-sources.test.ts` 两份 npmrc 真读真写，`settings.get` 与检索接口用假的
- **命令这一层**：`commands.test.ts` 在假 ctx 上运行 `apply`，按命令名调登记下来的处理函数；条目树、数据插件、设置插件、命令总线是假的，pnpm 用 `vi.mock` 换掉，其余是真代码。它证明每条命令的回执形状、参数校验、失败时动没动条目
- **和 cordis 对齐**：`loader.test.ts` 用 `devDependencies` 里固定版本的 loader、include、cordis 搭一个和内核相同的环境，证明取树、增删改、重新加载真的可行；`fiber-state.test.ts` 读装着的 cordis 的类型声明，核对照抄的状态名表
- **产物**：`artifact.test.ts` 证明构建产物里除了 node 内置模块一个包名 import 都没有，没构建时整组跳过；`main-entry.test.ts` 证明主入口只导出那几样

真 pnpm 装包、真 registry 检索、真的数据与设置插件、换内核后重启，只能实机验证：`devkit.home.new` 开一个隔离 home，`devkit.dev` 把这一版装进去，再用 `devkit.cdp` 调命令（见[测试 home](/docs/devkit/home)、[改一版看一版](/docs/devkit/dev)）。

**先读** `index.ts`：15 条命令的登记、参数校验，以及 `PluginManager` 类里每条命令的做法。ctx 只在这里持有，`tree.ts` 与 `vocab.ts` 从它身上取条目树、自己的条目 id 与内核服务。
