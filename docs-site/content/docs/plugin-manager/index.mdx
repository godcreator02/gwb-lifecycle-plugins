# 插件管理

**本页回答**：插件管理有哪些功能、别的模块经什么使用它、它依赖什么、哪些事不归它管。包名 `@godcreator/gwb-plugin-manager`，源码目录 `plugins/plugin-manager/`，入口文件 `src/index.ts`。

插件管理是 home 里一条普通条目加载的插件，单独发版，和别的插件一样用 `plugin-manager.update` 升级。它和 devkit 放在同一个仓里开发，原因见轨迹卡[插件管理迁入 devkit 仓](/trajectory/2026-09-24-plugin-manager-joins-devkit)。

## 功能

它管 home 里的两层东西：pnpm 装进来的**包**，和 `cordis.yml` 里指向包的**条目**。只装包、不加条目，插件不会运行；插件管理是唯一写这两层的插件，让两层对得上，并如实报告对不上的地方。

- **列出 home 里的包与条目**：每个包下面是它的条目，带启停、是否在运行；内核包与 `cordis` 不列，见 [home 的包与条目](/docs/plugin-manager/home)
- **报告每个插件 peer 里的包满没满足**：`list` 的每个包带 `unmetPeers`，内核包对照正在运行的内核、别的插件对照 home 里装着的版本，只报告、不拦加载，见 [peer 满没满足](/docs/plugin-manager/peers)与[内核兼容性](/docs/plugin-manager/kernel-compat)
- **装一个还没装的包并加一条条目**：一条命令做完，home 的 `package.json` 照 pnpm 默认写 `^` 范围，只等条目写入、不等加载；包已装就报错。**卸载**先删全部条目、再卸包，数据与设置留在磁盘上。见[安装与卸载](/docs/plugin-manager/install)
- **加删条目、启用或停用一条条目**：条目只经 loader 的条目树改，见 [home 的包与条目](/docs/plugin-manager/home#条目只经-loader-的条目树)
- **选条目 id**：包名去掉 scope 与 `gwb-` 前缀，条目树上重名加 `-2`、`-3` 后缀，不同源上的同名插件靠它共存，见[条目 id](/docs/plugin-manager/ids)
- **查新版本、热升级**：全部过期包、点名的几个过期包、或按给定写法装已装的包，三种恰好选一种；升级与重新加载在同一条命令里（停用 → 等旧的卸载完 → 启用 → 等新的加载完，见[重新加载条目](/docs/plugin-manager/remount)），真实目录变了的别的包一起重新加载；不重启、不整页重新加载，见[热升级](/docs/plugin-manager/upgrade)
- **升内核**：内核包写进 `update` 的 `specs`，装完照内核包 peer 里写的版本对齐 home 根上的 `cordis`；不重新加载任何条目，重启由人决定，见[升内核](/docs/plugin-manager/kernel-upgrade)
- **同一时刻只允许一个改动**：安装、卸载、升级重入时回 BUSY，同一个 home 里同一时刻最多一个写 home 的 pnpm，见[同一时刻只允许一个改动](/docs/plugin-manager/busy)
- **只用两个固定位置的 pnpm 12**：第一个存在的作数、核对版本，直接启动、不设超时，见 [pnpm](/docs/plugin-manager/pnpm)
- **找可装的插件**：在机器级 `~/.npmrc` 与 home 级 `<home>/.npmrc` 配好的每条 npm 源上检索，是不是插件只看包清单 `keywords` 里的 `gwb-plugin`；只读 npmrc、不改 home、不经 BUSY。第三方包源由说明书教 agent 手写 `~/.npmrc`，见[找插件](/docs/plugin-manager/sources)

## 接口

别的模块经下面这几样使用插件管理。

### 10 条命令

插件管理对外只有命令，都登记在命令总线上，`plugin` 写包名；页面、agent、别的插件调的是同一批命令。每条命令的参数与回执写在它登记时的 `usage` 里，agent 经 MCP 入口的 `search` 读到的就是它；怎么组合着用见说明书 [gwb-plugin-manager](/docs/outputs/skills/gwb-plugin-manager)。

| 命令（前缀 `plugin-manager.`） | 做什么 | 细节 |
| --- | --- | --- |
| `list` | 列出包与条目，带 peer 报告（含内核包） | [home 的包与条目](/docs/plugin-manager/home) |
| `install` / `uninstall` | 装一个还没装的包并加一条条目 / 删全部条目再卸包（经 BUSY 检查） | [安装与卸载](/docs/plugin-manager/install) |
| `add-entry` / `remove-entry` | 给已装的包加一条条目（只收 `{ pkg }`，id 自动生成）/ 删一条条目、留着包 | [home 的包与条目](/docs/plugin-manager/home)、[条目 id](/docs/plugin-manager/ids) |
| `enable` / `disable` | 启用 / 停用一条条目；手动重新加载一条就先停用再启用 | [home 的包与条目](/docs/plugin-manager/home)、[重新加载条目](/docs/plugin-manager/remount#手动重新加载一条条目) |
| `outdated` / `update` | 查新版本 / 升级已装的包，内核包也经 `update` 的 `specs`（`update` 经 BUSY 检查） | [热升级](/docs/plugin-manager/upgrade)、[升内核](/docs/plugin-manager/kernel-upgrade) |
| `search` | 在配好的全部源上找插件 | [找插件](/docs/plugin-manager/sources) |

- **回执只有一层 `ok`**：成功时 `data` 是结果本身，里面没有第二层 `ok`；执行中的失败（找不到 pnpm、pnpm 失败、条目写不进去）回 `{ ok: false, error }`，pnpm 输出的最后几行拼在 `error` 末尾。失败时还带结构化字段的只有一处：`update` 装上了内核包而 `cordis` 没对齐时带 `data: { kernel }`。为什么只留一层见轨迹卡[升内核并进 specs](/trajectory/2026-09-25-kernel-via-specs-caller-reloads)
- **调用方写错直接报错**：参数不是对象、有认不出的键、缺字段、包名不合规、条目不存在，处理函数直接抛错，不猜、不忽略；命令总线把抛出的错误转成 `{ ok: false, error }`

### 服务 gwbPluginManager

值是空对象，只表示「插件管理装着」；别的插件 inject 它，只为跟着插件管理一起加载、卸载（插件管理窗格就这样用它）。有没有破坏性变化看插件管理的版本号，服务上不放版本数字。同一件事如果既能调命令、又能调服务方法，两种调用方式会慢慢变得不一致，而 BUSY 检查只加在命令上，服务方法会绕过去，所以要加能力就加一条命令，不往服务上加方法。只表示存在的服务用 `ctx.provide` 提供普通对象，不继承 cordis 的 `Service` 类，插件管理因此在运行时不 import `cordis`。

### 主入口给 devkit 的导出

包主入口除了插件本身（`name`、`apply`），只导出 devkit 复用的几样——找 pnpm 的 `locatePnpm`、在 home 里启动 pnpm 用的环境 `homePnpmEnv`（见 [pnpm](/docs/plugin-manager/pnpm#参数环境与读回什么)）、内核包名 `KERNEL_PACKAGE`、peer 范围写法的判定 `isCaretRange`、取输出最后几行的 `tailLines`，以及 `devkit.dev` 调的三条命令名 `LIST_COMMAND`、`INSTALL_COMMAND`、`UPDATE_COMMAND`。devkit 在 peer 里写了插件管理，直接 import 这几样，规则只有这一份；devkit 构建时把 peer 里的包留在外面，运行时用的是 home 里装着的那一版插件管理。回执类型不从主入口导出，在下面的子路径 `./receipts`。devkit 怎么用这几样见接缝页 [devkit 调插件管理](/docs/seams/plugin-manager-calls)。

### 子路径 ./receipts：回执的类型

各条命令回执里 `data` 的类型（`list` 的 `PluginPackageView`、`update` 的 `Updated` 等）与通用的 `Outcome` 都写在 `src/receipts.ts`，经子路径 `@godcreator/gwb-plugin-manager/receipts` 导出，给插件管理窗格（`gwb-baseui` 的浏览器侧）`import type`，窗格不用再照 `usage` 手写一份回执形状。命令的 `usage` 与这些类型写的是同一个形状，改回执时两处一起改。

这个子路径在 `exports` 里只有 `types` 条件，没有运行时入口，按值 import 在调用方构建时就报错；`src/receipts.ts` 一个模块都不引用，构建出的 `dist/receipts.d.ts` 里没有包名：窗格的浏览器侧 tsconfig 只有 DOM 类型，这里引进一个包，窗格就得为它多列依赖（主入口的类型声明引了内核包、`cordis` 与 node 的全局类型，所以回执类型不放在主入口）。实现文件从 `src/receipts.ts` 取这些类型，不另写一份：

### 什么算破坏性变更

命令名、参数、回执形状，服务的值，主入口导出的名字、签名或 devkit 依赖的行为，子路径 `./receipts` 导出的类型名，这几样改了、删了都是破坏性变更，升 0.x 的 x、发之前通知下游；加命令、加可选参数、回执加字段、修 bug 升 y。怎么升、怎么通知照说明书 [gwb-release](/docs/outputs/skills/gwb-release)，发版用 `devkit.release`，`packages` 给 `plugins/plugin-manager`。

## 依赖

注入了哪些服务、必需还是局部注入、peer 怎么写、缺了会怎样，直接读写了 loader 的条目树与 home 里的哪些文件、抄了 cordis 的哪份状态数字、启动了哪些子进程、问了哪些源，都在[插件之间怎么连](/docs/wiring#godcreatorgwb-plugin-manager)。每一处读不到、读不懂时怎么报错，写在各机制页（[home 的包与条目](/docs/plugin-manager/home)、[peer 满没满足](/docs/plugin-manager/peers)、[热升级](/docs/plugin-manager/upgrade)、[pnpm](/docs/plugin-manager/pnpm)、[找插件](/docs/plugin-manager/sources)）。cordis、loader、include 写在 `devDependencies`；内核与两个插件的类型都从 peer 里的包 `import type`，构建产物里没有它们的 import。

内核对插件管理的承诺——home 的文件布局、loader 与 include 的版本、按真实路径解析包名——写在内核仓文档站的接缝页「home 布局与条目树」；插件管理用到 loader 的哪几样见接缝页[条目树 loader](/docs/seams/entry-tree)。

## 不做的事

- **不分调用方**：插件管理窗格、经 MCP 入口的 agent、经 CDP 调命令的 `devkit.dev` 调的是同一条命令；它不知道 devkit 的 `dev-packs/` 目录，只照 `file:` 写法交给 pnpm
- **不画界面**：插件管理窗格在界面平台仓的 `gwb-baseui`，它经命令调用插件管理
- **不管条目加载成没成功**：条目由 loader 加载，成没成功看 `list` 的 `active`，原因在 `gwb.log`；插件之间的依赖齐不齐也不管，缺服务的插件由 cordis 停在等待
- **不拦范围不包含当前内核、peer 没满足的插件，也不替它装或升级 peer 里的插件**：`unmetPeers` 只报告；发版前拒绝 peer 没写对的包是 `devkit.release` 的事
- **不替插件装 peer、库**：插件自己把库打包进去；peer 里的插件由人装，pnpm 的自动补装也关掉了，理由见[安装与卸载](/docs/plugin-manager/install#home-里只有插件内核包与-cordis)
- **不管数据与设置**：卸载包、删条目都不动它们，内容与归属记录归数据插件与设置插件管；插件管理选 id 不读归属记录，同名包读到别人留下的数据时由那两个插件报错
- **不重启工作台、不整页重新加载**：换了内核包只在回执里说要重启，重启由人决定；界面要换成新代码，由调用方拿到回执后自己调 `shell.reload`
- **不管进程外的 pnpm**：`devkit.home.new`、人手工运行的 pnpm 不经 BUSY，和插件管理的改动同时写 home 会丢改动
- **不替人装 pnpm，也不找 PATH 上的 pnpm**：两个固定位置都没有、或版本不对，就报错说明该怎么装
- **不写 npmrc，不看环境变量或 pnpm 全局配置里指定的源**：找源地址只读两份 npmrc；第三方包源由 agent 照说明书手写 `~/.npmrc`
- **不猜承载 `cordis.yml` 的条目叫什么**：条目树从自己那条条目的上一层取
