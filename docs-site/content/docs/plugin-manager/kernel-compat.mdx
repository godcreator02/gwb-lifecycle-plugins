# 内核兼容性

**本页回答**：插件怎么声明兼容哪些内核；`^x.y.z` 包不包含一个版本怎么判；`list` 怎么报范围不包含当前内核的插件、为什么只看插件；为什么只报告、不拦加载；发版前检查查什么。

## 插件在 peer 里写内核包的范围

插件包在 `package.json` 的 `peerDependencies` 里写 `"@godcreator/gwb-kernel-desktop": "^x.y.z"`，x.y.z 是它验过的那个内核的版本号。插件依赖内核提供的 cordis、loader 与 home 布局，这些随内核版本变化；内核是 home 里的一个 npm 包，用 npm 标准的 peer 写法声明兼容范围，pnpm 与插件管理读的是同一个字段。插件管理自己也这样写：

## 比对规则：^x.y.z 包不包含一个版本

只认 `^x.y.z` 这一种写法。主版本号为 0 时要求次版本号相同（`^0.3.0` 包含 `0.3.4`，不包含 `0.4.0` 与 `0.2.7`），≥1 时要求主版本号相同（`^1.4.0` 包含 `1.9.4`，不包含 `2.0.0`），并且不低于 x.y.z（`^0.3.2` 不包含 `0.3.0`）。只比 x.y.z 三段、不看预发布段，同一条线的开发版（`0.3.0-dev.…`）算在范围内。没写、写的不是 `^x.y.z`（`0.3.0`、`>=0.3.0`、`~0.3.0`、`^0.3`），一律算不包含。

除了预发布段，这就是 npm 对 `^` 的解释，也和全生态升版本号的规则（说明书 [gwb-release](/docs/outputs/skills/gwb-release)）对得上：0.x 时次版本号变了就可能有破坏性变化，≥1 以后只在主版本号上。只许一种写法，报告与发版前检查都不用处理各种范围语法。

## list 在 unmetPeers 里报内核包

`list` 给每个包读它装在 home 里的 `package.json`。插件 peer 里写了内核包、范围不包含**正在运行的内核**（内核服务 `gwbKernel` 的 `version`）时，这个包的 `unmetPeers` 列一项 `{ pkg: "@godcreator/gwb-kernel-desktop", range, installed: <运行中的内核版本> }`；范围写的不是 `^x.y.z` 也列，`range` 原样照抄。home 的 `node_modules` 里装着的内核包版本不参与判断：换了内核包、还没重启时，运行的仍是旧内核。内核包与别的 peer 是同一种判断——「peer 写的范围包不包含眼下那一版」，所以报在同一个字段里，别的 peer 怎么报见 [peer 满没满足](/docs/plugin-manager/peers)。

**只看插件**：`keywords` 里有 `gwb-plugin` 的包才比；peer 里没写内核包的插件不列这一项（发版前检查会拒它，见下）。库、第三方 cordis 插件（如 `@cordisjs/plugin-timer`）、清单读不到的包都不该声明兼容哪个内核，`unmetPeers` 一律为空——不然窗格里这些包都标黄，真正没适配当前内核的插件反而看不出来。内核包与 `cordis` 自己不在 `list` 里。

## 只报告，不拦加载

`unmetPeers` 里有内核包的插件照常加载、照常能装能升，插件管理不拦它。范围不包含当前内核不等于不能用，大多数插件换一个次版本的内核照样能运行；拦下来反而让人没法先试一试。这一项的用处是出了问题时先怀疑它；要保证发出去的插件都写对了范围，在发版时检查，而不是在装的时候拦。升内核重启之后，范围不包含新内核的插件由同一个 `list` 报出来（见[升内核](/docs/plugin-manager/kernel-upgrade)）。

## 发版前检查只查写法

`devkit.release` 构建之后、发第一个包之前，检查每个插件包 peer 里内核包的范围：必须写了、是 `^x.y.z`；有一个不对就一个都不发。它不拿范围对照哪个内核——那样能不能发版要看从哪个 home 调。不是插件的包不查。范围包不包含正在运行的内核，只由 `list` 在 home 里报。

比对规则只写在插件管理的 `src/kernel-compat.ts` 里，经包主入口导出 `KERNEL_PACKAGE` 与 `isCaretRange`（见[主入口给 devkit 的导出](/docs/plugin-manager#主入口给-devkit-的导出)）；`kernelRangeCovers` 只给 `list` 自己用，不导出。devkit 的发版前检查 import 那两个，所以改了「只许 `^x.y.z`」这条规则，`devkit.release` 的检查跟着变；改签名或 devkit 依赖的行为是破坏性变更（见[什么算破坏性变更](/docs/plugin-manager#什么算破坏性变更)）。两边怎么对上见接缝页 [peer 里的内核包与插件](/docs/seams/kernel-peer)。
