# 内核兼容性

**本页回答**：插件怎么声明兼容哪些内核；`^x.y.z` 包不包含一个版本怎么判；`list` 回执里的 `kernelRange` 与 `kernelUntested` 怎么算、为什么只标插件；为什么只报告、不拦加载；还有谁用同一条规则。

## 插件在 peer 里写内核包的范围

插件包在 `package.json` 的 `peerDependencies` 里写 `"@godcreator/gwb-kernel-desktop": "^x.y.z"`，x.y.z 是它验过的那个内核的版本号。插件依赖内核提供的 cordis、loader 与 home 布局，这些随内核版本变化；内核是 home 里的一个 npm 包，用 npm 标准的 peer 写法声明兼容范围，pnpm 与插件管理读的是同一个字段。插件管理自己也这样写：

## 比对规则：^x.y.z 包不包含一个版本

只认 `^x.y.z` 这一种写法。主版本号为 0 时要求次版本号相同（`^0.3.0` 包含 `0.3.4`，不包含 `0.4.0` 与 `0.2.7`），≥1 时要求主版本号相同（`^1.4.0` 包含 `1.9.4`，不包含 `2.0.0`），并且不低于 x.y.z（`^0.3.2` 不包含 `0.3.0`）。只比 x.y.z 三段、不看预发布段，同一条线的开发版（`0.3.0-dev.…`）算在范围内。没写、写的不是 `^x.y.z`（`0.3.0`、`>=0.3.0`、`~0.3.0`、`^0.3`），一律算不包含。

除了预发布段，这就是 npm 对 `^` 的解释，也和全生态升版本号的规则（说明书 [gwb-release](/outputs/skills/gwb-release)）对得上：0.x 时次版本号变了就可能有破坏性变化，≥1 以后只在主版本号上。只许一种写法，报告与发版前检查都不用处理各种范围语法。

## list 回执里的两个字段

`list` 给每个包读它装在 home 里的 `package.json`，回执里带两个字段：

- `kernelRange`：`peerDependencies` 里内核包范围的原值；没写或不是字符串时没有这个字段
- `kernelUntested`：范围不包含运行中的内核就是 `true`，包括没写、写的不是 `^x.y.z`

**只标插件**：`keywords` 里有 `gwb-plugin`、又不是内核包与 `cordis` 自己的包才比。库、第三方 cordis 插件（如 `@cordisjs/plugin-timer`）、内核包与 `cordis`、清单读不到的包都不该声明兼容哪个内核，一律 `kernelUntested: false`、不带 `kernelRange`——不然窗格里这些包都显示「内核未测过」，真正没适配当前内核的插件反而看不出来。

## 只报告，不拦加载

`kernelUntested` 是 `true` 的插件照常加载、照常能装能升，插件管理不拦它。范围不包含当前内核不等于不能用，大多数插件换一个次版本的内核照样能运行；拦下来反而让人没法先试一试。这个字段的用处是出了问题时先怀疑它；要保证发出去的插件都写对了范围，在发版时检查，而不是在装的时候拦。

## 还有谁用同一条规则

- **升内核**：`update` 的 `specs` 里有内核包时，装完新内核列出范围不包含新内核（或没写范围）的插件，放在回执的 `pluginsOutsideRange` 里，用的就是算 `kernelUntested` 的那个函数，同样只报告，见[升内核](/docs/plugin-manager/kernel-upgrade#回执多出的两个字段)
- **`devkit.release`**：构建之后、发第一个包之前，检查每个插件包 peer 里内核包的范围：必须写了、是 `^x.y.z`、并且包含运行中的内核；有一个不对就一个都不发。不是插件的包不查

比对规则只写在插件管理的 `src/kernel-compat.ts` 里，经包主入口导出 `KERNEL_PACKAGE`、`isCaretRange`、`kernelRangeCovers`（见[主入口给 devkit 的导出](/docs/plugin-manager#主入口给-devkit-的导出)）。devkit 的发版前检查直接 import 它们，所以改了这里的规则，`devkit.release` 的检查跟着变；改签名或 devkit 依赖的行为是破坏性变更（见[什么算破坏性变更](/docs/plugin-manager#什么算破坏性变更)）。两边怎么对上见接缝页 [peer 里的内核包与插件](/docs/seams/kernel-peer)。
