# 在哪个内核上测过

**本页回答**：插件怎么声明它在哪个内核上测过；`list` 回执里的 `testedKernel` 与 `kernelUntested` 怎么算出来；为什么只报告、不拦加载；发版时谁检查这个字段。

## 插件在 package.json 里声明

**是什么**：插件包在 `package.json` 的 `gwb` 字段里写 `testedKernel`，值是它验过的那个内核的版本号。插件管理自己也写了：

{/* ref file="../plugins/plugin-manager/package.json" lines="51-52" */}

**为什么**：插件依赖内核提供的 cordis、loader 与 home 布局，这些随内核版本变化，而插件的 `peerDependencies` 只能写 cordis 的版本范围，写不出「在哪个内核上验过」。出了问题时，先看这个字段就知道该不该怀疑内核换了版本。

插件管理自己的测试也按这个字段对齐：`loader.test.ts` 用的 loader、include、cordis 是 `devDependencies` 里写死的精确版本，要和 `gwb.testedKernel` 那个内核用的一致；内核换了其中任何一个，就把这几个版本改成内核的、跑一遍测试，再改 `testedKernel`。

## 比对规则：看同一条版本线

**是什么**：声明的版本和运行中的内核版本在同一条**版本线**上，才算测过。主版本号为 0 时版本线是前两位（`0.2.1` 与 `0.2.7` 在同一条上，与 `0.3.0` 不在），主版本号 ≥1 时只看主版本号。没声明、声明的不是合法版本号，一律算没测过。

**为什么**：内核在 0.x 时次版本号变了就可能有破坏性变化，补丁版本不会；≥1 以后破坏性变化只在主版本号上。这和全生态升版本号的规则（说明书 [gwb-release](/outputs/skills/gwb-release)）对得上。

## list 回执里的两个字段

**是什么**：`list` 给每个包读它装在 home 里的 `package.json`，回执里多两个字段：

- `testedKernel`：`gwb.testedKernel` 的原值；没写或不是字符串时没有这个字段
- `kernelUntested`：没在当前内核的版本线上测过就是 `true`，包括没声明、声明的不是合法版本号

**怎么读包清单**：按包名（含 scope）从 home 的 `node_modules` 读。文件不在（条目指向一个没装的包，或 pnpm 装到一半）就当没声明；文件在但读不了、或不是合法 JSON，`list` 直接报错并带上文件路径——那是 home 坏了，不该当成「没测过」混过去。

## 只报告，不拦加载

**是什么**：`kernelUntested` 是 `true` 的插件照常加载、照常能装能升，插件管理不拦它。

**为什么**：没测过不等于不能用，大多数插件换一个次版本的内核照样能运行；拦下来反而让人没法先试一试。这个字段的用处是出了问题时先怀疑它。要保证发出去的插件都测过，在发版时检查，而不是在装的时候拦。

## 发版前 devkit.release 检查同一个字段

**是什么**：`devkit.release` 在构建之后、发第一个包之前，检查每个插件包（`keywords` 含 `gwb-plugin` 的）的 `gwb.testedKernel`：必须写了、是合法版本号、并且和运行中的内核在同一条版本线上。有一个不对就一个都不发，回执里说该改成什么。不是插件的包（库、工具包）不查。
