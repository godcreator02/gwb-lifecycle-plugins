# 内核兼容性

**本页回答**：插件怎么声明它兼容哪些内核；`list` 回执里的 `kernelRange` 与 `kernelUntested` 怎么算出来；为什么只报告、不拦加载；还有谁用同一条规则。

## 插件在 peerDependencies 里写内核包的范围

**是什么**：插件包在 `package.json` 的 `peerDependencies` 里写 `"@godcreator/gwb-kernel-desktop": "^x.y.z"`，x.y.z 是它验过的那个内核的版本号。内核包和 `cordis` 装在 home 根上，pnpm 安装插件时顺带核对这个范围。插件管理自己也写了：

{/* ref file="../plugins/plugin-manager/package.json" lines="33-34" */}

**为什么**：插件依赖内核提供的 cordis、loader 与 home 布局，这些随内核版本变化。内核是 home 里的一个 npm 包，用 npm 标准的 peer 写法声明兼容范围，pnpm 与插件管理读的是同一个字段。出了问题时，先看这个范围就知道该不该怀疑内核换了版本。

插件管理自己的测试也按这个范围对齐：`loader.test.ts` 用的 loader、include、cordis 是 `devDependencies` 里写死的精确版本，要和范围下限那个内核用的一致；内核换了其中任何一个，就把这几个版本改成内核的、运行一遍测试，再改 peer 里的范围。

## 比对规则：^x.y.z 包不包含运行中的内核

**是什么**：只认 `^x.y.z` 这一种写法。主版本号为 0 时要求次版本号相同（`^0.3.0` 包含 `0.3.4`，不包含 `0.4.0` 与 `0.2.7`），≥1 时要求主版本号相同（`^1.4.0` 包含 `1.9.4`，不包含 `2.0.0`），并且不低于 x.y.z（`^0.3.2` 不包含 `0.3.0`）。只比 x.y.z 三段、不看预发布段，同一条线的开发版（`0.3.0-dev.…`）算在范围内。没写、写的不是 `^x.y.z`（`0.3.0`、`>=0.3.0`、`~0.3.0`、`^0.3`），一律算不包含。

**为什么**：除了预发布段，这就是 npm 对 `^` 的解释，也和全生态升版本号的规则（说明书 [gwb-release](/outputs/skills/gwb-release)）对得上：内核在 0.x 时次版本号变了就可能有破坏性变化，≥1 以后破坏性变化只在主版本号上。只许一种写法，报告与发版检查都不用处理各种范围语法。

## list 回执里的两个字段

**是什么**：`list` 给每个包读它装在 home 里的 `package.json`，回执里多两个字段：

- `kernelRange`：`peerDependencies` 里内核包范围的原值；没写或不是字符串时没有这个字段
- `kernelUntested`：范围不包含运行中的内核就是 `true`，包括没写、写的不是 `^x.y.z`

**只标插件**：`keywords` 里有 `gwb-plugin`、又不是内核包与 `cordis` 自己的包才比。库、第三方 cordis 插件（如 `@cordisjs/plugin-timer`）、
内核包与 `cordis`、清单读不到的包都不该声明兼容哪个内核，一律 `kernelUntested: false`、不带 `kernelRange`——不然窗格里这些包都显示「内核未测过」，
真正没迁的插件反而看不出来。是不是插件的判法与 `update-kernel` 回执里的 `pluginsOutsideRange` 相同：

## 只报告，不拦加载

**是什么**：`kernelUntested` 是 `true` 的插件照常加载、照常能装能升，插件管理不拦它。

**为什么**：范围不包含当前内核不等于不能用，大多数插件换一个次版本的内核照样能运行；拦下来反而让人没法先试一试。这个字段的用处是出了问题时先怀疑它。要保证发出去的插件都写对了范围，在发版时检查，而不是在装的时候拦。

## 还有谁用同一条规则

- **`plugin-manager.update-kernel`**：装完新内核，列出 home 里 `keywords` 含 `gwb-plugin`、范围不包含新内核（或没写范围）的插件，放在回执的 `pluginsOutsideRange` 里，同样只报告，见[升内核](/docs/plugin-manager/upgrade#升内核)
- **`devkit.release`**：构建之后、发第一个包之前，检查每个插件包（`keywords` 含 `gwb-plugin` 的）peer 里内核包的范围：必须写了、是 `^x.y.z`、并且包含运行中的内核。有一个不对就一个都不发，回执里说该改成什么。不是插件的包（库、工具包）不查

**两份规则**：比对规则在 devkit 与插件管理里各有一份（两边的 `src/kernel-compat.ts`），不跨包 import——devkit 不依赖插件管理的包。两个包在同一个仓里，改规则时一个提交改两份；devkit 的对照测试拿同一组输入运行两份，结果不同就失败。
