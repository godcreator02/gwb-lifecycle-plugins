# 同一时刻只允许一个改动

**本页回答**：哪几条命令经过 BUSY 检查、重入时回什么；为什么要这道检查、为什么不排队；它管不到哪几处。

## 三条改动命令经过 BUSY

`install`、`uninstall`、`update` 登记时包在同一道检查里。已经有一个在运行时，重入的直接回 `{ ok: false, error: "BUSY…" }`，不执行、不排队；运行中抛错也会释放标志。一个内核进程只服务一个 home，进程内的一个标志就够。插件管理对外只有命令，没有绕开这道检查的调用方式。

- 命令 A（`install`）通过 BUSY 检查、设上标志，它的 `pnpm add` 开始运行、写 home

- 命令 C（`outdated`）只读，不经过 BUSY，它的 `pnpm outdated` 和 A 的 `pnpm add` 同时运行，不写文件，不影响 A
- A 返回回执时释放标志（抛错也会释放），再来的改动命令又能通过

## 为什么要，为什么不排队

写 home 的 pnpm 都在这三条命令里运行（见[包：只经 applyToHome](/docs/plugin-manager/home#包只经-applytohome)），而两个写 home 的 pnpm 同时运行会丢改动：在和真 home 布局相同的临时 home 里，`pnpm add x` 与 `pnpm add y` 同时运行 5 轮，每轮清单与锁文件都只剩一个包；`pnpm add` 与 `pnpm remove` 同时运行 5 轮，每轮添加的那个包都丢了；两个 pnpm 都退出码 0、没有警告。`pnpm outdated --json` 不写文件，和 `pnpm add` 同时运行 5 轮，`add` 的结果都对，所以只读的 `outdated` 与找插件的 `search` 不经过 BUSY（实验见轨迹卡[两个 pnpm 同时改同一个 home](/trajectory/2026-09-25-concurrent-pnpm-loses-writes)）。

一次安装、一次热升级也不止一次 pnpm，还要改条目树、重新加载插件，中间插进另一个改动，状态就乱了。

不排队：排队会让界面看起来点了没反应；回 BUSY，调用方等前一个的回执再调。为什么删掉 pnpm 串行队列、只留这一道检查，见轨迹卡[删掉 pnpm 串行队列、只留 BUSY](/trajectory/2026-09-25-drop-pnpm-queue-keep-busy)。

## 管不到的三处

- **条目命令不经过 BUSY**：`add-entry`、`remove-entry`、`enable`、`disable` 不经过检查，`update` 正在重新加载某条条目时，别人可以同时停用或删掉它
- **插件管理重新加载自己的那段空档**：`update` 重新加载插件管理自己时，先发回执、释放标志，下一个宏任务才动手（见[重新加载条目](/docs/plugin-manager/remount#插件管理自己先回执后重新加载)）；这中间进来的改动命令能通过检查，可能运行到一半插件管理就被停用；重新加载出来的新实例标志是新的
- **插件管理进程外的 pnpm**：`devkit.home.new`（新 home 启动之前）、人在终端里手工运行的 pnpm，和插件管理的改动同时写同一个 home 时照样会丢改动。一个隔离 home 同一时间只给一个会话用，这条靠约定，不加锁（[隔离 home 靠约定](/trajectory/2026-09-25-isolated-home-by-convention)）
