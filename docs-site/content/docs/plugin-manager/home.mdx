# home 的包与条目

**本页回答**：home 里的包与条目是什么关系、`list` 怎么把两层对上；为什么只能由插件管理一个写 home、包和条目各经哪条路改。同一时刻只让一个改动写 home，见[同一时刻只允许一个改动](/docs/plugin-manager/busy)。

## 包与条目两层

**包**是 pnpm 装进 home 的 `package.json` 与 `node_modules` 的 npm 包；**条目**是 `cordis.yml` 里的一项，指向一个包，loader 按条目加载插件。一个包可以有好几条条目，各是一个实例、各存各的数据。插件管理自己、命令插件也各是一条条目，一样出现在 `list` 里。

两层各有各的清单：装包是 pnpm 的事，加载是 loader 的事。只装包、不加条目，插件不会运行；条目指向的包被删了，条目还在。插件管理让两层对得上，并如实报告对不上的地方。

内核包 `@godcreator/gwb-kernel-desktop` 与 `cordis` 也在 home 的 `package.json` 里，但没有条目，`list` 不列它们：列出来就是两个「装了包、没有条目」的包，看着像该卸掉的，而卸掉之后 home 就启动不了。它们怎么换见[升内核](/docs/plugin-manager/kernel-upgrade)。

## list 怎么对照

`list` 读 home 的 `package.json` 的 dependencies 和条目树，按包名对照，两层都不丢；再给每个包读它装在 `node_modules` 里的 `package.json`，加上内核兼容（见[内核兼容性](/docs/plugin-manager/kernel-compat)）与 peer 满没满足（见[peer 满没满足](/docs/plugin-manager/peers)）两组字段：

<Diagram name="pm-list" title="list 把 package.json 与 cordis.yml 两层对上，两层都不丢">
- 左边是 home 的 `package.json` 里的依赖，中间是 `cordis.yml` 的条目，右边是 `list` 按包名排好的结果
- 装了包、没有条目：报成 `entries: []`——只表示一条条目都没有，不推断原因
- 条目指向一个没装的包（手工改过 `cordis.yml`，或包被 `pnpm remove` 删了）：报成 `installed: false`
- 每条条目带 `active`：看的是 fiber 的状态是不是 `ACTIVE`，不是 fiber 在不在——依赖没满足的插件也有 fiber，只是永远到不了 `ACTIVE`
</Diagram>

## 只有插件管理写 home

改这两层的只有插件管理，而且各只有一条路：**包只经 `applyToHome` 运行 pnpm，条目只经 loader 的条目树**。

两层都不是「写一下文件」那么简单。pnpm 每次都读、改、写 `package.json` 与锁文件，两个同时运行会丢改动，而且都退出码 0；`cordis.yml` 的内容在 loader 的内存里也有一份，直接写文件，内存里的条目不知道，下一次写回就把磁盘上的改动覆盖掉。只有一个写入者、一条路，这两类覆盖才都不会发生。

`devkit.dev` 往隔离 home 装开发版也走这条路：包文件放进目标 home 的 `dev-packs/`，再调目标 home 的 `plugin-manager.update {"specs":…}`（已装的包）或 `plugin-manager.install`（新插件），见接缝页 [devkit 调插件管理](/docs/seams/plugin-manager-calls)。唯一的例外是 `devkit.home.new`：新 home 启动之前插件管理还没装、也没在运行，内核包、`cordis` 与基础插件只能由它直接用 pnpm 装进去。

### 包：只经 applyToHome

安装、卸载、升级（包括换内核包）都经 `applyToHome` 运行 pnpm：`add` 照 pnpm 默认在 home 的清单里写 `^` 范围，只有对齐 `cordis` 那一次自己带 `--save-exact`；`remove` 只删点名的那一个。调用它的四条命令都经过 BUSY 检查，所以插件管理在同一个 home 里同一时刻最多一个写 home 的 pnpm。只读的 `pnpm outdated --json` 不经过这里，也不经过 BUSY。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="603-610" */}

为什么写 `^` 范围：0.x.y 的 y 变了不破坏兼容，`^0.x.y` 正好是「这一条 x 线上的任何 y」；装什么由 home 的锁文件定，只有 `update` 会换版本。代价是清单里写成 `^` 的项挡住往回退版本：按点名的更旧版本装，pnpm 12 沿用 `^`、留着范围里更新的那个（本仓 `probes/2609241510_pnpm-add-exact-prefix/`），`specs` 装完的版本号核对会照实回 `ok: false`——不做回退，升坏了发新版往前修。`cordis` 例外：它是预发布版，写成范围时别的 rc 也算满足，而它要正好等于内核包 peer 里那个版本，所以写精确版本号（取舍见轨迹卡[home 清单写 ^ 范围，只有 cordis 写精确版本号](/trajectory/2026-09-25-home-manifest-caret)）。

### 条目：只经 loader 的条目树

条目的增删改只用条目树的 `create` / `update` / `remove`——它们把写回 `cordis.yml` 与当场加载、卸载一起做。启用传 `{ disabled: null }`（loader 把 `null` 当作删掉这个字段），停用传 `{ disabled: true }`；`remove-entry` 只删条目，包留在 home 里。entryId 写完整的（`home:hello`）或只写 id（`hello`）都认，条目树只认末段。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="540-566" */}

条目树在构造时从插件管理自己那条条目的上一层取（`ctx.fiber.entry.parent.tree`），不用知道承载 `cordis.yml` 的那条条目叫什么。按 loader 自己的类型 `EntryTree` 取、再赋给收窄后的 `EntryTreeLike`：loader 改了这几个方法的签名，类型检查就在这里失败。loader 这一侧的约定见接缝页[条目树 loader](/docs/seams/entry-tree)。

<Note>
**别直接写 cordis.yml**：绕过条目树改文件，内存里的条目不知道，改动要等下次重启才生效，而且中间任何一次写回都会用内存里的旧内容把它覆盖掉。
</Note>
