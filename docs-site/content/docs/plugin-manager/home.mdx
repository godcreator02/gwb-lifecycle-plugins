# home 的两层与唯一写入者

**本页回答**：home 里的包与条目是什么关系，`list` 怎么把它们对上；为什么只能有一个写入者；包和条目各经哪条路改；两个改动同时来时怎么办。

## 包与条目两层

home 里的插件分两层：**包**是 pnpm 装进 `package.json` 与 `node_modules` 的 npm 包；**条目**是 `cordis.yml` 里的一行，指向一个包，loader 按条目加载插件。一个包可以有好几条条目，各是一个实例、各存各的数据。插件管理自己、命令插件也各是 `cordis.yml` 里的一条条目，一样出现在 `list` 里。

**为什么分两层**：装包是 pnpm 的事，加载是 loader 的事，pnpm 和 loader 各有自己的清单。只装包、不加条目，插件不会运行；条目指向的包被删了，条目还在。插件管理的工作就是让两层对应上，并且如实报告对不上的地方。

**怎么做**：`list` 读 home 的 `package.json` 和条目树，按包名对照，两层都不丢；再给每个包读它自己的 `package.json`，带上它 peer 里内核包的范围包不包含运行中的内核（见[内核兼容性](/docs/plugin-manager/kernel-compat)）、peer 里别的插件满没满足（见[peer 满没满足](/docs/plugin-manager/peers)）：

<Diagram name="pm-list" title="list 把 package.json 与 cordis.yml 两层对上，两层都不丢">
- 左边是 home 的 `package.json` 里的依赖，中间是 `cordis.yml` 的条目，右边是 `list` 按包名排好的结果
- 装了包、没有条目：报成 `entries: []`——只表示一条条目都没有，不推断原因
- 条目指向一个没装的包（手工改过 `cordis.yml`，或包被 `pnpm remove` 删了）：报成 `installed: false`
- 每条条目带 `active`：看的是 fiber 的状态是不是 `ACTIVE`，不是 fiber 在不在——依赖没满足的插件也有 fiber，只是永远到不了 `ACTIVE`
</Diagram>

## 只有插件管理写 home

改这两层的只有插件管理，而且各只有一条路：**包只经 `applyToHome` 运行 pnpm，条目只经 loader 的条目树**。

**为什么**：两层都不是「写一下文件」那么简单。pnpm 每次都读、改、写 `package.json` 与锁文件，两个同时运行会丢改动，而且都退出码 0（实测见下一节）；`cordis.yml` 的内容在 loader 的内存里也有一份，直接写文件，内存里的条目不知道，下一次写回就把磁盘上的改动覆盖掉。只有一个写入者、一条路，这两类覆盖才都不会发生。

`devkit.dev` 是一个例外：它往隔离 home 装开发版时，自己把准确版本号写进那个 home 的 `package.json` 再运行 `pnpm install`，不经插件管理（`install` 对已经装过的包会再加一条条目，`pnpm add` 会把版本号写成范围）；装完重新加载仍然调 `plugin-manager.remount`，见[改一版看一版](/docs/devkit/dev)。这时不要同时在那个 home 里调插件管理的改动命令。

### 包：只经 applyToHome

**怎么做**：安装、卸载、热升级、升内核都经 `applyToHome` 运行 pnpm，直接启动，不排队。会写 home 的 pnpm 只在这里运行，调用它的四条命令都经过 BUSY 检查（见下面「同一时刻只允许一个改动」），所以插件管理在同一个 home 里同一时刻最多只有一个写 home 的 pnpm。只读的 `pnpm outdated --json` 不经过 `applyToHome`，也不经过 BUSY。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="819-826" */}

**实测**：在和真 home 布局相同的临时 home 里，`pnpm add x` 与 `pnpm add y` 同时运行 5 轮，每轮清单与锁文件都只剩一个包；`pnpm add` 与 `pnpm remove` 同时运行 5 轮，每轮添加的那个包都丢了。两个 pnpm 都退出码 0、没有警告，丢掉的包还留在 `node_modules` 里。`pnpm outdated --json` 不写文件，和 `pnpm add` 同时运行 5 轮，`add` 的结果都对。所以写 home 的 pnpm 必须互斥，`outdated` 不必（[两个 pnpm 同时改同一个 home](/trajectory/2026-09-25-concurrent-pnpm-loses-writes)）。

### 条目：只经 loader 的条目树

**怎么做**：条目的增删改只用条目树的 `create` / `update` / `remove`——它们把写回 `cordis.yml` 与当场加载、卸载一起做。启用传 `{ disabled: null }`（loader 把 null 当作删掉这个字段），停用传 `{ disabled: true }`；`remove-entry` 只删条目，包留在 home 里。

{/* ref file="../plugins/plugin-manager/src/index.ts" lines="765-782" */}

条目树在构造时从插件管理自己那条条目的上一层取（`ctx.fiber.entry.parent.tree`），不用知道承载 `cordis.yml` 的那条条目叫什么。按 loader 自己的类型 `EntryTree` 取，再赋给收窄后的 `EntryTreeLike`：loader 改了这几个方法的签名，类型检查就在这里失败。

<Note>
**别直接写 cordis.yml**：绕过条目树改文件，内存里的条目不知道，改动要等下次重启才生效，而且中间任何一次写回都会用内存里的旧内容把它覆盖掉。
</Note>

### 同一时刻只允许一个改动：BUSY

**为什么**：两个写 home 的 pnpm 同时运行会丢改动（见上面「包：只经 applyToHome」）；而且一次安装、一次热升级不止一次 pnpm，还要改条目树、重新加载插件，中间插进另一个改动，状态就乱了。

**怎么做**：`install`、`uninstall`、`update-all`、`update-kernel`、`remount` 五条命令在最外层先经过一道互斥检查。已经有一个在运行时，重入的直接返回 `{ ok: false, error: "BUSY…" }`，不排队——排队会让界面看起来点了没反应。一个内核进程只服务一个 home，所以进程内的一个标志就够了；运行中抛错也会释放。插件管理对外只有命令（见[对外只有命令](/docs/plugin-manager/commands)），没有绕开这道检查的调用方式。

<Diagram name="pm-busy" title="改动命令经过 BUSY 检查，同一时刻最多一个写 home 的 pnpm；只读的 outdated 不经过 BUSY">
- 命令 A（`install`）通过 BUSY 检查、设上标志，它的 `pnpm add` 开始运行、写 home
- 命令 B（`uninstall`）进来时标志还设着，不排队，马上得到 `{ ok: false, error: "BUSY…" }`
- 命令 C（`outdated`）只读，不经过 BUSY，它的 `pnpm outdated` 和 A 的 `pnpm add` 同时运行，不写文件，不影响 A
- A 返回回执时释放标志（抛错也会释放），再来的改动命令又能通过
</Diagram>

**已知边界**：BUSY 管不到下面三处，为什么不另外加检查见[删掉 pnpm 串行队列、只留 BUSY](/trajectory/2026-09-25-drop-pnpm-queue-keep-busy)。

- `add-entry`、`remove-entry`、`enable`、`disable`、`transfer-owner` 五条命令不经过 BUSY：`update-all` 正在重新加载某条条目时，别人可以同时停用或删掉它
- `update-all` 或 `remount` 重新加载插件管理自己时，先发回执、释放 BUSY，下一个宏任务才重新加载：这中间进来的改动命令能通过检查，可能运行到一半插件管理就被停用；重新加载出来的新实例 BUSY 标志是新的，不知道旧实例里还有没有命令在运行
- 管不到插件管理进程外的 pnpm：`devkit.home.new`、`devkit.dev`、人在终端里手工运行的 pnpm，和插件管理的改动同时写同一个 home 时照样会丢改动
