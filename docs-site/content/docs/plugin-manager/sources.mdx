# 找插件

**本页回答**：`search` 在哪些市场上找、每个市场去哪个源查；怎么判断一个包是插件；市场名单存在哪、谁来改；`search` 为什么不经 BUSY。命令怎么组合着用见说明书 [gwb-plugin-manager](/docs/outputs/skills/gwb-plugin-manager)。

代码在 `src/package-sources.ts`（命令逻辑，把下面几样接起来）、`src/sources.ts` 与 `src/search.ts`（纯逻辑）、`src/pnpm-config.ts`（问 pnpm 要配置）、`src/registry.ts`（网络）。

<Diagram name="pm-sources" title="search 在哪些市场上找，每个市场去哪个源查">
- 市场名单是设置插件公共区里的一项 `plugin-markets`，每项一个 scope，默认 `["@godcreator"]`；人在插件管理窗格「可安装」一栏加删，agent 用 `settings.set` 改
- 每个市场的源地址问 pnpm：在 home 里运行 `pnpm config list --json`，只认这个 scope 自己的 `@scope:registry`；pnpm 这份配置合了 `~/.npmrc`、`<home>/.npmrc`、pnpm 自己的全局配置与环境变量
- 私有源的凭据按源地址从当前 home 的共享 secret `npm-auth` 取
- 各市场并发发 `GET <源>/-/v1/search?text=<scope>&size=250`，包清单 `keywords` 含 `gwb-plugin` 的才算插件，合并进 `packages`；每个市场查得怎样写进 `markets`
- 装包的 `plugin-manager.install` 经 pnpm 读的是同一份配置，所以搜到的包就从这个源装
</Diagram>

## 市场名单：只在名单里的 scope 上找

npmrc 里的源不都是 gwb 的：pnpm 自带一条 `@jsr:registry`，机器上还可能有公司的私有源、换全局源的镜像。所以 `search` 不拿 npmrc 里的每条路由去查，只查**市场名单**里的 scope。名单是设置插件公共区（`section` 为 `*`）的一项 `plugin-markets`，字符串数组，默认只有 `@godcreator`。放公共区是为了地址固定：窗格与 agent 改它不用知道插件管理那条条目的 id；值和别的设置一样存在各个 home 自己的 `settings.json` 里，每个 home 一份，而源地址所在的 `~/.npmrc` 是整台机器共用的。插件管理只在设置插件与命令总线都在时声明这一项、登记 `search`。

## 源地址问 pnpm，和装包用同一份配置

每次 `search` 在 home 里运行一次 `pnpm config list --json`，拿到的是 pnpm 装包时用的那份合并配置：机器级 `~/.npmrc`、home 级 `<home>/.npmrc`、pnpm 自己的全局配置（`pnpm config set` 写进的地方）与环境变量都在里面。插件管理不自己读 npmrc，所以源配在哪一层，搜的和装的都是同一个源。这份输出里的机器凭据不使用。私有源只读当前 home 的共享 secret `npm-auth`，其中 JSON 对象以 `//主机/路径/:_authToken` 为键。缺值时匿名请求，删除后不会从机器配置复活。

**一个市场只认它自己的路由 `@scope:registry`**：没有这条时 pnpm 会去全局源装，那不是这个市场，查出来多半是空的；所以这时这个市场报「pnpm 里没配这个市场的源」，并说要往 `~/.npmrc` 加哪一行，不去全局源查。scope 写法不对（不是 `@` 开头的小写名字）也在这个市场上报错。

## 各市场并发查，一个失败只影响它自己

名单里的市场并发查，查成的合并进回执的 `packages`；每个市场查得怎样按名单顺序写进 `markets`（`scope`、`registry`、`ok`、查成时的 `count`、没查成的 `error`），没查成的另在 `note` 里点名；全都没查成才回 `ok: false`，原因逐个写明。

每个市场发 `GET <registry>/-/v1/search?text=<scope>&size=250`，有凭据就带 `Authorization: Bearer`，最多等 10 秒。检索接口是 npmjs、Verdaccio、gitea 都实现的标准协议，这里不认识任何具体的源。凭据只在这次请求里用，不进回执与日志。

{/* ref file="../plugins/plugin-manager/src/registry.ts" lines="4-31" hash="87bafebce13a" blob="56c6ac868cbd" */}

**是不是插件只看包清单 `keywords` 里有没有 `gwb-plugin`**，包名前缀、scope 都不参与判断。这个字段只在检索响应里有（单包详情接口会去掉它），一次请求就能判断完；判断完就从回执里拿掉，回执每行只有 `pkg`、`version`、`description`。gitea 的检索响应把 scope 与名字分开放，解析时拼回完整包名。

## 加一个市场：改名单，源配给 pnpm

源路由与凭据接入由说明书编排。加一个市场需要：往名单里加 scope（窗格「可安装」一栏，或 `settings.set {"section":"*","key":"plugin-markets",…}`），再让 pnpm 知道这个 scope 的源——往 `~/.npmrc` 加 `@<scope>:registry=<源地址>`，私有源通过 `credentials.import/copy` 填入本 home 的 `npm-auth`，回执不含原文。说明书 [gwb-plugin-manager](/docs/outputs/skills/gwb-plugin-manager) 的「加一个市场」写清这两步，做完调 `search` 看这个市场的 `ok`。`@godcreator` 的路由本来就要有：本机每个 home 的安装、每个源码仓的安装与发版都靠它。

## 不改 home，不经 BUSY

`search` 用不带 BUSY 检查的方式登记。BUSY 防的是两次改动同时改 home 的 `package.json`；`search` 只读设置、pnpm 的配置与网络，运行的 `pnpm config` 也不写 home。检索可能要等好几个市场，排在安装后面只会让「可安装」列表等到安装做完才出来。

真实 registry 与 pnpm 的配置只能实机验证：`devkit.home.new` 开一个隔离 home，在里面调 `search`。

## 子进程使用当前 home 的凭据

安装、升级、查更新和 devkit 发布使用 `withHomeRegistryAuth`。它只读指定 home 的 `credentials.json`，将非敏感源路由与凭据环境变量引用写进临时 auth-file，通过 pnpm 12 的 `NPM_CONFIG_USERCONFIG` 覆盖机器鉴权。旧认证环境变量先清除；完成或失败后清理临时文件，错误与回执里的已知认证值替换为占位符。配置文件不含凭据原文，系统 npmrc 不改。实际工作目录或所属工作区的 `.npmrc` 若含认证项，执行前拒绝，避免其优先级盖过 home 凭据；由接入 skill 先迁入指定 home 并移除工程旧认证行，源路由保留。

创建新 home 的引导安装使用发起 home 的凭据，凭据不会复制到新 home；新 home 后续操作需独立配置。普通终端 pnpm 沿用终端自己的配置。
