# 开发套件

`@godcreator02/gwb-devkit` 是**一个普通的 gwb 件**。它没有任何特权：装进 home 才有它的命令，
挂不上就什么都没有，跟 hello 一个待遇。这一点是理解它的起点——它看起来像「工具链」，
但它跟工具链最大的区别是**它自己也得走它教别人走的那条路**（起独立仓、发本机源、装进 home），
而且它确实是那么来的。

它解决的问题只有一个：**「在一个新文件夹里开发一个新件」这条路上，每一步都有个能被 agent
调到的口。** 建仓要有口、本机源的起停要有口、开一个干净的测试 home 要有口、从页面取证要有口。
没有这些口，每一步都是一段要人记在脑子里的 PowerShell。

## 一次调用从头到尾

拿最长的那条路——`devkit.scaffold`——走一遍，这套东西怎么转就清楚了：

1. **命令进来。** 它是登记在 `gwbCommands` 上的一条普通命令，参数是 `unknown`，第一件事是
   收窄。参数不对不报「参数错误」，把**整份说明**回给调用方——这条命令的主要调用方是 agent，
   命令总线不带参数形状，它认得出自己错在哪全靠这句话
2. **算计划。** 短名派生出包名、插件名、命令名前缀；目标目录绝对化；`docs` 与 `port` 定下来。
   这一步是纯函数，不碰盘
3. **整套模板在内存里渲染完。** 十个 `.tpl` 读进来、占位符替掉。**认不出的占位符当场抛**
4. **落盘。** 目标目录必须还不存在
5. **站那半，两步。** 件已经在盘上了，这时才去建文档站——而且**一步都不是自己建**：
   经命令总线调 `docs-site.create`（站件铺 fumadocs 骨架），再调 `docfirst.attach`
   （docfirst 件在刚铺好的骨架上装六区）
6. **回执。** 建了几个文件、骨架铺没铺、六区装没装、下一步做什么

第 2、3、4 步全是纯函数与盘操作，可以不起进程、只喂输入看输出；第 5 步要把活派给
别的件。这条分界线不是偶然，它就是下面「纯逻辑与真机器」那一节的分界线。

## 它管哪四件事

| | 是什么 | 口 |
| --- | --- | --- |
| 建仓 | 把一个新件的骨架落进一个新文件夹，默认连文档站一起（站那半两步转给别的件） | `devkit.scaffold` |
| 手册 | 写件的整条路、七条红线、验机怎么走，随包发。**只挂自己那份** | `skills/` 经 `gwbSkills` 挂载 |
| 本机源 | 本机 Verdaccio 的起 / 停 / 状态 / 日志，另有一扇窗格 | `registry.*` |
| 测试 home | 测试 home 的开 / 列 / 重开 / 停 / 删 | `devkit.home.*` |

外加一条经 `gwbNodeCli` 登记的外部 CLI：**`devkit.cdp-eval`**（从页面取证）。
（`devkit.livedoc` 0.3.0 起退役，理由在「站那半」那节。）

**CLI 形态的东西一律经 `gwbNodeCli` 登记，不做总线命令、不进程内调。** 理由不是洁癖：
node-cli 登记的命令自动镜像成同名总线命令，于是自动是 MCP 工具，回执自带 stdout、stderr
与退出码。自己写一遍 spawn 与超时，换来的是同一件事的第二种回执形状。

## 依赖方向

这一节是整份里最该看的。**devkit 一个别的件的包都不依赖。**

```text
devkit ──硬 inject──▶ gwbCommands                （唯一一条）
devkit ──可选──────▶ gwbNodeCli / gwbSkills / gwbSettings / gwbShell
devkit ──按名字找──▶ docs-site.create / docfirst.attach   （只在总线上，不依赖包）
```

**一、站那半是「找一条命令」，不是「依赖一个包」。** 2026-09-10 之前 devkit 的
`dependencies` 里有 `@godcreator02/live-doc-cli`：它解析那个包、起它的 `init`、
还把它的两份 skill 代挂给工作台。现在那条依赖没了，站那半改成在命令总线上按名字找
两条命令——找得到就调，找不到就跳过那一步、在回执里说清怎么补。

判据是那次拆分本身：站件、docfirst 件、开发件**三者互不依赖**，凭什么单单 devkit 要把
其中两个钉进自己的依赖树。换个角度问同一件事：一个不需要钉码的 fumadocs 站（容器里
那个 TypeScript 交互教学站就是）凭什么先装一套钉码机制。

两条命令名就是全部的耦合面——**两个字符串**。哪个件没装，`hasCommand` 当场就知道；
它**现问、不缓存**，因为件是热挂载的，装一个新件之后这个答案当场就变。

**二、除了 `gwbCommands`，别的件全是可选依赖。** 写法上的区别只有一处：硬依赖写
`export const inject = [...]`（缺了整件不挂），可选依赖写 `ctx.inject([...], fn)`
（开一条子 fiber，缺服务时那条 fiber 永远 PENDING，而主件照常挂上）。

上面这两行就是这件事的正本：**硬依赖只有一条**。没有命令总线，devkit 登记的一切都出不了
这个进程，那时它确实不该挂上；而没有 node-cli，它只是从页面取不了证——不是不能干活。

那条 node CLI 就挂在这条子 fiber 上。这里曾经还捕获过一格 `gwbNodeCli` 供建站用，
连带一个「服务撤了要把它还回去」的 `effect`；站那半改走总线之后那一格没了——
**耦合面缩小，随手也少掉一处生命周期陷阱**。

**三、说明书只挂自己那份。** 0.2.x 时 devkit 顺手把 docfirst 的 `skills/` 也 register
一次（理由：docfirst 那时是个 CLI 包、不是件，自己挂不上）。**现在不了**：

docfirst 成了件、自己挂那两份，而说明书是**全局单一命名空间**——同名的第二份直接不挂、

## 纯逻辑与真机器：隔离在哪一刀

{/* tree dir="../src" depth="1" */}

切法只有一条判据：**这段逻辑能不能不起进程、不开窗、只喂输入看输出。**

| 模块 | 它知道什么 | 它**不知道**什么 |
| --- | --- | --- |
| `scaffold.ts` | 短名怎么派生、占位符表、模板怎么渲染、落盘的两条纪律 | 不知道文档站、不知道 node-cli、不知道命令总线。**连「站建成没有」都是别人告诉它的** |
| `daemon.ts` | 本机源的起停时序、轮询多久算超时 | 不知道怎么起进程、怎么杀进程、怎么 ping——那三样是构造时传进来的接口 |
| `home.ts` | home 怎么命名、开之前要不要 build、删之前要不要拦 | 同上 |
| `node-registry-deps.ts` / `node-home-deps.ts` | 真机器：`child_process`、盘、进程表、端口持有者 | 不知道任何时序与判断，它们只是手 |
| `index.ts` | 接线：谁挂在哪个服务上、参数怎么收窄、回执长什么样 | 不写任何判断逻辑 |

`daemon.ts` 与 `home.ts` 的隔离是**显式接口**（`RegistryDeps` / `HomeDeps`）：
真跑时传 `node-*-deps.ts`，测试时传一套假的。换掉实现，时序那半一行不用改——
这正是「隔离靠抽象接口，不靠自觉」的那句判据问过去了。

`scaffold.ts` 的隔离是另一种形状：它根本不需要接口，因为它**只做纯计算与同步写盘**。
所以它的测试直接写临时目录跑——`writeRepo` 的活就是往盘上放文件，拿替身测等于没测。

{/* ref file="../src/scaffold.ts" lines="85-108" */}

`planScaffold` 是这条分界线上最清楚的一段：校验、派生、绝对化、缺省值，全在这儿，
一次都没碰盘。它抛出的错误是给人和 agent 看的，所以每一句都说得出该怎么改。

## 站那半：两条不属于本包的命令

{/* ref file="../src/index.ts" lines="545-575" */}

建站是**两步**，中间那几行是这一节的全部内容：

1. `docs-site.create`（站件）铺一个标准 fumadocs 骨架，**认站目录** `<仓>\docs-site`，
   端口由它扫邻居挑
2. `docfirst.attach`（docfirst 件）在骨架上装六区

**为什么中间不能插事。** `attach` 只在**还没写过内容的骨架**上装得了——站里已经有
`docfirst.config.mjs`、或 `content/` 下有骨架之外的东西，它报一句「这个站已有内容，
请人工接线」退非零，一个字都不改写。这不是保守：建骨架与装六区连着跑，中间没人碰过
文件，整个覆盖才是安全的；给一个跑了半年的站自作聪明地 AST 改写不是。`scaffold` 里
这两条紧挨着，正是那个安全的时刻。

**三种「没建成」，一种都不算建仓失败。** 件那半早已落盘：站件没装（总线上没有
`docs-site.create`）、`create` 自己失败、docfirst 件没装或 `attach` 失败——回执里
`built` 与 `attached` 两格分别说，`note` 写清卡在哪、怎么补，`nextSteps` 按这两格分三支。
**回执里给一条不存在的 `cd docs-site` 比不给还坏**，所以连 README 里讲站的那段话都
是在渲染之前按「站件在不在」定下来的。

**退役的那条。** 这里曾经是 `devkit.livedoc`——把 `@godcreator02/live-doc-cli` 的可执行
登记进 `gwbNodeCli`，`init` 建站、`check` / `confirm` / `render` 靠按次给的 `cwd`。
那个包线不再更新，那些活现在**在仓里发生**：`cd <仓>\docs-site` 之后 `pnpm doc` /
`pnpm doc:confirm` / `pnpm doc:render`，docfirst 件不转发、不起子进程。**一件事只留一个
入口**：留着旧那条，agent 有两条路可走，而其中一条指着一个不再更新的包。

## 怎么用

装：`plugins.install {"pkg":"@godcreator02/gwb-devkit"}`。挂上了看 `<home>\gwb.log`
那句「开发套件就绪」，它把这一版真登记上的命令逐条列了出来——**那一行就是「它真的在干活」
的证据**，不是「装完就好了」。

写件的整条路、七条红线、验机怎么走，在随包发的 skill「gwb-devkit」里，不在这儿复述。
