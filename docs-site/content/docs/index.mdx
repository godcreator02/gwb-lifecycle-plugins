**本页回答**：`gwb-lifecycle-plugins` 仓是什么、为什么存在；写一个插件从建仓到装进日常用的 home，每一步由哪个包做、跨过哪条接缝；带着不同的目的来接着读哪几页；两个包各有哪些模块、模块之间与仓外靠哪九条接缝相连。

## 是什么、为什么存在

god 工作台的本体只提供插件平台，功能全由插件实现。这个仓放的是**写插件、装插件用的两个插件**，都是 home 里的普通插件，没有任何特权：

- **开发套件** `@godcreator/gwb-devkit`（`plugins/devkit/`）：把「在一个新文件夹里开发一个新插件」这条路上的每一步做成 agent 能调用的命令——建仓、开关隔离 home、把改动装进隔离 home 验证、发正式版、在页面里取证——外加随包发布的写插件说明书与发版规则。使用者是 agent，没有界面
- **插件管理** `@godcreator/gwb-plugin-manager`（`plugins/plugin-manager/`）：home 里唯一写 home 的插件——装卸包、增删启停条目、热升级、换内核包，报告插件 peer 里的内核包与别的插件满没满足

两个包各自发版，放在一个仓里是因为改一处就要改另一处的地方多（`devkit.dev` 经插件管理装开发版、peer 范围的比对规则只在插件管理里写一份）。两个插件合起来覆盖一个插件从建仓到卸载的整个生命周期，仓因此叫 `gwb-lifecycle-plugins`；包名与说明书名仍是 `gwb-devkit`、`gwb-plugin-manager`。为什么这么切分、哪些决定错了难改，见[关键设计](/docs/design)。

## 写一个插件，从头走一遍

说明书 `gwb-devkit` 是这条路的操作步骤，这里只标出每一步由哪个包做、跨过哪条接缝：

1. **看能用什么**：读提供方插件的类型声明——它导出的类型、给 cordis 的 `Context` 补的项与文档注释——[cordis 服务怎么提供和使用](/docs/rules/services)
2. **建仓**：`devkit.scaffold` 把模板渲染进一个新目录（workspace 仓，插件在 `plugins/<短名>/`），不建文档站——[建仓与加插件](/docs/devkit/scaffold)。生成的插件包 peer 那几项过得了发版前检查——[4 模板与发版前检查](/docs/seams/template-release)
3. **改成真插件**：照[写插件的规矩](/docs/rules)写，仓根 `pnpm build`、`pnpm check`
4. **开隔离 home**：`devkit.home.new` 在新 home 里装好内核包、`cordis` 与基础插件（插件管理与提供 `timer` 服务的 `@cordisjs/plugin-timer` 都在其中），用宿主安装版启动，调试端口自动选——[测试 home](/docs/devkit/home)、[7 内核与 home](/docs/seams/kernel-home)
5. **改一版看一版**：`devkit.dev` 在仓根构建，每个包打成开发版的包文件放进隔离 home 的 `dev-packs`，经 CDP 在那个 home 的页面里调插件管理的 `install` / `update` 装包并重新加载，整页刷新，最后取证——[改一版看一版](/docs/devkit/dev)、[2 devkit 调插件管理](/docs/seams/plugin-manager-calls)、[6 CDP 驱动](/docs/seams/cdp)、[10 被测仓的形状](/docs/seams/repo-shape)
6. **在页面里取证**：`devkit.cdp` 在隔离 home 的页面里点击、读数、截图——[CDP 驱动](/docs/devkit/cdp)
7. **发正式版**：升版本号、提交，`devkit.release` 查过 git 工作区、产物、依赖写法、peer 里的内核包与插件之后，按依赖顺序发到各包的发布目标——[发正式版](/docs/devkit/release)、[3 peer 里的内核包与插件](/docs/seams/kernel-peer)、[9 pnpm 与包源](/docs/seams/pnpm-registry)
8. **装进日常用的 home**：在 `default` 里 `plugin-manager.install` 或 `plugin-manager.update`，调用方拿到回执后自己 `shell.reload`——[插件管理](/docs/plugin-manager)、[8 条目树](/docs/seams/entry-tree)
9. **清理**：`devkit.home.rm` 删掉验完的隔离 home

插件管理与开发套件在第 1、2 步之外处处相连：第 4 步装进新 home 的插件管理，就是第 5 步装开发版、第 8 步升级 `default` 的那一个。

## 按来意读

- **写一个新插件、改一个插件**：先读说明书 `gwb-devkit`（`skill.read {"name":"gwb-devkit"}`），规矩在[写插件的规矩](/docs/rules)
- **升版本号**：说明书 `gwb-release`；**发版**：说明书 `gwb-devkit` 的「发版」
- **在本仓动手**（第一次准备、提交前的检查、在隔离 home 里验证本仓的改动、发版、文档站）：[开发](/docs/develop)
- **改开发套件的某条命令**：[开发套件](/docs/devkit)的代码地图，再读那条命令的机制页
- **改插件管理**：[插件管理](/docs/plugin-manager)；它和内核之间的约定在 [8 条目树](/docs/seams/entry-tree)，和开发套件之间的在 [2 devkit 调插件管理](/docs/seams/plugin-manager-calls)
- **改建仓模板或发版前检查**：[4 模板与发版前检查](/docs/seams/template-release)，两边要在同一个提交里改
- **词不认得**：[术语表](/docs/glossary)

## 九条接缝

<Diagram name="seam-map" title="虚线框是包，连线是接缝，编号对应下面的表">
- 本仓两个包：开发套件（建仓、测试 home、改一版看一版、发正式版、CDP 驱动、建仓模板）、插件管理
- 仓外：工作台服务（`gwbCommands`、`gwbNodeCli`、`gwbSkills`）；内核与 home（exe、`runtime.json`、`gwb.log`）；cordis loader 的条目树；pnpm 与包源（npm 源、pnpm 的配置与 `~/.npmrc`、设置插件公共区的市场名单）；工作台页面（`window.gwb`）；被测插件仓
- 实线接缝有代码接口；点线接缝（3、4、6、7、10）只靠约定：命令名、文件格式、字段名或「两处一起改」
</Diagram>

| # | 接缝 | 连接的模块 | 交换什么 | 页 |
| --- | --- | --- | --- | --- |
| 1 | 工作台服务 | 开发套件、插件管理 ↔ 命令总线、node 命令行、说明书、外壳 | 登记命令、登记 `devkit.cdp`、登记说明书、报显示名 | [工作台服务](/docs/seams/workbench) |
| 2 | devkit 调插件管理 | 开发套件 ↔ 插件管理 | 从插件管理主入口 import pnpm 定位、版本范围判定与命令名；经 CDP 调 `install` / `update` / `list`；`home.new` 自己装包、写条目 | [devkit 调插件管理](/docs/seams/plugin-manager-calls) |

一条接缝连接的模块只要接口不变就能各自替换；每条接缝由什么测试保护，写在它自己那一页。内核那边对插件管理的承诺（home 布局、loader 与 include 的版本）写在内核仓文档站的接缝页「home 布局与条目树」。
