# 开发套件

`@godcreator02/gwb-devkit` 是**一个普通的 gwb 件**。它没有任何特权：装进 home 才有它的命令，
挂不上就什么都没有，跟 hello 一个待遇。这一点是理解它的起点——它看起来像「工具链」，
但它跟工具链最大的区别是**它自己也得走它教别人走的那条路**（起独立仓、发本机源、装进 home），
而且它确实是那么来的。

它解决的问题只有一个：**「在一个新文件夹里开发一个新件」这条路上，每一步都有个能被 agent
调到的口。** 建仓要有口、本机源的起停要有口、开一个干净的测试 home 要有口、从页面取证要有口。
没有这些口，每一步都是一段要人记在脑子里的 PowerShell。

## 一次调用从头到尾

拿最长的那条路——`devkit.scaffold`——走一遍，这套东西怎么转就清楚了：

1. **命令进来。** 它是登记在 `gwbCommands` 上的一条普通命令，参数是 `unknown`，第一件事是
   收窄。参数不对不报「参数错误」，把**整份说明**回给调用方——这条命令的主要调用方是 agent，
   命令总线不带参数形状，它认得出自己错在哪全靠这句话
2. **算计划。** 短名派生出包名、插件名、命令名前缀；目标目录绝对化；`docs` 与 `port` 定下来。
   这一步是纯函数，不碰盘
3. **整套模板在内存里渲染完。** 十个 `.tpl` 读进来、占位符替掉。**认不出的占位符当场抛**
4. **落盘。** 目标目录必须还不存在
5. **站那半。** 件已经在盘上了，这时才去建文档站——而且**不是自己建**：经 `devkit.livedoc`
   这条 node CLI 调 `livedoc init --dir <仓>`
6. **回执。** 建了几个文件、站建成没有、下一步做什么

第 2、3、4 步全是纯函数与盘操作，可以不起进程、只喂输入看输出；第 5 步要起一个真进程。
这条分界线不是偶然，它就是下面「纯逻辑与真机器」那一节的分界线。

## 它管哪四件事

| | 是什么 | 口 |
| --- | --- | --- |
| 建仓 | 把一个新件的骨架落进一个新文件夹，默认连文档站一起 | `devkit.scaffold` |
| 手册 | 写件的整条路、七条红线、验机怎么走，随包发 | `skills/` 经 `gwbSkills` 挂载 |
| 本机源 | 本机 Verdaccio 的起 / 停 / 状态 / 日志，另有一扇窗格 | `registry.*` |
| 测试 home | 测试 home 的开 / 列 / 重开 / 停 / 删 | `devkit.home.*` |

外加两条经 `gwbNodeCli` 登记的外部 CLI：**`devkit.livedoc`**（建站）与
**`devkit.cdp-eval`**（从页面取证）。

**CLI 形态的东西一律经 `gwbNodeCli` 登记，不做总线命令、不进程内调。** 理由不是洁癖：
node-cli 登记的命令自动镜像成同名总线命令，于是自动是 MCP 工具，回执自带 stdout、stderr
与退出码。自己写一遍 spawn 与超时，换来的是同一件事的第二种回执形状。

## 依赖方向

这一节是整份里最该看的。**devkit 依赖谁，谁都不知道 devkit 存在。**

```text
devkit ──依赖──▶ live-doc-cli        （运行时真依赖，dependencies）
devkit ──可选──▶ gwbCommands          （唯一的硬 inject）
devkit ──可选──▶ gwbNodeCli / gwbSkills / gwbSettings / gwbShell
```

**一、livedoc 是单向的运行时依赖。** devkit 知道 livedoc（解析它的包、调它的 `init`、
把它的两份 skill 挂给工作台）；livedoc 的 `init` 只认「一个仓 + 一份模板」，
**它不知道调它的人在写什么件，也不知道 gwb 这个生态存在**。判据用一句话就能问过去：
换掉 livedoc 的实现（比如换一个别的建站器），devkit 要改的只有一条 `entry` 的算法与一串
参数，别的一行不动。

这条方向定下来的那一刻，devkit 就永远不会长成「文档工具」——它只是知道去哪儿要一个站。

**二、除了 `gwbCommands`，别的件全是可选依赖。** 写法上的区别只有一处：硬依赖写
`export const inject = [...]`（缺了整件不挂），可选依赖写 `ctx.inject([...], fn)`
（开一条子 fiber，缺服务时那条 fiber 永远 PENDING，而主件照常挂上）。

## 纯逻辑与真机器：隔离在哪一刀

{/* tree dir="../src" depth="1" */}

切法只有一条判据：**这段逻辑能不能不起进程、不开窗、只喂输入看输出。**

| 模块 | 它知道什么 | 它**不知道**什么 |
| --- | --- | --- |
| `scaffold.ts` | 短名怎么派生、占位符表、模板怎么渲染、落盘的两条纪律 | 不知道文档站、不知道 node-cli、不知道命令总线。**连「站建成没有」都是别人告诉它的** |
| `daemon.ts` | 本机源的起停时序、轮询多久算超时 | 不知道怎么起进程、怎么杀进程、怎么 ping——那三样是构造时传进来的接口 |
| `home.ts` | home 怎么命名、开之前要不要 build、删之前要不要拦 | 同上 |
| `node-registry-deps.ts` / `node-home-deps.ts` | 真机器：`child_process`、盘、进程表、端口持有者 | 不知道任何时序与判断，它们只是手 |
| `index.ts` | 接线：谁挂在哪个服务上、参数怎么收窄、回执长什么样 | 不写任何判断逻辑 |

`daemon.ts` 与 `home.ts` 的隔离是**显式接口**（`RegistryDeps` / `HomeDeps`）：
真跑时传 `node-*-deps.ts`，测试时传一套假的。换掉实现，时序那半一行不用改——
这正是「隔离靠抽象接口，不靠自觉」的那句判据问过去了。

`scaffold.ts` 的隔离是另一种形状：它根本不需要接口，因为它**只做纯计算与同步写盘**。
所以它的测试直接写临时目录跑——`writeRepo` 的活就是往盘上放文件，拿替身测等于没测。

{/* ref file="../src/scaffold.ts" lines="84-113" */}

`planScaffold` 是这条分界线上最清楚的一段：校验、派生、绝对化、缺省值，全在这儿，
一次都没碰盘。它抛出的错误是给人和 agent 看的，所以每一句都说得出该怎么改。

## livedoc 那条命令为什么只适合 `init`

{/* ref file="../src/index.ts" lines="67-73" */}

`import.meta.resolve` 拿到的是包主入口 `dist/run.mjs`，可执行在它旁边。
**不读 `bin` 字段、不查 `.bin` 垫片**：node-cli 登记的是一个绝对路径的 js，
而垫片在 Windows 上是 `.cmd`，`process.execPath` 起不了它。

但这条命令**只适合 `init`**，这是一条真限制不是偏好：`livedoc init` 的目标由 `--dir` 给，
跟 cwd 无关；而 `check` / `confirm` / `render` 认的是 **cwd 里那份 `livedoc.config.mjs`**，
**node-cli 的 `cwd` 在登记时就定死、按次不可换**。所以那三条只能在那个仓的 `docs-site` 里
`pnpm livedoc …` 自己跑。

绕它的两条路都更坏：给 node-cli 加「按次传 cwd」是动一个被别人 inject 的件的契约面；
在 devkit 里进程内 import livedoc，是把一条 CLI 拉进本进程，回执形状与失败模式立刻分岔。

## 怎么用

装：`plugins.install {"pkg":"@godcreator02/gwb-devkit"}`。挂上了看 `<home>\gwb.log`
那句「开发套件就绪」，它把这一版真登记上的命令逐条列了出来——**那一行就是「它真的在干活」
的证据**，不是「装完就好了」。

写件的整条路、七条红线、验机怎么走，在随包发的 skill「gwb-devkit」里，不在这儿复述。
