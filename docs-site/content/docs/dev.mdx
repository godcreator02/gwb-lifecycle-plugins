# 改一版看一版

**本页回答**：`devkit.dev` 这条链凭什么站得住，它换的是什么、不换什么，以及为什么它必须站在
被换的那个进程外面。

## 管什么

一句话：**把工作区里的改动送进另一个 home 正在跑的那个进程，并且证明送到了。**

顺序是七步，一步都不能省：问目标页它是哪个 home、仓根构建、发开发版、在目标 home 里装那个准确
号并读回核对、重挂条目、整页重载、取证。中间任何一步失败当场停，回执里带着停在哪一步。

{/* ref file="../plugins/devkit/src/dev.ts" lines="332-351" */}

**重挂是目标进程里的一条命令，不是这边发的两条。** 每条条目调一次 `plugin-manager.remount`，
停用、等拆完、启用、等挂上都在那条命令里做完。拆成停用、启用两条的话，被换的正好是提供启用那条
命令的 plugin-manager 自己、或者命令总线本身时，第二条没人接，条目留在停用。回执有两种成功：
`remounted` 在回执之前就做完了，带着重挂后的状态，只有 `ACTIVE` 算挂上；`deferred` 是
plugin-manager 重挂它自己，回执先发、下一个宏任务才动手，这边就轮询 `plugin-manager.list`，
等它重新答话、那条条目 active，到点没等到回 `ok: false` 并说清卡在哪。所以目标 home 的
plugin-manager 要 0.4.0 起。

**装是「目标 home 清单写准确号，再 `pnpm install`」，装完读回核对。** 不走 `pnpm add <包>@<号>`：
清单里已有 `^` 声明时（`plugin-manager.install` 写出来的就是），pnpm 沿用那个前缀写回 `^<号>`，
锁里已解析的同 patch 旧预发布号被当成满足新范围、不重解析；源上有更新的同 patch 号时范围又解析到
它——装上的都不是这一趟发的号，退出码照样 0。清单里写死准确号就没有范围可解析。装完读
`node_modules/<包>/package.json` 的 `version`，对不上当场 `ok: false`、不重挂：

**版本号必须变，那是这条链的机制本身。** Node 的 ESM 模块图按 URL 缓存，同一个 URL 永远是同一
个模块实例；原地覆盖产物不改路径，于是 cordis 把插件停用再启用，`import()` 回来的还是旧的。发一个
开发版把号打成 `<patch+1>-dev.<戳>`，装上的版本变了就是路径变了，重挂那一下才真的重新求值。同 patch
的多趟 dev 号也成立：pnpm 虚拟仓目录名超长时截成前段加全名哈希，预发布段与 peer 后缀都在哈希里。
前提是这一趟的号真装上了，所以上一段那道核对不能省。

{/* ref file="../plugins/devkit/src/dev.ts" lines="57-75" */}

**覆盖 dist 那条近路不走。** home 里 `node_modules` 下的文件是硬链接到 pnpm
全局 store 的，覆盖写写的是共享那个 inode，store 里那份从此变成开发构建——此后这台机器上
任何人装那个版本拿到的都是它，而且不报错。加戳 import 是第三条路：不可逆泄漏，量级约等于插件 dist
体积的两倍。两条都不如发一个新号。

{/* ref file="../plugins/devkit/src/dev.ts" lines="14-24" */}

**最后一步是取证，不是刷新。** 少了它，人看到「重挂了、刷新了」就会说验过了。三样合起来才盖得
住那几种「看着成了」：装上的就是这一趟发的号（pnpm 退出码 0、条目全活、日志干净，跑着的也可能是
上一趟的版本），条目要真的 ACTIVE（判的是 fiber 状态，不是 fiber 建出来了），日志增量里
不许有 error（`apply` 里一条 async 静默 reject，现象正好是「挂上了但什么都没发生」，那一条只在
日志里）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="435-468" */}

**目标用名字指，端口是查出来的。** 给 `home` 名，端口从那个 home 的 `runtime.json` 里查（内核开机
写的那份），顺带验活：pid 还活着、且那个 pid 真的持着记录里那个端口。**两头都要**：记录回答
「你要的是哪个」，页面回答「你连上的实际是哪个」，不符当场拒——端口会被下一个进程占走，
只信记录就会把一趟改动静默推给另一个现场。

{/* ref file="../plugins/devkit/src/dev.ts" lines="115-119" */}

## 不知道什么

**不知道被换的是什么插件。** 它只认包名与版本号，插件干什么、有没有窗格、有没有命令，一概不问。

**不知道那份运行时记录是怎么来的。** 它只读，写它的是内核与 mcp 插件。

**不知道怎么连 CDP、怎么起进程、怎么读盘。** 那三样全在注入面后头。

**不知道目标 home 在哪**——那是问出来的，不是配出来的。目标页上的样式表与 importmap 都是带着
home 路径的 `file://` 地址，所以问一趟正在跑的那张页就有答案。配置里存一份 home 路径，只会在
人换了窗口之后继续指着旧的。

**不知道第一次装怎么装。** 目标 home 里没有这个包的条目时，它装完就停在那儿、在回执里说怎么补，
不替人建条目。装是一件事，挂是另一件事。

## 数据结构

三样：一趟的输入（点名要的那个 home、仓根、包目录、刷新后等谁、本插件自己住的 home）、一趟的回执
（目标 home、发了哪几个包哪几个号、重挂了哪几条条目、刷新结果、取证），以及取证本身（逐包的
发出号与装上号、条目表、没活过来的那几条、日志增量里的 error 与 warn）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="273-316" */}

输入里没有「要不要构建」，也没有源地址。**构建是这条链的正身**：产物不新就发等于发的是上一版，
而回执从头到尾一切正常；源这台机器上只有一个，收一个参数只会多出一条「发去了别处」的岔路。

## 提供的接口

对外只有一条命令，登记在命令总线上：`devkit.dev`，走整条链。

**取证只有 `collect` 这一条路，而且只在链里头走。** 判定要基线：哪些 error 是这一趟自己惹出来的，
只有拿装包之前那个日志长度才分得出来。单独摆一眼现状的东西不该长成一条命令——它没有基线，看到的
error 可能是几天前的，而人会拿它的绿色当验收，那正好是这条链防的那件事。

{/* ref file="../plugins/devkit/src/dev.ts" lines="471-473" */}

要现看一眼某个 home 的条目表，`devkit.cdp {"args":["<名>","cmd","plugin-manager.list"]}` 就是，
那是看，不是验。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `run` | 跑 pnpm 到结束，拿回输出尾巴 | `node-dev-deps.ts` 起子进程 | 记一行调用、按名字让某条失败 |
| `cdp` | 对目标页跑一个动作，拿回它打的 JSON | 起 `bin/cdp.mjs` 的子进程 | 直接回一张假回执 |
| `publish` | 在临时目录摆一份分发形态再发出去 | 真 `pnpm publish` | 只记一行 |
| `published` | 这个号在源上有没有 | `pnpm view` | 查一张表 |
| 盘那几条 | 读清单、问产物在不在、写目标 home 的清单、读回装上的包清单、取日志基线与增量 | `node:fs` | 内存里的文件表；假 `pnpm install` 照清单摆 `node_modules`，也能演「退出码 0 却没换号」 |
| `sleep` | 轮询回执之后才重挂的那一条时，两趟之间等一会儿 | `setTimeout` | 只记一行、不真等 |

{/* ref file="../plugins/devkit/src/dev.ts" lines="235-269" */}

**为什么 CDP 那条是起子进程，不是进程内连。** 那支驱动必须能在工作台没起的时候独立跑，那是它
的另一个身份；所以它是一支零依赖单文件的脚本，不是一个可 import 的模块。一趟循环多五六次进程
启动，几百毫秒，对一趟一分钟的链可以忽略。

**它也是按名字调的**，不是按端口：那支驱动自己查记录、自己核对页面自报的名字，于是链里每一步都
白得一次「我连的还是那个 home 吗」。传端口的话，这七步就成了七次没人看着的重新定位。

## 怎么单独测

喂一套假的注入面，整条时序在测试里跑得完，不必真发一次版、真开一个 home。假插件要能演出来的是
边角：目标是 `default`、目标就是自己所在那个 home、这个号已经在源上、构建失败、目标 home 没有
重挂命令、重挂回执没到 `ACTIVE`、部署的正是 plugin-manager 自己（回执之后才重挂，要轮询到它回来，
回不来要到点判失败）或命令总线、条目没活过来、日志增量里冒出 error、`pnpm install` 退出码 0 却
没换号（要当场停、不重挂）、装没成（清单要放回原样）。清单改写本身（已有 `^` 声明改成准确号、没有就
按名字排进去、缩进照原样）是纯函数，单测直接喂文本。

守卫那几道是这条链上最该测的：它们决定「拒不拒」，而一旦拒错了，代价是开发版进了日常那份 home、
这条命令把正在跑的自己停掉，或者一趟改动推给了另一个隔离现场。

## 代码地图

**在哪**：纯机在 `src/dev.ts`，真机器在 `src/node-dev-deps.ts`，页那半的身体在 `bin/cdp.mjs`
（见[那支驱动](/docs/cdp)），接线在 `src/index.ts`。

**先读** `runDev`：七步顺序摆在一个函数里，每一步一句话注释说清为什么在这个位置。

**读序**：`guardHome`（拒什么）→ `runDev`（顺序）→ `pinExact` / `checkInstalled`（怎么装、怎么认
装上了）→ `collect`（拿什么当证据）→ `DevDeps`（哪些
东西是注进来的）。真机器那一层最后读，它只是手。

**可跳过**：`node-dev-deps.ts` 里摆临时目录、改分发清单那几十行是 npm 打包的细节，跟这条链的
判断无关。
