# 改一版看一版

**本页回答**：`devkit.dev` 这条链凭什么站得住，它换的是什么、不换什么，以及为什么它必须站在
被换的那个进程外面。

## 管什么

一句话：**把工作区里的改动送进另一个 home 正在跑的那个进程，并且证明送到了。**

顺序是七步，一步都不能省：问目标页它是哪个 home、仓根构建、发开发版、在目标 home 里装那个准确
号、条目停用再启用、整页重载、取证。中间任何一步失败当场停，回执里带着停在哪一步。

{/* ref file="../src/dev.ts" lines="336-349" */}

**版本号必须变，那是这条链的机制本身。** Node 的 ESM 模块图按 URL 缓存，同一个 URL 永远是同一
个模块实例；原地覆盖产物不改路径，于是 cordis 把件停用再启用，`import()` 回来的还是旧的。发一个
开发版把号打成 `<patch+1>-dev.<戳>`，版本变了就是路径变了，重挂那一下才真的重新求值。

{/* ref file="../src/dev.ts" lines="57-76" */}

**最后一步是取证，不是刷新。** 少了它，人看到「重挂了、刷新了」就会说验过了。两样合起来才盖得
住那几种「看着成了」：条目要真的 ACTIVE（判的是 fiber 状态，不是 fiber 建出来了），日志增量里
不许有 error（`apply` 里一条 async 静默 reject，现象正好是「挂上了但什么都没发生」，那一条只在
日志里）。

{/* ref file="../src/dev.ts" lines="435-463" */}

**目标用名字指，口是查出来的。** 给 `home` 名，口从那个 home 的 `runtime.json` 里查（内核开机
写的那份），顺带验活：pid 还活着、且那个 pid 真的持着记录里那个口。手工起的老 home 没有记录，
那时给 `cdp` 直连。**两头都要**：记录回答「你要的是哪个」，页面回答「你连上的实际是哪个」，
不符当场拒——端口会被下一个进程占走，只信记录就会把一趟改动静默推给另一个现场。

## 不知道什么

**不知道被换的是什么件。** 它只认包名与版本号，件干什么、有没有窗格、有没有命令，一概不问。

**不知道那份运行时记录是怎么来的。** 它只读，写它的是内核与 mcp 件。

**不知道怎么连 CDP、怎么起进程、怎么读盘。** 那三样全在注入面后头。

**不知道目标 home 在哪**——那是问出来的，不是配出来的。目标页上的样式表与 importmap 都是带着
home 路径的 `file://` 地址，所以问一趟正在跑的那张页就有答案。配置里存一份 home 路径，只会在
人换了窗口之后继续指着旧的。

**不知道第一次装怎么装。** 目标 home 里没有这个包的条目时，它装完就停在那儿、在回执里说怎么补，
不替人建条目。装是一件事，挂是另一件事。

## 数据结构

三样：一趟的输入（目标调试口、点名要的那个 home、仓根、包目录、要不要构建、刷新后等谁、源地址、
本件自己住的 home）、
一趟的回执（目标 home、发了哪几个包哪几个号、重挂了哪几条条目、刷新结果、取证），以及取证本身
（条目表、没活过来的那几条、日志增量里的 error 与 warn）。

## 提供的接口

对外只有两条命令，都登记在命令总线上：`devkit.dev` 走整条链，`devkit.dev-check` 只摆现状。

**`dev-check` 不下判定，这是有意的。** 单独跑的时候没有「这一趟之前」的基线，看到的 error 可能
是几天前的。判定只发生在 `devkit.dev` 里头那一次，它在装之前记下了日志有多长。拿 `dev-check`
的绿色当验收，正好是这条链防的那件事。

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `run` | 跑 pnpm 到结束，拿回输出尾巴 | `node-dev-deps.ts` 起子进程 | 记一行调用、按名字让某条失败 |
| `cdp` | 对目标页跑一个动作，拿回它打的 JSON | 起 `bin/cdp.mjs` 的子进程 | 直接回一张假回执 |
| `publish` | 在临时目录摆一份分发形态再发出去 | 真 `pnpm publish` | 只记一行 |
| `published` | 这个号在源上有没有 | `pnpm view` | 查一张表 |
| 盘那几条 | 读清单、问产物在不在、取日志基线与增量 | `node:fs` | 内存里的文件表 |

{/* ref file="../src/dev.ts" lines="235-265" */}

**为什么 CDP 那条是起子进程，不是进程内连。** 那支驱动必须能在工作台没起的时候独立跑，那是它
的另一个身份；所以它是一支零依赖单文件的脚本，不是一个可 import 的模块。一趟循环多五六次进程
启动，几百毫秒，对一趟一分钟的链可以忽略。

## 怎么单独测

喂一套假的注入面，整条时序在测试里跑得完，不必真发一次版、真开一个 home。假件要能演出来的是
边角：目标是 `default`、目标就是自己所在那个 home、这个号已经在源上、构建失败、停用失败、条目
没活过来、日志增量里冒出 error。

守卫那几道是这条链上最该测的：它们决定「拒不拒」，而一旦拒错了，代价是开发版进了日常那份 home、
这条命令把正在跑的自己停掉，或者一趟改动推给了另一个隔离现场。

## 代码地图

**在哪**：纯机在 `src/dev.ts`，真机器在 `src/node-dev-deps.ts`，页那半的身体在 `bin/cdp.mjs`
（见[那支驱动](/docs/cdp)），接线在 `src/index.ts`。

**先读** `runDev`：七步顺序摆在一个函数里，每一步一句话注释说清为什么在这个位置。

**读序**：`guardHome`（拒什么）→ `runDev`（顺序）→ `collect`（拿什么当证据）→ `DevDeps`（哪些
东西是注进来的）。真机器那一层最后读，它只是手。

**可跳过**：`node-dev-deps.ts` 里摆临时目录、改分发清单那几十行是 npm 打包的细节，跟这条链的
判断无关。
