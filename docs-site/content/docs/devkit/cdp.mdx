**本页回答**：`bin/cdp.mjs` 管到哪里为止、它为什么是零依赖的纯 JS 单文件，以及它为什么不跟本包别的代码共用任何东西。

## 管什么

把「一个选择器」换算成「视口里的一个点」，检查那个点上最上层的确实是它，然后让浏览器把事件发下去；外加几个不看界面的动作。十二个动作分两类，依赖的东西不同：

| 类 | 动作 | 依赖的是 |
| --- | --- | --- |
| 浏览器输入 | `move` / `click` / `rclick` / `drag` / `type` / `key` / `scroll` / `shot` | Chromium 的 Input 与 Page 域 |
| 不看界面 | `eval` / `cmd` / `reload` / `home` | Runtime 域；`cmd` 还要页面上有 `window.gwb.command`，`home` 还要页面地址里带 home 路径 |

**点不到的时候会报出原因**，这是它比「在页面里自己构造事件」强的地方：构造出来的事件不做命中测试，目标被浮层挡住照样点得到，而遮挡正是界面最容易出的错；构造出来的事件 `isTrusted` 是 false，按可信输入做判断的地方行为不同。这里发的是浏览器层的事件，命中测试由浏览器自己做，点不到时把挡住它的那条祖先链和目标的 `pointer-events` 一起报出来。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="309-322" */}

**问一个页面属于哪个 home**，靠的是页面上那些 `file://` 地址里带着的 home 路径（外壳插入的样式表就是）。不用配置、不用猜；出现不止一个 home 就直接说不猜，不挑一个。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="398-418" */}

这个问题不只是 `home` 动作用，**每次运行都要问一次**：连上之后先拿它跟你给的名字对，对不上就停。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="609-621" */}

记录只说「它启动的时候用的是这个端口」，不说「此刻这个端口上还是它」。进程可能已经退出、端口被下一个进程占用，而记录还留在那里指着这个端口。名字是唯一的定位方式之后，这道核对就是「连对了没有」的最后一道检查；少了它，按名字定位只是看起来安全。

所以 `home` 这个动作回的**不是「对不对得上」**——那件事在 `run()` 之前已经做完了——而是那个 home 的绝对路径。`devkit.dev` 拿它来检查目标，拦住 `default` 与本插件自己所在的 home。

## 不知道什么

**不知道页面里有什么。** 要读取哪些值跟着界面走，界面改一版就要加一段、改一段；而这个脚本管的是怎么把事件发进页面，那件事很少需要改。混在一起，稳定的部分会跟着不稳定的部分一起改。所以要读一组值就写一个文件，用 `eval <文件> [JSON 参数]` 送进页面执行。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="378-396" */}

**文件里一律是一个函数表达式**，`(args) => 一张表`，要 await 就写成 async；不给参数就传空对象。只有这一条规则——「是函数就调用、不是就直接求值」其实是两条规则，而选错分支时不报错，只是回一个看不懂的值。文件放在哪是调用方的事，一次性的放 `out/`（它被 gitignore，本来就随时可以清空）；提交进仓的会随着界面变化而过时，而且不报错。

**不看工作目录。** 它的路径一概不依赖进程在哪里运行：经命令总线调用时，进程的工作目录是它自己所在的包目录（home 的 `node_modules` 里）；直接用 node 运行时，是输入命令的那个 shell 的目录，同一个相对路径在两种情况下指向不同的地方。所以截图缺省放在**被截图的那个 home 自己的目录** `<home>\out\cdp\`，要放别处只收绝对路径；`eval` 的文件只收绝对路径，相对路径当场拒。写磁盘之前还有一道检查：位置不能在本包目录与任何 `node_modules` 里。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="91-139" */}

**不知道本包别的代码存在。** 它不 import 任何东西，也不读 `src/`。按 home 名查端口也一样：它自己拼出 `runtime.json` 的路径去读，不用 `src/home.ts` 里的那套解析。

**不查 pid，也不查端口归谁。** 它只把端口读出来就去连，连不上就照实说连不上：

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="185-194" */}

光一个 `ECONNREFUSED` 会让人去查网络，而这种情况绝大多数是那个 home 已经退出、记录还留着（进程退出后记录不删，这是有意的）。**确认进程还在的检查在调用方**：`devkit.dev` 动手之前核对 pid 与监听端口的进程，那三道检查见[测试 home](/docs/devkit/home)。这里只负责「连上的这个页面到底是不是它」。

## 数据结构

没有持久的数据。一次运行就是：连上唯一的那个页面，发几条 CDP 消息，把结果作为一段 JSON 写到标准输出。失败时那段 JSON 照样写全，只把退出码设成非零。

## 提供的接口

两种调用方式，同一份代码：

- 工作台运行时经命令总线调用，`devkit.cdp {"args":["<home 名>","<动作>",…]}`，经 `gwbNodeCli` 登记，回执自带 stdout 与退出码
- 工作台没运行时直接 `node <包根>/bin/cdp.mjs <home 名> <动作>`

{/* ref file="../plugins/devkit/src/index.ts" lines="329-338" */}

<Diagram name="dk-cdp" title="一次 CDP 驱动的运行：两个入口，同一个脚本，五步">
- 两个入口：工作台运行时调 `devkit.cdp`（由 `gwbNodeCli` 登记，启动 node 子进程），工作台没运行时直接 `node bin/cdp.mjs`
- 第 1 步按 home 名查端口：读 `<home 根>/<名>/runtime.json` 的 `cdp` 字段，给数字当场拒
- 第 2 步连上唯一的页面：问 `http://127.0.0.1:<端口>/json/list`，候选不是正好一个就把候选列进报错；选定后用 WebSocket 连上
- 第 3 步核对页面属于哪个 home：从页面上带 home 路径的 `file://` 地址读出名字，跟给的名字对不上就停
- 第 4 步执行动作，以 `cmd` 为例：在页面里执行 `window.gwb.command(命令名, 参数)`
- 第 5 步把结果作为一段 JSON 写到标准输出，失败时退出码非零；经 `devkit.cdp` 调用时回执带 stdout、stderr 与退出码
</Diagram>

**第一个位置只收 home 名**，端口从 `<home 根>/<名>/runtime.json` 里查出来。给数字当场拒，不悄悄换成别的理解：

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="145-163" */}

**端口不是地址。** 它是一个没有含义的数字，输错一位就连到另一个 home，而那个 home 会照样收下你发的事件，事后也看不出哪里不对。名字有拼写、有记录、连上之后还能跟页面报的名字对一次，这三样端口都没有。代价是这个驱动从此**只能操作 gwb 的窗口**：别的 Chromium 页面没有那份记录，也答不出自己属于哪个 home。

**home 根目录与内核同一个算法**：`<appData>/gwb-kernel/homes`，Windows 上是 `%APPDATA%\gwb-kernel\homes`，没有 `APPDATA` 直接报错；devkit 插件的 `devkit.home.*` 与 `devkit.dev` import 的也是这个函数。记录不在、或者记录里没有 `cdp` 字段（启动时没带那个开关），都算「连不上」：照实报，让人停掉重开一次。

**选不出唯一一个页面时，候选页面的列表就在报错里**：一个都没有时报「现有这些」，不止一个时报「用 `--target` 选一个」，两种都带着各页面的标题与地址。所以不必先另跑一条命令去列页面——那条命令回的内容，正好是出错时本来就会输出的那些。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="198-204" */}

**这是它必须是零依赖单文件、必须是纯 JS 的全部理由。** 第二种调用方式是它存在的一半原因：工作台启动不了的时候，人还得有办法看看那个窗口到底怎么了。让它进类型检查，就得让它变成要先构建的东西，而要先构建的东西在「工作台启动不了」的时候正好用不上。代价是它那十二个动作没有类型检查。

## 依赖的接口

三样：Node 的 `fetch` 与 `WebSocket`（连 Chromium 的调试端口）、目标页面上的 `window.gwb.command`（只有 `cmd` 动作用）、home 里的 `runtime.json`（每次读一遍，只读 `cdp` 字段）。三样都不是本包的代码。

**超时按动作分档，不是一个数。** 它防的是页面卡住，不是「这条命令做的事久」：工作台的一条命令可能在装依赖、在构建，十几秒回不来很正常，按十五秒中断的话，中断的是一条正在做事的命令，而那边不会因此停下，回执从此没人收。输入与求值那几种还是十五秒，它们要么立刻回，要么就是页面真卡住了。

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="178-179" */}

五个开关：`--target` 页面不止一个时按标题或地址选、`--mod` 带修饰键、`--pad` 给 `shot` 的裁剪留边、`--size` 把视口当成这么大（对当前连接生效，必须跟动作写在同一次调用里）、`--timeout` 改超时。

## 怎么单独测

**决定文件写到哪的那部分有单元测试，其余只能实际运行。** 位置怎么算是一组纯函数（home 根目录、home 目录、截图位置、`eval` 的文件、写磁盘前的检查）。文件被 import 时只导出它们，文件末尾那段只在被 node 直接运行时才执行：

{/* ref file="../plugins/devkit/bin/cdp.mjs" lines="625-648" */}

`tests/cdp.test.ts` 直接 import 它、给路径看结果：截图缺省位置在被截图那个 home 的 `out\cdp\`、不在本包目录与任何 `node_modules` 里，两处相对路径都拒；另有一条检查整个文件里不出现 `process.cwd()`。

它做的其余每件事都要一个真的 Chromium 调试端口在另一头：发真实事件、做命中测试、截真实的图。用假实现能测到的只剩拼参数，而那不是它出错的地方。

它靠被使用来验收：`devkit.dev` 流程里的重新加载、刷新、取证三步就是启动它的子进程做的，流程通过说明这几个动作是通的。要单独看一眼，开一个隔离 home，`node bin/cdp.mjs <home 名> home` 是最小的一次运行：它有结果，就说明查端口、连页面、核对名字三件事都通了——任何一步不通它都不会往下走。

**只对隔离 home 用，绝不用在 `default` 上。** 这里发的是真实操作，会真的改动那个 home 里的数据。

## 代码地图

**在哪**：`bin/cdp.mjs`，一个文件，文件开头就是完整的动作表与开关表。

**先读**文件开头那几十行注释：动作怎么写、点怎么写、内核启动时要带哪两个开关都在那里。

**读序**：决定文件写到哪的那一段（`shotFileOf` / `evalFileOf` / `assertWritable`，纯函数）→ `portOf`（home 名怎么变成端口）→ `connect`（连上唯一的那个页面，一个都没有与不止一个时都把候选列进报错）→ `assertHome`（连上的这个页面是不是它）→ `probeExpr`（选择器怎么变成一个点）→ `run` 里的 switch（一个动作一个分支）。

**可跳过**：按键的虚拟键码表与鼠标事件的参数拼装，那是 CDP 规定的形状，不是这个脚本的判断。

**内核要这样启动**，两个开关缺一不可：`--remote-debugging-port=<端口>` 打开调试入口，`--disable-backgrounding-occluded-windows` 关掉窗口被遮挡时的降频。少了后一个，窗口被别的窗口完全挡住时 Chromium 认为它不可见、停止渲染新帧，截图拿到的是旧画面、`requestAnimationFrame` 一次都不回调。
