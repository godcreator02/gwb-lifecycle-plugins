**本页回答**：`devkit.release` 依次做哪几步、每一步为什么排在那里；发版前检查对每个包查什么、按什么判；它不碰哪些东西；怎么单独测、代码从哪读起。发版的操作步骤（发之前验什么、发完怎么升级 `default`）在说明书 `gwb-devkit` 的「发版」，升哪一位在说明书 `gwb-release`，本页不复述。

## 管什么

一句话：**只从提交过的状态、只在全部检查都过了之后，把一组包发成正式版。**

收仓根 `dir` 与要发的包目录 `packages`（必给，非空数组，相对仓根，按依赖顺序），可选收额外的源 `alsoPublishTo`（http(s) 地址的数组，见下面「额外的源」），依次做六步：

<Diagram name="dk-release" title="devkit.release 发正式版：六步依次做，任何一处没过，一个包都不发">
- 第 1 步仓根 git 工作区干净（`git status --porcelain=v1`），不干净或问不出连构建都不运行；第 2 步仓根 `pnpm build`
- 第 3 步每个包：清单读得出、`publishConfig.registry` 认得出、`files` 白名单里的产物都在；第 4 步这个版本号在包的每个发布目标上都还没有
- 第 5 步发版前检查，要发的包一起查、一次列全：peer 只有 `cordis`、内核包与插件、peer 里的插件和源上 latest 在同一条线、peer 不成环、peer 里内核包的写法、产物里的 import、带界面插件的样式、插件注入的服务与 peer 对不对得上；dev 依赖不查
- 第 6 步在临时目录组装发布内容，按 `packages` 给的顺序发到各自的发布目标、标上 latest
- 最下面那个框：任一项没过，一个包都不发，回执按包列出每一项问题
</Diagram>

每一步的位置都有理由：

- **git 工作区在构建之前查**：把没提交的改动发成 latest，是事后最难发现的错误；版本号也在仓里升、随提交走
- **在仓根构建，不在包目录**：工作区里的插件常常用着同仓另一个包的产物
- **产物清单就是 `files` 白名单**：不另列一份，两份清单迟早对不上，现象是新写的代码发出去不生效
- **同号已在发布目标上就拒**：同一个版本号永不重发；问不出有没有（源连不上）也不往下发
- **全部检查在发第一个包之前做完、问题一次列全**：发到一半停下，源上各包的 latest 就是新旧两版混在一起；只报第一处的话，每改一处都要再完整构建一次才看得到下一处
- **同一次发的包之间写 `^新版本号`**：依赖方装得到这一次发的那一版，也跟得上之后破坏边界以内的版本

发布目标是包自己 `package.json` 的 `publishConfig.registry`；没写、或写的不是 http(s) 地址就拒，报错写明要加什么、给出 npmjs 的写法作例子：

它写进临时目录里发布内容清单的 `publishConfig.registry`，命令行不带 `--registry`；「同号已在源上」也问这个源。为什么这么传见 [pnpm 与包源](/docs/seams/pnpm-registry)。`publishConfig` 里别的字段（如 `access`）原样留在发布内容清单里。

**额外的源**：给了 `alsoPublishTo`，每个包发到自己的发布目标之后，再依次发到这几个源，一个包的各个源都发完再发下一个包；回执的 `shipped` 每个源一条。用在换源的过渡期：本机按范围行从旧源装，新源已经开始收包。「同号已在源上」对每个源都问，有一个已有就拒；某个包的 `publishConfig.registry` 也写在 `alsoPublishTo` 里时拒，同一个源只发一次。参数不是 http(s) 地址的数组、有重复，在命令入口就拒。

## 发到 npmjs：交给 GitHub Actions

发布目标里有 npmjs（`https://registry.npmjs.org/`，结尾的 `/` 写没写都算）的包，不在本机发。npmjs 要求账号开两步验证，本机发包每次都要人在浏览器里批准；npmjs 给 CI 的办法是 trusted publishing：npmjs 上给每个包登记「哪个 GitHub 仓的哪个工作流可以发它」，工作流运行时用 GitHub 签发的身份证明去发，不存 token。

发版前检查都过了之后、发任何一个包之前，先查三件事，有一件不满足就拒：仓根有 `.github/workflows/publish.yml`；这些包的 `repository` 都指向同一个 GitHub 仓；HEAD 已经推到那个仓上（Actions 照这个提交建 release）。然后本机先发完别的源，再把同样组装好的发布内容按 `packages` 的顺序打成包文件，文件名前加两位序号，在 HEAD 上建一个 GitHub release（tag 是 `release-<UTC 年月日>-<时分秒>`）：先建草稿、传上包文件，再公开。公开那一刻触发 `publish.yml`，它下载包文件、按文件名排序依次 `npm publish`，已经在 npmjs 上的跳过，所以失败后在网页上重跑不会重复发。

{/* ref file="../plugins/devkit/src/release.ts" lines="512-578" hash="9329029ed66c" blob="70da389b6287" */}

包文件在本机构建与检查，工作流只负责发，所以它关掉了 provenance：provenance 声称包是在那次运行里构建的，和实际不符。工作流的模板在 devkit 包的 `template/repo/.github/workflows/publish.yml.tpl`，`devkit.scaffold` 建仓时一起生成。

等那次运行跑完最多 3 分钟。跑成功了回执 `ok: true`，`data.actions` 是 release 与那次运行的网址；没跑完或失败回 `ok: false`，写明本机已经发完的源和运行的网址。新版本过几分钟才查得到，紧接着升级 `default` 可能还看不到它。

查提交、等运行这类只读请求遇到网络错误会隔几秒重试几次；建 release、传包文件不重试，免得重复建。GitHub 的凭据用 git 凭据管理器里 github.com 那一份，就是推送用的同一份，不弹登录窗口、不写盘：

{/* ref file="../plugins/devkit/src/node-github.ts" lines="14-51" hash="26b498d64052" blob="062e9221bf77" */}

npmjs 上每个包要先存在、再登记 trusted publisher，所以一个包第一次发到 npmjs 还是由人在本机发（`npm publish --auth-type=web`，浏览器里批准）；之后用 `npm trust github <包名> --repo <owner>/<仓名> --file publish.yml --yes` 登记，登记后两天内要有一次成功的发布，不然登记作废。

## 不知道什么

- **不碰任何 home**：只往各包的发布目标发包，从哪个 home 调用结果都一样；升级 `default` 是之后的事
- **不改仓里任何文件**：发布内容在系统临时目录里组装，`workspace:` 与 `catalog:` 依赖在那份清单里改写，仓里的 `package.json` 一个字不动
- **不决定版本号**：发的是 `package.json` 里写的版本号，升哪一位由人照说明书 `gwb-release` 定
- **不知道该问哪个源要别的包的 latest**：交给用户级 `~/.npmrc` 的范围行，命令行不指定源
- **不做类型检查**：关掉 `skipLibCheck` 的那次类型检查由改依赖的人自己运行（见[依赖怎么写](/docs/rules/deps)）
- **不查 dev 依赖**：dev 只在构建与类型检查时用，落后于源上 latest 不影响运行；写了源上没有的号，仓根 `pnpm install` 当场失败，用不着等到发版

## 提供的接口

对外一条命令 `devkit.release {"dir","packages","alsoPublishTo"?}`。发版前检查对**每个要发的包**查：

- 产物里的 import：相对 import 指向的文件都在，产物按 JS 语法读得下去

**插件包**（`keywords` 含 `gwb-plugin`）另查七项：

- peer 里只有 `cordis`、内核包 `@godcreator/gwb-kernel-desktop` 与别的插件。是不是插件读包目录 `node_modules` 里它的清单：`keywords` 含 `gwb-plugin` 的是 gwb 插件，同时含 `cordis` 与 `plugin` 的是第三方 cordis 插件（如 `@cordisjs/plugin-timer`），两种都算。不是插件、清单读不到都拒，报错写明按「运行时谁提供」该改写成 dev 还是 `dependencies`
- peer 里的每个插件（不分包名范围；内核包、`workspace:` 除外）写法是 `^x.y.z`，并且和源上 latest 在同一条线：主版本号为 0 时只比次版本号，≥1 时只比主版本号。不在同一条线说明上游出了破坏性版本；问不出 latest 也拒
- peer 不成环：从本包出发，顺着 peer 里的 gwb 插件的已装清单一路往下走，走回本包就拒，理由里列出环（`A → B → A`）。怎么走见下面「peer 不成环」
- peer 里写了内核包，写法是 `^x.y.z`；拒绝理由里写着改成 `^<验证时那个内核的版本号>`。范围包不包含哪个内核不查：对照调用它的那个 home 里的内核，能不能发版就取决于从哪个 home 调。范围由人在隔离 home 里验过之后改（说明书 `gwb-devkit` 的「发版」第 1 步）
- 带界面的插件（构建后有 `dist/style.css`）过样式检查，和 `devkit.dev` 构建之后查的是同一套，见下面「样式检查」
- 注入与 peer 一致：`src/` 下源码注入的每个服务，提供方写在 peer 里，必需注入的不标 `optional`；注入写法认不出就拒。怎么扫、怎么判见下面「注入与 peer」

**peer 不成环**：插件管理升级时按 peer 排重新加载的先后，被依赖的先；peer 成了环，环上的包排不出先后，只能重启工作台才换上新版本（见[热升级](/docs/plugin-manager/upgrade#重新加载的先后被依赖的先)）。所以发版前从本包出发，顺着 peer 里的 gwb 插件（`keywords` 含 `gwb-plugin`；`cordis` 与内核包不算）往下走，走回本包就拒，每个直接 peer 各报一条最短的环。往下走读的是装上的清单：本包 peer 里的包在包目录的 `node_modules` 里找，再往下照 node 的解析规则从那个包的真实目录往上找——pnpm 把一个包 peer 里的包放在它真实目录的旁边；同一次发的包按工作区里的清单算（它们 peer 里写 `workspace:*`，装着的未必是这一版）。读不到清单的包不往下走，第一层读不到由「peer 只许三类包」那项报。

**样式检查**在 `src/style-check.ts`，`devkit.release` 与 `devkit.dev` 共用。插件包构建后有 `dist/style.css` 才查：

## 依赖的接口

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `gitStatus` | 仓根工作区干不干净；问不出也是一种答案：拒 | `git status --porcelain=v1`，改动行由 `dirtyLines` 按 porcelain 条目的样子认（stderr 里的警告不算） | 回预设的干净、不干净或问不出 |
| `run` | 仓根 `pnpm build` | `runCaptured`，超时终止整棵进程树 | 记一行调用、可以让它失败 |
| `published` | 这个版本号在发布目标上有没有 | `pnpm view <包>@<版本> version`，指定去问发布目标；退出码 0 是有，报 `ERR_PNPM_PACKAGE_NOT_FOUND` / `ERR_PNPM_FETCH_404` 是没有，别的失败抛出 | 一张「已发过」的表 |
| `latest` | peer 里的 gwb 插件在源上的 `dist-tags.latest`（dev 依赖不问） | `pnpm view <包> dist-tags.latest`，不指定源；失败回 `undefined`，由检查报「问不出」 | 一张 latest 表，可以缺项 |
| `publish` | 在临时目录组装发布内容并发出、标上 latest；npmjs 不经它 | `node-dev-deps.ts` 的组装（与开发版打包共用），最后 `pnpm publish --no-git-checks --tag latest` | 记下发了什么、写进去的依赖范围，可以让某一个失败 |
| `packRelease` | 发 npmjs 的包：同样组装，打成包文件交给 Actions | 同一套组装，最后 `pnpm pack --pack-destination` | 记下打了什么、写进去的依赖范围 |
| `headCommit` / `github` | HEAD 的提交号；查提交在不在 GitHub 上、建 release、传上包文件、等 `publish.yml` 跑完 | `git rev-parse HEAD`；`node-github.ts` 经 GitHub REST API，凭据取自 git 凭据管理器 | 固定的提交号；可以让提交不在、让运行失败或没跑完 |
| `tempDir` / `removeDir` / `now` | 放包文件的临时目录；release 的 tag 用的时刻 | 系统临时目录下新建、`removeTree`；`Date.now()` | 固定的目录与时刻 |
| `readText` / `exists` | 读清单、查产物、读 peer 的清单与内核包页面入口 | `node:fs` | 内存里的文件表 |
| `filesUnder` / `tailwindOf` | 样式检查：列出样式入口与 `.tsx`；从被检查包的 `@tailwindcss/cli` 旁边找 Tailwind 编译器。注入检查也用 `filesUnder` 列 `src/` 下的源码与提供方的运行时代码 | `node-dev-deps.ts` 里的同名函数 | 内存里的文件表；假编译器，颜色类与 `@apply` 那几条用真实编译器 |
| `realpath` | peer 不成环：包目录链接指向的真实目录，从那里往上找它 peer 里的包 | `fs.realpathSync` | 原样返回，或一张链接表 |
| `workspacePackageDirs` | 注入检查判「写 peer 会成环」时，工作区里有哪些包目录 | `node-dev-deps.ts` 里的同名函数，仓根往下扫两层 | 给定的目录表 |
| `pnpm` | 上面几条启动的 pnpm | 命令开头在两个固定位置找到并核对过版本的那个 | 一个假路径 |

组装发布内容时改写依赖的范围：临时目录不在工作区里，pnpm 不会替换 `workspace:` 与 `catalog:`，所以在发布内容清单里换成具体范围。dependencies 里同一次发的包写 `^新版本号`，不管它原来写的是什么；其余的 `workspace:` 写 `^<工作区里的版本号>`（从仓根往下扫两层找，找不到直接报错）；`catalog:` 写仓根 `pnpm-workspace.yaml` 的 catalog 里同名包的范围。peer 里不写同一次发的准确版本号，`workspace:` 与 `catalog:` 照样改写。细节见[被测仓的形状](/docs/seams/repo-shape)。

## 代码地图

**在哪**：流程与版本号规则在 `src/release.ts`，产物检查在 `src/artifact-check.ts`，注入与 peer 的检查在 `src/wiring-check.ts`，真机器操作（git、pnpm、组装临时目录）在 `src/node-dev-deps.ts`，GitHub 那一步（凭据、release、等运行）在 `src/node-github.ts`，命令登记与参数校验在 `src/index.ts` 的 `registerReleaseCommand`。

**先读** `runRelease`：六步的顺序在这一个函数里。

**读序**：`runRelease` → `planPackages`（每个包的清单、发布目标、产物、同号）→ `ticketFor`（一个包的全部检查）→ `peerLineProblems` / `peerProblems` / `peerCycleProblems` / `kernelPeerProblems` / `artifactProblems` / `wiringProblems` → `ReleaseDeps`（哪些是注入的）。

**可跳过**：`sameReleaseLine`、`dirtyLines` 这几个小函数，形状简单、有测试覆盖；`node-dev-deps.ts` 里复制文件、写临时清单的那几十行是 npm 打包的细节。
