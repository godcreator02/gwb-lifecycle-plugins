**本页回答**：`devkit.release` 依次做哪几步、每一步为什么排在那里；发版前检查对每个包查什么、按什么判；它不碰哪些东西；怎么单独测、代码从哪读起。发版的操作步骤（发之前验什么、发完怎么升级 `default`）在说明书 `gwb-devkit` 的「发版」，升哪一位在说明书 `gwb-release`，本页不复述。

## 管什么

一句话：**只从提交过的状态、只在全部检查都过了之后，把一组包发成正式版。**

收仓根 `dir` 与要发的包目录 `packages`（必给，非空数组，相对仓根，按依赖顺序），依次做六步：

{/* ref file="../plugins/devkit/src/release.ts" lines="354-383" hash="901b7771b278" blob="49970d7b348f" */}

<Diagram name="dk-release" title="devkit.release 发正式版：六步依次做，任何一处没过，一个包都不发">
- 第 1 步仓根 git 工作区干净（`git status --porcelain=v1`），不干净或问不出连构建都不运行；第 2 步仓根 `pnpm build`
- 第 3 步每个包：清单读得出、`publishConfig.registry` 认得出、`files` 白名单里的产物都在；第 4 步这个版本号在包的发布目标上还没有
- 第 5 步发版前检查，要发的包一起查、一次列全：peer 只有 `cordis`、内核包与插件、peer 里的插件和源上 latest 在同一条线、peer 里内核包的写法、产物里的 import、带界面插件的样式、插件注入的服务与 peer 对不对得上；dev 依赖不查
- 第 6 步在临时目录组装发布内容，按 `packages` 给的顺序发到各自的发布目标、打 latest
- 最下面那个框：任一项没过，一个包都不发，回执按包列出每一项问题
</Diagram>

每一步的位置都有理由：

- **git 工作区在构建之前查**：把没提交的改动发成 latest，是事后最难发现的错误；版本号也在仓里升、随提交走
- **在仓根构建，不在包目录**：工作区里的插件常常用着同仓另一个包的产物
- **产物清单就是 `files` 白名单**：不另列一份，两份清单迟早对不上，现象是新写的代码发出去不生效
- **同号已在发布目标上就拒**：同一个版本号永不重发；问不出有没有（源连不上）也不往下发
- **全部检查在发第一个包之前做完、问题一次列全**：发到一半停下，源上各包的 latest 就是新旧两版混在一起；只报第一处的话，每改一处都要再完整构建一次才看得到下一处
- **同一次发的包之间写 `^新版本号`**：依赖方装得到这一次发的那一版，也跟得上之后破坏边界以内的版本

发布目标是包自己 `package.json` 的 `publishConfig.registry`；没写、或写的不是 http(s) 地址就拒，报错写明要加什么、给出团队源地址作例子：

## 不知道什么

- **不碰任何 home**：只往各包的发布目标发包，从哪个 home 调用结果都一样；升级 `default` 是之后的事
- **不改仓里任何文件**：发布内容在系统临时目录里组装，`workspace:` 依赖在那份清单里改写，仓里的 `package.json` 一个字不动
- **不决定版本号**：发的是 `package.json` 里写的版本号，升哪一位由人照说明书 `gwb-release` 定
- **不知道该问哪个源要别的包的 latest**：交给用户级 `~/.npmrc` 的范围行，命令行不指定源
- **不做类型检查**：关掉 `skipLibCheck` 的那次类型检查由改依赖的人自己运行（见[依赖怎么写](/docs/rules/deps)）
- **不查 dev 依赖**：dev 只在构建与类型检查时用，落后于源上 latest 不影响运行；写了源上没有的号，仓根 `pnpm install` 当场失败，用不着等到发版

## 提供的接口

对外一条命令 `devkit.release {"dir","packages"}`。发版前检查对**每个要发的包**查：

- 产物里的 import：相对 import 指向的文件都在，产物按 JS 语法读得下去

**插件包**（`keywords` 含 `gwb-plugin`）另查六项：

- peer 里只有 `cordis`、内核包 `@godcreator/gwb-kernel-desktop` 与别的插件。是不是插件读包目录 `node_modules` 里它的清单：`keywords` 含 `gwb-plugin` 的是 gwb 插件，同时含 `cordis` 与 `plugin` 的是第三方 cordis 插件（如 `@cordisjs/plugin-timer`），两种都算。不是插件、清单读不到都拒，报错写明按「运行时谁提供」该改写成 dev 还是 `dependencies`
- peer 里的每个插件（不分包名范围；内核包、`workspace:` 除外）写法是 `^x.y.z`，并且和源上 latest 在同一条线：主版本号为 0 时只比次版本号，≥1 时只比主版本号。不在同一条线说明上游出了破坏性版本；问不出 latest 也拒
- node 侧产物的包名 import 只有 node 内置模块、`electron` 与本包 peer 里写了的包；浏览器侧产物只 import 页面 importmap 里的名字
- peer 里写了内核包，写法是 `^x.y.z`；拒绝理由里写着改成 `^<验证时那个内核的版本号>`。范围包不包含哪个内核不查：对照调用它的那个 home 里的内核，能不能发版就取决于从哪个 home 调。范围由人在隔离 home 里验过之后改（说明书 `gwb-devkit` 的「发版」第 1 步）
- 带界面的插件（构建后有 `dist/style.css`）过样式检查，和 `devkit.dev` 构建之后查的是同一套，见下面「样式检查」
- 注入与 peer 一致：`src/` 下源码注入的每个服务，提供方写在 peer 里，必需注入的不标 `optional`；注入写法认不出就拒。怎么扫、怎么判见下面「注入与 peer」

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `gitStatus` | 仓根工作区干不干净；问不出也是一种答案：拒 | `git status --porcelain=v1`，改动行由 `dirtyLines` 按 porcelain 条目的样子认（stderr 里的警告不算） | 回预设的干净、不干净或问不出 |
| `run` | 仓根 `pnpm build` | `runCaptured`，超时终止整棵进程树 | 记一行调用、可以让它失败 |
| `published` | 这个版本号在发布目标上有没有 | `pnpm view <包>@<版本> version`，钉住去问发布目标；退出码 0 是有，报 `ERR_PNPM_PACKAGE_NOT_FOUND` / `ERR_PNPM_FETCH_404` 是没有，别的失败抛出 | 一张「已发过」的表 |
| `latest` | peer 里的 gwb 插件在源上的 `dist-tags.latest`（dev 依赖不问） | `pnpm view <包> dist-tags.latest`，不指定源；失败回 `undefined`，由检查报「问不出」 | 一张 latest 表，可以缺项 |
| `publish` | 在临时目录组装发布内容并发出、打 latest | `node-dev-deps.ts` 的组装（与开发版打包共用），最后 `pnpm publish --no-git-checks --tag latest` | 记下发了什么、写进去的依赖范围，可以让某一个失败 |
| `readText` / `exists` | 读清单、查产物、读 peer 的清单与内核包页面入口 | `node:fs` | 内存里的文件表 |
| `filesUnder` / `tailwindOf` | 样式检查：列出样式入口与 `.tsx`；从被检查包的 `@tailwindcss/cli` 旁边找 Tailwind 编译器。注入检查也用 `filesUnder` 列 `src/` 下的源码与提供方的运行时代码 | `node-dev-deps.ts` 里的同名函数 | 内存里的文件表；假编译器，颜色类与 `@apply` 那几条用真实编译器 |
| `workspacePackageDirs` | 注入检查判「写 peer 会成环」：工作区里别的插件包在哪 | `node-dev-deps.ts` 里的同名函数，仓根往下扫两层 | 给定的目录表 |
| `pnpm` | 上面几条启动的 pnpm | 命令开头在两个固定位置找到并核对过版本的那个 | 一个假路径 |

组装发布内容时 `workspace:` 依赖写成 `^`：同一次发的写 `^新版本号`，其余写 `^<工作区里的版本号>`（从仓根往下扫两层找，找不到直接报错）；peer 里不写同一次发的准确版本号。细节见[被测仓的形状](/docs/seams/repo-shape)。

## 代码地图

**在哪**：流程与版本号规则在 `src/release.ts`，产物检查在 `src/artifact-check.ts`，注入与 peer 的检查在 `src/wiring-check.ts`，真机器操作（git、pnpm、组装临时目录）在 `src/node-dev-deps.ts`，命令登记与参数校验在 `src/index.ts` 的 `registerReleaseCommand`。

**先读** `runRelease`：六步的顺序在这一个函数里。

**读序**：`runRelease` → `planPackages`（每个包的清单、发布目标、产物、同号）→ `ticketFor`（一个包的全部检查）→ `peerLineProblems` / `peerProblems` / `kernelPeerProblems` / `artifactProblems` / `wiringProblems` → `ReleaseDeps`（哪些是注入的）。

**可跳过**：`sameReleaseLine`、`dirtyLines` 这几个小函数，形状简单、有测试覆盖；`node-dev-deps.ts` 里复制文件、写临时清单的那几十行是 npm 打包的细节。
