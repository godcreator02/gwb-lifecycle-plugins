**本页回答**：一个测试 home 是怎么打开的、名字为什么是那个形状、启动的是哪个应用、装了哪些包、调试端口是怎么选出来的、删一个 home 之前检查什么，以及「我要操作哪个 home」是怎么变成一个调试端口的。

## 管什么

把在隔离 home 里实际验证的那几步做成命令：开一个新的、列出现有的、重开一个已有的、删掉，外加一个不对外登记成命令的定位函数：给一个 home 名，回能连上它的调试端口。

**调试端口由这部分代码自己选，人给不了。** 名字是找到一个 home 的唯一方式，而名字要变成端口全靠运行时记录里的 `cdp` 字段；没有这个字段的 home 启动之后就连不上。收一个手给的端口，唯一多出来的用法就是「敲错一位连到别人的端口上」。

home 在 `%APPDATA%\gwb-kernel\homes\<名>\`。打开哪一个由环境变量 `GWB_HOME` 决定，这部分代码做的只是用这个名字再启动一次宿主应用，再从磁盘上读出它是谁。

## 不知道什么

不知道 home 里的插件加载成功没有。那归插件管理，问 `plugin-manager.list`。`devkit.home.new` 只在启动之前写好 `cordis.yml`、装好内核包、cordis 与基础插件；装完只核对装上的内核包版本与它要的 cordis 版本，插件加载成功没有不核对。

**不写运行时记录**，只读。`runtime.json` 由内核启动时生成，其中的 `mcp` 字段由 MCP 入口插件 `gwb-mcp` 补上；这部分代码只建目录（`new` 还装包、写 `cordis.yml`），然后读。

不知道调试端口拿来干什么，只负责选一个、放到命令行上、再从记录里读回来。

**不知道还有谁在用这个 home。** 没有锁，靠约定：一个隔离 home 同一时间只给一个会话用，名字各起各的（`short` 写这个会话要验的东西），不拿别的会话开的 home 来验；`devkit.dev` 装包经那个 home 的插件管理，同时来的第二个改动回 `BUSY`（为什么靠约定不加锁见[隔离 home 靠约定](/trajectory/2026-09-25-isolated-home-by-convention)）。

还有一个前提：这些命令要求本插件运行在一个正在运行的 home 里。一个 home 都没运行时，先从开始菜单「gwb-kernel」把工作台打开。

运行时记录，一个 home 一份，home 删了它也就没了：

**写它的是内核与 MCP 入口插件，不是本包。** 内核每次启动整份重写 `pid`、`startedAt`、`appDir`、`cdp`，`gwb-mcp` 绑定端口之后读出、补上 `mcp` 字段再写回。记录里认不出的字段不读。谁写哪个字段按「谁知道这个值」分：调试端口是 Chromium 的命令行开关，只有启动进程的一方知道，而内核是唯一一定在场的进程；MCP 端口绑定成功之后才确定，只有那个插件知道。

**少一个字段不算坏记录。** `cdp` 只有启动时带了那个开关才有，`mcp` 只有装了 MCP 入口插件且绑定成功才有。缺哪个字段就是那件事没发生。

{/* ref file="../plugins/devkit/src/home.ts" lines="66-88" */}

**进程退出了记录不删**，读的人负责确认进程还在。崩溃与被结束进程很常见，「退出时删」在这两种情况下根本不会执行；留着的那份是「它上一次用的哪个端口」的唯一线索，而下一次启动时内核会整份重写。

两个端口按记录如实报，**不因为「进程看起来不在了」就去掉**：一个过时的端口正是人要看到的线索。

**名字是 `<短名>-<yyMMddHHmm>`**，重名了改用秒，再重名就直接拒：

{/* ref file="../plugins/devkit/src/home.ts" lines="112-121" */}

不悄悄加序号，因为名字里每一段都得能读出时间。同一个插件的 home 因此在目录里挨在一起、按时间排，正好是清理时要的顺序。

**`devkit.home.new` 在启动之前装好内核包、cordis 与基础插件。** 安装包只带启动器，启动器从 home 里加载内核，home 里没有内核包就启动不了。写 `cordis.yml`（文件已存在就不写）之后在 home 目录里依次 `pnpm add` 三次：先装内核包 `@godcreator/gwb-kernel-desktop`，版本是运行这条命令的内核的精确版本（`gwbKernel.version`）；装完读 `node_modules` 里内核包的清单，版本对得上、peer 里的 `cordis` 是精确版本号，再装这个版本的 `cordis`，装完同样读清单核对版本；最后装七个基础插件。home 里除了内核包与 `cordis` 只装插件。任何一步不成都不启动，回执里带 pnpm 输出的最后几十行：

{/* ref file="../plugins/devkit/src/home.ts" lines="363-390" */}

**内核包与 `cordis` 在 home 的 `package.json` 里必须是精确版本号**，所以这两次都带 `--save-exact`，并且只在清单里还没有这两项的新 home 上这样装：清单里已有 `^` 声明时，pnpm 12 的 `pnpm add <包>@<精确版本> --save-exact` 退出码是 0，写回的却还是 `^`、装上的是范围里更新的版本。装完读 `node_modules` 里的清单核对版本，就是为了抓住这种不报错的偏差（实测见轨迹卡[清单里原来写 ^ 时 pnpm add 照样装上更新的预发布版](/trajectory/2026-09-24-pnpm-add-keeps-caret)）。

**顺序是内核包、`cordis`、基础插件**：`cordis` 的版本要照内核包 peer 里写的精确版本装，这个版本只有内核包装上之后才读得到；基础插件装的时候 home 根上已经有 `cordis`，它们的 peer `cordis` 解析到同一份，内核与插件用的是同一份 cordis。基础插件不带 `--save-exact`，清单里写 `^` 范围。

**`new` 与 `open` 都不构建内核、不认内核仓，启动的是宿主自己那个应用**（安装版里只有启动器，内核从 home 里的内核包加载）：

{/* ref file="../plugins/devkit/src/home.ts" lines="125-133" */}

启动的永远是宿主当前运行着的那个应用，日常就是安装版；内核版本跟着 home 走：`new` 装的是运行这条命令的内核的版本，之后每个 home 里的内核包各自升级。改了内核源码要验证，走内核仓自己的流程，这里不代劳。`open` 与 `new` 的区别在另一件事上：**机器重启之后回到原来那个 home 只有 `open`**，`new` 永远建新目录，插件得全部重装一遍。

启动进程之前还有一道检查：同一个 home 不能开两个实例。两个窗口写同一份日志、同一个 home，而按记录停止的那条路只认得记录里那一个。

**所有可能失败的步骤都排在启动进程之前。** 启动之后再失败，会留下一个没有记录的窗口，谁也管不了它。

启动之后观察五秒：

「启动成功没有」没有接口可问，进程还活着是此刻唯一拿得到的信号。这五秒只为抓住「刚启动就退出」这一种最常见的失败（产物不在、端口被占），真正成功没有，由那个窗口和人来判断。

**观察完再读一次记录**：

{/* ref file="../plugins/devkit/src/home.ts" lines="438-447" */}

记录是内核启动时才写的，而它是之后「按名字找到这个 home」的全部依据，所以回执里要说清它出现没有。**读不到不算启动失败**：窗口已经开了，只是内核写得比这五秒晚，或者写坏了。那时按名字定位与按记录停止都用不了，回执里说明；之后的命令只认名字、每次现读记录，一直读不到就停掉重开一次。

调试端口**放在命令行上，不放在环境变量里**：

{/* ref file="../plugins/devkit/src/home.ts" lines="135-154" */}

内核不认任何调试相关的环境变量，`--remote-debugging-port` 是 Chromium 自己的开关，写在命令行上就生效。开了调试端口就同时带 `--disable-backgrounding-occluded-windows`：窗口被完全挡住时 Chromium 停止渲染新帧，取证时发的输入事件会卡住、截图拿到的是旧画面。`new` 与 `open` 用同一个启动计划，两条都带。

**这次用哪个端口，启动之前自己定，定不出来就不启动。**

{/* ref file="../plugins/devkit/src/index.ts" lines="173-191" */}

**先沿用这个 home 上次那个端口**，它空着就用它。一个 home 的端口固定下来有好处：人记得住、日志里对得上、开着的检查器不用换地址；每次换一个，除了每次都得重新查一遍之外什么都换不来。

被别人占了才另选，另选过两道筛。第一道：**别的** home 记录里写着的端口一律跳过，**过时的记录也算占着**——那份记录还指着这个端口，再分给第二个 home 的话，两份记录会同时声称自己是这个端口，而按名字定位全靠端口唯一。**自己那份记录不算**，不然重开一次时，自己上一次的记录会让这个端口被跳过、换成别的。

{/* ref file="../plugins/devkit/src/home.ts" lines="488-497" */}

第二道：此刻真有进程在监听的跳过，从 9400 起逐个问，问到空的就用。换了端口会在回执的 `cdpNote` 里说一句——不说的话，人会以为还是上次那个。

{/* ref file="../plugins/devkit/src/home.ts" lines="499-513" */}

**选好端口到 electron 真正绑定之间有一段时间**。这段时间里别人占了这个端口，记录里就会写着一个不属于它的端口。这段时间里被别人占了，这里既防不住、事后也改不了记录；这种情况由后面「监听端口的进程必须是记录里的 pid」那道检查抓住。一个空端口都找不到时直接拒、不启动——说明这台机器上有很多没停的 home，该清理了。

给子进程的环境变量要**去掉 `ELECTRON_RUN_AS_NODE`**：

{/* ref file="../plugins/devkit/src/home.ts" lines="156-169" */}

插件运行在 Electron 主进程里，会启动 node 子进程的插件会带上这个变量。它漏进这里，启动的就不是一个窗口，而是一个看不见的 node 进程。

**按名字定位：`resolveTarget`。** 它不是一条命令，是「我要操作哪个 home」这句话的实现——`devkit.dev` 的 `home` 参数经它变成调试端口。**这是唯一的一条路**：那条命令不收端口，给了当场拒，所以这个函数失败了就是真的连不上，没有别的办法绕过去。

{/* ref file="../plugins/devkit/src/home.ts" lines="517-522" */}

**三道检查都要过**，少一道就可能把这次改动推给另一个进程：

{/* ref file="../plugins/devkit/src/home.ts" lines="523-549" */}

记录读得出；pid 还活着，且认得出是一个 home 进程；那个 pid 确实在监听记录里的端口。端口会被下一个进程占用，pid 会被复用，所以「记录里写着 9401」本身不能当依据。「查不出」与「确定不在」分开报：前者不导出任何动作，后者是明确的「它没在运行」。

三道之后还有第四道，但不在这里：CDP 驱动连上页面之后，要拿页面自己报的 home 名跟你要的那个再对一次。**记录回答「你要的是哪个」，页面回答「你连上的实际是哪个」**，两边都要。

**`devkit.home.rm` 是删除，也是唯一会停止一个 home 的地方。** 停一个测试 home 唯一的用途就是接着删它，所以没有单独的停止命令：

`force` 是同一个意思用在两处，都是**越过检查**：一处是「它还在运行，停了再删」，另一处是「`default` 是日常用的 home，确实要删」。**但两处不叠加**——`default` 正在运行时带了 `force` 也不停它。开发工具不该去关人正在用的窗口，那不是删一个测试 home，是打断人正在做的事；照实说，让人自己关。

{/* ref file="../plugins/devkit/src/home.ts" lines="634-655" */}

记录里的进程「查不出还在不在」时不删：不知道它还在不在用这个目录，删了可能删到正在使用的文件。停不掉也不删——删掉一半的目录加上大量 EBUSY 报错，比一句「没删成」难收拾得多。确实停了的话，停的是哪个 pid 写进回执：人得知道自己刚才顺带结束了一个进程。

## 依赖的接口

{/* ref file="../plugins/devkit/src/home.ts" lines="196-218" */}

| 接口 | 用来做什么 | 运行时的实现 | 测试时的实现 |
| --- | --- | --- | --- |
| `fs` | 读运行时记录与装上的内核包、`cordis` 的清单，列 home 目录、写 `cordis.yml`、删整个目录 | `node:fs`，删除是自己逐个遍历目录（见下） | 一张内存文件表加一张目录表，删除可以模拟「返回成功但目录还在」 |
| `spawn` | 启动 detached 且**看得见**的 electron；`stdio` 全部 `ignore`、`unref`，和开它的 home 之间没有管道也没有 IPC，结束它不牵连开它的 home（[实测](/trajectory/2026-09-25-runner-tree-kill)） | `child_process.spawn`，不带 `windowsHide` | 记一笔，回假 pid |
| `appSpawnPlan` | 拼再启动一次宿主应用的命令行：安装版启动那个 exe，开发态 electron 读不出应用目录就拒 | 从宿主进程的 `execPath` / `argv` 拼（`hostAppFacts` → `hostAppSpawnPlan`） | 回一份写死的计划（或抛错），不碰真宿主 |
| `run` | 在前台运行装内核包、`cordis`、基础插件的三条 `pnpm add` 到结束，回输出的最后几行；三条都带环境变量 `pnpm_config_auto_install_peers=false`，基础插件 peer 里写的插件不会被 pnpm 自动补装；pnpm 是 `home.new` 开头在两个固定位置找到的那个可执行文件，经 `install.pnpm` 传进来 | `runCaptured` 合并输出；超时终止整棵进程树、确认都退出了才回，回执的 `timedOut` 说整棵树终止了没有（`node-process-tree.ts`） | 按预设回成功或失败 |
| `processName` / `portOwner` / `kill` | 判断进程在不在、停进程 | `node-probe-deps.ts` | 直接给三种状态与端口占用者 |
| `execPath` / `env` | 认宿主映像名、拼子进程环境 | 宿主进程自己的值 | 给固定值 |

**映像名只认 electron 与宿主自己**：宿主是安装版时 exe 名是产品名，开发态是 electron。把 node 也认进来只会在 pid 被复用时多误判。

`portOwner` 在这部分代码里有三处用：停止之前的第二次核对、`resolveTarget` 的最后一道检查、选新端口时「这个候选有没有人占着」。前两处问的是同一件事——「那个端口上监听的是不是记录里那个 pid」；第三处只问有没有人占，谁占的不重要。

`fs.removeDir` 的运行时实现自己遍历一遍目录：文件逐个删除、目录清空后删除、junction 只删链接本身不进去，错误原样往上抛。不用 `fs.rmSync` 的递归删除：宿主 electron 带的 Node 会跟进 junction 删掉它指向的内容（指向 home 外面的也删），遇到悬空的 junction（指向这次先删掉的兄弟目录）又会不报错地停下，而装过包的 home 里全是 junction。它返回成功也不算数，删没删掉由 `rm` 用 `exists` 再查一次磁盘（见上一节）。

## 怎么单独测

用假磁盘、假进程表、假时钟，整个流程在 `tests/home.test.ts` 里运行完，不真的启动窗口。

测的是：名字重了怎么改用秒、秒也重了时直接拒；宿主是开发态 electron 而读不出应用目录时一个动作都不做；内核包、cordis 与基础插件哪一步装不上都不启动进程，装的时候先写 `cordis.yml`、再装内核包、读它清单里的 cordis 版本、再装 cordis、最后装基础插件，前两次带 `--save-exact`，三次都关掉自动补装 peer；内核包清单读不到、内核包或 cordis 装上的版本对不上、内核包 peer 里的 cordis 不是精确版本号时拒；启动得来时环境变量与观察时间都对、读回的记录写进回执；记录没出现时不算失败但回执要说明；刚启动就退出时立刻报并指向那个 home 的日志；同一个 home 已有实例在运行时拒开第二个；选端口时记录里占着的与有进程监听的各自会不会被跳过（**过时记录里的端口也算占着**）；按名字定位的三道检查各自能拦住什么；停止之前的两次核对各自能拦住什么；`default` 不带 `force` 删不了、正在运行时带 `force` 也删不了；还在运行、没带 `force` 拒删，带了 `force` 先停再删，停不掉就不删；信号发出后进程晚几轮才退时等到它退、一直不退时不删；删除调用返回成功而目录还在时不说已删，晚一点删得掉时照删。

记录是**测试预先放在假磁盘上的**，不是 `launchHome` 写的——这正是现在的实际情况：启动之后它去读，读到什么算什么。测试里让假的 `spawn` 顺带把记录放上去，模拟的正是「内核启动时才写」这个时序。

## 代码地图

**在哪**：纯逻辑在 `src/home.ts`，真实的机器操作在 `src/node-home-deps.ts`（判断进程与端口的那几个在 `src/node-probe-deps.ts`，超时终止整棵进程树在 `src/node-process-tree.ts`），四条命令与 `home` 参数的处理在 `src/index.ts`。

**可跳过**：`parseRecord` 是读记录，形状简单。
