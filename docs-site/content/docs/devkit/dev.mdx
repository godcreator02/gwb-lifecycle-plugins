**本页回答**：`devkit.dev` 这条流程为什么可靠，它换的是什么、不换什么，以及为什么它必须运行在被换的那个进程之外。

## 管什么

一句话：**把工作区里的改动装进另一个 home 正在运行的进程，并且证明它真的在运行。**

六步，一步都不能省：问目标页面它是哪个 home、在仓根构建、把每个包打成包文件放进目标 home、经目标 home 的插件管理装（插件管理在同一条命令里重新加载条目）、整页刷新、取证。任何一步失败当场停，回执里写着停在哪一步。

**只收插件与内核包。** 每个包目录的清单要读得出、`files` 里的产物都在；`keywords` 里没有 `gwb-plugin`、也不是内核包的，直接拒：库打包进用它的插件，不单独装进 home。内核包 `peerDependencies.cordis` 必须是精确版本号，home 根上的 cordis 只能照精确版本装。

{/* ref file="../plugins/devkit/src/dev.ts" lines="442-478" */}

**开发版不进团队源，打成包文件放进目标 home。** 打包沿用发正式版的那套组装：在临时目录里放 `files` 里的东西、README 与改写过的清单（版本号换成这次的、`workspace:` 换成工作区里的版本号），再在临时目录里 `pnpm pack --pack-destination <目标 home>\dev-packs`。`pnpm pack` 会按清单的 `files` 再挑一遍文件，漏写进 `files` 的文件不在包文件里，装上之后照样暴露。仓里的文件一个都不改。

**包文件的路径每一版都不同，已经存在就拒。** pnpm 虚拟存储里的目录名由包文件的路径决定，不看内容：新包文件覆盖写到同一个路径，`pnpm add` 回「锁文件已是最新」，退出码 0，装着的仍是旧代码，版本号相同所以核对版本号也看不出来。版本号带到秒的时间戳，包文件名用 `pnpm pack` 的默认写法（`<scope>-<名字>-<版本号>.tgz`），每一版自然是新路径；同一秒里跑两次会撞上，那时当场拒。

{/* ref file="../plugins/devkit/src/dev.ts" lines="51-62" */}

**构建、打包超时，终止的是整棵进程树，确认都退出了才回失败。** pnpm 会再启动 node 去跑脚本、跑构建，只结束最上面那个进程的话，下面的还在读临时目录、写包文件，而这边已经在删临时目录。所以超时之后在 Windows 上用 `taskkill /T /F` 按父子关系终止整棵树，再逐个确认它报出的每个进程都已退出；别的平台让子进程启动时自成一个进程组，对整组发 `SIGKILL`，等组里一个都不剩。`run` 的结果里 `timedOut` 分两种：`tree-killed` 是整棵树确认退出了，照常删临时目录；`kill-failed` 是没能确认，pnpm 可能还在读，这时临时目录不删，错误里写明它留在哪。

{/* ref file="../plugins/devkit/src/node-process-tree.ts" lines="90-115" */}

**旧的包文件不删。** home 清单里的 `file:` 写法一直引用着装进去的那个包文件；删掉它，这个 home 里之后任何一次 `pnpm add`（插件管理的 `install`、`update` 都是）都失败，报那个包文件不存在。`dev-packs` 目录只增不减，隔离 home 整个删掉时一起删。

{/* ref file="../plugins/devkit/src/dev.ts" lines="14-15" */}

**装包与重新加载都交给目标 home 的插件管理。** 开发套件只读目标 home 的 `package.json`：已在 `dependencies` 里的包合成一条 `plugin-manager.update {"specs":{"<包>":"file:./dev-packs/<包文件>"}}`，不在的插件逐个 `plugin-manager.install {"pkg","spec"}`（新建一条条目），先 install 再 update。写法是相对 home 的路径，清单里不写 home 所在的位置。内核包不在目标 home 里直接拒：内核没装进这个 home，开发版的内核包换不进去。

{/* ref file="../plugins/devkit/src/dev.ts" lines="248-270" */}

`update` 用一次 `pnpm add` 装齐，重新加载这些包的条目，也重新加载装前装后真实目录变了的别的包（peer 里写了被换的包的插件，它们的目录跟着换）；插件管理自己的条目推迟到回执发出之后才重新加载，回执带 `selfDeferred: true`，这边就轮询 `plugin-manager.list`，等插件管理的条目重新答复、在运行，超时没等到就回 `ok: false` 并说清卡在哪。`update` 回执 `ok: false` 时整体失败，错误原样带回来。`specs` 不整页重载，页面由这边刷新。

{/* ref file="../plugins/devkit/src/dev.ts" lines="575-606" */}

**整页刷新没成就停。** 页面代码要整页重新加载才会按 `file://` 重新取；给了 `waitFor` 就等那个选择器出现，不给只等 `readyState`。驱动退出码非零、或回执里「等到了」不是 `true`，整体回 `ok: false`，错误里写明等的是什么、最后看到了什么——接着取证的话，量到的会是刷新途中或上一版的页面。

{/* ref file="../plugins/devkit/src/dev.ts" lines="608-619" */}

**版本号必须变，这是这条流程起作用的前提。** Node 的 ESM 模块图按 URL 缓存，同一个 URL 永远是同一个模块实例；原地覆盖产物不改路径，cordis 把插件停用再启用，`import()` 拿回的还是旧的。包文件的路径变了，pnpm 虚拟存储里的目录就变了，重新加载时才真的重新执行模块。前提是这次的版本号真的装上了，所以取证里核对装上的版本号那一样不能省。

**不走覆盖 `dist` 的捷径。** home 里 `node_modules` 下的文件是硬链接到 pnpm 全局存储的，覆盖写改的是共享的那份文件，存储里那份从此变成开发构建——之后这台机器上任何人装那个版本拿到的都是它，而且不报错。给 import 地址加时间戳是另一条路：每加载一次就在内存里多留一份模块、回收不掉，每次大约是插件 `dist` 体积的两倍。两条都不如换一个新版本号。

**装了内核包时，整页刷新换成重启目标 home。** 内核包 `@godcreator/gwb-kernel-desktop` 装在 home 里，由启动器在进程启动时加载，主进程里运行着的内核换不掉。内核包 peer 里 cordis 的精确版本号和内核包放进同一条 `update`，插件管理装完不重新加载任何条目，回执带 `restartRequired: true`。这边停掉目标 home 的进程、用同一个 home 再启动，然后轮询 `shell.env`，直到回执里的 `versions.kernel` 就是这次打包的版本号；报出的是别的版本号当场判失败——那说明启动器加载的不是 home 里装上的那份。装了内核包而回执里没有 `restartRequired` 也判失败。取证照常做。

{/* ref file="../plugins/devkit/src/dev.ts" lines="552-573" */}

**最后一步是取证，不是刷新。** 少了它，人看到「装了、刷新了」就会说验过了。三样合起来才能排除那几种「看起来成功了」：装上的就是这次打包的版本号（插件管理对 `file:` 写法不核对版本号，运行着的也可能是上一次的版本）；条目真的是 `ACTIVE`（看的是加载状态，不是条目存在）；日志新增的部分里没有 error（`apply` 里一个 async 调用不报错地 reject，现象正好是「加载了但什么都没发生」，那一条只在日志里）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="695-721" */}

**目标用名字指定，端口是查出来的。** 给 `home` 名，端口从那个 home 的 `runtime.json` 里查（内核启动时写的），同时确认进程还在：pid 还活着，且那个 pid 确实在监听记录里的端口。**两边都要核对**：记录回答「你要的是哪个」，页面回答「你连上的实际是哪个」，对不上当场拒——端口会被下一个进程占用，只信记录就会不声不响地把改动装进另一个 home。

{/* ref file="../plugins/devkit/src/dev.ts" lines="89-92" */}

## 不知道什么

**不知道被换的是什么插件。** 它只认包名、版本号与 `keywords` 里有没有 `gwb-plugin`，插件做什么、有没有窗格、有没有命令，一概不问。

**不知道运行时记录是怎么来的。** 它只读，写它的是内核与 MCP 入口插件。

**不知道条目怎么重新加载、跟着重新加载哪些包。** 那是插件管理的事：它在 `update` 里比较装前装后的真实目录，自己决定重新加载谁。开发套件只看回执里的 `ok`、`selfDeferred`、`restartRequired`，最后用 `plugin-manager.list` 取证。

**不写目标 home 的清单。** 目标 home 的 `package.json` 只读，写它的是插件管理启动的 pnpm。开发套件在目标 home 里写的只有 `dev-packs` 下的新包文件。

**不知道怎么连 CDP、怎么启动进程、怎么读写磁盘。** 这三样都在注入的 `DevDeps` 后面。

**不知道目标 home 的目录在哪**——这是问出来的，不是配置出来的。目标页面上外壳插入的样式表是带着 home 路径的 `file://` 地址，所以问一次正在运行的页面就有答案。配置里存一份 home 路径，人换了窗口之后它还指着旧的。

**同一个 home 同时只该有一次 `devkit.dev`。** 装包经插件管理，它的改动命令同一时刻只允许一个，第二个回 `BUSY`；一个隔离 home 同一时间只给一个会话用，名字各起各的，这一条靠约定（[隔离 home 靠约定](/trajectory/2026-09-25-isolated-home-by-convention)）。

## 数据结构

三样：一次的输入（指定的 home、仓根、包目录、刷新后等哪个选择器、本插件自己所在的 home）、一次的回执（目标 home、打包了哪几个包各是什么版本号、包文件在哪、经 `update` 还是 `install` 装的与 `install` 新建的条目、`update` 的回执原样、刷新结果、取证；装了内核包时没有刷新结果，换成 `kernel`：页面报出的内核版本号与重启的经过），以及取证本身（每个包打包的版本号与装上的版本号、条目表、没在运行的几条、日志新增部分里的 error 与 warn）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="351-406" */}

输入里没有「要不要构建」，也没有源地址。**构建是这条流程的必需一步**：产物不是最新的就打包，等于装的是上一版，而回执从头到尾一切正常；开发版不经过任何源。

## 提供的接口

对外只有一条命令：`devkit.dev`，登记在命令总线上，走完整条流程。

**取证只有 `collect` 这一个函数，而且只在这条流程里调用。** 判断要有基线：哪些 error 是这次自己引起的，只有拿装包之前的日志长度才分得出来。单独看一眼现状的东西不该做成一条命令——它没有基线，看到的 error 可能是几天前的，而人会把它的绿色当成验收通过，那正是这条流程要防的事。

{/* ref file="../plugins/devkit/src/dev.ts" lines="695-703" */}

要看一眼某个 home 的条目表，`devkit.cdp {"args":["<名>","cmd","plugin-manager.list"]}` 就行，那是看，不是验证。

## 依赖的接口

| 接口 | 用来做什么 | 运行时的实现 | 测试时的实现 |
| --- | --- | --- | --- |
| `run` | 仓根 `pnpm build` 到结束，拿回输出的最后几行；超时的话带回整棵进程树终止了没有 | `node-home-deps.ts` 的 `runCaptured`，启动子进程与超时终止整棵树在 `node-process-tree.ts` | 记一行调用、按名字让某一条失败 |
| `cdp` | 对目标页面执行一个动作，拿回它打印的 JSON；插件管理的 `install`、`update`、`list` 都经它在目标页面里调 | 启动 `bin/cdp.mjs` 子进程 | 直接回一份假回执，假的 `install` / `update` 把这次的版本号写进内存里的 `node_modules` |
| `pack` | 在临时目录组装发布内容，`pnpm pack` 到目标 home 的 `dev-packs` | 与发正式版共用组装的那段，最后一步换成 `pnpm pack` | 记一行、在内存里的文件表放一个包文件 |
| 读磁盘的几个函数 | 读清单、查产物与包文件在不在、读目标 home 的清单与装上的包清单、取日志基线与新增部分 | `node:fs` | 内存里的文件表 |
| `sleep` | 轮询插件管理重新加载自己、轮询重启后的 `shell.env` 时，两次之间等一会儿 | `setTimeout` | 只记一行、不真等 |
| `restartHome` | 装了内核包时停掉目标 home 再启动 | `src/index.ts` 用测试 home 的停止与启动（`bringDownHome`、`launchHome`）接上，调试端口先沿用上次那个 | 记一行调用、可以让它失败 |
| `pnpm` | 构建、打包时启动的 pnpm 可执行文件 | 命令开头在两个固定位置找到并核对过版本的那个（见[pnpm 与包源](/docs/seams/pnpm-registry)），找不到就不开始 | 一个假路径 |

**CDP 那一项为什么是启动子进程，而不是在进程内连接。** CDP 驱动必须在工作台没运行的时候也能单独用，所以它是零依赖单文件的脚本，不是一个可以 import 的模块。一次流程多启动几次进程，几百毫秒，对一次一分钟左右的流程可以忽略。

**它也是按名字调用的**，不是按端口：驱动自己查记录、自己核对页面报的名字，于是流程里每一步都顺带核对一次「我连的还是那个 home 吗」。传端口的话，这六步就成了六次没人核对的重新定位。

## 怎么单独测

注入一套假的 `DevDeps`，整个流程在测试里跑完，不必真的打包、真的开 home。假实现要能模拟的是边界情况：目标是 `default`、目标就是自己所在的 home、构建失败、库包（被拒）、这次的包文件路径已经存在（被拒，旧包文件原样留着）、打包失败、已装的包走一条 `update` 而没装的插件走 `install`、`install` 失败、`update` 回执 `ok: false`（错误原样传出、不刷新）、`selfDeferred`（轮询到插件管理回来；回不来要超时判失败）、刷新带不带 `waitFor`、刷新没等到页面回来或驱动退出码非零、条目没在运行、日志新增部分里有 error、装上的版本号不是这次的。装内核包那条路另测：内核包和 cordis 放进同一条 `update`、回执 `restartRequired` 时重启而不刷新、内核包不在目标 home 里（被拒）、peer 里的 cordis 写成范围（被拒）、回执里没有 `restartRequired`、重启失败、重启后页面报的内核版本不对（当场判失败，不接着等）、`shell.env` 一直报不出内核版本（到点判失败）。分哪个包走 `update`、哪个走 `install` 是纯函数 `pluginManagerCallsFor`，单测直接给清单。超时终止整棵树用真的子进程测：父进程再派生一个不接管道的孙进程，超时之后孙进程也必须没了（`tests/process-tree.test.ts`）。

检查目标的那几道是这条流程上最该测的：它们决定拒不拒，而一旦判错，代价是开发版进了日常用的 home、这条命令把正在运行的自己停掉，或者这次改动装进了另一个隔离 home。

## 代码地图

**在哪**：纯逻辑在 `src/dev.ts`，真实的机器操作在 `src/node-dev-deps.ts`（前台运行命令与超时终止整棵进程树在 `src/node-home-deps.ts` 与 `src/node-process-tree.ts`），页面上的操作在 `bin/cdp.mjs`（见 [CDP 驱动](/docs/devkit/cdp)），命令登记在 `src/index.ts`。

**先读** `runDev`：六步的顺序在这一个函数里，长一点的步骤各是一个函数（`probeTargetHome`、`planDevPackages`、`packDevPackages`、`installNewPlugins`、`updateInstalledPackages`、`restartForKernel`、`collect`），位置不显然的那几步旁边有一句注释说明为什么在这里。

**读序**：`guardHome`（拒什么）→ `runDev`（顺序）→ `planDevPackages` / `pluginManagerCallsFor`（收哪些包、各经哪条命令装）→ `updateInstalledPackages`（怎么接插件管理的回执）→ `collect`（拿什么当证据）→ `DevDeps`（哪些东西是注入的）。真实机器操作那一层最后读，它只执行、不判断。

**可跳过**：`node-dev-deps.ts` 里组装临时目录、改写发布用清单的那几十行是 npm 打包的细节，跟这条流程的判断无关。
