**本页回答**：`devkit.dev` 这条流程为什么可靠，它换的是什么、不换什么，以及为什么它必须运行在被换的那个进程之外。

## 管什么

一句话：**把工作区里的改动送进另一个 home 正在运行的进程，并且证明送到了。**

七步，一步都不能省：问目标页面它是哪个 home、在仓根构建、发开发版、在目标 home 里装那个准确的版本号并读回核对、重新加载条目、整页刷新、取证。任何一步失败当场停，回执里写着停在哪一步。

- 左列在控制台 home 里做：`devkit.dev` 收 `home`、`dir`、`packages`，仓根 `pnpm build`，发开发版（版本号 `<patch+1>-dev.<yyyyMMddHHmm>`）到团队源

- 取证三样：装上的是这次的版本号、条目是 `ACTIVE`、`gwb.log` 在装包之前那个长度之后新增的部分没有 error
- 取证之后读回执、回到改代码，再调一次 `devkit.dev`；任何一步失败当场停，回执写明停在哪一步
</Diagram>

**重新加载是目标进程里的一条命令，不是这边发的两条。** 每条条目调一次 `plugin-manager.remount`，停用、等卸载完、启用、等加载完都在那一条命令里做完。拆成停用、启用两条的话，被换的正好是提供启用命令的插件管理自己、或者命令总线时，第二条没人接收，条目停在停用状态。回执有两种成功：`remounted` 表示回执之前就做完了，带着重新加载后的状态，只有 `ACTIVE` 算加载成功；`deferred` 是插件管理重新加载它自己，先发回执、下一个宏任务才动手，这边就轮询 `plugin-manager.list`，等它重新答复、那条条目在运行，超时没等到就回 `ok: false` 并说清卡在哪。所以目标 home 的插件管理要 0.4.0 起。

{/* ref file="../plugins/devkit/src/dev.ts" lines="555-603" */}

**安装是「在目标 home 的清单里写准确版本号，再 `pnpm install`」，装完读回核对。** 不用 `pnpm add <包>@<号>`：清单里已有 `^` 声明时（`plugin-manager.install` 写的就是），pnpm 沿用这个前缀写回 `^<号>`，锁文件里已解析的同一补丁号的旧预发布版被当成满足新范围、不重新解析；源上有更新的同一补丁号时范围又解析到它——装上的都不是这次发的版本，退出码照样是 0。清单里写死准确版本号就没有范围可解析。装完读 `node_modules/<包>/package.json` 的 `version`，对不上当场 `ok: false`、不重新加载：

{/* ref file="../plugins/devkit/src/dev.ts" lines="491-524" */}

**版本号必须变，这是这条流程起作用的前提。** Node 的 ESM 模块图按 URL 缓存，同一个 URL 永远是同一个模块实例；原地覆盖产物不改路径，cordis 把插件停用再启用，`import()` 拿回的还是旧的。发一个开发版，版本号是 `<patch+1>-dev.<时间戳>`，装上的版本变了路径就变了，重新加载时才真的重新执行模块。同一个补丁号的多个开发版也成立：pnpm 虚拟存储的目录名超长时截成前段加全名哈希，预发布段与 peer 后缀都在哈希里。前提是这次的版本号真的装上了，所以上一段那道核对不能省。

{/* ref file="../plugins/devkit/src/dev.ts" lines="59-77" */}

**不走覆盖 `dist` 的捷径。** home 里 `node_modules` 下的文件是硬链接到 pnpm 全局存储的，覆盖写改的是共享的那份文件，存储里那份从此变成开发构建——之后这台机器上任何人装那个版本拿到的都是它，而且不报错。给 import 地址加时间戳是另一条路：每加载一次就在内存里多留一份模块、回收不掉，每次大约是插件 `dist` 体积的两倍。两条都不如发一个新版本号。

{/* ref file="../plugins/devkit/src/dev.ts" lines="14-26" */}

**最后一步是取证，不是刷新。** 少了它，人看到「重新加载了、刷新了」就会说验过了。三样合起来才能排除那几种「看起来成功了」：装上的就是这次发的版本号（pnpm 退出码 0、条目都在运行、日志没有错误，运行着的也可能是上一次的版本）；条目真的是 `ACTIVE`（看的是加载状态，不是条目存在）；日志新增的部分里没有 error（`apply` 里一个 async 调用不报错地 reject，现象正好是「加载了但什么都没发生」，那一条只在日志里）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="605-644" */}

**目标用名字指定，端口是查出来的。** 给 `home` 名，端口从那个 home 的 `runtime.json` 里查（内核启动时写的），同时确认进程还在：pid 还活着，且那个 pid 确实在监听记录里的端口。**两边都要核对**：记录回答「你要的是哪个」，页面回答「你连上的实际是哪个」，对不上当场拒——端口会被下一个进程占用，只信记录就会不声不响地把改动推给另一个 home。

## 不知道什么

**不知道被换的是什么插件。** 它只认包名与版本号，插件做什么、有没有窗格、有没有命令，一概不问。

**不知道运行时记录是怎么来的。** 它只读，写它的是内核与 MCP 入口插件。

**不知道怎么连 CDP、怎么启动进程、怎么读写磁盘。** 这三样都在注入的 `DevDeps` 后面。

**不知道目标 home 的目录在哪**——这是问出来的，不是配置出来的。目标页面上的样式表与 importmap 都是带着 home 路径的 `file://` 地址，所以问一次正在运行的页面就有答案。配置里存一份 home 路径，人换了窗口之后它还指着旧的。

**不管第一次安装。** 目标 home 里没有这个包的条目时，它装完就停在那里、在回执里说怎么补，不替人建条目。装包是一件事，加载条目是另一件事。

## 数据结构

三样：一次的输入（指定的 home、仓根、包目录、刷新后等哪个选择器、本插件自己所在的 home）、一次的回执（目标 home、发了哪几个包各是什么版本号、重新加载了哪几条条目、刷新结果、取证），以及取证本身（每个包发出的版本号与装上的版本号、条目表、没在运行的几条、日志新增部分里的 error 与 warn）。

{/* ref file="../plugins/devkit/src/dev.ts" lines="366-411" */}

输入里没有「要不要构建」，也没有源地址。**构建是这条流程的必需一步**：产物不是最新的就发，等于发的是上一版，而回执从头到尾一切正常；源在这台机器上只有一个，收一个参数只会多出一种「发到了别处」的可能。

## 提供的接口

对外只有一条命令：`devkit.dev`，登记在命令总线上，走完整条流程。

**取证只有 `collect` 这一个函数，而且只在这条流程里调用。** 判断要有基线：哪些 error 是这次自己引起的，只有拿装包之前的日志长度才分得出来。单独看一眼现状的东西不该做成一条命令——它没有基线，看到的 error 可能是几天前的，而人会把它的绿色当成验收通过，那正是这条流程要防的事。

{/* ref file="../plugins/devkit/src/dev.ts" lines="647-649" */}

要看一眼某个 home 的条目表，`devkit.cdp {"args":["<名>","cmd","plugin-manager.list"]}` 就行，那是看，不是验证。

## 依赖的接口

| 接口 | 用来做什么 | 运行时的实现 | 测试时的实现 |
| --- | --- | --- | --- |
| `run` | 跑 pnpm 到结束，拿回输出的最后几行 | `node-dev-deps.ts` 启动子进程 | 记一行调用、按名字让某一条失败 |
| `cdp` | 对目标页面执行一个动作，拿回它打印的 JSON | 启动 `bin/cdp.mjs` 子进程 | 直接回一份假回执 |
| `publish` | 在临时目录组装发布内容再发出去 | 真的 `pnpm publish` | 只记一行 |
| `published` | 这个版本号在源上有没有 | `pnpm view` | 查一张表 |
| 读写磁盘的几个函数 | 读清单、查产物在不在、写目标 home 的清单、读回装上的包清单、取日志基线与新增部分 | `node:fs` | 内存里的文件表；假的 `pnpm install` 照清单放 `node_modules`，也能模拟「退出码 0 却没换版本」 |
| `sleep` | 轮询插件管理重新加载自己时，两次之间等一会儿 | `setTimeout` | 只记一行、不真等 |

{/* ref file="../plugins/devkit/src/dev.ts" lines="324-362" */}

**CDP 那一项为什么是启动子进程，而不是在进程内连接。** CDP 驱动必须在工作台没运行的时候也能单独用，所以它是零依赖单文件的脚本，不是一个可以 import 的模块。一次流程多启动五六次进程，几百毫秒，对一次一分钟左右的流程可以忽略。

**它也是按名字调用的**，不是按端口：驱动自己查记录、自己核对页面报的名字，于是流程里每一步都顺带核对一次「我连的还是那个 home 吗」。传端口的话，这七步就成了七次没人核对的重新定位。

## 怎么单独测

注入一套假的 `DevDeps`，整个流程在测试里跑完，不必真的发版、真的开 home。假实现要能模拟的是边界情况：目标是 `default`、目标就是自己所在的 home、这个版本号已经在源上、构建失败、目标 home 没有重新加载命令、重新加载的回执不是 `ACTIVE`、被换的正是插件管理自己（回执之后才重新加载，要轮询到它回来，回不来要超时判失败）或命令总线、条目没在运行、日志新增部分里有 error、`pnpm install` 退出码 0 却没换版本（要当场停、不重新加载）、安装失败（清单要恢复原样）。改写清单本身（已有 `^` 声明改成准确版本号、没有就按名字排序插进去、缩进照原样）是纯函数，单测直接给文本。

检查目标的那几道是这条流程上最该测的：它们决定拒不拒，而一旦判错，代价是开发版进了日常用的 home、这条命令把正在运行的自己停掉，或者这次改动推给了另一个隔离 home。

## 代码地图

**在哪**：纯逻辑在 `src/dev.ts`，真机器操作在 `src/node-dev-deps.ts`，页面上的操作在 `bin/cdp.mjs`（见 [CDP 驱动](/docs/devkit/cdp)），命令登记在 `src/index.ts`。

**先读** `runDev`：七步的顺序在一个函数里，每一步有一句注释说明为什么在这个位置。

**读序**：`guardHome`（拒什么）→ `runDev`（顺序）→ `pinExact` / `checkInstalled`（怎么装、怎么确认装上了）→ `collect`（拿什么当证据）→ `DevDeps`（哪些东西是注入的）。真机器那一层最后读，它只执行、不判断。

**可跳过**：`node-dev-deps.ts` 里组装临时目录、改写发布用清单的那几十行是 npm 打包的细节，跟这条流程的判断无关。
