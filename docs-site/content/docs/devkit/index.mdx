**本页回答**：开发套件 `@godcreator/gwb-devkit` 管哪几件事、刻意不管哪些；它对外提供的命令、说明书与建仓模板各是什么、细节在哪一页；它依赖哪些服务和外部程序、缺了会怎样；怎么测、代码从哪读起。

## 管什么

开发套件是**一个普通的 gwb 插件**，源码在 `plugins/devkit/`：装进 home 才有它的命令，加载不成功就什么都没有，和别的插件一样由插件管理安装、升级、卸载。它把「在一个新文件夹里开发一个新插件」这条路上的每一步做成 agent 能调用的命令，使用者是 agent，所以没有界面，结果全在命令回执里。为什么这么切分见[关键设计](/docs/design)。

六组功能，每组的机制各有一页：

| 功能 | 命令 | 机制在 |
| --- | --- | --- |
| 建仓与加插件：把模板渲染进一个新目录（workspace 仓），默认连文档站一起建；往已有的 workspace 仓再加一个插件包 | `devkit.scaffold`、`devkit.scaffold.plugin` | [建仓与加插件](/docs/devkit/scaffold) |
| 测试 home：开一个装好内核包、`cordis` 与七个基础插件的隔离 home，重开、列出、删除；调试端口自动选，之后只按名字找 | `devkit.home.new`、`open`、`list`、`rm` | [测试 home](/docs/devkit/home) |
| 改一版看一版：构建、打成开发版的包文件放进另一个 home，经那个 home 的插件管理装并重新加载，整页刷新，最后取证 | `devkit.dev` | [改一版看一版](/docs/devkit/dev) |
| 发正式版：检查 git 工作区、产物、依赖写法、peer 里的内核包与插件，全过才按顺序发到各包的发布目标 | `devkit.release` | [发正式版](/docs/devkit/release) |
| 服务总览：从调用它的那个 home 里各包的 `.d.ts` 现读有哪些可以 inject 的服务、谁提供、类型定义原文 | `devkit.services` | [服务表与类型声明](/docs/seams/service-table) |
| CDP 驱动：在一个 home 的页面里点击、输入、截图、执行工作台命令、问页面属于哪个 home | `devkit.cdp`（`bin/cdp.mjs`） | [CDP 驱动](/docs/devkit/cdp) |

## 不知道什么

- **不画界面**：没有窗格、没有浏览器侧代码，只向外壳报一个显示名
- **不管文档站的内容**：生成初始站点归站点插件，装六区归 docfirst 插件；本包不依赖它们的任何包，只按命令名调用（[借用别的插件的命令](/docs/seams/borrowed-commands)），自己只在建仓与加插件时写一页插件页草稿
- **不自己增删 home 里的条目、不写 home 的清单**：安装与条目归插件管理。唯一的例外是 `devkit.home.new` 在新 home 启动之前直接 `pnpm add`、写 `cordis.yml`，那时插件管理还没装、home 还没启动
- **不写 `runtime.json`**：它由内核与 MCP 入口插件写，本包只读
- **不升级日常用的 `default`**：`devkit.dev` 拒绝以它为目标，`devkit.release` 只发到源
- **不收端口**：定位一个 home 只按名字，端口从那个 home 的运行时记录里查
- **不构建内核**：`devkit.home.new` 装的是源上的内核包，启动用的是宿主自己那个安装版应用
- **不替别的插件登记说明书**：说明书名全局唯一，重名的那份不登记
- **不自动清理旧 home、不巡检别的仓**：`devkit.home.new` 的回执带着现有 home 清单，删哪个由调用方决定；依赖写法与产物只在各仓发版时由 `devkit.release` 查

## 数据结构

本包自己**不存任何状态**：没有设置项，不写数据目录。它读写的都是别人的东西——home 目录（`runtime.json` 只读；`cordis.yml` 与 home 清单只由 `devkit.home.new` 在启动之前写；`dev-packs` 下的包文件由 `devkit.dev` 写）、被处理的仓（只有建仓与加插件往里写文件，`pnpm build` 生成产物）、系统临时目录（组装发布内容）。

每条命令的回执都是命令总线的 `{ ok, data?, error? }`，各命令 `data` 的形状写在各自的 `usage` 与机制页里。

`devkit.cdp` 是 `bin/cdp.mjs` 经 `gwbNodeCli` 登记出来的：登记的脚本自动成为同名命令，回执带 stdout、stderr 与退出码。工作台没运行时可以直接 `node <包根>/bin/cdp.mjs <home 名> <动作>`。

**就绪日志**：`apply` 最后往 `<home>\gwb.log` 写一行「开发套件就绪」，列出此刻命令总线上 `plugin` 是本包的全部命令。有这一行说明 `apply` 执行完了；`devkit.cdp` 在不在取决于 `gwbNodeCli` 那个插件有没有加载，所以名单现问命令总线，不抄一份。

### 三份说明书

放在包根的 `skills/`，经 `gwbSkills` 登记，agent 用 `skill.read` 读：

| 说明书 | 管什么 | 正本 |
| --- | --- | --- |
| `gwb-devkit` | 新写插件、改插件、改一版看一版、在页面里取证；附件 `references/rules.md` 是规矩总表，`references/evidence.md` 讲在页面里取证，`references/ui.md` 只指向外壳的说明书 `gwb-shell` | [gwb-devkit](/outputs/skills/gwb-devkit)；规矩总表就是[写插件的规矩](/docs/rules)这一页 |
| `gwb-release` | 全生态的发版规则：升哪一位、改依赖版本号、发正式版、发破坏性版本多做的两步 | [gwb-release](/outputs/skills/gwb-release) |
| `fresh-eyes` | 生态自举验收：派一个没有上下文的子代理，只给 MCP 入口，让它从 `index` 出发建一个插件走完全程 | 包里的 `skills/fresh-eyes/SKILL.md`，手写 |

### 建仓模板

包根的 `template/` 是给别的仓用的初始文件，只有两条建仓命令读它：`template/repo/` 生成仓根，`template/pkg/` 生成插件包，`template/site/plugin.mdx.tpl` 生成文档站现状区里的插件页。模板怎么分部分、有哪些占位符、改模板要守什么，见[建仓与加插件](/docs/devkit/scaffold)。

## 怎么单独测

纯逻辑模块（`scaffold.ts`、`home.ts`、`dev.ts`、`release.ts`、`artifact-check.ts`、`services.ts`、`probes.ts`）用假实现把整条流程运行完，各机制页写了各自喂什么、证明什么。命令登记这一层由 `tests/commands.test.ts` 在假上下文上运行 `apply`、按命令名调处理函数：命令总线不在就抛、参数不对回用法、认不出的键被拒、`packages` 不合格被拒、建仓在站点插件装没装时各回什么。

构建之后，`tests/built-artifact.test.ts` 对产物跑一遍发版前检查的产物部分，另起一个 node 进程 import 产物，再加载产物调几条不碰 home 的命令，看包内路径（`bin/`、`skills/`、`template/`）解析得到；没有 `dist/` 时整组跳过：

## 代码地图

**在哪**：`plugins/devkit/`。`src/` 是插件本体，`bin/cdp.mjs` 是不经构建的 CDP 驱动，`template/` 是建仓模板，`skills/` 是说明书（除 `fresh-eyes` 外都由文档站生成）。

{/* tree dir="../plugins/devkit/src" depth="1" glob="*.ts" */}

**先读** `src/index.ts` 的 `apply`：全部命令在那里登记，一眼看出对外有哪些命令、参数怎么校验、调哪个纯逻辑函数。

**读序**：`index.ts`（登记与参数）→ 纯逻辑（`scaffold.ts`、`home.ts`、`dev.ts`、`release.ts` 与 `artifact-check.ts`、`services.ts`、`probes.ts`）→ 真机器操作（`node-home-deps.ts`、`node-dev-deps.ts`、`node-probe-deps.ts`、`node-services-deps.ts`、`node-process-tree.ts`）。真机器那一层认识纯逻辑，纯逻辑不认识它；`vocab.ts` 是共用的小函数与常量（团队范围、团队源、版本号正则、`requireKernel`、`isRecord`）。

**可跳过**：`dist/` 是构建产物；`template/` 下的 `.tpl` 是给别的仓的内容，不是本包的逻辑。
