**本页回答**：开发套件有哪些功能；它对外提供哪些命令、说明书与模板，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归别的模块。包名 `@godcreator/gwb-devkit`，源码目录 `plugins/devkit/`，入口文件 `src/index.ts`；另有一个不经构建的命令行脚本 `bin/cdp.mjs`。

开发套件是**一个普通的 gwb 插件**，没有任何特权：装进 home 才有它的命令，加载不成功就什么都没有。它自己也走它教别人走的那条路——在自己的仓里开发、发到团队源、装进 home。它的使用者是 agent，所以没有界面，全部结果都在命令回执里。在[接缝图](/docs)上它是「开发套件」那个框；为什么这么切分见[关键设计](/docs/design)。

## 功能

- **建仓**：`devkit.scaffold` 把新插件的骨架写进一个还不存在的目录（workspace 仓，插件在 `plugins/<短名>/`），默认连文档站一起建；`devkit.scaffold.plugin` 往已有的 workspace 仓再加一个插件包——[建仓与加插件](/docs/devkit/scaffold)
- **结构体检**：`devkit.audit-structure` 只读地查一个仓或全生态离模板生成的布局有多远，旧布局仓收到一份按实际文件名列好的迁移清单——[结构体检](/docs/devkit/structure)
- **依赖对账**：`devkit.audit-deps` 扫容器根下各仓的 `package.json`，`@godcreator` 的 dev 依赖对照团队源上的最新正式版，报出写了源上没有的版本、落后、出范围的，插件包的 peer 写了 `cordis` 以外的包也报；只报告，不拦——见下面[依赖对账的判据](#依赖对账的判据)
- **测试 home**：`devkit.home.new` 开一个装好七个基础插件的隔离 home，`open` 重开、`list` 列出、`rm` 删除；调试端口自动选，之后只按名字找——[测试 home](/docs/devkit/home)
- **改一版看一版**：`devkit.dev` 把工作区的改动发成开发版，装进另一个 home 正在运行的进程，重新加载、整页刷新，最后取证——[改一版看一版](/docs/devkit/dev)
- **发正式版**：`devkit.release` 从仓根把包按依赖顺序发到团队源，发之前检查 git 工作区、构建产物、依赖写法与插件的 `gwb.testedKernel`、`gwb.requires`，不改仓里任何文件——见下面[发正式版的检查](#发正式版的检查)
- **能用什么**：`devkit.services` 与 `devkit.capabilities` 当场问 cordis 与 home 里的包：这个 home 有哪些服务、各由谁提供、怎么用，已装的包有哪些 import 入口、类型文件在哪
- **CDP 驱动**：`devkit.cdp`（`bin/cdp.mjs`）在隔离 home 的页面里点击、输入、截图、执行工作台命令、问页面属于哪个 home；工作台没运行时也能直接用 node 运行——[CDP 驱动](/docs/devkit/cdp)

### 发正式版的检查

`devkit.release` 依次做：仓根 git 工作区不干净就拒；仓根 `pnpm build`；按 `files` 白名单检查产物；同一个版本号已在源上就拒；发版前检查；在临时目录组装发布内容、发到 latest（`workspace:` 依赖写成 `^`：同一次发的写 `^新版本号`，其余写 `^<工作区里的版本号>`）。任何一个包没过检查，一个都不发，回执按包一次列全。它只碰团队源、不碰任何 home，所以从哪个 home 调用都可以。

<Diagram name="dk-release" title="devkit.release 发正式版：六步依次做，任何一处没过，一个包都不发">
- 第 1 步仓根 git 工作区干净（`git status`），不干净连构建都不跑；第 2 步仓根 `pnpm build`
- 第 3 步按 `files` 白名单查产物都在；第 4 步查这个版本号在源上没发过
- 第 5 步发版前检查，要发的包一起查、一次列全。每个包查五项：不在 0.0.x、`@godcreator` 的 dev 范围包含源上的 latest、产物里没有空 import、相对 import 指向的文件都在、`tsc --noEmit` 类型检查；插件包另查四项：peer 只有 `cordis`、包名 import 的两份名单、`gwb.testedKernel` 与运行中的内核在同一条版本线、`gwb.requires` 的写法
- 第 6 步在临时目录组装发布内容，按 `packages` 给的顺序发到 latest
- 最下面一格：任一项没过，一个包都不发，回执按包列出每一项问题
</Diagram>

发版前检查对每个要发的包查：

- 自己不在 0.0.x；`@godcreator` 的 dev 依赖范围包含源上的 `dist-tags.latest`（写法认不出、下限比 latest 还新、latest 超出范围才拒，范围内落后放行）
- 构建产物里没有 `import {} from '…'` 这种空 import（源码写了 `import { type X }`），相对 import 指向的文件都在
- 在包目录里用本仓装的 tsc 跑 `tsc --noEmit -p <tsconfig> --skipLibCheck false`，要通过。这项检查守的是构建产物的类型链，测试与构建脚本不查：node 侧有 `tsconfig.build.json` 就按它查，没有才按 `tsconfig.json` 查，两份都没有就拒；有 `src/client/tsconfig.json` 就再查一次浏览器侧。报错写明没过的是哪一份

插件包（`keywords` 含 `gwb-plugin`）另查：

- peer 里只有 `cordis`，别的 peer 一律拒，报错写明按「运行时谁提供」该改写成 dev 还是 `dependencies`；node 侧产物按值 import 了 `cordis` 而 peer 里没有，拒；写了 peer `cordis` 而产物没有 import 它，只在回执的 `reminders` 里提醒
- node 侧产物的包名 import 只有 node 内置模块、`electron`、`cordis`；浏览器侧产物只 import importmap 里的名字
- `gwb.testedKernel` 与运行中的内核在同一条版本线上（没写、不是合法版本号、不在同一条线都拒）
- 写了 `gwb.requires` 的：它是 `{ 包名: 最低版本号 }` 的对象，每个值是合法的 x.y.z，每个包也写在 `devDependencies` 里，要求的版本不高于 dev 范围的下限（dev 写 `workspace:` 的不比下限）；没写不查

### 依赖对账的判据

`devkit.audit-deps` 扫容器根（缺省调 `unit-folder.list` 取）下各仓的 `package.json`，退役单元与测试插件不扫，`private` 清单只查 dev 依赖。「最新」认源上的 `dist-tags.latest`。只报告，不拦；要拦的由 `devkit.release` 的发版前检查在发版时拦。findings 的种类：

- `@godcreator` 的 dev 依赖：`dead-pin`（写的版本源上没有）、`behind`（落后 latest 但还在 `^` 范围内——提示，不用处理）、`out-of-range`（latest 超出范围，必须跟进）、`loose-dev-pin`（写法既不是准确版本号也不是 `^`）
- 插件包（`keywords` 含 `gwb-plugin`）的 peer：`peer-not-cordis`（写了 `cordis` 以外的包，一条 peer 一条；不看写法、不问源）。库不查 peer

<Diagram name="dk-audit-deps" title="依赖对账：一条 dev 依赖从上往下问四个问题，插件包的 peer 另查一条">
- 一条 `@godcreator` 的 dev 依赖（`workspace:*` 不查）依次问：写法是准确版本号或 `^x.y.z` 吗？不是报 `loose-dev-pin`
- 源上有这个版本号（准确版本号，或 `^` 的下限）吗？没有报 `dead-pin`，安装必然失败
- 源上的 latest 比它新吗？不新就不报
- latest 还在 `^` 范围内吗？在报 `behind`，只是提示；不在报 `out-of-range`，上游出了破坏性版本，必须跟进
- 插件包的每条 peer，不是 `cordis` 就报一条 `peer-not-cordis`；`private` 的清单与库不查 peer
- 除了 `behind`，四种都要处理（图里画成橙色框）；这条命令只报告，拦下发版是 `devkit.release` 的事
</Diagram>

### 模板

包根的 `template/` 是给别的仓用的骨架，只有 `devkit.scaffold` 与 `devkit.scaffold.plugin` 读它：`template/repo/` 生成仓根（`package.json`、`pnpm-workspace.yaml`、`README.md`、`.gitignore`），`template/pkg/` 生成插件包（源码、测试、tsconfig、vitest、oxlint、构建脚本），`template/site/plugin.mdx.tpl` 生成文档站现状区里的插件页（写出插件注入的服务名，自述检查要求它们出现在现状区里）。生成的插件包清单里没有 peer；浏览器侧构建的外置名单与样式的令牌映射都从外壳 `@godcreator/gwb-shell` 取。文件一律带 `.tpl` 后缀，占位符只有 `{{name}}`、`{{title}}`、`{{pkg}}`、`{{pkgName}}`、`{{cssPrefix}}`、`{{testedKernel}}`、`{{docsBlock}}` 七个，`{{testedKernel}}` 填运行命令的那个 home 的内核版本号。模板也是结构体检规则的正本，两者由往返测试保证一致（[结构体检](/docs/devkit/structure#规则与模板的一致模板是唯一正本)）。生成的插件包里的两份测试守卫来自同仓的 [repo-kit](/docs/repo-kit)。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令插件的服务 `gwbCommands`（`@godcreator/gwb-commands`，写在 `export const inject`） | 登记 12 条命令；按名字查找并调用别的插件的命令 | 插件不加载：cordis 等到这个服务出现才调用 `apply`。这是唯一的必需依赖 |

| 外壳插件的服务 `gwbShell`（局部注入） | `describeSelf` 报显示名「开发套件」与图标 | 插件清单里没有显示名，别的不受影响 |
| node 命令行插件的服务 `gwbNodeCli`（局部注入） | 把 `bin/cdp.mjs` 登记成 `devkit.cdp` | 没有 `devkit.cdp` 命令；`devkit.dev` 不受影响，它自己启动 `bin/cdp.mjs` 子进程 |
| 说明书插件的服务 `gwbSkills`（局部注入） | 登记 `skills/` 下三份说明书 | agent 读不到这三份说明书，命令照常 |
| 站点插件的 `docs-site.create`、docfirst 插件的 `docfirst.attach`（按命令名查找） | `devkit.scaffold` 建文档站的两步 | 插件的文件照样写到磁盘，跳过建站，回执写明怎么补 |

## 不做的事

- **不画界面**：没有窗格、没有浏览器端代码，只向外壳报一个显示名；使用者是 agent，读回执
- **不管文档站的内容**：生成骨架归站点插件 `@godcreator/gwb-docs-site`，装六区与核对文档归 docfirst 插件 `@godcreator/gwb-docfirst-workflow`；本包不依赖它们的任何包，只按命令名调用。本包只在建仓与加插件时往现状区写一页插件页草稿
- **不增删 home 里的条目**：条目归插件管理 `@godcreator/gwb-plugin-manager`。`devkit.dev` 在目标 home 里没有条目时装完就停、回执里说用 `plugin-manager.install` 补；唯一的例外是 `devkit.home.new` 在新 home 启动之前写好基础插件的 `cordis.yml`
- **不写 `runtime.json`**：它由内核与 MCP 入口插件写，本包只读
- **不升级日常用的 `default`**：`devkit.dev` 拒绝以 `default` 为目标，`devkit.release` 只发到源；升级 `default` 走 `plugin-manager.update-all`
- **不收端口**：定位一个 home 只按名字，端口从记录里查
- **不构建内核、不认内核仓**：启动 home 用的是宿主自己那个应用；改内核源码的验证走内核仓自己的流程
- **不替别的插件登记说明书**：说明书名全局唯一，重名的那份不登记；别的插件的说明书由它自己登记
- **没有设置项**：不注入 `gwbSettings`，一项设置都不定义；缺省的容器根问 `unit-folder.list`
- **不自动清理旧 home**：`devkit.home.new` 的回执带着现有 home 清单，删哪个由人或 agent 决定
