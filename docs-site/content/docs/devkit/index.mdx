**本页回答**：开发套件有哪些功能；它对外提供哪些命令、说明书与模板，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归别的模块。包名 `@godcreator/gwb-devkit`，源码目录 `plugins/devkit/`，入口文件 `src/index.ts`；另有一个不经构建的命令行脚本 `bin/cdp.mjs`。

开发套件是**一个普通的 gwb 插件**，没有任何特权：装进 home 才有它的命令，加载不成功就什么都没有，和别的插件一样由插件管理安装、升级、卸载。它的使用者是 agent，所以没有界面，全部结果都在命令回执里。在[接缝图](/docs)上它是「开发套件」那个框；为什么这么切分见[关键设计](/docs/design)。

## 功能

- **建仓**：`devkit.scaffold` 把新插件的初始文件写进一个还不存在的目录（workspace 仓，插件在 `plugins/<短名>/`），再在插件包目录调 shadcn 官方 CLI 加上窗格用的 `button`，不建文档站；`devkit.scaffold.plugin` 往已有的 workspace 仓再加一个插件包——[建仓与加插件](/docs/devkit/scaffold)
- **测试 home**：`devkit.home.new` 开一个装好内核包、`cordis` 与基础插件（含提供 `timer` 服务的 `@cordisjs/plugin-timer`）的隔离 home，`open` 重开、`list` 列出、`rm` 删除；调试端口自动选，之后只按名字找——[测试 home](/docs/devkit/home)
- **改一版看一版**：`devkit.dev` 把工作区的改动打包成开发版的包文件放进另一个 home，经那个 home 的插件管理装进正在运行的进程并重新加载，整页刷新，最后取证——[改一版看一版](/docs/devkit/dev)
- **发正式版**：`devkit.release` 从仓根把包按依赖顺序发到各包的发布目标（`package.json` 的 `publishConfig.registry`），发之前检查 git 工作区、构建产物、依赖写法、插件 peer 里的内核包与别的插件、插件注入的服务与 peer 对不对得上，不改仓里任何文件——[发正式版](/docs/devkit/release)
- **CDP 驱动**：`devkit.cdp`（`bin/cdp.mjs`）在隔离 home 的页面里点击、输入、截图、执行工作台命令、问页面属于哪个 home；工作台没运行时也能直接用 node 运行——[CDP 驱动](/docs/devkit/cdp)

`devkit.cdp` 是 `bin/cdp.mjs` 登记出来的：经 `gwbNodeCli` 登记的脚本自动成为同名命令，回执带 stdout、stderr 与退出码。工作台没运行时可以直接 `node <包根>/bin/cdp.mjs <home 名> <动作>`。

加载完成时往 `<home>\gwb.log` 写一行「开发套件就绪」，列出此刻命令总线上 `plugin` 是本包的全部命令：有这一行说明 `apply` 执行完了。`devkit.cdp` 在不在取决于 node 命令行插件有没有加载，所以名单每次当场向命令总线查询，不另存一份：

### 说明书

两份说明书放在包根的 `skills/`，由说明书插件登记，agent 经 MCP 入口的 `skill.read` 读：

| 说明书 | 管什么 | 正本 |
| --- | --- | --- |
| `gwb-devkit` | 新写插件、改插件、改一版看一版、在页面里取证、发版；附件 `references/rules.md` 是规矩总表，`references/evidence.md` 讲在页面里取证 | [gwb-devkit](/docs/outputs/skills/gwb-devkit)、[附件 evidence](/docs/outputs/skills/gwb-devkit-evidence)；规矩总表就是[写插件的规矩](/docs/rules)这一页 |
| `gwb-release` | 全生态的版本号规则：升哪一位、改依赖版本号、发破坏性版本多做的两步 | [gwb-release](/docs/outputs/skills/gwb-release) |

说明书只写步骤、完成判据和工具不会报出来的注意事项；命令的参数、回执、拒绝条件写在命令的 `usage` 里，说明书不重复。

### 模板

包根的 `template/` 是给别的仓用的初始文件，只有 `devkit.scaffold` 与 `devkit.scaffold.plugin` 读它：`template/repo/` 生成仓根，`template/pkg/` 生成插件包。模板分几部分、有哪些占位符、改模板要守什么，见[建仓与加插件](/docs/devkit/scaffold)；模板带的产物测试与发版前检查用同一套包名 import 名单，见 [4 模板与发版前检查](/docs/seams/template-release)。

## 依赖

注入了哪些服务、必需还是局部注入、peer 怎么写、缺了会怎样，按值 import 了插件管理主入口的哪几样，经 CDP 调了目标 home 的哪些命令，直接读写了哪些文件、启动了哪些子进程，都在[插件之间怎么连](/docs/wiring#godcreatorgwb-devkit)。发布目标、pnpm 源路由与发起 home 的凭据怎样配合，见 [pnpm 与包源](/docs/seams/pnpm-registry)。运行时自己用的库（yaml、es-module-lexer）写 dev、由构建打包进 `dist/index.js`，构建怎么做见[开发](/docs/develop#提交前的检查)。

## 不做的事

- **不画界面**：没有窗格、没有浏览器侧代码，只向外壳报一个显示名；使用者是 agent，读回执
- **不建文档站、不写文档页**：建仓与加插件只写插件的文件；建站（`docfirst.create`）与核对文档归 docfirst 插件 `@godcreator/gwb-docfirst-workflow`，本包不调它的命令
- **不自己增删 home 里的条目、不写 home 的清单**：安装与条目归插件管理。`devkit.dev` 装没装过的插件时调目标 home 的 `plugin-manager.install`，由插件管理新建条目；唯一的例外是 `devkit.home.new` 在新 home 启动之前直接 `pnpm add` 装包、写好基础插件的 `cordis.yml`（那时插件管理还没装、home 还没启动）
- **不写 `runtime.json`**：它由内核与 MCP 入口插件写，本包只读
- **不升级日常用的 `default`**：`devkit.dev` 拒绝以 `default` 为目标，`devkit.release` 只发到源；升级 `default` 用插件管理
- **不收端口**：定位一个 home 只按名字，端口从记录里查
- **不构建内核、不认内核仓**：`devkit.home.new` 从源上装内核包，版本是运行中的内核的版本，启动用的是宿主自己那个安装版应用；改内核源码的验证走内核仓自己的流程
- **不替别的插件登记说明书**：说明书名全局唯一，重名的那份不登记；别的插件的说明书由它自己登记
- **不另定义设置项**：不注入 `gwbSettings`；registry 凭据经插件管理提供的内部函数读取发起 home 的共享 `npm-auth`
- **不自动清理旧 home**：现有的 home 由 `devkit.home.list` 列出，删哪个由调用方决定
- **不巡检别的仓**：不扫容器根下各仓的依赖与布局；依赖写法与产物在各仓发版时由 `devkit.release` 查；不是 workspace 布局的仓要先照模板迁
- **不核对文档站内容**：核对、确认、重新生成生成物归 docfirst，在仓的文档站目录里运行，本包不转发、不替人启动
- **不替人决定版本号**：`devkit.release` 发的是包清单里写着的版本号，同一个版本号已在源上就拒；升哪一位照说明书 `gwb-release`
- **不做自动升级、不做回退**：升坏了往前修，再发一版再升
- **不删团队源上的旧开发版**：devkit 0.20.0 之前发到团队源的 `-dev.*` 版本留着，删除不可逆（[未来区悬着的三件定为不做](/trajectory/2026-09-25-future-leftovers-settled)）
