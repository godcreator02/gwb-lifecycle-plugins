**本页回答**：开发套件有哪些功能；它对外提供哪些命令、说明书与模板，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归别的模块。包名 `@godcreator/gwb-devkit`，源码目录 `plugins/devkit/`，入口文件 `src/index.ts`；另有一个不经构建的命令行脚本 `bin/cdp.mjs`。

开发套件是**一个普通的 gwb 插件**，没有任何特权：装进 home 才有它的命令，加载不成功就什么都没有。它自己也走它教别人走的那条路——在自己的仓里开发、发到团队源、装进 home。它的使用者是 agent，所以没有界面，全部结果都在命令回执里。在[接缝图](/docs)上它是「开发套件」那个框；为什么这么切分见[关键设计](/docs/design)。

## 功能

- **建仓**：`devkit.scaffold` 把新插件的骨架写进一个还不存在的目录（workspace 仓，插件在 `plugins/<短名>/`），默认连文档站一起建；`devkit.scaffold.plugin` 往已有的 workspace 仓再加一个插件包——[建仓与加插件](/docs/devkit/scaffold)
- **测试 home**：`devkit.home.new` 开一个装好内核包、cordis 与七个基础插件的隔离 home，`open` 重开、`list` 列出、`rm` 删除；调试端口自动选，之后只按名字找——[测试 home](/docs/devkit/home)
- **改一版看一版**：`devkit.dev` 把工作区的改动打包成开发版的包文件放进另一个 home，经那个 home 的插件管理装进正在运行的进程并重新加载，整页刷新，最后取证——[改一版看一版](/docs/devkit/dev)
- **发正式版**：`devkit.release` 从仓根把包按依赖顺序发到团队源，发之前检查 git 工作区、构建产物、依赖写法、插件 peer 里的内核包与别的插件，不改仓里任何文件——见下面[发正式版的检查](#发正式版的检查)
- **服务总览**：`devkit.services` 从调用它的那个 home 里各包的 `.d.ts` 现读：这个 home 有哪些可以 inject 的服务、各由哪个包提供、类型定义的原文——[服务表与类型声明](/docs/seams/service-table)
- **CDP 驱动**：`devkit.cdp`（`bin/cdp.mjs`）在隔离 home 的页面里点击、输入、截图、执行工作台命令、问页面属于哪个 home；工作台没运行时也能直接用 node 运行——[CDP 驱动](/docs/devkit/cdp)

### 发正式版的检查

`devkit.release` 依次做：仓根 git 工作区不干净就拒；仓根 `pnpm build`；按 `files` 白名单检查产物；同一个版本号已在源上就拒；发版前检查；在临时目录组装发布内容、发到 latest（`workspace:` 依赖写成 `^`：同一次发的写 `^新版本号`，其余写 `^<工作区里的版本号>`）。任何一个包没过检查，一个都不发，回执按包一次列全。它只碰团队源、不碰任何 home，所以从哪个 home 调用都可以。

这几步的顺序与取舍各有原因：

- **在仓根构建，不在包目录**：工作区里的插件常常用着同仓另一个包的产物。
- **全部检查在发第一个包之前做完**：发到一半停下，源上各包的 latest 就是新旧两版混在一起。
- **问题一次列全**：只报第一处的话，每改一处都要再完整构建一次才看得到下一处。
- **产物清单就是 `files` 白名单，不另列一份**：两份清单迟早对不上，现象是新写的代码发出去不生效。
- **同一次发的包之间写 `^新版本号`**：依赖方装得到这一次发的那一版，也跟得上之后破坏边界以内的版本。
- **git 工作区必须干净**：把没提交的改动发成 latest，是事后最难发现的错误。

- 第 5 步发版前检查，要发的包一起查、一次列全。每个包查三项：`@godcreator` 的 dev 范围包含源上的 latest、产物里没有空 import、相对 import 指向的文件都在；插件包另查四项：peer 只有 `cordis`、内核包与插件，peer 里的插件和源上 latest 在同一条线、包名 import 的两份名单、peer 里内核包的范围包含运行中的内核
- 第 6 步在临时目录组装发布内容，按 `packages` 给的顺序发到 latest
- 最下面那个框：任一项没过，一个包都不发，回执按包列出每一项问题

发版前检查对每个要发的包查：

- `@godcreator` 的 dev 依赖范围包含源上的 `dist-tags.latest`（写法认不出、问不出源上的 latest 或它不是版本号、下限比 latest 还新、latest 超出范围才拒，范围内落后放行）
- 构建产物里没有 `import {} from '…'` 这种空 import（源码写了 `import { type X }`），相对 import 指向的文件都在

插件包（`keywords` 含 `gwb-plugin`）另查：

- peer 里只有 `cordis`、内核包 `@godcreator/gwb-kernel-desktop` 与别的插件：是不是插件读包目录 `node_modules` 里它的清单，`keywords` 含 `gwb-plugin` 或同时含 `cordis` 与 `plugin` 才算；不是插件、清单读不到都拒，报错写明按「运行时谁提供」该改写成 dev 还是 `dependencies`
- peer 里的每个 `@godcreator` 插件（内核包与 `workspace:` 除外）写法是 `^x.y.z`，并且和源上 `dist-tags.latest` 在同一条线：主版本号为 0 时只比次版本号，≥1 时只比主版本号。不在同一条线就是上游出了破坏性版本，拒绝理由里写着适配、验过之后改成的 `^<latest>`；问不出源上的 latest 也拒
- node 侧产物的包名 import 只有 node 内置模块、`electron` 与本包 peer 里写了的包；浏览器侧产物只 import 页面 importmap 里的名字，也就是内核包页面入口 `dist/index.html` 里 importmap 的键
- peer 里写了内核包，写法是 `^x.y.z`，范围包含运行中的内核（没写、写法不对、不包含都拒，拒绝理由里写着该改成的 `^<运行中的内核的 x.y.z>`）

### 模板

包根的 `template/` 是给别的仓用的骨架，只有 `devkit.scaffold` 与 `devkit.scaffold.plugin` 读它：`template/repo/` 生成仓根（`package.json`、`pnpm-workspace.yaml`、`README.md`、`.gitignore`），`template/pkg/` 生成插件包（源码、测试、tsconfig、vitest、oxlint、构建脚本），`template/site/plugin.mdx.tpl` 生成文档站现状区里的插件页（功能、命令与窗格、依赖的服务、不做的事）。生成的插件包清单 peer 里是内核包与模板用到的命令总线、外壳两个插件，node 侧源码从内核包 `import type` 接口类型；浏览器侧构建的外置名单从内核包页面入口 `dist/index.html` 里的 importmap 读，样式的令牌映射从外壳 `@godcreator/gwb-shell` 取。文件一律带 `.tpl` 后缀，占位符只有 `{{name}}`、`{{title}}`、`{{pkg}}`、`{{pkgName}}`、`{{cssPrefix}}`、`{{kernelVersion}}`、`{{docsBlock}}` 七个，`{{kernelVersion}}` 填运行命令的那个 home 的内核版本号的 x.y.z 三段，生成 peer 里内核包的范围 `^x.y.z`。模板带的产物测试与发版前检查用同一套包名 import 名单（[模板与发版前检查](/docs/seams/template-release)）。

## 不做的事

- **不画界面**：没有窗格、没有浏览器端代码，只向外壳报一个显示名；使用者是 agent，读回执
- **不管文档站的内容**：生成骨架归站点插件 `@godcreator/gwb-docs-site`，装六区与核对文档归 docfirst 插件 `@godcreator/gwb-docfirst-workflow`；本包不依赖它们的任何包，只按命令名调用。本包只在建仓与加插件时往现状区写一页插件页草稿
- **不自己增删 home 里的条目、不写 home 的清单**：安装与条目归插件管理 `@godcreator/gwb-plugin-manager`。`devkit.dev` 装没装过的插件时调目标 home 的 `plugin-manager.install`，由插件管理新建条目；唯一的例外是 `devkit.home.new` 在新 home 启动之前直接 `pnpm add` 装包、写好基础插件的 `cordis.yml`（那时插件管理还没装、home 还没启动）
- **不写 `runtime.json`**：它由内核与 MCP 入口插件写，本包只读
- **不升级日常用的 `default`**：`devkit.dev` 拒绝以 `default` 为目标，`devkit.release` 只发到源；升级 `default` 用 `plugin-manager.update {"all":true}`
- **不收端口**：定位一个 home 只按名字，端口从记录里查
- **不构建内核、不认内核仓**：`devkit.home.new` 从团队源装内核包，版本是运行中的内核的版本，启动用的是宿主自己那个应用；改内核源码的验证走内核仓自己的流程
- **不替别的插件登记说明书**：说明书名全局唯一，重名的那份不登记；别的插件的说明书由它自己登记
- **没有设置项**：不注入 `gwbSettings`，一项设置都不定义
- **不自动清理旧 home**：`devkit.home.new` 的回执带着现有 home 清单，删哪个由人或 agent 决定
- **不巡检别的仓**：不扫容器根下各仓的依赖与布局；依赖写法与产物在各仓发版时由 `devkit.release` 查，布局照模板、改到哪个仓迁哪个
