**本页回答**：开发套件有哪些功能；它对外提供哪些命令、说明书与模板，各属于哪条接缝；它依赖什么、缺了会怎样；哪些事常被以为归它、其实归别的模块。包名 `@godcreator/gwb-devkit`，源码目录 `plugins/devkit/`，入口文件 `src/index.ts`；另有一个不经构建的命令行脚本 `bin/cdp.mjs`。

开发套件是**一个普通的 gwb 插件**，没有任何特权：装进 home 才有它的命令，加载不成功就什么都没有，和别的插件一样由插件管理安装、升级、卸载。它的使用者是 agent，所以没有界面，全部结果都在命令回执里。在[接缝图](/docs)上它是「开发套件」那个框；为什么这么切分见[关键设计](/docs/design)。

## 功能

- **建仓**：`devkit.scaffold` 把新插件的初始文件写进一个还不存在的目录（workspace 仓，插件在 `plugins/<短名>/`），不建文档站；`devkit.scaffold.plugin` 往已有的 workspace 仓再加一个插件包——[建仓与加插件](/docs/devkit/scaffold)
- **测试 home**：`devkit.home.new` 开一个装好内核包、`cordis` 与七个基础插件的隔离 home，`open` 重开、`list` 列出、`rm` 删除；调试端口自动选，之后只按名字找——[测试 home](/docs/devkit/home)
- **改一版看一版**：`devkit.dev` 把工作区的改动打包成开发版的包文件放进另一个 home，经那个 home 的插件管理装进正在运行的进程并重新加载，整页刷新，最后取证——[改一版看一版](/docs/devkit/dev)
- **发正式版**：`devkit.release` 从仓根把包按依赖顺序发到各包的发布目标（`package.json` 的 `publishConfig.registry`），发之前检查 git 工作区、构建产物、依赖写法、插件 peer 里的内核包与别的插件，不改仓里任何文件——[发正式版](/docs/devkit/release)
- **CDP 驱动**：`devkit.cdp`（`bin/cdp.mjs`）在隔离 home 的页面里点击、输入、截图、执行工作台命令、问页面属于哪个 home；工作台没运行时也能直接用 node 运行——[CDP 驱动](/docs/devkit/cdp)

`devkit.cdp` 是 `bin/cdp.mjs` 登记出来的：经 `gwbNodeCli` 登记的脚本自动成为同名命令，回执带 stdout、stderr 与退出码。工作台没运行时可以直接 `node <包根>/bin/cdp.mjs <home 名> <动作>`。

### 模板

包根的 `template/` 是给别的仓用的初始文件，只有 `devkit.scaffold` 与 `devkit.scaffold.plugin` 读它：`template/repo/` 生成仓根，`template/pkg/` 生成插件包。模板分几部分、有哪些占位符、改模板要守什么，见[建仓与加插件](/docs/devkit/scaffold)；模板带的产物测试与发版前检查用同一套包名 import 名单，见 [4 模板与发版前检查](/docs/seams/template-release)。

## 依赖

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令插件的服务 `gwbCommands`（`@godcreator/gwb-commands`，写在 `export const inject`，peer 必需） | 登记 8 条命令；就绪日志列出此刻总线上本包的命令 | 插件不加载：cordis 等到这个服务出现才调用 `apply`；`apply` 里取不到它就抛错。这是唯一的必需服务 |
| 插件管理包 `@godcreator/gwb-plugin-manager` 主入口导出的函数（peer 必需） | 找 pnpm 的 `locatePnpm`、在 home 里启动 pnpm 用的环境 `homePnpmEnv`、内核包名与 peer 范围的判定、取输出最后几行的 `tailLines`，以及 `devkit.dev` 调的三条命令的名字 `LIST_COMMAND`、`INSTALL_COMMAND`、`UPDATE_COMMAND` | 模块 import 不到，插件加载失败 |
| 内核服务 `gwbKernel` 的 `dataDir` 与 `version`（用 `requireKernel` 取，不写进 `inject`） | `dataDir` 是本插件自己所在的 home：`devkit.dev` 拒绝以它为目标（home 根目录不从它推，按 `%APPDATA%\gwb-kernel\homes` 算）；`version` 是建仓与加插件时新包 peer 里内核包范围的下限、`devkit.home.new` 装进新 home 的内核包版本 | 用到它的命令抛错「ctx.gwbKernel 不在」 |
| 外壳插件的服务 `gwbShell`（局部注入） | `describeSelf` 报显示名「开发套件」与图标 | 插件清单里没有显示名，别的不受影响 |
| node 命令行插件的服务 `gwbNodeCli`（局部注入） | 把 `bin/cdp.mjs` 登记成 `devkit.cdp` | 没有 `devkit.cdp` 命令；`devkit.dev` 不受影响，它自己启动 `bin/cdp.mjs` 子进程 |
| 说明书插件的服务 `gwbSkills`（局部注入） | 登记 `skills/` 下两份说明书 | agent 读不到这两份说明书，命令照常 |
| 目标 home 里的插件管理：`plugin-manager.install`、带 `specs` 参数的 `plugin-manager.update` 与 `plugin-manager.list`，经 CDP 调用 | `devkit.dev` 装包、新建条目、重新加载条目、取证 | `devkit.dev` 回 `ok: false`，带插件管理回执里的原因 |
| 各 home 的 `runtime.json`（内核与 MCP 入口插件写） | 按名字查 pid 与调试端口 | 连不上那个 home，回执说停掉重开一次 |
| 宿主应用（`process.execPath`，安装版） | `devkit.home.new` / `open` 再启动一次它 | 宿主是开发态 electron 时拒 |
| `tasklist`、`netstat`、`taskkill` | 查进程表、查端口被谁监听、超时终止整棵进程树（开发套件只支持 Windows） | 查不出就报错：列出、定位、停止、删除 home 都失败，不给一个可能不对的结果 |
| 机器上的 pnpm | 构建、发布、打包开发版、往新 home 里安装、`pnpm view` 查源 | 对应的命令回 `ok: false`，带 pnpm 输出的最后几行 |
| git | `devkit.release` 查仓根工作区干不干净 | 查不出也拒发 |
| 各包的发布目标（`package.json` 的 `publishConfig.registry`），发布 token 写在用户级 `~/.npmrc` | 发正式版、查这个版本号发过没有；开发版不经过它 | 发版失败 |
| 团队源，`@godcreator` 的范围行写在用户级 `~/.npmrc` | 建仓不给 `registry` 参数时写进插件包的发布目标；查 peer 里 `@godcreator` 插件的 latest；往新 home 里装内核包、`cordis` 与基础插件 | 发版与安装失败；机器上没有 `@godcreator` 的范围行时问不出 latest，发版前检查拒 |
| 内核包 `@godcreator/gwb-kernel-desktop` 包根导出的类型（peer 里写的就是它） | `GwbContext`、`GwbKernelApi` 的类型 | 只在编译时用 |

外壳、node 命令行、说明书三个服务用 `ctx.inject([...], fn)` 局部注入：缺哪个，只有那一部分停在等待状态，主插件照常加载。这三个插件在 peer 里标 `optional`，命令插件、插件管理与内核包是必需的 peer（见[用到的插件写 peer](/docs/rules/plugin-peers)）。服务怎么提供和使用的规矩见 [cordis 服务怎么提供和使用](/docs/rules/services)。运行时自己用的库（yaml、es-module-lexer）写 dev、由构建打包进 `dist/index.js`，构建怎么做见[开发](/docs/develop#提交前的检查)。

## 不做的事

- **不画界面**：没有窗格、没有浏览器侧代码，只向外壳报一个显示名；使用者是 agent，读回执
- **不建文档站、不写文档页**：建仓与加插件只写插件的文件；生成初始站点归站点插件 `@godcreator/gwb-docs-site`，装六区与核对文档归 docfirst 插件 `@godcreator/gwb-docfirst-workflow`，本包不调它们的命令
- **不自己增删 home 里的条目、不写 home 的清单**：安装与条目归插件管理。`devkit.dev` 装没装过的插件时调目标 home 的 `plugin-manager.install`，由插件管理新建条目；唯一的例外是 `devkit.home.new` 在新 home 启动之前直接 `pnpm add` 装包、写好基础插件的 `cordis.yml`（那时插件管理还没装、home 还没启动）
- **不写 `runtime.json`**：它由内核与 MCP 入口插件写，本包只读
- **不升级日常用的 `default`**：`devkit.dev` 拒绝以 `default` 为目标，`devkit.release` 只发到源；升级 `default` 用插件管理
- **不收端口**：定位一个 home 只按名字，端口从记录里查
- **不构建内核、不认内核仓**：`devkit.home.new` 从源上装内核包，版本是运行中的内核的版本，启动用的是宿主自己那个安装版应用；改内核源码的验证走内核仓自己的流程
- **不替别的插件登记说明书**：说明书名全局唯一，重名的那份不登记；别的插件的说明书由它自己登记
- **没有设置项**：不注入 `gwbSettings`，一项设置都不定义
- **不自动清理旧 home**：现有的 home 由 `devkit.home.list` 列出，删哪个由调用方决定
- **不巡检别的仓**：不扫容器根下各仓的依赖与布局；依赖写法与产物在各仓发版时由 `devkit.release` 查；不是 workspace 布局的仓要先照模板迁
