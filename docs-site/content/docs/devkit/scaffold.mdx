**本页回答**：`devkit.scaffold` 与 `devkit.scaffold.plugin` 从收到参数到回执之间做了什么、哪几步不能换顺序、模板分几部分、改模板要守什么。写新插件的整条流程在说明书 `gwb-devkit` 的「新写一个插件」，本页不复述。

## 只有一种仓的布局

workspace 仓：仓根是一个不发布的 private 包（`pnpm build` / `pnpm check` 递归到各成员，自己没有代码），插件放在 `plugins/<短名>/`，不是插件的包放在 `packages/`（插件共用的库之类，按需）。**只有一个插件的仓不是另一种布局**，只是 `plugins/` 下恰好一个目录；加第二个插件永远是 `devkit.scaffold.plugin` 往 `plugins/` 再生成一个，不会出现「当初建小了、现在要迁移」的情况。插件包自带全部配置（tsconfig、oxlint 配置、构建脚本都在包内），放在哪个仓里都一样。

插件包里只有插件自己：node 侧与浏览器侧的入口、样式入口、构建脚本、三份 tsconfig（node 侧、浏览器侧、只出类型声明的那份）、oxlint 配置与清单。不带测试文件：构建产物的包名 import 与样式的检查由 `devkit.dev` 与 `devkit.release` 做，复制进各仓的测试副本不会跟着 devkit 更新（取舍见轨迹卡[写插件的规矩只留有工具查的](/trajectory/2026-09-25-rules-only-checked-ones)）。node 侧和浏览器侧都用 esbuild 打成一个文件，外置名单照发版前检查的两份名单，其余依赖打包进去。

模板分两部分：`template/repo/` 生成仓根，`template/pkg/` 生成 `plugins/<短名>/`（插件包，**唯一正本**——建仓与加插件生成的是同一份，两条命令生成的格式一致靠这个保证）。`devkit.scaffold.plugin` 只收 workspace 仓，别的当场拒。

## 管什么

一个短名派生出一组名字：包名 `<scope>/gwb-<短名>`、插件名 `gwb-<短名>`、命令名 `<短名>.<动作>` 的前半。模板里要显示名的地方（README 标题、仓根与插件包的 `description`、窗格标题、加载日志、窗格里的问候）也用短名，要中文名的自己改生成的文件。包的身份就是 `package.json` 的 `name`，发到哪里就是 `publishConfig.registry`，都用 npm 的标准字段：`scope` 参数定包名范围（缺省 `@godcreator`），`registry` 参数写进插件包的 `publishConfig.registry`（缺省团队源），`devkit.release` 照它发。没有团队源发布权限的开发者给自己的范围与源，就能走完建仓、改一版看一版、发正式版。这部分代码把包内 `template/` 的两部分按这组名字渲染好、写进一个还不存在的目录，再把「接下来做什么」放进回执。

两条命令都只写插件的文件，不建文档站、不往已有的文档站里写页，也不调别的插件的命令：要文档站的仓，照站点插件与 docfirst 插件自己的说明书去建。加插件不碰仓根，README 里插件清单的更新由人做（`nextStepsPlugin` 最后一步提醒）。

<Diagram name="dk-scaffold" title="devkit.scaffold 建仓的四步，都在本包里">
- 第 1 步 `planScaffold` 算计划：校验短名、`scope` 与 `registry`，派生包名 `<scope>/gwb-<短名>` 与插件名、定下发布目标，peer 里内核包、命令总线、外壳的范围取运行建仓命令的那个 home 里的版本号（x.y.z 三段）；不碰磁盘
- 第 2 步在内存里渲染 `template/repo/` 与 `template/pkg/`；认不出的占位符当场抛错
- 第 3 步 `writeRepo` 写磁盘：目标目录必须还不存在；仓根写四个文件，插件包写到 `plugins/<短名>/`
- 第 4 步回执：`nextSteps` 只写这次建仓特有的——仓与插件包在哪，流程指向说明书 `gwb-devkit` 的「新写一个插件」

## 不知道什么

不知道文档站、代码引用怎么核对，也不知道命令总线存在：`scaffold.ts` 里的函数连 `ctx` 都拿不到。

也不知道生成出来的仓将来怎么发版：发版的做法在说明书 `gwb-release` 里，生成的 README 与回执都只指向它。

## 数据结构

六个类型，两条流程：建仓（参数 `ScaffoldInput` → 计划 `ScaffoldPlan` → 渲染好的 `RenderedFile[]`）、加插件（`ScaffoldPluginInput` → `ScaffoldPluginPlan` → 同样的 `RenderedFile[]`）。

`ScaffoldPlan` 与 `ScaffoldPluginPlan` 算出来之后，后面每一步只看计划，不再回头看参数。两种参数里的 `peerVersions` 不是命令参数：`src/index.ts` 调 `homePeerVersions`，内核取运行中的内核服务的 `gwbKernel.version`，命令总线与外壳读这个 home 的 `node_modules/<包>/package.json`（没装就拒，报错写出读的是哪个文件）。计划里只留 x.y.z 三段（开发版去掉预发布段），渲染时分别填进生成的 `package.json` peer 里三个包的范围 `^x.y.z`。模板里因此不写死任何 `@godcreator` 包的版本号：写死的数字会随上游发版过时，上游一升 x，新仓第一次发版就被「和源上 latest 不在同一条线」拒掉（取舍见轨迹卡[建仓模板的 peer 版本号从 home 读](/trajectory/2026-09-25-scaffold-peers-from-home)）。

## 提供的接口

对外两条命令：`devkit.scaffold { name, dir, scope?, registry? }` 与 `devkit.scaffold.plugin { name, repo, scope?, registry? }`。两条的回执都是 `{ repoDir, pluginDir, pkg, registry, name, files, nextSteps }`：`pkg` 是完整包名，`registry` 是写进 `publishConfig.registry` 的发布目标。**参数不对时把整份用法说明放进报错**，而不只回一句「参数错误」：这两条命令的主要调用方是 agent，命令总线不带参数形状，它能不能看出自己错在哪全靠这段话。认不出的参数键直接拒，报出是哪个键（devkit 的每条命令都这样）。

## 依赖的接口

| 接口 | 用来做什么 | 运行时的实现 | 测试时的实现 |
| --- | --- | --- | --- |
| `node:fs` | 读包内模板、检查仓的布局、把渲染好的文件写下去 | 直接调用，不注入 | 不替换，真写临时目录 |
| 包内 `template/`（两部分） | 初始文件的正本，`packageRoot` 从本模块所在目录向上找 `package.json` 定位，找到盘根都没有就抛 | 发布出去的包里那份 | 同一份，测试读的就是它 |
| yaml 库 | 读 `pnpm-workspace.yaml` 的 `packages` | 打包进 `dist/index.js` 的那一份 | 不替换，测试直接 import 它 |

## 怎么单独测

给一份参数，看抛什么、算出什么；给一个临时目录，看磁盘上写下了什么。整个过程不启动进程、不开窗口，`tests/scaffold.test.ts` 直接测这几件事：

短名的正则会不会放过 `x--` 这种结尾；`planScaffold` 的派生与缺省值，计划里没有显示名；给了 `scope`、`registry` 时包名、`publishConfig.registry`、README 与回执跟着变，内核包与模板用到的两个插件仍在 `@godcreator` 下，不给时是团队范围与团队源，不合规的范围与地址（不带 `@`、大写、非 http(s)、不是规范写法、带账号或查询串）建仓与加插件都拒；`planScaffoldPlugin` 对不存在的 repo、`pnpm-workspace.yaml` 的 `packages` 里没有 `plugins/*` 的拒绝，以及带引号、块列表、流式列表、注释、CRLF 几种写法都收，YAML 写坏了、`packages` 不是字符串列表时报出文件与行列；`dir` / `repo` 用正斜杠写与用反斜杠写得到同一个路径；`nextSteps` / `nextStepsPlugin` 写了什么、`packages` 参数有没有带上、流程指向说明书而不在回执里复述、不提文档站；生成的 `package.json` 在 peer 里写了内核包 `^<运行命令的内核版本号>`、命令总线与外壳 `^<home 里装着的版本号>`，开发版只取 x.y.z 三段，模板里这两项是占位符、不写死数字；`homePeerVersions` 读 home 里装着的版本，没装外壳时拒并写出读的是哪个文件；模板登记命令不写 `plugin`；窗格入口的 `PaneArgs`、`PaneHandle` 从外壳的 `@godcreator/gwb-shell/pane` 取；认不出的占位符真的会抛错，`{{title}}` 也算认不出；`.tpl` 后缀与两部分的去向（`landRel`）对不对；包内 `template/` 里每个文件都声明了属于哪部分、只有两部分；要显示名的地方都是短名；生成的文件里没有文档站；生成的清单 peer 里有内核包、只在 node 侧按值 import 了 `cordis` 时才写 peer `cordis`，命令总线与外壳写在 peer、不写 dev；生成的 node 侧源码从 peer 里的内核包 `import type` 接口类型；构建脚本从内核包页面入口 `dist/index.html` 里的 importmap 读外置名单、不写 react 包名的字面量，node 侧也用 esbuild 打成一个文件、外置 peer 与 `electron`、`cordis`，tsc 只出类型声明，tsconfig 里没有 `verbatimModuleSyntax`；样式入口从外壳引令牌映射；模板不带测试文件、dev 里没有 `@tailwindcss/node`；清单的 `keywords` 只有 `gwb-plugin`、`files` 只有 `dist`、`exports` 只有 `.`、没有 `author` 与 `engines`、没有 `prepublishOnly`；生成的 `description` 是一句话、不带计数，生成的文件里没有已退役的 `gwb-repo-kit`；生成的 JSON、YAML 都解析得了；在临时 workspace 仓里真的生成一个 `plugins/<短名>/`；`writeRepo` 对已存在的目录真的拒绝；`packageRoot` 找到盘根都没有就抛；回执里给的命令参数都过得了 `JSON.parse`。`tests/commands.test.ts` 在假上下文上调两条命令，测回执只有那几个字段、不调别的插件的命令、不写文档站。

## 模板里两处看着多余、其实少不了

- **`pnpm-workspace.yaml` 里的 `allowBuilds`**：pnpm 11 只从这个文件读这项设置，不读 `package.json` 的 `pnpm` 字段；esbuild 的安装脚本要在这里放行。不放行的现象是连锁的：install 报「Ignored build scripts」，`pnpm run` 核对依赖时自动补装又遇到同样的拒绝，最后的调用栈在 pnpm 内部，看不出是构建脚本没放行
- **`oxlint-tsgolint`**：`oxlint` 需要类型信息的规则要用它，少了 `pnpm lint` 报 "Failed to find tsgolint executable"。模板里它与 `oxlint` 都写准确版本号

## 改模板时要守的三条

- **`template/` 下的文件一律带 `.tpl` 后缀**，写到磁盘时去掉：`npm pack` 固定不打包 `.gitignore`，给所有文件统一加后缀，一条规则就管住了全部文件
- **`.oxlintrc.json` 放在插件包里、不放仓根**：oxlint 按工作目录找配置，插件包自带配置，搬到哪个仓都不用改
- **模板里不写死 `@godcreator` 包的版本号**：peer 里的内核包、命令总线 `gwb-commands`、外壳 `gwb-shell` 都用占位符，由建仓那个 home 填（见上面「数据结构」）。模板要用到新的 `@godcreator` 插件时同样加占位符、从 home 读，不写数字；写死的数字一过时，新仓第一次发版就被「和源上 latest 不在同一条线」拒掉

## 代码地图

**在哪**：纯逻辑全在 `src/scaffold.ts`；命令登记在 `src/index.ts` 的 `devkit.scaffold` / `devkit.scaffold.plugin` 两段；初始文件的正本在包根的 `template/repo/` 与 `template/pkg/`。

**先读**：`planScaffold`，建仓流程的入口与全部校验；加插件从 `planScaffoldPlugin` 读起。

**读序**：先算计划，`placeholders` 与 `render` 把模板变成内存里的文件表，`landRel` 决定两部分各写到哪，`writeRepo` 写磁盘，`nextSteps` / `nextStepsPlugin` 生成回执末尾的下一步。

**可跳过**：`template/` 下那 13 个 `.tpl` 是给别的仓用的内容，不是这部分的逻辑。要看模板长什么样就看那两个目录本身，这一页不抄。
