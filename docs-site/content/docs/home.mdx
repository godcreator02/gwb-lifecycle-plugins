# 测试 home

**本页回答**：一个测试 home 是怎么被开起来的、名字为什么长成那样、起的是哪个应用、
调试端口是从哪儿挑出来的、删一个 home 拦住了什么、以及「我要操作哪个 home」是怎么变成
一个调试端口的。

## 管什么

把实机验证那几步命令化：开一个新的、列出现有的、重开一个已有的、删掉，外加一条
不对外露面的定位：给一个 home 名，回够得着它的那个调试端口。

**调试端口由这块自己挑，人给不了。** 名字是够到一个 home 的唯一地址，而名字要落到端口上全靠记录里
那一格；没有那一格的 home 起完就够不着。收一个手给的端口，剩下的全部用法就只有「敲错一位落在
别人的端口上」。

home 建在 `%APPDATA%\gwb-kernel\homes\<名>\`。开哪一个由环境变量 `GWB_HOME` 决定，这块要做的只是
把宿主那个应用按那个名字再拉一份，再从盘上读出它是谁。

## 不知道什么

它不知道 home 里装了哪些插件，也不知道插件挂上了没有。那是 plugin-manager 插件的事，问 `plugin-manager.list`。

它**不写那份运行时记录**，只读。`package.json`、空的 `cordis.yml` 与 `runtime.json` 都归内核自己铺，
`runtime.json` 里 `mcp` 那格归门插件（gwb-mcp）补；这块只建目录，然后读。

它不知道 CDP 端口拿来干什么，只负责挑一个、把那个开关摆到命令行上、再从记录里把它读回来。

它还有一条前提：这套命令要求本插件跑在一个活着的 home 里。一个 home 都没活着的时候，只能按手工那四步
先把工作台起起来。

**写它的是内核与门插件，不是这块。** 内核开机整份重写前四格，gwb-mcp 绑上端口之后读改写补

## 提供的接口

四条命令：`devkit.home.new`、`list`、`open`、`rm`，外加一条给同仓别处用的定位函数。

**命名是 `<短名>-<yyMMddHHmm>`**，撞了退到秒，再撞就照实拒：

{/* ref file="../plugins/devkit/src/home.ts" lines="145-157" */}

不静默加序号，因为名号里每一段都得能读出时间。同一个插件的 home 因此在目录里挨在一起、各自按时间排，
正好是清理时要的顺序。

**`new` 与 `open` 都不 build 内核、不认内核仓，拉的是宿主自己那个应用**：

{/* ref file="../plugins/devkit/src/home.ts" lines="353-367" */}

home 跑的永远是宿主正跑着的那个应用，日常就是安装版，内核版本跟着安装包走；内核源码改动的验机是内核仓
自己的路，这块不代劳。`open` 与 `new` 的分别在另一件事上：**机器重启之后回到原来那个现场只有 `open`**，
`new` 永远造新目录，插件得全部重装一遍。

起进程之前还有一道：同一个 home 不许开两个实例。两扇窗写同一份日志、同一个 home，而按记录停它的那条
路只认得住记录里那一个。

**所有还会摔的步骤都排在 spawn 前面。** spawn 之后再失败，会留下一扇没有记录的窗，谁也管不着它。

起来之后看五秒：

{/* ref file="../plugins/devkit/src/home.ts" lines="406-416" */}

「起没起来」没有 ping 可打，进程还活着是此刻唯一拿得到的信号。这五秒只为抓住「秒退」这一种最常见的
死法（产物不在、端口被占），真正成没成，那扇窗和人说了算。

**观察窗过完再读一眼记录**：

{/* ref file="../plugins/devkit/src/home.ts" lines="417-425" */}

记录是内核开机那一下才写的，而它是下游「按名字找得着这个 home」的全部凭据，所以回执里要说清它出没
出现。**读不到不算起失败**：窗已经在那儿了，只是这个内核版本还不写、或者写晚了。那时按名字定位与
按记录停它都用不了，而且没有退路可走——上游只认名字，所以只能停掉、换一个写这份记录的内核再开。

CDP 调试端口**走命令行，不走环境变量**：

{/* ref file="../plugins/devkit/src/home.ts" lines="175-202" */}

内核不认识任何调试相关的环境变量，`--remote-debugging-port` 是 Chromium 自己的开关，命令行上就生效。
开了调试口就一并带 `--disable-backgrounding-occluded-windows`：窗口被整个盖住时 Chromium 停止产帧，
取证的输入派发会挂住、截图拿到陈旧帧。`new` 与 `open` 走同一个计划，两条都带。

**这一趟用哪个端口，起之前自己定，定不出来就不起。**

{/* ref file="../plugins/devkit/src/index.ts" lines="183-207" */}

**先沿用这个 home 上次那个端口**，它空着就是它。一个 home 的端口稳定下来是有价值的：人记得住、
日志里对得上、开着的检查器不用换地址；而重开一次换一个数，除了「每次都得重新问一遍」之外
什么都换不来。

被别人占了才另挑，另挑两道筛。第一道是**别的** home 记录里占着的一律跳过，**陈旧的也算占着**：
那份记录还指着那个数，再分给第二个 home 的话，两份记录会同时声称自己是同一个端口，而按名字定位
全靠这个数唯一。**自己那份不算**，不然重开一次就被自己上一次的记录挤走。

{/* ref file="../plugins/devkit/src/home.ts" lines="484-492" */}

第二道是此刻真有人 listen 的跳过，一个一个问，问到空的就用它。换没换在回执的 `cdpNote` 里
说一句——不说的话，人会以为端口还是上次那个。

{/* ref file="../plugins/devkit/src/home.ts" lines="506-519" */}

**挑完到 electron 真绑上之间有个缝**。那一瞬别人抢走了这个端口，记录里就会写着一个不属于它的数。
这儿不去赌那个缝，赌不起也补不上；那种情况由下游「端口持有者要等于 pid」那道守卫抓。
一个空端口都找不到时照实拒、不起——那说明这台机器上攒了一堆没停的 home，该清了。

给子进程的环境要**剥掉 `ELECTRON_RUN_AS_NODE`**：

{/* ref file="../plugins/devkit/src/home.ts" lines="204-219" */}

插件跑在 Electron 主进程里，起 node 子进程的插件会带上这个变量。漏进这儿，起的就不是一扇窗而是一个看不见
的 node。

**按名字定位：`resolveTarget`。** 它不是一条命令，是「我要操作哪个 home」这句话的落地——
`devkit.dev` 的 `home` 参数经它变成一个调试端口。**那是上游唯一的一条路**：那条命令不收端口，
给了当场拒，所以这个函数摔了就是真的够不着，没有第二条路绕过去。

{/* ref file="../plugins/devkit/src/home.ts" lines="523-536" */}

**三道都要验**，少一道就可能把一趟改动推给另一个进程：

{/* ref file="../plugins/devkit/src/home.ts" lines="547-563" */}

记录读得出、pid 还活着且认得出是个 home 进程、那个 pid 真的持着记录里那个端口。端口会被下一个进程占走，
pid 会被复用，所以「记录里写着 9347」本身不构成凭据。「查不出」与「确凿地不在」分开报：前者不导出
任何动作，后者是明确的「它没在跑」。

这三道之后还有第四道，但不在这块：驱动连上页面之后要拿页面自报的 home 名跟你要的那个再对一次。
**记录只回答「你要的是哪个」，页面才回答「你连上的实际是哪个」**，两头都要。

**`rm` 是删，也是唯一要停一个 home 的地方。** 停一个测试 home 唯一的用处就是接着删它，所以没有
单独的一条停：

{/* ref file="../plugins/devkit/src/home.ts" lines="664-674" */}

`force` 是同一个意思的两面，都是**越过守卫**：一面是「它还在跑，连停带删」，另一面是「`default`
是日常那份，真要删」。**但这两面不叠加**——`default` 正跑着的时候 `force` 也不停它。一条开发工具
不该去关人正在用的那扇窗，那不是删一个测试现场，那是把人的桌子掀了；如实说，让人自己关。

{/* ref file="../plugins/devkit/src/home.ts" lines="679-701" */}

记录「查不出还在不在」时不删：不知道占没占着目录，下手就是在赌。停不掉也不删——半个目录加一屏
EBUSY 比一句「没删成」难收拾得多。真停了的话，停的是哪个 pid 跟着回执走：人得知道自己刚才顺手
杀了一个进程。

**「停了」是进程真退了，不是信号发出去了。** 发完信号按 pid 轮询到查得「不在」才算停，到点还在或
一直查不出就回停不掉：

{/* ref file="../plugins/devkit/src/home.ts" lines="578-593" */}

**「已删」只认盘。** 删的调用回成功不算数，删一次核对一次目录还在不在；还在就隔一会儿再删（刚停的
home 的子进程晚几秒才放开句柄），试满次数还在就回没删掉、列出还剩什么：

{/* ref file="../plugins/devkit/src/home.ts" lines="703-719" */}

那一停**两道核对再杀**，跟本机源那半同一个道理：

{/* ref file="../plugins/devkit/src/home.ts" lines="595-629" */}

**手工起的 home 也在这条路上**：记录归内核写，于是「它是谁」的凭据不再只有 devkit 起的那几个有。
没有记录仍然如实说没有可停的，不猜、不按名字扫进程。

## 依赖的接口

{/* ref file="../plugins/devkit/src/home.ts" lines="247-270" */}

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `fs` | 读运行时记录、列 home 目录、整目录删 | `node:fs`，删是自己走树（见下） | 一张内存文件表加一张目录表，删可以演「回成功目录还在」 |
| `spawn` | 起 detached 且**看得见**的 electron | `child_process.spawn`，不 `windowsHide` | 记一笔，回假 pid |
| `appSpawnPlan` | 拼再拉一份宿主应用的命令行：安装版拉那个 exe，开发态 electron 读不出应用目录就拒 | 从宿主进程自报的 `execPath` / `argv` 拼（`hostAppFacts` → `hostAppSpawnPlan`） | 假件回一份计划（或抛），不碰真宿主 |
| `run` | 前台跑底座安装（`pnpm add`）到结束，回输出尾巴 | 合流 capture，超时杀 | 按脚本回成功或失败 |
| `processName` / `portOwner` / `kill` | 判活与停 | 跟本机源那半共用同一批 | 直接喂三态与端口持有者 |
| `execPath` / `env` / `platform` | 认宿主映像名、拼底座安装命令行与子进程环境 | 宿主进程自己那份 | 给死值，两种平台都演得出来 |

判活那几样跟本机源那半共用，因为同一台机器上「查 pid 与停 pid」的坑是同一批。但**映像名的判据不同**：
这半认 electron 与宿主自己，不认 node。本机源那半的子进程是纯 node，这半不是，把 node 也认进来只会
放宽 pid 复用时的误判面。

`portOwner` 在这块有三处用：停之前那道第二重核对、`resolveTarget` 认端口的最后一道，以及挑新端口时
「这个候选有没有人占着」。前两处问的是同一件事，「那个端口上 listen 的到底是不是记录里那个 pid」；
第三处只问有没有人，谁占的不重要。

`fs.removeDir` 的真身自己走一遍树：文件 unlink、目录清空后 rmdir、junction 只删链接本身不进去，
错误照原话往上交。不用 `fs.rmSync` 的递归删：宿主 electron 带的 Node 会跟进 junction 删掉它指向的内容
（指向 home 外面的也删），删到悬空 junction（指向同一趟里先删掉的兄弟目录）又静默停手不抛错，而装过包的
home 里全是 junction。它回成功也不作数，删没删掉由 `rm` 那半拿 `exists` 再问一次盘（见上一节）。

## 怎么单独测

喂假盘、假进程表、假时钟，整条时序在 `tests/home.test.ts` 里跑完，不真拉起一扇窗。

证明的是：名字撞了怎么退让、退无可退时照实拒；electron 二进制不在时连 build 都不跑；build 失败时
不起进程；起得来时环境与观察窗都对、记录读回来报给人；记录没出现时不算失败但回执要明说；秒退时
立刻报并指向那个 home 的日志；同一个 home 已有实例在跑时拒开第二个；挑端口时记录占着的与有人 listen 的
各自会不会被跳过（**陈旧记录里那个端口也要算占着**）；按名字定位那三道各自能拦住什么；删之前那两道
核对各自能拦住什么；`default` 不 `force` 守得住、正跑着时 `force` 也守得住；还在跑没带 `force` 拒删、
带了 `force` 先停再删、停不掉就不删；信号发了进程晚几趟才退时等到它退、一直不退时不删；删的调用回成功
而目录还在时不说已删、晚一步删得掉时照删。

记录是**假盘摆上去的**，不是 `launchHome` 写的——那一点本身就是这块现在的形状：起完之后它去读，
读到什么算什么。测试里让假的 `spawn` 顺手把记录摆上，演的正是「内核开机才写」那个时序。

## 代码地图

**在哪**：纯机在 `src/home.ts`，真机器在 `src/node-home-deps.ts`（判活那几样从 `node-probe-deps.ts`
拿），四条命令与 `home` 参数的接线在 `src/index.ts`。

**先读**：`launchHome`，开一个 home 的全部顺序都在里面；接着 `resolveTarget`，按名字找人的三道验活
都在里面。

**读序**：命名那几个纯函数在最前面，接着是启动计划（命令行与环境），再往下是起、列、挑端口、
按名字定位、停、删六条时序——停那条没有自己的命令，只被删那条调。
