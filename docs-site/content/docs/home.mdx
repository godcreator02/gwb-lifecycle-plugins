# 测试 home

**本页回答**：一个测试 home 是怎么被开起来的、名字为什么长成那样、为什么默认先 build、
停和删各自拦住了什么。

## 管什么

把实机验证那几步命令化：开一个新的、列出现有的、重开一个已有的、停掉、删掉。

home 建在 `%APPDATA%\gwb-kernel\homes\<名>\`。开哪一个由环境变量 `GWB_HOME` 决定，这块要做的只是
把 electron 按那个名字拉起来，并且记下它是谁。

## 不知道什么

它不知道 home 里装了哪些件，也不知道件挂上了没有。那是 plugins 件的事，问 `plugins.list`。

它**不铺 home 的最小形态**。`package.json` 与空的 `cordis.yml` 归内核自己铺，而那要等内核起来；
这块只建目录、落自己那份启动记录，两边互不冲突。

它不知道 CDP 口拿来干什么，只负责把那个开关摆到命令行上。

它还有一条前提：这套命令要求本件跑在一个活着的 home 里。一个 home 都没活着的时候，只能按手工那四步
先把工作台起起来。

## 提供的接口

五条命令：`devkit.home.new`、`list`、`open`、`stop`、`rm`。

**命名是 `<短名>-<yyMMddHHmm>`**，撞了退到秒，再撞就照实拒：

{/* ref file="../src/home.ts" lines="102-114" */}

不静默加序号，因为名号里每一段都得能读出时间。同一个件的 home 因此在目录里挨在一起、各自按时间排，
正好是清理时要的顺序。

**`new` 默认先 build 内核，而且 build 失败就是失败**：

{/* ref file="../src/home.ts" lines="269-301" */}

「改了内核没 build，起的是上一次的产物」是实机验证里最隐蔽的一种空验：界面看着一切正常，验的是旧代码。
所以 build 是这条命令的正身，不是可省的优化，赶时间才给 `skipBuild`。

起进程之前还有一道：同一个 home 不许开两个实例。两扇窗写同一份日志、同一个 home，而 `stop` 只认得住
记录里那一个。

**所有还会摔的步骤都排在 spawn 前面。** spawn 之后再失败，会留下一扇没有记录的窗，谁也管不着它。

起来之后看五秒：

{/* ref file="../src/home.ts" lines="320-330" */}

「起没起来」没有 ping 可打，进程还活着是此刻唯一拿得到的信号。这五秒只为抓住「秒退」这一种最常见的
死法（产物不在、端口被占），真正成没成，那扇窗和人说了算。

CDP 调试口**走命令行，不走环境变量**：

{/* ref file="../src/home.ts" lines="128-144" */}

内核不认识任何调试相关的环境变量，`--remote-debugging-port` 是 Chromium 自己的开关，命令行上就生效。

给子进程的环境要**剥掉 `ELECTRON_RUN_AS_NODE`**：

{/* ref file="../src/home.ts" lines="161-176" */}

件跑在 Electron 主进程里，起 node 子进程的件会带上这个变量。漏进这儿，起的就不是一扇窗而是一个看不见
的 node。

**`stop` 两道核对再杀**，跟本机源那半同一个道理：

{/* ref file="../src/home.ts" lines="397-414" */}

它只停「有启动记录的那个」。手工起的 home 如实说没有可停的：没有记录就没有「它是谁」的凭据，
不猜、不按名字扫进程。

**`rm` 两道守卫**：

{/* ref file="../src/home.ts" lines="435-457" */}

`default` 是人每天住的地方，不给 `force` 不删；还在跑的拒删，删一个跑着的 home 只会得到半个目录和
一屏 EBUSY。记录「查不出还在不在」时同样不删，不知道占没占着目录就下手是在赌。

## 依赖的接口

{/* ref file="../src/home.ts" lines="209-230" */}

| 接口 | 用来做什么 | 生产实现 | 测试实现 |
| --- | --- | --- | --- |
| `fs` | 读写启动记录、列 home 目录、整目录删 | `node:fs`，删带重试 | 一张内存文件表加一张目录表 |
| `spawn` | 起 detached 且**看得见**的 electron | `child_process.spawn`，不 `windowsHide` | 记一笔，回假 pid |
| `run` | 前台跑 build 到结束，回输出尾巴 | 合流 capture，超时杀 | 按脚本回成功或失败 |
| `processName` / `portOwner` / `kill` | 判活与停 | 跟本机源那半共用同一批 | 直接喂三态与端口持有者 |
| `execPath` / `env` / `platform` | 拼命令行与子进程环境 | 宿主进程自己那份 | 给死值，两种平台都演得出来 |

判活那几样跟本机源那半共用，因为同一台机器上「查 pid 与停 pid」的坑是同一批。但**映像名的判据不同**：
这半认 electron 与宿主自己，不认 node。本机源那半的子进程是纯 node，这半不是，把 node 也认进来只会
放宽 pid 复用时的误判面。

删目录那条在 Windows 上带重试：electron 刚停，子进程偶尔还握着目录几秒。真被占死的让错误走出去，
吞了它，人看到的就是「删掉了」，而那个 home 还在盘上。

## 怎么单独测

喂假盘、假进程表、假时钟，五条命令的整条时序在 `tests/home.test.ts` 里跑完，不真拉起一扇窗。

证明的是：名字撞了怎么退让、退无可退时照实拒；electron 二进制不在时连 build 都不跑；build 失败时
不起进程也不落记录；起得来时环境、记录、观察窗三样都对；秒退时立刻报并指向那个 home 的日志；
同一个 home 已有实例在跑时拒开第二个；停之前两道核对各自能拦住什么；`default` 守得住；跑着的拒删。

**读序**：命名那几个纯函数在最前面，接着是启动计划（命令行与环境），再往下是起、列、停、删四条时序。

**可跳过**：`parseRecord` 与 `renderRecord` 是启动记录的读写，形状简单；判活那几个函数在本机源那一页
已经讲过。
