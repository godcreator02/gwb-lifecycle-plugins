# 全生态机制定案

**本页回答**：内核与全套插件之间每一个配合机制最终定成什么样、为什么这么定、删掉什么、分几期做、做到什么算完。
做完把内容放回各自的位置：做法写进各仓现状页并引用代码，每条定下的结论写一张轨迹卡，然后删掉这一页。

这一页原在内核仓文档站，2026-09-24 随「写插件的规矩归 devkit」搬到本站。下文说「内核仓」「内核仓文档站」的，指 `igldu-gwbkernel/gwb-kernel` 那个仓。

**由来**。2026-09-23 在总控台的会话里审查了一遍内核与全套插件的配合（dev、peer、importmap），查实内核本身已经很干净
（七个文件），复杂度集中在 devkit 与插件管理两个插件里，根源有三条：开发与发版都要经过 registry、peer 要手写，还要和
dev 依赖逐条对应、同一个事实在好几处重复抄写。人的原话：

> 可以都改我觉得，就是保持简洁，除了必要的功能不增加多余的复杂度。我们现在就在重构，应该朝着最干净、最整洁的方向努力。

随后逐条追问：「peer 和可选 peer 是不是完全可以退役」「不是 devdependencies 吗」，最后纠正到「件里的 cordis 打进包
肯定不对啊，应该区分什么时候用peer什么时候不用啊」——由此定下本页第一节的依赖模型：**按「运行时这份代码由谁提供」
决定写法**，其余各节都建立在它之上。

**它改的是被别的插件 inject 使用的那部分接口**（插件管理的命令接口、词汇表包的导出、devkit 的发版前检查与模板），也推翻了内核仓与
devkit 仓已经写下的几条判据（见文末「要改写的轨迹卡与红线」）。方向人已同意（2026-09-23），做法定稿在本站[写插件的规矩](/docs/rules)。

## 待决定

## 已决定（2026-09-23）

- 依赖、importmap、跨插件交互、卸载清理这几类的做法写进本站[写插件的规矩](/docs/rules)，是正本；本页
  各节只留和实施相关的归属、删掉什么与代价。[页面代码与 importmap](/docs/rules/importmap) 不承认「体积」是进 importmap 的理由
- 拿现有插件做案例分析后定的三条：**去掉可选 peer**（类型链由使用方在 dev 里列齐，提交前检查关掉 `skipLibCheck`）；**服务还是命令改成
  「扩展点用服务，数据与动作用命令，同一能力只提供一种调用方式」**；**不加安装期依赖字段**（缺了就停在等待依赖的状态，看得见）
- **扩展点服务一律继承 cordis 的 `Service` 类**：服务方法里的 `this.ctx` 是调用方的上下文，注册随调用方卸载自动撤销，调用方不再自己包
  `ctx.effect`；代价是这些插件写 peer `cordis`。commands 从 `ctx.provide` 改过来，已经自己包了 `ctx.effect` 的调用方不受影响
  （[cordis 服务怎么提供和使用](/docs/rules/services)）
- 插件里的 cordis **不打包进构建产物**：宿主提供的东西写 peer（[依赖怎么写](/docs/rules/deps)第一条）
- 插件运行时自己用的库打包进构建产物、写 dev；插件之间不通过 import 耦合（第一节、第七节）
- 词汇表包不改名、不并进内核应用包、不加「运行时内核版本」兼容字段；契约收窄（第五节）
- 不做：给命令分权限等级（页面边界由第四节的导航锁保证）；跨 home 调命令改走 MCP 入口（原候选第 10 条，不做）
- 不动：importmap 归内核、MCP 入口只有三个工具且不再增加、单进程

## 已决定（2026-09-24）

- **兼容性靠插件声明测过的内核版本**：插件在 `package.json` 的 `gwb.testedKernel` 写它在哪个内核版本上测过；`plugin-manager.list`
  拿它和运行中的内核比，按包报 `kernelUntested`；`devkit.release` 发插件前检查它。内核改了接缝上已有的东西（包括升级 loader、
  include 的版本、改 home 布局）就升 x（[在哪个内核上测过](/docs/rules/tested-kernel)）
- **写插件的规矩归 devkit**：内核仓文档站只留「关键设计」里进内核还是做成插件的判据；插件管理进 devkit 仓
- **react 改由内核提供，删掉 `gwb.shared` 机制**：排成第五期，在第三期之后做。第三期里 block-note 撤掉自己的声明之后，
  声明 `gwb.shared` 的只剩 shell 一家，这套机制（扫描 home 清单、只收插件做提供方、同名冲突处理）只为 react 四个包名存在；
  全生态都用 React，react 由内核打包、importmap 由内核直接写这四个名字，机制整个删掉。页面上仍然要有 importmap，
  浏览器解析包名只能查它。代价：react 升级要重新打安装包；内核的准入判据要改写（今天写的是「内核不认识 react」）；
  第六节「外置名单只从 shell 的 `gwb.shared` 读」要换一个来源，内核不发 npm 包，插件构建时从哪里拿名单到第五期再定
- **两份 cordis 改在内核仓讨论「内核装进 home」**：rc.9（内核）与 rc.10（home 里 pnpm 补装）并存，
  讨论过由内核在 Node 一侧做包名映射，最后改为讨论把内核作为 npm 包装进每个 home 的 `node_modules`、exe 只负责启动
  Electron——那样插件的 peer `cordis` 由 pnpm 解析到内核用的同一份，映射不必做，peer 也能检查内核版本。方案、代价与要推翻的
  已有决定写在内核仓文档站的交接页「内核装进 home」，人看过再决定做不做；定下之前第一节的判据不变

## 一、依赖模型：按「运行时谁提供」决定写法

**做法**：见[依赖怎么写](/docs/rules/deps)。实施上补一条：无法打包进构建产物的自用库（原生模块、运行时读自己文件的包）才写
`dependencies`，并在清单注释里写明原因——插件管理自带的 pnpm 原生可执行文件是一个。

**归属**：规矩与检查在 devkit（模板、`devkit.release`、写插件手册）；各插件照此迁移。

**删掉**：用 peer 声明其他插件、库、react、旧共享包的全部写法；依赖三档（旧红线 3，换成「依赖怎么写」那张表）；「相对 import 带
`.js`、每个包名 import（直接写包名、不带相对路径的 import）都在依赖表里」（旧红线 4，交给打包器负责）；发版前检查里「peer 下限 = dev 下限」那一类规则与 audit-deps 里
对应的四类发现；home 里的库、共享包与依赖树——home 里除插件之外只剩 pnpm 按必选 peer 补装的那一份 `cordis`。

**判据**：见「依赖怎么写」的「为什么」。实施时要知道的一条事实：home 里 pnpm 按 peer 补装的那份 cordis（rc.10）与内核打包进
app.asar 的那份（rc.9）今天就不是同一个物理实例；要让两边真是同一份，得由内核在 Node 一侧做包名 import 映射，目前没有实际发生的故障，按内核的准入判据
不做。另一条让两边成为同一份的路是把内核装进 home，在内核仓交接页「内核装进 home」讨论（见 2026-09-24 的决定）。「库独立热替换」只有 docfirst 插件运行时查找 docfirst 库这一个用例，有意放弃（见「放弃的能力」）。

**会失去什么**：安装插件时对库与其他插件的 peer 警告（一直只警告不拦截，由开发期的 audit-deps 代替）；库单独升级（要重新发布用到它的插件
——块笔记系列插件与 bn-papers 都是同仓同时发布）；报错堆栈指向构建产物（esbuild 不压缩，基本可读；不做 sourcemap，要做得先通过内核
准入判据）。

## 二、home 与安装卸载：home 里只有插件，只由插件管理写 home

**做法**。home 的 `package.json` 只列插件，一律写精确版本号，以锁文件为准；**唯一写 home 的是插件管理**，一切变更（安装、
升级、换装开发版）走同一个入口：确定版本 → 运行一次 pnpm → 重新加载有变化的插件 → 如果 shell 变了就整页重载。插件之间只通过服务交互，
「依赖它的插件跟着重新加载」由 cordis 的 inject 自己完成，插件管理不计算依赖图。

**归属**：插件管理（devkit 仓 `plugins/plugin-manager/`，被 inject 使用的那部分接口）；devkit 的 `home.new` 与 `dev` 改为调用它。

**删掉**：install 里提升 peer 的那一步（必选 peer 只剩宿主提供的 `cordis`，pnpm 自己补装一份给所有插件共用，不必写进清单）、
`pnpm peers check` 与 `peerWarnings`、`peers.ts` / `peer-warnings.ts`、「库 / 共享包」分类；`plugin-manager.update`（并进 `update-all {"only":[…]}`）；devkit 里自己写清单、读回核对、
重新加载的那一套；`home.new` 里绕过插件管理直接运行的 `pnpm add`。内核 `INSTALL.md` 的安装方法随之改成「装插件管理与 MCP 入口插件，其余经
`plugin-manager.install`」或同一份首次安装的插件集清单（见第九节）。

**判据**。今天有六个入口在写 home 清单、写法不一（`^` 与精确版本号混用，pnpm 沿用第一次的写法）；三个插件在 default 里
加载失败，正是因为升级了一个库，而依赖它的插件没人重新加载。库不进 home，这类事故就无从发生。

## 三、开发循环：开发版不进 registry

**做法**。`devkit.dev` 在仓里构建、用 `pnpm pack` 打出带时间戳的 tgz，通过第二节的入口以 `file:` 安装进**隔离
home**，再查看运行结果。registry 只放正式版。「写插件只有一条路：发布、安装、验证」不变——pack 按 `files` 白名单打包，漏导出、
漏文件照样会在安装那一步暴露。

**归属**：devkit。

**删掉**：dev tag、临时目录发布、每个包用 `pnpm view` 查重；将来的「清理开发版」命令。构建改成只构建被测包及其依赖
（`pnpm -r --filter <包>...`），不再全仓构建。

## 四、importmap 与页面边界

**做法**。
- importmap 放什么按[页面代码与 importmap](/docs/rules/importmap)：只放整页必须只有一份的运行时，今天是 shell 的 react 四个包名，
  第五期改由内核提供。
  `@godcreator/block-note` 撤掉自己的 `gwb.shared`，块笔记系列插件把解析库各自打包进构建产物
- importmap 只在页面发来 hello 消息时计算一次（页面本来就只注入一次），名字冲突就拒绝、只报一次
- 只读状态页只在没有外壳时推送；日志的 warn / error 不再触发推送
- 页面只可能是本地 `index.html`：主框架跳转、`window.open` 一律拒绝（`will-navigate` / `will-redirect` /
  `setWindowOpenHandler`）；`gwb:command` 只接收顶层框架的调用

**归属**：内核（`main.ts`、`index.html`）；block-note 撤掉声明、块笔记系列插件改构建脚本里的外置名单。

**删掉**：每条 warn 都扫一次磁盘、日志自我触发的循环（warn → 推送 → 重新计算 → warn）、`setShell` 直接推送 / 去抖 / hello 三条推送
路径合并成一条、页面里 pending 与 current 的双重保险。将来的命令权限等级不必设计。

**判据**。importmap 页面只注入一次，推送时重新计算的结果用不上；页面能调用整条命令总线，页面边界是唯一必须保证的边界，
保证它比给命令分级便宜得多。块笔记的解析库只是体积大、不要求全页只有一份，由各插件打包进构建产物——页面从本机加载，重复几百 KB 可以接受。

## 五、契约（对外承诺的接口）

**做法**。`@godcreator/gwb-plugin-api` 是纯类型包，与内核同仓、同版本号；插件写 dev。公共接口：
`gwbKernel` 四项（`dataDir` / `version` / `emit` / `setShell`）、`window.gwb` 的 `command` / `on`、外壳默认导出
`ShellBoot`；只增不减。`GwbResult` 移到 commands 插件（它是命令总线统一的返回结构，不是内核的概念）；`onShell` 移出公共接口
（只有内核自己的页面用，第四节改推送方式时不再牵动任何插件）。

**归属**：内核仓 `packages/gwb-plugin-api`；commands 插件先导出自己的返回结构类型。

**判据**。类型必须有一个共用的包（各插件各自内联会让 `window.gwb` 的全局声明互相冲突）；运行中的内核版本与 home 里
那份类型包的版本本来就是两回事，peer 管不到运行时——加兼容字段是新机制，只增不减的契约用不着。插件与内核的兼容性由插件自己声明
`gwb.testedKernel`（见 2026-09-24 的决定），不放进词汇表包。

## 六、共享的包名只有一个来源

**做法**。页面一侧的构建产物外置哪些包名，只从提供方的 `gwb.shared` 读取：shell 导出一个构建期函数，各插件的 `build.ts`
调用它，不再手抄 react 四个包名。

**归属**：shell（加一个子路径导出）；devkit 模板与各插件照此迁移。

**删掉**：十三份手抄的外置名单。

第五期删掉 `gwb.shared` 之后这个来源不再存在，名单改从哪里取到第五期再定。

## 七、跨插件边界

**做法**：见[插件之间怎么交互](/docs/rules/interaction)。实施上要改的是块笔记的存储行格式：`LIBRARY_CONTRACT` 对不上时改成拒绝加载，
不只打 warn。

**归属**：写插件手册；块笔记系列插件（`LIBRARY_CONTRACT` 那一处）。

**判据**。块笔记两个仓里所有 `instanceof CommandError` 捕获的都是本插件自己创建的对象，命令总线只传返回结构——各插件私有
一份不会出错；真正的风险是版本不一致导致写盘格式对不上。

## 八、插件的卸载清理

**做法**：见[卸载清理](/docs/rules/dispose)。

**归属**：写插件手册；node-cli、py-cli、windows-backup、bn-core、mcp 各有一处要补。

**判据**。内核退出时只等「返回的 promise」；今天 restic 可以在卸载之后再跑六小时，bn-core 关闭数据库并写盘的操作没有返回
promise，退出时可能丢数据。

## 九、检查、审计与文档

**做法**。
- **构建产物检查**（`devkit.release` 构建之后、发布之前，自动执行）：Node 一侧构建产物里的包名 import ⊆ Node 内置模块 ∪ `electron` ∪ 必选
  peer（今天只有 `cordis`）；页面一侧 ⊆ importmap 里的包名；类型检查在 `skipLibCheck: false` 下通过（拦住类型链缺包导致的
  不报错的 any）；构建产物里没有空 import（`import { type X }` 留下的）
- **audit-deps** 只报需要处理的（超出版本范围、指定了源上没有的版本号）；**audit-structure** 只查「能装上」所需的（`exports` /
  `files` / `keywords` / 入口可解析），不查从目录名推导名字的那一串规则；两条都支持无参数调用
- **首次安装的插件集清单只有一份**：devkit 里的首次安装插件集是正本，`INSTALL.md` 由它生成或引用它，不再手抄
- **文档不写会变的数字**：AGENTS、README、说明书不写版本号、行数、别的仓的路径、命令条数，写获取方法

**归属**：devkit；docfirst 规矩（「不写会变的数字」可以加一条正则检查）。

## 放弃的能力

- **库的独立热替换**（peer 加上运行时查找 home 的直接依赖，见内核仓的轨迹卡「依赖热换」）：唯一用例
  是 docfirst 插件运行时查找 docfirst 库；改为随插件一起发布
- **安装插件时对库与其他插件的 peer 警告**：一直只警告不拦截，由开发期 audit-deps 代替
- **库单独升级**：要重新发布用到它的插件

## 分期与验收

每期开工前读 devkit 的说明书「gwb-release」确定版本号（契约动了的升次版本号）；每期都在隔离 home 验证，不拿 default 验证。
