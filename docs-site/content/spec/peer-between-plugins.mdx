# 插件之间的运行时要求写 peer

**本页回答**：插件「要求 home 里别的插件至少到哪一版」为什么改写成 peer、pnpm 装 peer 时有哪两处要处理、插件管理与发版检查各改什么、哪几件事要人先定。

**状态：五条待决定都按推荐项确认；devkit 仓的代码、现状页、说明书与轨迹卡已改完（未提交）。还剩隔离 home 实测、发版、内核仓 `INSTALL.md`、通知下游。实验材料已提交（`probes/2609242300_peer-between-plugins/`）。**

## 验收

- [x] 插件的 peer 可以写 `cordis`、内核包与别的插件（清单 `keywords` 含 `gwb-plugin` 的包）；库、接口定义包不许进 peer
- [x] `gwb.requires` 删掉：插件清单不再写，插件管理不再报，发版检查不再查
- [x] 发版检查：peer 里每个 `@godcreator` 插件的范围要和源上 `latest` 在同一条线（0.x 比 x，≥1 比主版本号；不在同一条线就是上游出了破坏版，先适配）；内核包的范围照旧要包含运行中的内核；peer 里出现插件、`cordis`、内核包以外的包就拒
- [x] 插件管理 `list`：每个包报 home 里没满足的 peer（没装、版本不在范围里）；只报告，不拦加载、不拦安装
- [x] 插件管理 `update-all`：升级了某个包，home 里 peer 写了它的插件的条目一起重新加载，回执里列出来
- [x] home 里不会自动补装缺的 peer：插件管理、`devkit.home.new`、`devkit.dev` 与 `INSTALL.md` 的手工步骤都关掉 pnpm 的自动补装（插件仓里不关）
- [x] 模板：用到的插件（命令总线、外壳）从 dev 挪到 peer
- [ ] 隔离 home 实测：升级一个被 peer 的插件后，写 peer 的插件换到新目录并在运行；home 里缺一个 peer 时不会被自动装上，`list` 报出来

## 由来

`gwb.requires`（2026-09-24 定，轨迹卡「要求别的插件的最低版本：清单字段 gwb.requires 加报告」）没写成 peer 的理由是「peer 等于把别的插件当成运行时依赖，和各插件各自安装、各自升级冲突」。这条站不住：插件 peer 里写内核包，本来就是「运行时 home 里的内核要在这个范围里」，插件并不 import 内核包；别的插件也是同样的关系。`gwb.requires` 其实是自造了一个只报告的 peer。

真正的问题在 pnpm 怎么装 peer。实验（`probes/2609242300_peer-between-plugins/`，A 的 peer 写了 B）测到三件事：

1. **B 升级，A 的安装目录跟着换**：目录名带着它链接的 B 的版本，`A@1.0.0_B@1.0.0` 变成 `A@1.0.0_B@1.1.0`；pnpm 的输出里只写 B 变了。旧目录默认留在磁盘上（pnpm 文档说 7 天，实验没等），期间 A 照旧运行旧目录里的代码；旧目录被清掉之后 A 再加载自己的文件就会失败
2. **缺 peer 默认自动补装**：home 里没有 B，装 A 时 pnpm 不声不响地把 B 装进 `node_modules/.pnpm`，不写进 home 的 `package.json`，也没有条目。home 的 `pnpm-workspace.yaml` 写 `autoInstallPeers: false`，或环境变量 `pnpm_config_auto_install_peers=false` 能关；命令行参数 `--config.auto-install-peers=false` 关不掉
3. **范围不满足只警告**：A 直接链到 home 里那一版 B，pnpm 不另装一份；`pnpm peers check` 报出来

第 1 条对内核包与 `cordis` 无害，它们升级本来就要重启；插件是热升级的，所以要重新加载写 peer 的插件。第 2 条关掉就行。第 3 条正好对应插件管理「只报告、不拦」。

## 方案

- **插件的依赖怎么写**：运行时要从 home 里得到的东西——`cordis`（按值 import 时）、内核包、用到的别的插件（它的服务、命令、样式令牌）——写 peer，范围 `^x.y.z`。插件仓里 pnpm 会把 peer 装进 `node_modules`，类型从那里取，别的插件不再另写 dev。打包进产物的库、接口定义包、构建工具照旧写 dev
- **发版检查**（回答「该查 peer 还是 dev」）：
  - peer 里每个 `@godcreator` 插件：范围要包含源上 `latest`，规则照现在对 dev 的那条（落后但在范围内放行，出范围拒）
  - peer 里的内核包：照旧要包含运行中的内核
  - peer 里的包是不是插件：读包目录 `node_modules` 里它的清单，`keywords` 含 `gwb-plugin` 才算；`cordis`、内核包另认；别的一律拒，提示改成打包进产物
  - dev 里 `@godcreator` 的包：只剩库与接口定义包，查法见待决定第 3 条
  - `gwb.requires` 的检查删掉
- **插件管理**：
  - `list`：删掉 `requires`、`unmetRequires`、`requiresInvalid`；加 `unmetPeers`（每条 `{ pkg, range, installed? }`，只看 `@godcreator` 插件的 peer；内核包照旧用 `kernelRange` / `kernelUntested`，界面插件的窗格在用）
  - `update-all`：pnpm 装完后，找出 peer 里写了本次升级的包的插件，把它们的条目一起重新加载；回执加 `dependents`（哪些包因为 peer 跟着重新加载了）
  - `install` / `uninstall` 不拦 peer 没满足的情况，`list` 报
- **关掉自动补装**：见待决定第 1 条
- **迁移**：各插件把用到的别的插件从 dev 挪到 peer、删 `gwb.requires`（现在没有插件写过），和适配内核 0.5 放在同一轮重发；往下游收件页再投一条

## 待决定（五条都已按推荐项确认）

1. **关掉自动补装放在哪**：推荐**启动 pnpm 时带环境变量** `pnpm_config_auto_install_peers=false`：插件管理与 devkit 在自己启动 pnpm 的地方加上，`INSTALL.md` 的手工步骤先设这个变量。只改两处代码，已有的 home 不用迁移。另一种是每个 home 的 `pnpm-workspace.yaml` 写 `autoInstallPeers: false`：人手工在 home 里运行 pnpm 也生效，但要由创建 home 的一方写，已有的 home（包括 default）都要补
2. **插件管理升哪一位**：`list` 回执删掉三个字段，按 gwb-release 是破坏性改动，推荐**升 x（0.9.0），服务的 `contract` 加一**，发之前通知界面插件仓（窗格只读 `kernelRange` / `kernelUntested`，实际不受影响）
3. **dev 里 `@godcreator` 库还查不查源上 `latest`**：推荐**继续查**：库是打包进产物的，不跟上游也能运行，但跟着查能让全生态的库版本不散开；查法不变
4. **内核包的 peer 比对谁**：推荐**不变，比运行中的内核**：它说明「在这个内核上验过」，比源上 `latest` 更贴近实际
5. **哪些插件依赖要写 peer**：推荐**运行时用到的全写**（服务、命令、样式令牌），包括命令总线。代价：几乎每个插件都 peer 命令总线，命令总线一热升级，home 里大部分插件都会被一起重新加载；cordis 在命令总线重新加载时本来就会让 inject 它的插件跟着重新加载，所以实际多出来的只是「从新目录重新 import」

## 不做的事

- 不拦加载：peer 没满足只在 `list` 里报
- 不替插件装它 peer 里缺的插件：装哪个插件由人决定
- 不开 pnpm 的严格 peer（`strictPeerDependencies`）：实验里它报错退出，但 `node_modules` 照样写完了，拦不住，只会让插件管理的安装回执变成失败
