# 派单（一字不改——上下文隔离的关键就是派单里没有多余信息）

```
你要在一台 Windows 机器上开发一个 gwb 插件。
有一台工作台开着，HTTP 门在 http://127.0.0.1:2870（无鉴权，只绑本机）。
你的第一步是：用 Bash 跑 curl -s http://127.0.0.1:2870/surface
在做任何其他事之前，先执行这条命令、读它的回执——上面有 instructions 告诉你怎么干活。
不要读本地文件来找答案——所有答案都在那个 HTTP 门上。
从那开始自己找到路子：建一个插件、写代码、跑通门禁、发版、装进隔离 home 验证。
安全线：别碰 default home，一切活落在隔离环境里。
```

# 功能指定（附在派单后面，也是它唯一多收到的信息）

给个具体功能，别让它自己想——想什么不是考题，怎么建才是。功能要小而全：碰命令、碰数据、碰窗格，各面浅尝。默认题：**gwb-notes，agent 与人共享的便签板**（`notes.add {"text"}` / `notes.list` / `notes.clear`，落 gwbData，窗格里人看得见）。

# 判据（三层，跑完后由审查会话评）

| 等级 | 判据 |
| --- | --- |
| **过了** | 六步全通：check / build / publish / install / ping / 窗格可见 |
| **勉强过** | 走通了但绕弯——说明书有的信息没找到，靠猜或反复试错碰对了 |
| **没过** | 卡住走不下去，或做出来的东西是错的 |

「勉强过」比「没过」更值钱——它告诉你手册有那条信息但藏得太深（发现面出了问题），修法不同。

# 发现去哪

投目标仓的 `feedback/inbox`。**改的是正本（skill / 代码），不是派单**——在派单里补一句提示等于把洞糊上，下次换个角度还是漏。修完删 inbox。

# 什么时候跑

- 发了大版之后（devkit / 模板 / 门有大改）
- 人觉得「改得够多了该验一遍了」
- 不需要频繁跑——它测的是知识充分性，不是代码回归

# 跑法

Agent 工具派 `general-purpose` 子代理。主会话只观察不动手：轨迹回来后对着判据评、归因每一步卡壳（说明书缺信息？藏太深？流程 bug？）、发现投 inbox。**子代理的工作目录要干净**——如果跑在总控台里，先把 `out/` 清空；或者指定一个空目录。
